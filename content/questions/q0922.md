::: testing
Whether you can compare the two on **design philosophy and consequences** rather than reciting "GPU has more cores". The interviewer wants:

1. Latency-optimized vs throughput-optimized, and how each spends transistors (caches, speculation vs lanes, registers).
2. How each hides memory latency (caches and out-of-order vs massive multithreading).
3. When each wins: serial, branchy, irregular code vs data-parallel, regular code.
4. System-level awareness: separate memories, PCIe transfers, power, and that they cooperate as host and accelerator.
:::

::: why
Almost every compute system today has both, and choosing where to run a workload is a daily engineering decision. For hardware engineers, the CPU/GPU contrast explains why chips look the way they do and where an accelerator's design budget goes. The answer also frames the trade-offs in [[q0923]] and the performance models in [[q0924]], and it is the basis for SoC integration choices later ([[q0926]]).
:::

::: concepts
- **CPU**: few complex cores optimized for single-thread latency. See [[q0900]].
- **GPU**: many simple lanes optimized for throughput. See [[q0919]].
- **Latency vs throughput**: time per task versus tasks per second.
- **Latency hiding**: caches and out-of-order versus warp switching. See [[q0920]].
- **Amdahl's law and offload**: serial portions and data transfers limit accelerator gains.
- **Roofline**: performance limited by compute peak or by memory bandwidth times arithmetic intensity.
:::

::: answer
"A CPU is designed to make one thread run as fast as possible, and a GPU is designed to finish as much total work per second as possible. That one decision drives everything else.

A CPU spends its transistors on a few big cores with out-of-order execution, branch predictors and large caches, because it needs to cope with branchy, irregular code and keep latency low. A GPU spends them on thousands of simple ALU lanes, huge register files and wide memory interfaces. Its threads are slower individually, but there are tens of thousands of them.

They hide memory latency differently too. A CPU uses big caches and speculation to avoid stalling. A GPU just switches to another warp when one stalls, so it needs lots of parallel work. A GPU also executes threads in lockstep groups, so divergent branches hurt.

The result is that CPUs win on serial, control-heavy, latency-sensitive code like operating systems and most application logic, while GPUs win on regular data-parallel work like graphics, matrix multiplication and image processing, often by 10 to 100 times. In a real system they're partners: the CPU runs the control flow and ships the heavy parallel kernels to the GPU, as long as the data transfer cost doesn't eat the gain."
:::

::: technical
**Comparison.**

| Aspect | CPU | GPU |
|---|---|---|
| Goal | Minimize latency of one thread | Maximize aggregate throughput |
| Cores / lanes | 4 to 128 large cores | thousands of simple lanes in tens to over a hundred SMs |
| Threads in flight | tens (SMT 2 per core) | tens of thousands |
| Control | OoO, deep speculation, big branch predictors | in-order lanes, SIMT lockstep, little speculation |
| Latency hiding | caches, prefetch, OoO window | massive multithreading, zero-cost warp switch |
| Cache per thread | MBs shared among few threads | KBs per many threads; big register files |
| Memory bandwidth | tens to ~100+ GB/s (DDR) | hundreds of GB/s to multiple TB/s (GDDR/HBM) |
| Clock | 3 to 5+ GHz | about 1 to 2.5 GHz |
| Branchy code | handled well | divergence penalty |
| Peak FP32 | up to about 1 to 3 TFLOP/s per socket | tens to hundreds of TFLOP/s |
| Memory model | coherent, virtual memory, OS support | often separate memory, weaker coherence, accelerator role |
| Power | 15 to 300 W | 5 to 700 W |

**Peak arithmetic example.** CPU: 8 cores x 4 GHz x 32 FP32 FLOP/cycle (two 256-bit FMA ports: $2\times8\times2$) $=1.02$ TFLOP/s. GPU: 10,000 lanes x 2 FLOP x 1.75 GHz $=35$ TFLOP/s. Ratio about 35x. Memory bandwidth ratio: 900 GB/s / 50 GB/s $=18\times$.

**Roofline.** Attainable $=\min(P_{peak},\,BW\times I)$ where $I$ is arithmetic intensity (FLOP/byte). Ridge point: CPU $1000/50=20$ FLOP/B; GPU $35000/900\approx39$ FLOP/B. At $I=2$: CPU 100 GFLOP/s, GPU 1.8 TFLOP/s (18x, equal to the bandwidth ratio).

**System view.** A discrete GPU has its own memory and sits across PCIe. A host-to-device copy at about 25 GB/s effective moves 256 MB in about 10 ms. Offload pays only when kernel time saved exceeds transfer time. Integrated GPUs and unified-memory SoCs share DRAM with the CPU, removing the copy but sharing bandwidth.

**Energy.** Per-FLOP energy is much lower on a GPU, because instruction fetch/decode is amortized over 32 lanes and there is little speculation overhead.
:::

::: short
"A CPU is latency-optimized: a few big out-of-order cores with big caches and branch prediction to run one thread fast. A GPU is throughput-optimized: thousands of simple lanes running in lockstep, hiding memory latency by switching among tens of thousands of threads, with very high memory bandwidth. CPUs win on branchy serial code, and GPUs win on regular data-parallel work like graphics and matrix math. In practice the CPU orchestrates and the GPU does the heavy parallel part."
:::

::: long
"The core difference is what each is optimized for. A CPU minimizes the latency of a single thread. A GPU maximizes total throughput across many threads. You can see it in how they use silicon.

A CPU core is big: it has out-of-order execution, deep branch prediction, large multi-level caches and prefetchers, all aimed at keeping one instruction stream moving even through branchy, pointer-heavy code. You get a few to a few dozen of these cores running at 3 to 5 GHz. A GPU instead packs thousands of small ALU lanes organized in clusters, with a very large register file instead of big caches, and a very wide memory interface giving hundreds of GB/s to terabytes per second.

Latency is the clearest contrast. When a CPU thread misses the cache, it relies on out-of-order execution and prefetch to overlap the wait. A GPU just has so many threads that when one warp stalls, the scheduler issues another, for free, because all the registers are on chip. That means the GPU needs lots of independent work to stay efficient, while the CPU can run a single thread well.

GPUs also run groups of 32 threads in lockstep, so divergent branches serialize, and irregular memory access wastes bandwidth. So GPUs shine on regular, data-parallel workloads like graphics, linear algebra and image processing, where they can be 10 to 100 times faster and use less energy per operation. CPUs are better for operating-system code, control-heavy logic, small or serial tasks.

At the system level they work together. The CPU is the host that runs the program and launches kernels, and a discrete GPU has separate memory across PCIe, so copying data can dominate for small jobs. The right design question is how much of the work is parallel enough, and how much data movement it needs."
:::

::: terms
- **Latency-optimized / throughput-optimized**: designing for one fast thread versus many tasks per second.
- **Out-of-order execution**: dynamic instruction reordering used in CPUs.
- **SIMT**: GPU lockstep thread-group execution.
- **Arithmetic intensity**: FLOPs performed per byte moved from memory.
- **Roofline**: performance bound set by peak compute or memory bandwidth.
- **PCIe**: the bus connecting a discrete GPU to the host.
- **Unified / shared memory**: CPU and GPU using the same DRAM.
- **Host / device**: the CPU orchestrating, and the accelerator executing kernels.
:::

::: exceptional
**An average answer** says "GPUs have more cores and are better for parallel work".

**An exceptional answer**:
- Frames the comparison as **latency vs throughput** and derives the consequences (cache vs registers, speculation vs multithreading).
- Gives numbers: ~1 TFLOP/s vs ~35 TFLOP/s peak, ~50 vs ~900 GB/s, and the ridge points on a roofline.
- Explains *how* each hides latency and what workload shape each needs.
- Mentions divergence, coalescing and why irregular code fails on GPUs.
- Brings in system aspects: PCIe transfer cost and the break-even for offload, unified memory on SoCs.
- Finishes with energy per operation, and the point that they are complementary.
:::

::: mistakes
- **"A GPU is just many CPUs."** Lanes lack independent control flow and speculation, and share instruction streams in warps.
- **"GPUs are always faster."** Small, serial or branchy workloads and transfer-dominated jobs often run better on a CPU.
- **Comparing clock speeds.** The GPU's lower clock is irrelevant; compare achieved throughput and bandwidth.
- **Ignoring data movement.** Over PCIe, copying can cost more than the compute saved.
- **Believing GPUs have no caches.** They do (L1/L2, texture caches), but sized for streaming and reuse patterns, not for per-thread latency.
- **Saying CPUs can't do parallel work.** Multicore plus SIMD (AVX) is substantial; it is just a different balance.
:::

::: deep
## Same silicon, two bets

Imagine you have a fixed transistor budget, power budget and memory system. You can make a bet on *latency* or on *throughput*.

A CPU designer's constraint: the program is an arbitrary single instruction stream, full of dependencies and unpredictable branches, and the software industry will not rewrite it. So the hardware must extract parallelism dynamically (out-of-order window of hundreds of instructions), predict branches (>95% accuracy to keep a 15+ stage pipeline full) and avoid memory stalls (multi-level caches, prefetchers). All that machinery is overhead. A large fraction of a CPU core's area and power goes to structures that do no arithmetic: rename tables, reorder buffers, schedulers, predictors, caches.

A GPU designer's constraint: the software is written for massive parallelism already. So you can strip the overhead and spend area on arithmetic and on registers to keep many threads resident. You accept that each thread is slow.

## How the two hide latency

A DRAM miss costs about 80 ns on a CPU (240 cycles at 3 GHz). The CPU tolerates this with:

1. **Caches**: L1 hits in about 4 cycles, L2 about 12 and L3 about 40; a well-behaved program hits above 95% of the time.
2. **OoO window** of hundreds of instructions, overlapping about 10 outstanding misses per core.
3. **Prefetchers** that detect strides and fetch lines early.

A GPU tolerates a 400+ cycle miss with 2048 threads per SM (64 warps), all registers on chip. Per SM the register file is about 256 KB, comparable to a CPU's L2 cache but used as per-thread state. Bandwidth-delay product (see [[q0919]]): 900 GB/s x 400 ns = 360 KB in flight needs about 90,000 4-byte loads outstanding, easily provided by 80 SMs x 2048 threads = 163,840 threads. A CPU with 8 cores x 10 misses x 64 B = 5 KB in flight at 80 ns sustains 64 GB/s at most.

## Memory per thread: the same story in bytes

Divide on-chip storage by the number of threads sharing it and the difference becomes concrete. A server CPU with 32 MB of L3 and 16 hardware threads gives each thread about $32\times10^6/16=2$ MB of last-level cache, plus its own L1 and L2. A GPU with 80 SMs x 2048 threads = 163,840 resident threads and a 6 MB L2 gives each thread about $6\times10^6/163{,}840\approx37$ bytes of L2. Even the register file (256 KB per SM over 2048 threads) is only 128 bytes, or 32 registers, per thread. The CPU thread's cache share is therefore about $2\times10^6/37\approx54{,}000$ times larger. A GPU thread cannot rely on caching its working set between accesses; it relies on the data being streamed, on explicit reuse through shared memory by the whole block, or on having 100,000 siblings so the memory system always has something to do. This is also why GPU performance collapses for algorithms with large per-thread working sets (each thread walking its own big data structure) and thrives when threads cooperate on a shared tile.

## The offload break-even

Suppose a task takes 40 ms on the CPU and 2 ms of kernel time on the GPU, but must move 256 MB in and 256 MB out over PCIe at about 25 GB/s effective.

- Transfer each way: $256\times10^6/25\times10^9=10.2$ ms.
- GPU total: $2+10.2+10.2=22.4$ ms.
- Speedup: $40/22.4=1.8\times$ instead of the 20x kernel speedup.

If the data stays on the GPU across many kernels (as in a neural network), transfer is amortized and the kernel speedup shows. If the job is run once on small data, the CPU may win outright. Integrated GPUs and unified-memory SoCs avoid the copy (the GPU reads the same DRAM), but they share bandwidth with the CPU. This is a main reason phone and laptop SoCs integrate both ([[q0926]]).

## Energy per operation

At peak, a 150 W CPU socket delivering 1 TFLOP/s spends 150 pJ per FLOP of package power, and a 300 W GPU delivering 35 TFLOP/s spends about 8.6 pJ per FLOP. These peak-to-peak figures are illustrative (real utilization differs, and both rarely hit peak), but the order-of-magnitude gap is real: control overhead is amortized over a 32-lane warp, there is no speculation waste, and the data path is simpler. This matters for datacenters, where energy cost scales with the work done.

> [!UNCERTAIN]
> The peak-power and TFLOP numbers are representative for a high-end CPU socket and a high-end GPU card and vary widely by product; use them as order-of-magnitude illustrations rather than specifications.

## Where the CPU still wins, and convergence

CPUs win when: the task is mostly serial (Amdahl), data is small, control flow is irregular (parsing, compilers, databases with pointer chasing), latency per request matters, or the code needs full OS features. The two are converging: CPUs add wide SIMD (AVX-512, SVE) and matrix units; GPUs add caches, better branching support and independent thread scheduling; and SoCs merge them on one die with shared memory and coherent links.

> [!INTERVIEW]
> If asked "which is better?", say it depends on arithmetic intensity, parallelism, divergence and data movement, then show the roofline reasoning. Avoid declaring a winner without the workload.
:::

::: applications
- **Operating system and application logic**: CPU, due to branchy, latency-sensitive, pointer-heavy code.
- **Graphics, video effects, image processing**: GPU, with abundant data parallelism.
- **Deep learning training and inference**: GPU (or similar accelerator), dominated by matrix multiply.
- **Databases and analytics**: mix; scans and joins can use GPUs, transaction processing remains CPU-centric.
- **Phone SoCs**: CPU clusters for control and apps, GPU for UI and games, NPU for ML, all sharing LPDDR.
:::

::: assumptions
- Peak numbers are illustrative for recent high-end parts; mobile and embedded devices are far smaller.
- "CPU" means a general-purpose out-of-order core; small in-order microcontrollers differ.
- The roofline uses a single bandwidth and compute ceiling; real machines have multiple ceilings (L1, L2, special function units).
- PCIe throughput of about 25 GB/s is a representative achieved figure for a PCIe 4.0 x16 link (theoretical about 31.5 GB/s); newer generations are faster, and unified-memory systems avoid the copy.
:::

::: followups
### Why not just make a CPU with thousands of simple cores?
You can, and it looks like a GPU (or manycore chips such as Xeon Phi). But you'd still need the enormous memory bandwidth, a programming model for lockstep or massive threading, and workloads that parallelize. For general software with serial portions, Amdahl's law limits the gain, so the market keeps a few strong cores for serial work.

### Why does a GPU need more memory bandwidth than a CPU?
Because it executes so many more operations per second. With the same bytes-per-FLOP, 35x more FLOPs need 35x more bytes per second. Even with reuse in caches and shared memory, streaming kernels are bandwidth-limited, which is why GPUs use GDDR or HBM with very wide buses.

### Can a GPU run branchy code like a compiler?
Poorly. Divergence serializes paths within a warp, the working set is irregular and pointer-chasing, and there is little instruction-level parallelism per thread. A single GPU thread is also much slower than a CPU thread, so serial code loses by 10x or more.

### Your offload shows 20x kernel speedup but 1.8x end-to-end. What do you do?
Reduce transfers: keep data resident on the GPU across kernels, overlap copies with compute using streams and double buffering, use pinned memory, compress or send smaller types, fuse kernels, or use unified memory/shared-DRAM hardware. Also check CPU-side preprocessing and launch overhead.

### How would you decide whether a given workload belongs on the GPU?
Check parallelism (thousands of independent items), arithmetic intensity versus the roofline ridge, branch uniformity, memory access regularity, data size relative to transfer costs, and the lifetime of data on the device. If it is parallel, regular and reuses data on the device, use the GPU.
:::
