::: testing
Whether you understand strings as **bytes in memory**, not as a magical type. The interviewer is checking:

1. The distinction: a `char` is a single character (a one-byte integer in C); a string is a sequence of them.
2. How strings are usually implemented: in C an array of chars ending with a `'\0'` terminator, with the consequences (length is O(n), buffer overflows, `sizeof` versus `strlen`).
3. That there are other designs (length-prefixed, pointer plus length, small-string optimization, immutable Unicode strings in Python) and the trade-offs between them.
4. Awareness of encoding: ASCII versus UTF-8, and that a character is not always one byte.
5. Safe handling: bounds, termination, and the difference between `'A'` and `"A"`.
:::

::: why
Strings are everywhere in hardware work: UART command interfaces, log messages, instrument commands (SCPI), configuration files, packet payloads and debug output. In C and firmware, string handling is also one of the biggest sources of crashes and security holes (buffer overflows, missing terminators). Knowing how a string is laid out in memory lets you reason about its size, copy it safely, send it over a serial link, and answer the follow-up coding questions such as reversing a string or finding a substring ([[q0973]]).
:::

::: concepts
- **Character as integer**: `'A'` is the number 65 (0x41) in ASCII; a `char` is just a small integer. See [[q0968]].
- **Array and pointer**: a C string is a `char` array; a `char *` points to its first byte. See [[q0942]] for memory.
- **Null terminator**: the byte `0x00` marks the end of a C string, so storage needs length + 1 bytes.
- **Encoding**: ASCII (7 bits), UTF-8 (1 to 4 bytes per character), UTF-16/32.
- **Immutability**: Python and Java strings cannot be changed in place; C strings can (unless they are string literals).
- **Serial transmission**: each character is sent as a UART frame, so string length sets transfer time.
:::

::: answer
"A `char` is a single character: in C it's a one-byte integer, so `'A'` is just the number 65. A string is a sequence of characters.

In C, the usual implementation is a null-terminated array: the characters are stored one after another, followed by a zero byte that marks the end. So the string `"Hi!"` is four bytes in memory, 0x48, 0x69, 0x21 and 0x00. That means `strlen` has to walk the string until it finds the zero, which is O(n), and the buffer must be one byte longer than the text. It's also why `'A'` and `"A"` are different: `'A'` is a single character with value 65, while `"A"` is a two-byte array holding 65 and 0.

The downsides are that it's easy to overflow a buffer if you copy a string that's too long, or to forget the terminator. Other languages make different choices. Some store the length alongside the data, so length is O(1) and the string can contain zero bytes. C++'s `std::string` stores a pointer, size and capacity, and often keeps short strings inline to avoid allocating, which is called small string optimization. Python strings are immutable Unicode objects that store their length.

Finally, a character isn't always a byte: in UTF-8 a character can be one to four bytes, so the byte length and the character count can differ."
:::

::: technical
**Char.** In C, `char` is an integer type of one byte holding a character code (ASCII for 0 to 127). `'A'` is the value 65; arithmetic works: `'a' - 'A' = 32`, and flipping bit 5 (`^ 0x20`) toggles case in ASCII. A character constant has type `int` in C (so `sizeof('A')` is 4 on a typical platform) and `char` in C++ (1).

**String (C).** An array of `char` terminated by `'\0'`. On a typical 64-bit system:

```c
char a[] = "Hi!";   // sizeof(a) = 4, strlen(a) = 3   bytes: 48 69 21 00
const char *p = "Hi!";   // sizeof(p) = 8 (a pointer), points to read-only literal
```

`strlen` counts bytes before the first `'\0'` and is $O(n)$; `sizeof` of an array includes the terminator. `char x = 'A'` is 1 byte but `char y[] = "A"` is 2 bytes.

**Common implementations.**

| Design | Layout | Pros | Cons | Used by |
|---|---|---|---|---|
| Null-terminated | bytes + `0x00` | Simple, tiny overhead, works with any pointer | $O(n)$ length, no embedded zeros, overflow-prone | C, C stdlib |
| Length-prefixed | length + bytes | $O(1)$ length, binary-safe | Length field limits size, extra byte(s) | Pascal strings, many protocols |
| Pointer + length (+ capacity) | struct with pointer, size, capacity | $O(1)$ length, growable | Heap allocation, struct overhead | C++ `std::string` (typical) |
| Small-string optimization | short strings stored inside the object | No allocation for short text | Larger object; implementation-specific threshold | C++ `std::string` |
| Immutable Unicode objects | header + length + encoded data | Safe, hashable, no overflow | Cannot edit in place; overhead per object | Python, Java |

With GCC's libstdc++ on a 64-bit system, `sizeof(std::string)` is 32 bytes and its inline capacity is 15 characters; the 16th forces a heap allocation. This is implementation-specific.

**Encodings.** ASCII uses 7 bits per character. UTF-8 uses 1 byte for ASCII and 2 to 4 bytes otherwise: `é` is 2 bytes (`c3 a9`), `€` is 3 (`e2 82 ac`), and an emoji is 4 (`f0 9f 98 80`). Byte length therefore differs from character count.

**Safe handling in C.** Size buffers for length + 1, use bounded functions (`snprintf`, `strncpy` with explicit termination, or `strlcpy` where available), and validate input lengths. `snprintf(buf, 4, "%s", "Hello")` leaves `"Hel"` and a terminator, and returns the length it wanted to write so truncation can be detected.

::: long
"A `char` is a single character. In C it's really just a one-byte integer, so `'A'` is the number 65, which is why you can do arithmetic like `'a' - 'A'` to get 32. A string is a sequence of characters.

The traditional C implementation is a null-terminated array. The characters sit in consecutive bytes and a zero byte marks the end. So `"Hi!"` takes four bytes: 0x48, 0x69, 0x21, 0x00. A few consequences follow. The buffer has to be one byte longer than the visible text, so a 'size of the array' and the 'length of the string' differ by one: `sizeof` gives 4 and `strlen` gives 3. Finding the length means scanning for the zero, which is O(n). A string can't contain a zero byte in the middle. And `'A'` versus `"A"`: the first is the integer 65, the second is a two-byte array of 65 and 0. The weak point is safety: copy a long string into a short buffer and you overwrite whatever's next to it, which is a classic bug and security hole. So I'd use bounded functions like `snprintf`, check lengths, and make sure the terminator is there.

Other languages choose differently. A length-prefixed string stores the length first, so length is O(1) and zero bytes are allowed, at the cost of a length field. C++'s `std::string` keeps a pointer, a size and a capacity, and many implementations store short strings inside the object to avoid a heap allocation. Python's strings are immutable objects that know their length and store Unicode, so you can't overflow them but you also can't edit one in place.

One more thing: a character isn't always a byte. ASCII is one byte per character, but in UTF-8 an accented letter takes two bytes and an emoji four, so byte length and character count can differ. For hardware that matters when I send text over a UART, where each character costs one frame of ten bits at 8N1, and when I parse protocol commands, where I'm usually treating the string as raw bytes."
:::

::: terms
- **char**: a one-byte integer type used to hold a character code.
- **String**: a sequence of characters treated as one value.
- **Null terminator (`'\0'`)**: the zero byte that ends a C string.
- **ASCII**: the 7-bit character encoding (0 to 127) used by most embedded text.
- **UTF-8**: variable-length Unicode encoding using 1 to 4 bytes per character, ASCII-compatible.
- **String literal**: text in quotes in source code, stored in read-only memory in C.
- **Buffer overflow**: writing past the end of an array, often from an unchecked string copy.
- **Length-prefixed string**: representation that stores the length before the characters.
- **Small-string optimization (SSO)**: storing short strings inside the string object itself instead of on the heap.
- **Immutable**: cannot be modified after creation; operations return new strings.
:::

::: mistakes
- **Forgetting the terminator in size calculations.** `char s[3] = "Hi!";` has no room for `'\0'`. The array needs 4 bytes.
- **Confusing `sizeof` and `strlen`.** For `char a[] = "Hi!"`, `sizeof(a)` is 4 and `strlen(a)` is 3. For a `char *p`, `sizeof(p)` is the pointer size (8 on 64-bit).
- **Mixing `'A'` and `"A"`.** Comparing a `char` to a string literal compares an integer to a pointer.
- **Using `strcpy` or `gets` on untrusted input.** They never check the destination size. Use `snprintf` or a bounded copy plus explicit termination.
- **Modifying a string literal.** `char *p = "Hi!"; p[0] = 'J';` is undefined behavior because literals are typically in read-only memory. Use an array: `char a[] = "Hi!";`.
- **Assuming one character is one byte.** `len('€')` is 1 in Python but its UTF-8 encoding is 3 bytes; indexing bytes can split a character.
:::

::: deep
## Characters are numbers

A `char` stores a small integer code, and the encoding gives each code a meaning. In ASCII, `'A'` is 65 (0x41), `'a'` is 97 (0x61), and `'0'` is 48 (0x30). Because the codes are laid out sensibly, you can compute with them:

- Case conversion: `'a' - 'A' = 32 = 0x20`, so toggling bit 5 flips case (`'A' ^ 0x20 = 'a'`).
- Digit to value: `'7' - '0' = 7`.
- Ordering: `'A' < 'a'` is true because 65 < 97, which is why uppercase sorts before lowercase in a plain byte comparison.

Because `char` is an integer, signedness matters for codes above 127: with a signed `char`, `char c = 200;` holds −56 ([[q0968]]). Use `unsigned char` or `uint8_t` for raw bytes.

**`'A'` versus `"A"`.** `char x = 'A';` is one byte with value 65. `char y[] = "A";` is two bytes, 65 and 0 (`sizeof(y) = 2`, `y[1] == 0`). A function expecting a string will not accept `'A'`, and vice versa. In C, `sizeof('A')` is 4 because a character constant is an `int`; in C++ it is 1.

## Copying and overflow

The classic bug:

```c
char buf[4];
strcpy(buf, "Hello");   // needs 6 bytes, writes 6: overruns buf by 2
```

The destination is 4 bytes; "Hello" plus terminator is 6, so two bytes overwrite neighboring memory (other variables, a saved return address). Safer patterns:

```c
snprintf(buf, sizeof buf, "%s", "Hello");   // buf = "Hel", always terminated
```

That leaves `"Hel"` and `strlen(buf) = 3`: it truncates, never overruns, and GCC even warns about the truncation at compile time. `snprintf` returns the length it would have written (5 here), so you can detect truncation by checking `ret >= sizeof buf`. `strncpy` is a trap: it does **not** terminate when the source fills the buffer, so you must add `buf[n-1] = '\0'` yourself.

> [!WARNING]
> `gets()` cannot be used safely; it was removed from the C standard in C11. Never read unbounded input into a fixed buffer.

## Other implementations and why

**Pointer + length** (as in C++ `std::string_view`, Rust slices, Go strings): the length is known, no terminator is needed, and substrings are cheap views without copying. This is the preferred design for new APIs.

**`std::string` and small-string optimization.** A heap allocation costs time and memory, and most strings are short. Implementations therefore store short text inside the object. With GCC's libstdc++ on a 64-bit system, `sizeof(std::string)` is 32 bytes and an empty string reports a capacity of 15 characters; a 16-character string already needs a heap buffer. The threshold differs between standard libraries, so don't rely on it.

**Python `str`.** Immutable, knows its length (`len` is O(1)), and stores Unicode code points. Indexing returns a one-character string, since Python has no separate char type: `'A'` and `"A"` are the same kind of object. Assignment such as `s[0] = 'J'` raises `TypeError: 'str' object does not support item assignment`. `ord('A')` gives 65 and `chr(97)` gives `'a'`. Each string object has header overhead, so many small strings are memory-hungry.

> [!UNCERTAIN]
> Exact object sizes in Python (for example `sys.getsizeof('')`, which is 41 bytes on recent 64-bit CPython 3.12+ builds and 49 on older 3.x builds) vary between Python versions and builds. Quote them as approximate.

## Encodings: bytes versus characters

ASCII defines 128 characters, one byte each. UTF-8, the dominant encoding for files and the web, is backward compatible: ASCII characters are the same single byte, and others take two to four bytes:

| Character | Code point | UTF-8 bytes | Hex |
|---|---|---|---|
| `A` | U+0041 | 1 | 41 |
| `é` | U+00E9 | 2 | c3 a9 |
| `€` | U+20AC | 3 | e2 82 ac |
| 😀 | U+1F600 | 4 | f0 9f 98 80 |

So `len("€")` is 1 character in Python but `len("€".encode())` is 3 bytes. In C, `strlen("€")` counts bytes (3). Cutting a UTF-8 string at an arbitrary byte can split a character and produce invalid text. For most embedded work (commands, log messages) staying within ASCII avoids all of this.

## Strings and hardware: the UART view

When firmware prints a string over a UART, each character becomes a frame: start bit, 8 data bits LSB first, stop bit, which is 10 bit-times per character at 8N1. At 115,200 baud one character takes $10/115200 = 86.8\ \mu s$, so `"Hi!"` (3 characters, without a newline) takes $3\times86.8 = 260.4\ \mu s$. That is also why long debug prints inside an ISR hurt timing: a 40-character message takes about 3.5 ms. The terminator is not transmitted; the transmit routine stops when it reads the `'\0'`.


## Debug checklist for string bugs

1. Is the buffer at least length + 1 bytes? Is the terminator present?
2. Is the string a literal being modified (read-only)?
3. Does a copy function check the destination size?
4. Is the data actually text, or binary that may contain `0x00` (use length-aware functions like `memcpy`)?
5. Is the encoding what you expect (ASCII versus UTF-8), and are you counting bytes or characters?
6. For parsing, are there stray `'\r'` or `'\n'` bytes at the end (common with serial commands)?

::: applications
- **UART command interfaces**: a microcontroller reads text commands like `"LED ON\n"`, tokenizes them and replies with text.
- **Instrument control**: SCPI commands such as `MEAS:VOLT?` sent as ASCII strings over USB, GPIB or Ethernet.
- **Logging and debug output**: formatted messages with `snprintf` into a fixed buffer, queued for slow transmission.
- **Protocol parsing**: separating fields in NMEA GPS sentences or AT commands for cellular modems.
- **File and config handling**: parsing log files, netlists and register lists in scripts ([[q0967]]).
- **Display drivers**: character LCDs and OLEDs index into font tables using each character's code as an offset.

::: followups
### What is the difference between `'A'` and `"A"` in C?
`'A'` is a character constant: the integer 65 (type `int` in C). `"A"` is a string literal: a two-element `char` array `{65, 0}`, whose expression value is a pointer to its first element. You can store `'A'` in a `char`; you can only point at `"A"`. `sizeof("A")` is 2.

### Why is `strlen` O(n), and how could you make length O(1)?
A null-terminated string carries no length, so `strlen` must scan until it hits `'\0'`. To get O(1) length, store the length with the data: a length prefix, a struct with pointer and size, or a language-level string type. The cost is extra storage and having to keep the length in sync.

### How do you safely copy a string into a fixed 16-byte buffer?
`snprintf(dst, sizeof dst, "%s", src);` always terminates and never writes more than 16 bytes, truncating if necessary; check the return value if truncation matters. Alternatively check `strlen(src) < sizeof dst` first and `memcpy` the length + 1 bytes. Avoid `strcpy`, and remember `strncpy` does not terminate on truncation.

### Why can't you modify `char *p = "Hi!"; p[0] = 'J';`?
String literals live in read-only memory (typically `.rodata`), so writing to them is undefined behavior and usually a crash on a system with memory protection. Declare `char a[] = "Hi!";` to get a writable copy on the stack, or `const char *p` to make the read-only nature explicit.

### How many bytes does the string "Température" take in UTF-8?
There are 11 characters. Ten of them are ASCII (1 byte each) and `é` takes 2 bytes, so 12 bytes. `strlen` would return 12 although there are 11 characters. In Python `len` would give 11 and `len(s.encode())` would give 12.

### How long does it take to send "Hello, World!" followed by a newline over a 9600-baud UART (8N1)?
That is 13 + 1 = 14 characters at 10 bit-times each, so 140 bits. At 9600 baud: $140/9600 = 14.6$ ms. At 115,200 baud it would be 1.2 ms. If this runs in an interrupt or main loop with blocking transmission, it can break timing, so use a TX buffer with interrupts or DMA.
