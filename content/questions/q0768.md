::: basics
### In plain words
A daisy chain connects SPI slaves one after another, like links in a chain. The master's data goes into the first chip. Each chip passes its data on to the next, and the last chip sends it back to the master. All the chips share one clock and one chip select. The whole chain acts like one long row of storage cells.

### Picture it
Imagine a line of people, each holding a card. On every beat of a drum, each person hands their card to the next person down the line. To end up with a chosen card in every hand, you feed in the card for the farthest person first. Cards for nearer people go in later. When a whistle blows, everyone keeps the card they hold. In SPI, that whistle is chip select going high.

### Words you need
- **Daisy chain**: devices connected in series, so data passes through each one in turn.
- **Shift register**: a row of storage cells that moves every bit one place along on each clock tick.
- **Frame**: one period with chip select low. Here it spans the whole chain.
- **Latch**: copying the collected bits into the part that drives the outputs. It happens when chip select goes high.
- **Chip select (CS)**: the shared wire that marks the frame. See [[q0765]].

### The simplest example
Chain three chips, each holding 8 bits. You want them to end up with bytes A, B and C, in order from nearest the master to farthest. Pull CS low. Send C first, then B, then A. That is 24 clock ticks, or 2.4 µs at 10 MHz. The first byte travels through two chips and settles in the last one. Raise CS, and all three chips latch their bytes at the same moment. That is the whole idea. The rest of this page covers the readback order, timing limits, and why not every SPI chip can be chained.
:::

::: testing
Whether you understand the shift-register nature of SPI well enough to chain devices. The interviewer wants:

1. The topology: MOSI into slave 1; each slave's data output into the next slave's input; the last output back to MISO; SCLK and CS shared.
2. The behaviour: the chain acts as one long shift register, so a frame is $N\times$ word length clocks, and the first word sent ends up in the *last* device.
3. When the outputs update: on CS rising edge (or a latch pin).
4. The trade-offs: fewer wires and simultaneous update versus latency, all-or-nothing frames, and device support.
:::

::: why
Daisy-chaining is how a handful of pins can drive dozens of LED drivers, DACs, shift registers or analog switches. It also tests whether you really understand SPI as shifted bits rather than "commands to addresses". Getting the data order right (farthest device first) is a classic bring-up detail.
:::

::: concepts
- **Shift register ring**: each device's interface is a shift register. See [[q0764]], [[q0886]] and [[q0882]].
- **Chip select framing**: CS low for the whole chain frame; rising edge latches. See [[q0766]].
- **Shared clock**: all devices shift together. See [[q0767]].
- **Pin-count scaling**: four wires for any $N$. See [[q0765]].
- **Propagation per hop**: each stage re-registers data on the clock, so delay doesn't accumulate along the data path.
:::

::: answer
"Daisy-chaining means connecting SPI slaves in series so they act like one long shift register. The master's MOSI goes into slave 1's data input, slave 1's data output goes into slave 2's input, and so on, and the last slave's output returns to the master's MISO. SCLK and chip select are shared by all of them, so it's four wires no matter how many devices.

To use it, I pull CS low and clock out enough bits to fill every device: with N devices of 16 bits each that's 16N clocks. Data flows down the chain as it shifts, so the first word I send ends up in the last device, and the last word I send stays in the first. When I raise CS, each device latches whatever is in its shift register, so all of them update at the same time. While I'm sending, whatever was in the chain comes back on MISO, which is how I read results.

The advantages are the minimal wiring and simultaneous updates. The disadvantages are that every transaction has to move data for the whole chain, even to change one device; latency grows with chain length; and only parts that support it, with a data output and latch-on-CS behaviour, can be chained. Common examples are 74HC595 shift registers, LED drivers, DAC and ADC arrays."
:::

::: technical
**Topology.** Master MOSI → SDI(1); SDO(1) → SDI(2); … ; SDO(N) → MISO. SCLK to all devices; CS to all devices (one CS line).

**Frame.** With $N$ devices of $w$ bits each, one frame is $N\cdot w$ clocks with CS low throughout. The first word shifted in travels through all devices and ends in device $N$; the last word ends in device 1. So to load words $D_1, \dots, D_N$ into devices $1\ldots N$, send $D_N$ first and $D_1$ last.

**Latch.** Devices copy their shift register into the active register on CS rising edge (some use a separate latch pin such as RCLK on a 74HC595, or LOAD on other parts). All outputs update simultaneously.

**Readback.** The words shifted out of device $N$ during the frame are the *previous* contents of each device's shift register (output/result data), arriving in the order $N, N-1, \dots, 1$; the master reads them from MISO.

**Timing.** Each device re-times the data on the clock edge, so the data path adds one register delay per hop but does **not** accumulate skew: each link only needs to satisfy $t_{co}+t_{su}$ within a clock period. The SCLK and CS distribution does accumulate: loading and skew on the shared lines limit the clock rate for long chains.

**Frame time.** $T=N\cdot w/f_{SCLK}$. Example: 4 devices × 16 bits at 10 MHz = 64 clocks = 6.4 µs.

**Device requirements.** The slave needs an SDO that forwards shift-register data (rather than only register read replies), defined behaviour for CS frames longer than one word, and latch-on-CS or a latch pin. Datasheets say "daisy-chain mode" explicitly; some devices need a command bit to enable it or a "no-op" opcode so unaddressed devices ignore data.

> [!UNCERTAIN]
> Details such as whether the chain forwards data in non-daisy modes, whether a no-op code is needed, and latch behaviour differ per device. Always follow the device datasheet's daisy-chain section.
:::

::: long
"A daisy chain connects the SPI slaves in series instead of in parallel. The master's MOSI goes to the data input of slave 1. Slave 1's data output goes to slave 2's input, and so on down the line, and the output of the last slave goes back to the master's MISO. SCLK and chip select go to every device. So whether I have 3 devices or 30, the master only needs four signals.

The reason it works is that SPI slaves are fundamentally shift registers. When the clock runs, bits move one place along. With the devices linked, the chain is just one long shift register, and the master sees it as a frame that is N words long. So to talk to a chain of four 16-bit devices, I pull CS low, clock out 64 bits, and raise CS. The order matters: the first word I send travels all the way through and ends up in the last device, and the last word I send ends up in the first. So I send the data for the farthest device first.

CS is more than a select here: it frames the whole shift, and when it rises, every device latches its shift register contents into its working register at once. That's a nice feature, because all the outputs, say four DAC voltages or a row of LED drivers, change at the same instant. The data coming back on MISO during the frame is what was previously in the shift registers, so the master can read status or conversion results in the same transaction, though they arrive in far-to-near order and lagged.

The trade-offs are that a change to one device means shifting the whole chain, latency grows with chain length, you can't address one device in isolation unless the part supports a no-op code, and the chip has to be designed to be chained. Timing-wise, each hop re-registers the data, so the delay doesn't pile up, but the shared SCLK has to reach every chip cleanly, which limits the clock for long chains. Typical parts: 74HC595 shift registers, LED drivers, DAC and ADC arrays."
:::

::: terms
- **Daisy chain**: series connection of devices so data passes through each.
- **SDI / SDO**: a slave's data in and data out.
- **Frame**: one CS-low period; here $N\cdot w$ clocks long.
- **Latch**: copying the shift register to the output/working register, on CS rising edge or latch pin.
- **No-op / bypass command**: command that makes a device ignore data while passing it along.
- **Chain length**: number of devices in series.
- **Shift register**: bit storage that moves one position per clock. See [[q0886]].
- **Parallel (star) topology**: shared MOSI/MISO with separate CS lines. See [[q0765]].
:::

::: exceptional
**An average answer** says "slaves are connected in series so you only need one CS".

**An exceptional answer**:
- Describes the topology and explains it as one long shift register, with frame length $N\cdot w$.
- Gets the data order right (first word ends in the last device) and when outputs update (CS rising / latch).
- Explains readback lag and order.
- Gives trade-offs: latency, all-or-nothing frames, device support, shared SCLK loading; and notes that data-path timing doesn't accumulate.
- Names real parts (74HC595, LED drivers, DAC/ADC arrays) and compares with independent CS.
:::

::: mistakes
- **Sending data for device 1 first.** It ends up in the last device. Send the farthest device's word first.
- **Raising CS between words.** That latches a partial frame and corrupts the chain.
- **Assuming any SPI slave can be chained.** It needs an SDO that forwards the shift register and latch-on-CS behaviour.
- **Expecting independent access.** Updating one device means resending (or no-op'ing) the others.
- **Wrong frame length.** Missing one device's worth of clocks shifts every word by a device.
- **Thinking timing accumulates down the chain.** Each hop re-registers the data; it's SCLK distribution that limits the speed.
:::

## The chain is one long shift register

Each device contains a shift register of $w$ bits between its SDI and SDO. Connected end to end, the three devices form a $3w$-bit shift register. Every clock edge moves every bit one place along. After $3w$ clocks, the first bit sent has gone through all three devices and the entire frame is distributed.

A concrete example with $w=8$ and three devices, loading D1 = 0x11, D2 = 0x22, D3 = 0x33:

| Clock count | What the master sends | Where it ends up |
|---|---|---|
| clocks 1–8 | 0x33 (D3 first) | passes devices 1 and 2, ends in device 3 |
| clocks 9–16 | 0x22 | ends in device 2 |
| clocks 17–24 | 0x11 | stays in device 1 |

Then CS rises and all three devices latch: outputs become 0x11, 0x22, 0x33 together. The frame took 24 clocks: 2.4 µs at 10 MHz.

## Worked example: a four-device DAC chain

Four 12-bit DACs that each take a 16-bit SPI word (code in the low 12 bits), 5 V reference. Wanted outputs: 1.25 V, 2.50 V, 3.75 V and full scale (codes 1024, 2048, 3072, 4095 for a 4096-count scale: $1.25/5\times4096=1024$, $2.5/5\times4096=2048$, $3.75/5\times4096=3072$; the top code 4095 gives $5\times4095/4096\approx4.999$ V).

Send the word for DAC 4 first (0x0FFF), then DAC 3 (0x0C00), DAC 2 (0x0800), DAC 1 (0x0400): 64 clocks. At 20 MHz that is 3.2 µs. CS rises, and the four outputs step together, which is the whole point: with independent chip-selects you would update them one at a time over 4 × (16 clocks + CS gap), and the outputs would move at different instants, which matters for multi-axis control or phase-aligned waveforms.

What if only DAC 2 should change? Resend the shadow copy of the others (or use their no-op code): still 64 clocks. That is the cost of the topology.

## Readback

While the master shifts words in, each device's *old* shift-register contents come out of its SDO and travel to the master's MISO. The first word to arrive at MISO is whatever device 3 held, then device 2's, then device 1's, so readback is far-to-near and lags the write by one frame. Many ADC and sensor chains work this way: the frame that sets up the next conversion also returns the last conversion results. For pure reads you send no-op frames.

## Timing: what accumulates and what doesn't

Each device samples SDI on the clock edge and presents the bit on SDO after $t_{co}$, so the link from SDO(k) to SDI(k+1) needs only $t_{co}+t_{prop}+t_{su}\le$ half or one period, independent of position in the chain. What does scale with chain length:

- **SCLK and CS fan-out:** load capacitance and skew across devices; at higher clocks the shared lines need buffering or termination.
- **Total frame time:** $T=N\cdot w/f_{SCLK}$.
- **Hold-time risk:** if SCLK arrives later at device $k+1$ than at device $k$ (skew) while data from device $k$ is quick, device $k+1$ can capture the *new* bit: a classic daisy-chain hold violation. Keep skew below the data path $t_{co,min}$.

For $N=8$ devices of 16 bits at 10 MHz: $128/10\text{ MHz}=12.8$ µs per frame. The same eight devices with independent CS take roughly the same number of clock cycles if you update all of them, but with CS toggling overhead and *non-simultaneous* outputs; for updating only one, independent CS needs 16 clocks and the chain needs 128.

## When to use a chain

| Good fit | Poor fit |
|---|---|
| Many identical output devices updated together (LED drivers, DACs, shift registers) | Random access to one of many devices |
| Pins/board routing are the constraint | Low-latency single-device access |
| Simultaneous update is a feature | Devices with different modes or word lengths |
| Slow-to-medium clocks | Long chains at very high clocks (SCLK loading and skew) |

If a device in the chain must be skipped, many parts provide a **bypass or no-op command**; the data still flows through, but that device ignores its payload.

## Parts you'll meet

- **74HC595** serial-in/parallel-out shift register: cascade via QH' to the next SER; latch with RCLK. It is a pure shift register, with no CS, but the same principle.
- **LED driver and display ICs** (e.g. MAX7219-style): 16-bit words, cascaded through DOUT, latched on LOAD/CS.
- **Multi-channel DACs/ADCs and analog switch arrays**: daisy-chain modes documented in the datasheet.

> [!INTERVIEW]
> Say "it's one long shift register" and "the first word sent ends up in the last device". Those two sentences prove you understand rather than recite.
:::

::: applications
- **LED matrix and 7-segment drivers**: many drivers cascaded on one SPI port.
- **Multi-channel DAC boards**: eight or sixteen DACs updated simultaneously.
- **Shift-register I/O expansion**: 74HC595 chains for digital outputs, 74HC165 for inputs.
- **Battery management monitors**: stacks of cell-monitor ICs communicating through a daisy chain (often over isolated variants).
- **Analog switch matrices** configured by a long serial word.
:::

::: assumptions
- **Devices that support daisy-chain mode** with SDO forwarding the shift register, word length $w$, and latch on CS rising edge.
- **One CS shared**, a common SPI mode, and identical word lengths. Mixed devices need different frame calculations.
- **Moderate clock speed** so SCLK skew isn't an issue.
- **Master/slave naming** as in the rest of the section.

If the chain is of different devices, the total length is the sum of their word lengths and each word is placed according to its distance from the MISO end.
:::

::: followups
### In what order do I send the data for a chain of devices?
Farthest device first. The first word goes through every other device and ends up in the last one, so send the word for device N first and device 1 last. Sending in the other order loads each device with another device's data.

### How do I update only one device in the chain?
Either resend the current values for all other devices, or use the device's no-op/bypass command for them. Keep a shadow copy of each device's register in firmware so you can regenerate the whole frame.

### How does the master read data back?
During any frame, MISO carries the old shift-register contents from the last device first. So readback of results lags by one frame and arrives far-to-near. Many designs send a NOP frame to flush results out.

### How is a chain different from independent CS wiring electrically?
Data runs point-to-point between devices (short, clean links), while SCLK and CS are shared bus lines. There's no shared MISO, so no tri-state contention. The cost is loading on SCLK/CS and the all-device frame time.

### What goes wrong if CS glitches high mid-frame?
The devices latch partial data: each gets a shifted, incorrect word and outputs jump to wrong values. Protect CS with a pull-up and clean routing, and avoid hardware CS modes that toggle between bytes.
:::

::: interpretations
"How does daisy-chaining work?" in the SPI section refers to the series-connected slave topology (shared SCLK and CS, data passing from device to device). It is not the same as the generic "daisy chain" of cables. For the parallel option see [[q0765]]; for general wiring [[q0767]].
:::
