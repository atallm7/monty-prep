::: basics
### In plain words
A GPU helps with any job that applies the same operation to a huge amount of independent data. The headline example is machine learning, which is mostly multiplying big grids of numbers, called matrices. Others are scientific simulation, image and video processing, and Monte Carlo methods (averaging many random trials). A GPU does not help with branchy code, tiny problems, or jobs where copying the data takes longer than the math.

### Picture it
A combine harvester is fantastic on a huge, uniform wheat field. It does the same simple action over and over across a wide area. It is useless for picking fruit from a few winding orchard trees, where each tree needs a different decision. GPU work is the wheat field. The harvester also has to be driven to the field first, and that trip counts.

### Words you need
- **Data parallelism**: the same operation on many independent data elements.
- **GPGPU**: general-purpose computing on a GPU, outside of graphics.
- **Tensor core**: hardware that does a small matrix multiply-add in one operation.
- **Arithmetic intensity**: operations done per byte of memory traffic.
- **Offload**: sending a job to the GPU, which adds copying costs ([[q0907]]).

### The simplest example
Multiplying two $N \times N$ matrices takes about $2N^3$ operations on about $12N^2$ bytes of data (three matrices of 4-byte numbers). Double $N$, and the arithmetic grows 8 times, but the data grows only 4 times. So for small $N$, the copy and launch overhead make the GPU slower. Past some size the arithmetic outgrows the copying, and the GPU wins. The page's example hardware has a break-even near $N = 300$.

That is the whole idea: the GPU wins when the job is wide, regular and arithmetic-heavy compared with its data. The rest of this page walks through machine learning, simulations and image filters with numbers, and lists where a GPU is the wrong tool.
:::

::: testing
Whether you understand **why** GPUs help on some non-graphics jobs and not others, rather than reciting "AI and crypto". The interviewer is looking for:

1. A concrete list: machine learning, scientific simulation, signal/image/video processing, Monte Carlo, hashing, linear algebra, database scans.
2. The common properties that make a task a good fit: lots of independent data, regular memory access, high arithmetic intensity or streaming bandwidth.
3. The matching counter-examples (pointer chasing, branchy serial code, tiny problems, transfer-bound jobs) and the reason each fails.
4. Awareness of the cost side: host-device transfers, programming model, precision and memory capacity.
:::

::: why
GPU compute (GPGPU) is now the default platform for training neural networks, and a major tool in simulation, finance and media. Hardware engineers need to know which workload properties map to GPU strengths, because those properties drive what gets built into silicon: tensor cores, HBM, large register files, high-speed interconnects. The same reasoning appears in SoC design when deciding whether a task goes to the CPU, GPU, NPU or a fixed-function block ([[q0928]]).
:::

::: concepts
- **Data parallelism**: the same operation applied to many independent data items. See [[q0920]].
- **Arithmetic intensity**: FLOP per byte of memory traffic. See [[q0924]].
- **Throughput vs latency**: GPUs trade per-thread speed for total work per second. See [[q0922]].
- **Coalesced access**: neighboring threads reading neighboring addresses so memory is used efficiently.
- **Amdahl's law**: speed-up is limited by the serial fraction, including data transfers.
- **Reduced precision and matrix engines**: FP16/BF16/INT8 and tensor units for ML. See [[q0923]].
:::

::: answer
"Pretty much anything that is the same operation applied to a huge amount of independent data. The headline example today is machine learning: training and inference are dominated by big matrix multiplies and convolutions, which are exactly the high-arithmetic-intensity, regular, parallel workloads a GPU is built for, and modern GPUs even have tensor cores for it. Scientific simulation is another: molecular dynamics, fluid dynamics, N-body, weather. Then image and video processing, signal processing like FFTs, Monte Carlo methods in finance, hash computation and cryptographic brute-force, genomics alignment, and database scans and sorts.

The why is the same in every case. The work is data-parallel, so thousands of threads can run without talking to each other. Memory access is regular, so the wide memory bus is used well. And either the arithmetic per byte is high, so the FLOPS get used, or the job just streams data, so the huge memory bandwidth, ten times a CPU's, is what helps.

It doesn't help for things like pointer-chasing, a lot of branching, small problems, or jobs where moving data over PCIe takes longer than the compute."
:::

::: technical
**Good-fit criteria.**
1. **Massive independent parallelism**: at least $10^4$ to $10^6$ threads of work to fill and hide latency ([[q0923]]).
2. **Regular, coalescable memory access**: adjacent threads touch adjacent addresses.
3. **High arithmetic intensity** (compute roof) *or* a streaming pattern that exploits bandwidth (memory roof). See the roofline in [[q0924]].
4. **Low divergence**: threads in a warp follow the same path.
5. **Compute grows faster than data movement**: $O(N^3)$ compute on $O(N^2)$ data (GEMM) or $O(N^2)$ on $O(N)$ (N-body).

**Examples with the reason.**

| Task | Why it maps well | Typical limiter |
|---|---|---|
| Neural-network training/inference | Dense matmul/conv, intensity in the hundreds of FLOP/B, tolerates FP16/INT8 | Memory capacity, interconnect |
| Dense linear algebra (GEMM, LU) | $2N^3$ FLOP over $\sim12N^2$ B, intensity $\sim N/6$ | Compute roof |
| N-body, molecular dynamics | $O(N^2)$ pair interactions on $O(N)$ data, tiled in shared memory | Compute, neighbor-list irregularity |
| FFT, stencils, CFD | Regular grids, streaming; intensity of a few FLOP/B | Memory bandwidth |
| Image/video filters | Per-pixel independence | Memory bandwidth |
| Monte Carlo (pricing, ray/path tracing) | Independent samples, random number streams per thread | Divergence in path tracing |
| Hashing / brute force | Independent trials, integer ops | Integer throughput |

**Counter-examples.** Pointer-chasing (linked lists, graphs with irregular degree), deeply branchy or serial control logic, tiny problems (launch overhead of microseconds exceeds the compute), and jobs dominated by PCIe transfers.

**Transfer break-even.** For $N\times N$ FP32 matrix multiply: $t_{GPU}\approx 2N^3/P_{gpu}+12N^2/BW_{PCIe}$. The cubic compute grows faster than the quadratic transfer, so there is an $N$ above which offload wins. With the example numbers in the deep dive, the break-even is around $N\approx300$.
:::

::: short
"GPUs excel at anything that's the same operation over lots of independent data: machine learning, which is mostly matrix multiplies, scientific simulation, image and video processing, FFTs, Monte Carlo and hashing. The reasons are thousands of parallel threads, regular memory access that uses the wide high-bandwidth memory, and high arithmetic intensity. They struggle with branchy, serial or pointer-chasing code, small problems, and jobs dominated by PCIe transfers."
:::

::: long
"A GPU is a throughput machine: thousands of simple lanes, very high memory bandwidth, and it needs a lot of independent work to stay busy. So the question is which non-graphics tasks look like that.

The biggest today is machine learning. Training and inference are mostly large matrix multiplies and convolutions: regular, parallel, hundreds of FLOP per byte, and they tolerate reduced precision, so GPUs added tensor cores that run FP16 or INT8 matrix operations at many times the rate of normal lanes.

Scientific computing is the original GPGPU use case. N-body and molecular dynamics have order N-squared interactions on order N data, so intensity is high. Fluid dynamics and weather codes use stencils over regular grids, which are bandwidth-bound, but a GPU has maybe ten times a CPU's bandwidth, so they still win. FFTs and image and video filters are the same story.

Monte Carlo methods suit GPUs because each sample is independent, like options pricing or path tracing. Hashing and password cracking are millions of independent trials.

The common thread is data parallelism, regular memory access, and either high arithmetic intensity or a streaming pattern.

And the limits matter. A pointer-chasing graph traversal, a branchy state machine, or a problem so small the kernel launch overhead dominates will not speed up. Neither will something where copying data over PCIe costs more than the computation. So I'd always compare the compute time against the transfer time and check the Amdahl limit before porting anything."
:::

::: terms
- **GPGPU**: general-purpose computing on a GPU, via CUDA, OpenCL, Vulkan compute or similar.
- **Data parallelism**: same operation on many independent data elements.
- **Tensor core / matrix engine**: hardware doing small matrix multiply-accumulates in one operation.
- **Kernel**: a function launched across many GPU threads.
- **Coalescing**: merging a warp's neighboring memory accesses into few transactions.
- **Stencil**: computation of each grid point from its neighbors.
- **Monte Carlo**: estimating a result by averaging many independent random samples.
- **Amdahl's law**: overall speed-up limited by the non-accelerated fraction.
- **HBM**: stacked high-bandwidth memory used on compute GPUs.
:::

::: exceptional
**An average answer** says "AI, crypto mining and scientific computing because they have lots of cores".

**An exceptional answer**:
- Derives the **criteria** (independence, regular access, intensity, low divergence) and uses them to explain *each* example.
- Separates **compute-bound** (GEMM, N-body) from **bandwidth-bound** (FFT, stencils) examples, and explains that both can win for different reasons.
- Mentions precision tolerance (FP16/INT8/BF16) as an enabler for ML.
- Gives a counter-example with the reason, and discusses transfer cost and Amdahl.
- Notes that specialized accelerators (TPUs/NPUs, ASICs for mining) exist because GPUs are general, and that the boundary moves.
:::

::: mistakes
- **"GPUs are just faster CPUs."** They are faster only at throughput on parallel work.
- **Ignoring transfers.** Offloading a small job over PCIe can be slower than the CPU.
- **Assuming any loop parallelizes.** Loop-carried dependencies or atomics serialize work.
- **Forgetting that memory-bound tasks still benefit.** The gain equals the bandwidth ratio, not the FLOPS ratio.
- **Claiming GPUs are best for everything numeric.** Double-precision throughput is much lower on consumer GPUs than FP32, and irregular sparse workloads reach a small fraction of peak.
- **Ignoring memory capacity.** Problems larger than device memory force slow paging over PCIe.
:::

::: deep
## What makes a workload "GPU-shaped"

Recall the design bet from [[q0923]]: a GPU spends its silicon on thousands of lanes, a huge register file and wide memory instead of big caches and speculation. That bet pays off when:

1. **There is a lot of independent work.** The machine hides a ~400-cycle DRAM latency by switching among warps. With 80 SMs $\times$ 2048 threads = 163,840 resident threads, a problem with 10,000 elements leaves most of the chip idle.
2. **Threads do the same thing.** SIMT executes 32 lanes in lockstep, so divergence wastes lanes.
3. **Memory accesses line up.** If neighboring threads read neighboring 4-byte words, one 128-byte transaction serves the whole warp; scattered access may need 32 transactions, an 8x or worse bandwidth loss.
4. **Either the math is dense or the data streams.** Dense math uses the compute roof; streaming uses the bandwidth.

## Machine learning: the canonical case

A fully connected layer with input vector length $n$, output length $m$ and batch $B$ is a $(B\times n)\cdot(n\times m)$ matrix multiply: $2Bnm$ FLOP. For $B=256$, $n=m=4096$: $2\times256\times4096^2=8.6$ GFLOP, moving about $(256\cdot4096+4096^2+256\cdot4096)\times2$ bytes in FP16 $=37$ MB. Intensity $=8.6\times10^9/37\times10^6\approx230$ FLOP/B, well above a typical ridge point, so compute-bound and ideal for matrix engines.

Two further properties help: the networks tolerate **reduced precision** (FP16, BF16, INT8) which doubles or quadruples throughput per watt, and they are so regular that a dedicated matrix array (tensor core) does a small matrix multiply-accumulate in a single operation. This is why AI accelerators converged on GPU-like designs with HBM, and why specialized NPUs appear in SoCs ([[q0928]]).

## Scientific simulation

**N-body / molecular dynamics.** Each body interacts with every other: $N^2$ pair computations, each roughly 20 FLOP. For $N=10^6$ that is $2\times10^{13}$ FLOP. At 50% of a 34.8 TFLOPS peak this takes 1.1 s on the GPU. A CPU at 0.5 TFLOPS sustained needs 40 s. Positions are 16 bytes per body, so tiles of bodies sit in shared memory and each loaded byte is reused thousands of times, giving huge arithmetic intensity.

**Stencils and fluid dynamics.** Each grid point updates from neighbors; arithmetic per byte is small, so these are bandwidth-bound. The GPU wins by the bandwidth ratio (for example 512 GB/s vs 50 GB/s, about 10x). Careful use of shared memory to reuse neighboring values helps.

**FFT.** A radix-2 complex FFT performs about $5N\log_2N$ FLOP on $16N$ bytes of FP32 complex data if read and written once: intensity $\approx 5\log_2N/16$, which is 3.1 for $N=1024$ and 6.3 for $N=2^{20}$. Both are well below the ridge point of 68, so FFTs are bandwidth-bound and speed up by roughly the bandwidth ratio.

## Media and signal processing

A 3x3 filter on a 4K image does 9 multiply-adds (18 FLOP) per pixel and moves about 8 bytes (read 4, write 4): intensity 2.25. Memory traffic for a 3840x2160 frame is 66 MB, which at 512 GB/s takes 0.13 ms. Per-pixel independence and regular access make it trivially parallel. Video codecs and image-signal-processing on a SoC often use dedicated blocks instead for energy reasons, even though a GPU could do the math ([[q0928]]).

## Monte Carlo, hashing and other embarrassingly parallel tasks

Each sample or hash trial is independent, so there is no communication to coordinate. Each thread runs its own random-number stream (counter-based generators are common because they need no shared state). Cryptocurrency hashing and password cracking are integer-heavy and also parallel; once the algorithm is stable, ASICs beat GPUs by a wide margin because the fixed-function logic can drop everything not needed, the same trade-off described in [[q0923]].

## When the GPU is the wrong tool

- **Pointer chasing and irregular graphs**: each access depends on the last, so latency is exposed; warps diverge on different-degree nodes.
- **Branchy control-flow code**: divergence serializes paths.
- **Small problems**: kernel launch costs microseconds and the machine cannot be filled.
- **Transfer-bound jobs**: if you touch each byte once, the PCIe copy is slower than just computing on the CPU.

- **Deep learning training and inference**: data-center GPUs with tensor cores and HBM; edge GPUs in embedded modules.
- **Scientific computing**: molecular dynamics, CFD, weather and seismic imaging codes running on GPU supercomputers.
- **Media**: video encode filters, image processing pipelines, computational photography.
- **Finance**: Monte Carlo option pricing and risk calculations.
- **Signal processing**: radar, communications and software-defined radio FFT chains.
- **Data analytics**: GPU-accelerated database scans, sorting and joins.

- The speed-up plot assumes FP32 dense GEMM, 80% achieved on the GPU, 0.8 TFLOPS on the CPU, 25 GB/s effective PCIe, one copy-in of three matrices and no overlap of copy with compute. Overlapping transfers or keeping data resident changes the break-even.

- "GPU" here means a discrete or integrated programmable GPU. Integrated GPUs on SoCs share memory with the CPU, so there is no PCIe copy but bandwidth is lower.
- Precision matters: double-precision rates on consumer GPUs are a small fraction of FP32.

::: followups
### Why is machine learning such a good fit for GPUs?
Layers reduce to large dense matrix multiplications with intensity in the hundreds of FLOP/B, they are fully parallel across batch and features, memory access is regular, and the models tolerate FP16/BF16/INT8. That lets GPUs use tensor units and HBM at high utilization. The work is also big enough to amortize launch and transfer overheads.

### Why do FFTs and stencils speed up even though they are memory-bound?
The GPU's advantage is bandwidth as well as FLOPS. At 512 GB/s versus perhaps 50 GB/s for a desktop CPU, a bandwidth-bound kernel runs about 10x faster, even though it uses under 10% of the GPU's arithmetic peak. Efficiency per watt is still better than the CPU.

### Why did people move from GPUs to ASICs for crypto mining?
Once the hash algorithm is fixed, a dedicated chip can omit everything a GPU carries for generality (texture units, graphics pipeline, big register files, flexible scheduling) and spend all its area and energy on the hash datapath. That gives order-of-magnitude better energy per hash. It is the specialization-versus-flexibility trade-off from [[q0923]].

### A colleague wants to move a 2 ms CPU function to the GPU. What do you check first?
How much data it touches and how many times it runs. If it processes a few MB once, the PCIe copy (about 0.1 ms per 2.5 MB at 25 GB/s) plus launch may eat most of the gain. I would check intensity, parallelism (are there thousands of independent items?), divergence, and whether the data could stay on the device across several steps. Then prototype and profile end to end.

### What if the algorithm is branchy and irregular, like a graph traversal. Is the GPU hopeless?
Not hopeless, but you need to restructure. Frontier-based BFS formulations, sorting nodes by degree, and processing in warp-sized chunks can recover efficiency. Still, utilization is often a small fraction of peak, so the speed-up might be modest. Sometimes a CPU with large caches is the better choice.
