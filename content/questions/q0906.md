::: basics
### In plain words
The five-stage pipeline splits the work of each instruction into five steps: fetch, decode, execute, memory and writeback. Each step has its own hardware, so five instructions can be in progress at once, each at a different step. Once the pipeline is full, one instruction finishes every clock cycle.

### Picture it
Think of laundry with a washer, a dryer and a folding table. You don't wait for load 1 to be folded before washing load 2. While load 1 is in the dryer, load 2 is in the washer. Every step stays busy, and loads come out at a steady pace. The catch is when one load needs something the previous load has not finished yet, and you have to wait.

### Words you need
- **Stage**: one step of the instruction's work, with its own hardware ([[q0909]]).
- **Pipeline register**: storage between stages that carries each instruction's partial results to the next stage.
- **Throughput vs latency**: how many instructions finish per second, versus how long one instruction takes.
- **Hazard**: a situation where the next instruction can't safely go ahead yet, such as needing a result not ready.
- **Stall**: a cycle where a stage waits and does no useful work.

### The simplest example
Run 5 instructions through 5 stages. Without a pipeline, each takes 5 cycles, so 25 cycles in total. With a pipeline, the first one finishes after 5 cycles and one more finishes every cycle after that. So the total is 5 + 4 = 9 cycles. That is a speedup of 25 / 9, about 2.8. For 100 instructions it is 500 / 104, about 4.8, closing in on 5.

That is the whole idea. The rest of this page adds what each stage does in detail, the three kinds of hazard and their fixes (including forwarding a result straight to where it is needed), and how stalls change the cycle count.
:::

::: why
The classic five-stage RISC pipeline is the mental model behind almost every CPU, from a Cortex-M3 (three stages) to high-end out-of-order cores (many more stages). Reasoning about stalls, forwarding, and branch penalties is how architects and firmware engineers understand why code runs at a given speed. Interviewers use it to test whether you can move from a block diagram to timing and to spot where an instruction sequence will lose cycles. It also underlies later questions on branch prediction, throughput and microarchitecture ([[q0908]], [[q0910]], [[q0912]]).
:::

::: answer
"The classic five-stage pipeline splits instruction execution into five steps, each handled by its own hardware so five instructions can be in flight at once.

First, instruction fetch, IF: read the instruction from instruction memory at the PC and compute PC plus four. Second, instruction decode, ID: decode the opcode, read the source registers from the register file, and sign-extend the immediate. Third, execute, EX: the ALU computes the arithmetic result, a load or store address, or a branch condition. Fourth, memory, MEM: loads read the data memory and stores write it. Fifth, writeback, WB: the result goes back into the register file.

Between stages there are pipeline registers that hold each instruction's partial state and control signals, clocked every cycle. Once the pipeline is full, one instruction finishes every cycle, so throughput is up to five times higher than a non-pipelined design with the same logic, though one instruction's latency is still five cycles.

The catch is hazards. A structural hazard is two instructions needing the same resource; a data hazard is an instruction needing a result that isn't written back yet, fixed mostly by forwarding results from later stages, plus a one-cycle stall for a load followed by a dependent instruction; and a control hazard is a branch, where the instructions fetched after it may be wrong, fixed with branch prediction and flushing."
:::

::: technical
**Stages and datapath contents.**
| Stage | Work | Hardware |
|---|---|---|
| IF | $IR\leftarrow M_I[PC]$, $PC\leftarrow PC+4$ | PC, instruction memory/I-cache |
| ID | decode, read $rs1$, $rs2$, immediate, hazard check | decoder, register file (2 read ports) |
| EX | ALU op / address / branch compare | ALU, forwarding muxes, branch adder |
| MEM | load/store | data memory/D-cache |
| WB | $R[rd]\leftarrow$ result | register file write port |

**Pipeline registers**: IF/ID, ID/EX, EX/MEM, MEM/WB carry the instruction's data, destination register number, and control bits.

**Timing.** Clock period $T\ge \max_i t_{stage,i}+t_{clk\to Q}+t_{su}$ (plus skew). Ideal throughput 1 instruction/cycle; $N$ instructions take $N+4$ cycles. Speedup over an unpipelined design of the same logic: $5N/(N+4)$, i.e. 2.78 for $N=5$, 4.81 for $N=100$, 4.98 for $N=1000$, approaching but never reaching 5.

**Hazards and fixes.**
- Structural: separate instruction and data memories (or caches); register file written in first half-cycle and read in second half.
- Data (RAW): forwarding from EX/MEM and MEM/WB into ALU inputs removes stalls for back-to-back ALU ops. A load followed immediately by a use of its result still stalls 1 cycle (load-use hazard). Without forwarding the same ALU dependency stalls 2 cycles.
- Control: branch resolved in EX (or ID with extra hardware): taken branches flush the 1 to 2 younger instructions. Static prediction (not-taken), delayed branches, or dynamic predictors reduce the penalty ([[q0910]]).

**CPI model.** $\text{CPI}=1+\sum(\text{stall frequency}\times\text{stall cycles})$. Example: 25% loads, 40% of which are immediately followed by a dependent use (1-cycle stall), plus 15% branches mispredicted 20% of the time with a 2-cycle penalty: $\text{CPI}=1+0.25\times0.4\times1+0.15\times0.2\times2=1.16$.
:::

::: short

Hazards break the ideal: data hazards are fixed with forwarding plus a one-cycle stall for load-use, and control hazards with branch prediction and flushing."
:::

::: long
"The classic RISC pipeline has five stages, and each stage does one piece of the fetch-execute cycle with its own dedicated hardware.

Stage one is instruction fetch: the PC addresses the instruction memory and the PC is incremented. Stage two is decode: the control unit decodes the opcode, the register file reads the source registers, and the immediate is sign-extended. Stage three is execute: the ALU does the arithmetic, or computes an address for a load or store, or compares for a branch. Stage four is memory: loads read data memory and stores write to it. Stage five is writeback: the result is written to the destination register.

Between each pair of stages is a pipeline register that stores the instruction's data and control signals. Each cycle, every instruction moves one stage forward, so five different instructions are being worked on at once. When it's full, one instruction finishes each cycle. That's the key point: pipelining improves throughput, not latency. Each instruction still takes five cycles, and with the register overhead it may take slightly longer than non-pipelined. With a clock set by the slowest stage, you get nearly a 5 times speed-up for long instruction streams.

The ideal breaks down with hazards. Structural hazards, like fetch and data access fighting over one memory, are solved by having separate instruction and data memories. Data hazards occur when an instruction needs a result that an earlier instruction hasn't written back. Forwarding paths take the result straight from the EX/MEM or MEM/WB registers back to the ALU inputs, so back-to-back ALU instructions don't stall. A load followed immediately by an instruction using the loaded value still has to stall one cycle, because the data only exists after the memory stage. Control hazards come from branches: by the time the branch resolves, the pipeline has fetched following instructions, which have to be flushed if the branch is taken. Branch prediction reduces that cost. The overall CPI is then 1 plus the average stall cycles per instruction."
:::

::: terms
- **Pipeline stage**: one step of instruction processing with its own hardware.
- **Pipeline register**: flip-flop bank between stages holding in-flight state.
- **Throughput vs latency**: completion rate vs time to complete one instruction.
- **Hazard**: situation that prevents the next instruction from executing in its clock cycle.
- **RAW (read-after-write) hazard**: instruction reads a register before a prior instruction writes it.
- **Forwarding (bypassing)**: routing a result directly from a later stage to an earlier stage's input.
- **Stall / bubble**: a cycle in which a stage does no useful work.
- **Load-use hazard**: instruction depending on a load's result immediately after the load.
- **Flush**: discarding wrongly fetched instructions after a branch redirect.
- **CPI**: cycles per instruction.
:::

::: exceptional
**An average answer** lists the five stage names.

**An exceptional answer**:
- Says what hardware each stage uses and what each pipeline register carries.

- Classifies hazards, gives the fix for each, and quantifies stalls (load-use 1 cycle; 2 without forwarding).
- Computes CPI for an example instruction mix.

:::

::: mistakes
- **"Pipelining makes each instruction faster."** It increases throughput. Each instruction still passes through all stages, so latency is the same or slightly longer.
- **Claiming a perfect 5x speedup.** Unbalanced stages, register overhead and hazards reduce it; for $N=100$ the ideal is 4.81x and real code with stalls is less.
- **Thinking forwarding eliminates all data hazards.** A load followed by a dependent instruction still stalls one cycle.
- **Forgetting the register file's two read ports and one write port**, and the same-cycle write/read case (write first half, read second half).
- **Mixing up MEM and WB.** MEM accesses data memory; WB writes the register file. Stores have no WB; branches have neither.
- **Believing deeper is always better.** Deeper pipelines raise clock frequency but increase hazard penalties and power.
:::

## Why five stages, and what each pipeline register carries

An unpipelined (single-cycle) processor has one long combinational path from fetch to writeback. Cut it into five roughly equal-delay pieces and put a register between each; now the clock only needs to cover one piece, and every piece works on a different instruction.

Instruction $i$ occupies stage $s$ in cycle $i+s$ (counting from 0):

| Cycle | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| I1 | IF | ID | EX | MEM | WB | | |
| I2 | | IF | ID | EX | MEM | WB | |
| I3 | | | IF | ID | EX | MEM | WB |

Three instructions need $5+(3-1)=7$ cycles. In general $N$ instructions need $N+4$ cycles, so speedup over $5N$ unpipelined cycles is $\frac{5N}{N+4}$.

Each pipeline register carries the instruction's state forward. IF/ID holds the instruction and PC+4. ID/EX holds both register operands, the immediate, the destination register number, and control bits for EX, MEM and WB. EX/MEM holds the ALU result, the store data, the destination register number and remaining controls. MEM/WB holds the ALU result or loaded data and the destination register. The destination register number and `RegWrite` have to travel with the instruction until WB, otherwise the result would be written to the wrong register after later instructions have passed through ID.

## Clock period and imbalance

The clock must satisfy $T\ge \max(t_{IF},t_{ID},t_{EX},t_{MEM},t_{WB})+t_{clk\to Q}+t_{su}$. With illustrative stage delays IF 250, ID 150, EX 200, MEM 250, WB 100 ps and 50 ps of register overhead, $T=300$ ps (3.33 GHz). The unpipelined path is about 900 ps, so the real speedup is $900/300=3\times$ rather than $5\times$. Balancing stages and splitting slow ones (e.g. a two-cycle cache access) is how real designs improve this.

## Data hazards and forwarding

Consider:

```
add x1, x2, x3
sub x4, x1, x5     ; needs x1
and x6, x1, x7     ; needs x1
```
`add` produces $x1$ at the end of EX (cycle 3), writes it in WB (cycle 5). Without forwarding, `sub` would read the stale $x1$ in its ID stage (cycle 3), so it must stall until `add` has written the register: with a register file that writes in the first half and reads in the second half of a cycle, `sub` can read in cycle 5, i.e. 2 stall cycles.

With forwarding, a multiplexer in front of each ALU input chooses between the register-file value and results from EX/MEM (one instruction ahead) or MEM/WB (two ahead). The hazard-detection logic compares destination register numbers in later stages with source registers in EX. `sub` then gets $x1$ at the start of its EX stage straight from the EX/MEM register: zero stalls.

**Load-use.** For

```
lw  x1, 0(x2)
add x4, x1, x5
```
the loaded data exists only at the end of MEM (cycle 4) but `add` needs it at the start of EX (cycle 4 if not stalled): one cycle too early. Even with forwarding from MEM/WB, a one-cycle bubble is required. Compilers schedule an independent instruction into that slot to hide it.

## Control hazards

A branch is resolved in EX. By then, two younger instructions have been fetched. If taken, they are flushed: a 2-cycle penalty (1 if resolved in ID with comparator hardware). Options:

1. Stall on every branch: CPI penalty $b\times P$ where $b$ is the branch frequency.
2. Predict not-taken and flush when wrong.
3. Dynamic prediction with a branch history table and BTB ([[q0910]]).

With branch frequency 15%, a 2-cycle penalty and a 20% misprediction rate, the CPI contribution is $0.15\times0.2\times2=0.06$; with always-stall it would be $0.15\times2=0.30$, five times worse.

## Putting numbers together: CPI

Instruction mix: 25% loads (40% followed by a dependent instruction), 15% branches (20% mispredicted, penalty 2). $\text{CPI}=1+0.25\times0.4\times1+0.15\times0.2\times2=1.16$ (computed in code). At 300 ps the execution time per instruction is $1.16\times300=348$ ps versus 900 ps unpipelined: about $2.6\times$ faster overall.

## Structural hazards

If instruction and data share one memory port, a load or store in MEM conflicts with a fetch in IF in the same cycle. Fixes: a Harvard-style split (separate I and D caches), or a stall. This is the pipeline reason for split L1 caches ([[q0898]]). The register file has a similar potential conflict between WB writing and ID reading the same register in the same cycle, solved by writing in the first half of the cycle and reading in the second (or by internal bypassing).

## Real pipelines

- **Arm Cortex-M0/M3/M4**: 3-stage pipelines (fetch, decode, execute; the Cortex-M0+ cuts it to 2), no branch predictor in the smallest cores, tiny and low-power.
- **Classic 5-stage RISC cores** (MIPS R3000, early ARM9-class, many teaching and embedded RISC-V cores): the structure above.
- **High-performance cores**: 10 to 20+ stage pipelines, superscalar and out-of-order, with large predictors; the misprediction penalty is on the order of 10 to 20 cycles, which is why predictor accuracy dominates.
- **Pipelining beyond the CPU**: GPUs, DSP datapaths, floating-point units and memory controllers all use the same idea.

> [!UNCERTAIN]
> Exact stage counts and branch penalties of commercial cores vary by design and are often not published precisely. The ranges above are typical, not specific.

> Draw the table of instructions against cycles (the staircase). Then point at the load-use case and say "this is the one forwarding can't fix". It shows you've reasoned about it rather than memorized the stage names.
:::

::: applications
- **Embedded RISC cores** (Cortex-M, RISC-V MCUs): short pipelines for low power and deterministic timing.
- **Application CPUs**: deep pipelines with prediction and forwarding for GHz clocks.
- **DSP and FPU datapaths**: pipelined multipliers/adders with throughput of one result per cycle.
- **GPU shader cores**: deeply pipelined arithmetic units fed by many threads.
- **Digital signal chains in FPGAs**: pipelining combinational paths to meet timing.
:::

::: assumptions
- **Classic in-order 5-stage RISC pipeline** (MIPS/RISC-V teaching model), branches resolved in EX, with forwarding unless stated.
- **One-cycle memory access** (cache hits); misses stall the whole pipeline.
- **Stage delays are illustrative** and unbalanced to show the effect; real designs balance them.
- **Register file writes in the first half and reads in the second half** of the clock.
- **Single-issue**: one instruction enters per cycle. Superscalar designs issue several.
- **Penalties** (2-cycle branch, 1-cycle load-use) apply to this model only.

::: followups
### What is the difference between latency and throughput in a pipeline?
Latency is the time for one instruction to go through (5 cycles here, perhaps slightly more with register overhead); throughput is how many complete per unit time (up to one per cycle once full). Pipelining raises throughput without reducing latency.

### How does forwarding work and why can't it fix load-use hazards?
Forwarding muxes route a result from EX/MEM or MEM/WB directly to an ALU input so a dependent instruction doesn't wait for writeback. A load's data only becomes available at the end of the MEM stage, which is too late for the immediately following instruction's EX stage, so one stall cycle is unavoidable. Compiler scheduling can fill it.

### How many cycles does it take to run 10 independent instructions on a 5-stage pipeline?
$10+4=14$ cycles ($5+(10-1)$). CPI over the run is $14/10=1.4$, approaching 1 for long streams.

### What happens on a taken branch resolved in EX?
The two instructions fetched after the branch are wrong-path and flushed (converted to bubbles), the PC is loaded with the target and fetch restarts: a 2-cycle penalty. With a predictor that guessed correctly there's no penalty.

### Would you add more stages to run at higher clock rates?
Deeper pipelines cut per-stage logic and raise frequency, but there are diminishing returns: register overhead takes a larger fraction of the cycle, hazards and misprediction penalties grow (a 20-stage pipeline loses about 15 to 20 cycles per mispredict), and power rises with frequency. Modern designs balance depth against predictor quality and power, which is why clock rates have flattened near a few GHz.
:::
