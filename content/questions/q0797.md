::: basics
### In plain words
When an interrupt fires, hardware and software share the work. On an Arm Cortex-M chip, the hardware automatically saves eight registers, which are tiny storage cells inside the processor, onto the stack. It then fetches the handler's address and jumps there. Because of this, the handler can be an ordinary C function. The handler's job is short: read the data, clear the flag, and update shared variables. Returning triggers the hardware to restore everything and resume.

### Picture it
Picture hot-desking. Before a colleague borrows your desk, a porter automatically boxes up everything the colleague is allowed to move, and notes where you were working. If he touches any protected items, he must put them back himself. When he finishes, the porter unpacks the box, and you carry on as if nothing happened. The porter is the hardware. The colleague's duty to restore protected items is the compiler's job.

### Words you need
- **Register**: a tiny, fast storage cell inside the processor that holds values being worked on.
- **Stack frame**: the saved state the hardware pushes onto the stack, a memory area used as scratch space. On Cortex-M that is 8 words, 32 bytes.
- **Magic return value**: a special value, EXC_RETURN, that tells the hardware "this is an interrupt return, so restore the saved state".

### The simplest example
At 72 MHz, entry takes about 12 cycles, so $12/72\text{ MHz} \approx 167$ ns. The handler reads a received serial byte, which also clears the flag. The return takes about 12 more cycles. That is 24 cycles, or about 0.33 µs of overhead per interrupt. At 50,000 interrupts per second, the overhead alone is $24/72\text{ MHz} \times 50{,}000 \approx 1.7\%$ of the processor. On a small 8-bit AVR chip, the hardware pushes only the return address, and the compiler adds the rest, so the same job costs about 34 cycles. That is the whole idea. The rest of this page covers the cost on other chips, buffer sizing and shared-data bugs.
:::

::: testing
Whether you can narrate a single ISR **cycle by cycle across the hardware/software boundary**: what the silicon does for free (stacking, vector fetch, mode change, priority update) and what the compiler and your code must do (callee-saved registers, volatile data, clearing flags, return). Contrast between a Cortex-M (hardware does the work, plain C handler) and an 8-bit core like AVR (compiler-generated prologue) separates people who have read a reference manual from those who have only used an SDK.
:::

::: why
Understanding the exact split explains the numbers you quote in design reviews: latency, stack depth, why floating point in an ISR is costly, why tail-chaining makes back-to-back interrupts cheap, and why `volatile` and atomicity matter. It is also the basis for debugging HardFaults, since the stacked frame is the post-mortem record of where the CPU was.
:::

::: concepts
- **Instruction boundary and precise interrupts**: state is consistent when the interrupt is taken ([[q0796]]).
- **Hardware stacking**: automatic push of the caller-saved context.
- **Vector fetch and mode change**: PC loaded from the vector table, core enters handler mode with the interrupt's priority.
- **Calling convention (AAPCS)**: the reason a C function can be an ISR on Cortex-M.
- **EXC_RETURN**: special LR value that triggers hardware unstacking.
- **Shared data**: `volatile`, atomicity, critical sections ([[q0802]]).
- **Tail-chaining and late arrival**: hardware optimisations to cut latency between ISRs.
:::

::: answer
"I'll describe a Cortex-M since that's most common.

At the hardware level, a peripheral sets a flag and the NVIC decides this interrupt is the one to take. The core finishes the current instruction and then automatically pushes eight registers onto the stack: R0 to R3, R12, the link register, the return address and the status register. At the same time it fetches the handler address from the vector table, switches to handler mode, records the interrupt as active, and loads the link register with a special value called EXC_RETURN. All of that is roughly 12 cycles with no software.

Because the hardware already saved the registers a C function is allowed to trash, the ISR can be a perfectly ordinary C function. The compiler will push the callee-saved registers if it needs them. My code reads the data, clears the interrupt flag, and updates any shared variables, which have to be volatile and accessed atomically. When the function returns, loading that special EXC_RETURN value into the PC tells the hardware to pop the saved frame and resume the main code.

On an AVR it's more manual. The hardware only pushes the program counter and clears the global interrupt flag. The compiler's ISR macro generates the prologue that saves the status register and every register the handler uses, then ends with a RETI. So the same event costs more cycles, and nesting is off unless you explicitly re-enable interrupts."
:::

::: technical
**Cortex-M hardware sequence (Armv7-M).**
1. *Pend.* Peripheral flag to NVIC pending bit.
2. *Accept.* At an instruction boundary, if the pending priority is higher than the current execution priority (taking PRIMASK/BASEPRI into account), the core starts exception entry. Multi-cycle LDM/STM can be abandoned and restarted.
3. *Stack.* Push R0-R3, R12, LR, ReturnAddress, xPSR on the current stack (MSP or PSP). If the FPU context is active, additionally S0-S15 and FPSCR (lazy stacking can defer the actual writes).
4. *Vector.* Read the handler address from $VTOR+4(16+n)$ in parallel with stacking.
5. *State.* Set IPSR to the exception number, set the active bit, LR$\leftarrow$EXC_RETURN (e.g. 0xFFFFFFF9 return to thread mode on MSP, 0xFFFFFFFD thread/PSP, 0xFFFFFFF1 for handler mode), switch to handler mode (privileged), and start fetching the ISR. Total 12 cycles for zero-wait-state memory.
6. *Exit.* `BX LR` (or `POP {..., PC}`) with an EXC_RETURN value triggers unstacking of the 8-word frame, restoration of mode and stack, and resumption. About 12 cycles.
7. *Optimisations.* **Tail-chaining**: if another interrupt is pending at exit, skip unstack/stack and enter directly (about 6 cycles). **Late arrival**: if a higher-priority interrupt arrives during stacking of a lower one, the higher takes the already-stacked frame. **Pop preemption**: an interrupt arriving during unstacking can abort it and restart entry.

**AVR hardware sequence (typical).** Finish current instruction, push PC (2 or 3 bytes), clear the I flag in SREG, jump to the vector (minimum 4 cycles then a 3-cycle `JMP` in the vector table). Compiler-generated ISR prologue saves SREG, `r0`, the zero register `r1` handling and any registers used; epilogue restores and executes `RETI`, which re-enables interrupts (4 cycles). Interrupt flags are generally cleared by hardware when the vector is taken.

**Software obligations.**
- Clear the source flag (and ensure the clear has taken effect).
- Access shared variables as `volatile` and atomically; multi-byte access can tear.
- Don't call blocking or non-reentrant functions.
- Keep the stack budget: 32 bytes frame + locals per active level.

**Register ownership (AAPCS).** Caller-saved R0-R3, R12 (hardware-stacked), callee-saved R4-R11 (compiler-saved if used). The ISR must preserve R4-R11 and the 8-byte stack alignment (hardware realigns and records it in xPSR).

> [!UNCERTAIN]
> Cycle counts (12, 6) apply to Cortex-M3/M4 with zero wait states; Cortex-M0/M0+ and M7 numbers differ (M0 takes about 16 cycles), and flash wait states or caches add jitter.
:::

::: short
"In hardware, the NVIC picks the interrupt, the core finishes its instruction, pushes eight registers onto the stack, reads the handler address from the vector table and switches to handler mode, about 12 cycles on a Cortex-M. Because the caller-saved registers are already saved, the ISR is a plain C function: it reads the data, clears the flag and touches volatile shared variables. Returning with the special EXC_RETURN value makes the hardware pop the frame and resume. On AVR the software prologue does more of this."
:::

::: long
"Let me walk through one interrupt on a Cortex-M, splitting hardware from software.

Hardware first. An event sets a flag in the peripheral, and the NVIC latches it as pending. The NVIC compares its priority with what's currently executing. If it wins and isn't masked, the core takes it at the next instruction boundary. Entry is done entirely by the hardware: it pushes eight words onto the stack, which are xPSR, the return address, LR, R12 and R3 to R0, while in parallel it reads the ISR address from the vector table. It sets the interrupt number in the status register, marks the interrupt active, enters handler mode, and loads LR with a magic value, EXC_RETURN, that records which stack and mode to return to. That whole thing takes about 12 cycles, so 167 nanoseconds at 72 MHz.

Software next. Since the hardware saved exactly the registers that a C function is allowed to overwrite, the ISR is a normal C function. The compiler adds a push of R4 to R11 only if the code needs them. In the handler I read the status, grab the data, clear the flag, and update shared state. Anything shared with main code is volatile, and multi-byte updates need to be atomic. I keep it short, because while it runs, any equal or lower priority interrupt waits.

The return is the clever part. The handler returns by writing that EXC_RETURN value to the PC, and the hardware sees the magic number, pops the eight words and resumes the main code on the right stack and mode. If another interrupt is pending, it skips the unstack and goes straight in, tail-chaining, in about 6 cycles.

On an 8-bit AVR it's more manual: hardware pushes only the PC and clears the global interrupt bit, and the compiler generates the register saves and the RETI. That makes overhead larger, and nested interrupts require explicitly re-enabling interrupts."
:::

::: terms
- **Stacking / exception frame**: the 8 registers pushed on entry (R0-R3, R12, LR, PC, xPSR).
- **Handler mode**: privileged mode in which ISRs run on Cortex-M.
- **EXC_RETURN**: magic LR value (0xFFFFFFxx) that makes a return an exception return.
- **Tail-chaining**: moving directly from one ISR to the next without full unstack/stack.
- **Late arrival**: a higher-priority interrupt taking over while an earlier one is being stacked.
- **AAPCS**: Arm procedure call standard (which registers a function must preserve).
- **RETI**: AVR return from interrupt, re-enabling interrupts.
- **Lazy stacking**: deferring FPU register stacking until the ISR actually uses the FPU.
:::

::: exceptional
An average answer says "registers are saved, ISR runs, registers restored." An exceptional answer:

- Lists the **eight stacked registers** and explains why those and not R4-R11 (AAPCS), hence C-function ISRs.
- Describes **EXC_RETURN** as the mechanism for exit.
- Quotes **12 cycles** entry, **6 cycles** tail-chain and says where jitter comes from.
- Contrasts **AVR** (compiler saves, I flag cleared) to show the design difference.
- Mentions **FPU lazy stacking** and the stack-depth cost of nesting.
- Ties the software duties (flag clear, volatile, atomicity, short) to the hardware behaviour.
:::

::: mistakes
- **Putting `__attribute__((interrupt))` or an assembly wrapper on every Cortex-M3/M4 ISR.** Not needed: hardware stacking follows AAPCS, so a plain C function works. Special attributes or wrappers matter on other cores (8-bit parts, many RISC-V cores) that do not auto-stack.
- **Thinking registers R4-R11 are saved by hardware.** The compiler saves those.
- **Using floating point in an ISR without considering stacking cost.** It enlarges the frame (18 extra words) and can lengthen latency.
- **Forgetting that the ISR runs on the main stack** (MSP), so stack usage counts toward the main stack budget.
- **Not clearing the flag or clearing it too early**, leading to re-entry or lost events ([[q0801]]).
:::

::: deep
## What the silicon does for free

Look at it as three hardware tricks:

1. **Automatic state save** in parallel with the vector fetch, so entry takes 12 cycles instead of the 30-50 a software push of 8+ registers plus a table lookup would take.
2. **A magic return value** instead of a special `RETI` instruction, so the ISR is a normal function.
3. **Priority bookkeeping**: the core tracks the "current execution priority" so the NVIC knows what may preempt.

The cost of the fixed overhead on a 72 MHz Cortex-M3: entry $12/72\text{ MHz}=167$ ns, exit 167 ns, so 333 ns per event. At 100 kHz event rate that is 3.3% of the CPU in overhead alone, before any ISR code.

## Tail-chaining and its payoff

If two interrupts are pending, a naive implementation would unstack after the first and restack for the second: $12+12=24$ cycles. With tail-chaining the core skips both, using about 6 cycles. For back-to-back interrupts that saves 18 cycles (250 ns at 72 MHz) and avoids needless memory traffic.

## Software view: what the compiler generates

A C ISR on Cortex-M:

```c
volatile uint8_t rx_buf[64]; volatile uint8_t head;
void USART1_IRQHandler(void) {
    if (USART1->SR & USART_SR_RXNE) {
        rx_buf[head++ & 63] = USART1->DR;   // reading DR also clears RXNE
    }
}
```
At -O2 the generated code is just a handful of loads/stores, often with no prologue at all (no callee-saved registers used). The frame is entirely the hardware's. On AVR the same logic compiles to a prologue like `push r1; push r0; in r0, SREG; push r0; clr r1; push r24; ...` and an epilogue with matching pops and `reti`, so overhead scales with the registers used.

## FPU and stack cost

On a Cortex-M4F, if the FPU has been used before the interrupt, the frame grows by S0-S15 and FPSCR: 18 extra words (72 bytes), so 104 bytes in total, and entry becomes about 29 cycles (lazy stacking can reserve the space but delay the actual writes). So avoid float in high-rate ISRs, or keep ISRs integer-only and do floating point in thread context.

## Shared data and the software contract

The ISR runs between any two instructions of main code. Three consequences:

- **Visibility**: the compiler may keep a shared variable in a register in main; mark it `volatile` so each access goes to memory ([[q0802]]).
- **Atomicity**: a 32-bit store is atomic on Cortex-M (a single instruction), a read-modify-write like `count++` is not; if main code and the ISR both modify it, use a critical section or atomic operations.
- **Ordering**: if the ISR sets a `ready` flag after writing data, add a barrier so the flag isn't observed first on cores with write buffers.

## Debugging with the stacked frame

When a fault occurs, the core uses the same stacking mechanism. Reading the stacked PC from the stack in a HardFault handler tells you the instruction that faulted. This is the standard post-mortem technique, and it only works because the frame layout is architecturally fixed.

## Worked example: entry and exit cost on two cores

Count the fixed overhead on an AVR at 16 MHz against a Cortex-M3 at 72 MHz for the same trivial ISR that increments a counter. The AVR numbers are a typical avr-gcc ISR that uses two working registers, on a part like the ATmega328P (2-byte PC, `JMP` in the vector table); the exact count depends on the compiler and registers used. An AVR at 16 MHz runs from flash with no wait states, so its instruction timings are exact, but the 4-cycle response is a minimum: add the rest of any multi-cycle instruction in progress, and 4 more cycles if the core was asleep. The Cortex-M3 numbers are the architectural zero-wait-state figures (12 cycles in, about 12 out); a real 72 MHz flash part needs flash wait states (typically 2 at 72 MHz on common parts), so the vector fetch and the first handler instructions cost somewhat more unless the vector table and handler sit in zero-wait RAM or a prefetch/accelerator hides it:

| Phase | AVR cycles | Cortex-M3 cycles |
|---|---|---|
| Hardware entry (push PC / stack 8 words, fetch vector) | 4 (minimum) | 12 (zero wait states) |
| Vector-table jump | 3 | (included) |
| Prologue: push `r1`, `r0`, `SREG`, clear `r1`, push two working registers | 12 | 0 |
| Exit: pop the same registers, restore `SREG` | 11 | (hardware unstack) ≈12 |
| `RETI` | 4 | (included) |
| **Total overhead** | **34** | **24** |

At 16 MHz, 34 cycles is 2.1 µs; at 72 MHz, 24 cycles is 0.33 µs. The Cortex-M part is both 1.4 times better in cycles and 4.5 times faster in clock, which is a factor of about 6 in time (less once flash wait states are counted, but still several times). The same counting explains why a 100 kHz event rate is 3.3% load of overhead on the Cortex-M3 and 21% on the AVR (before any ISR body). It also shows where the architecture's design choices land: the AVR pays in software for each register the handler uses, while the Cortex-M frame is fixed and written by hardware in parallel with the vector fetch.

## Worked example: sizing the buffer behind the ISR

The receive ISR above writes into a 64-byte ring buffer. Suppose the main loop drains the buffer only once every 10 ms, because it does other work. At 115,200 baud the arrival rate is 11,520 bytes/s, so between drains $11{,}520\times0.01 = 115$ bytes arrive. A 64-byte buffer overflows, silently, because the handler as written has no overflow check. The buffer must hold at least the worst-case drain interval times the byte rate, so 115 bytes means 128 with a power-of-two size (keeping the cheap `& 127` mask). The general rule is $N \ge r\cdot T_{drain}$, with margin for the worst-case gap, not the average. If the main loop occasionally stalls for 50 ms (a flash write, say), $N \ge 11{,}520\times0.05 = 576$ and the answer becomes 1 KB. The choice is between more RAM and a faster consumer, and the DMA alternative ([[q0800]]) reduces the problem to a buffer size and a half-transfer interrupt.

The code also needs a consumer index and a way to detect overflow. A single-producer, single-consumer ring buffer is safe without disabling interrupts if only the ISR writes `head`, only the main code writes `tail`, and the index updates are single-instruction accesses. On an 8-bit core a 16-bit index is not atomic, so use an 8-bit index with a buffer size of 256 or smaller, or guard the access.

## Worked example: a torn read

The software contract above says a read-modify-write or a multi-byte access can be interrupted. Make it concrete on an 8-bit AVR with a 16-bit counter `count` that the ISR increments. The main code reads it with two byte loads, low byte then high byte. If the counter is $0x00FF$ when the low byte is read (value 0xFF) and the interrupt then increments it to $0x0100$ before the high byte is read (value 0x01), the main code assembles $0x01FF = 511$, which was never the counter's value. The correct values were 255 and 256, so the error is 256 counts. This is a genuine intermittent bug, happening only when the interrupt lands in a window a few cycles wide, which is why it survives testing and fails in the field. The fixes are to read inside a short critical section (disable interrupts, copy, restore the previous state), to read twice until the two values agree, or to use hardware that latches the high byte on a low-byte read (AVR 16-bit timer registers such as `TCNT1` do exactly that through a shared temporary register, but only for the hardware register, not for your own variables). On Cortex-M a 32-bit aligned load is a single instruction and is atomic, which hides the problem until the variable becomes 64 bits.

## What the clean picture leaves out

**The stacked frame is also a security and debugging surface.** The return address in the frame can be overwritten by a stack overflow in a handler, and a corrupted frame returns to a wrong place. That is also why the HardFault post-mortem technique works: the same frame holds the faulting PC. On parts with a memory protection unit, you can place a guard region under the stack so overflow faults immediately instead of corrupting data.

**Late arrival and tail-chaining make timing non-obvious.** A higher-priority interrupt that arrives while a lower one is still being stacked takes over that stacking and the vector fetch switches to its handler, so its own latency from arrival is under 12 cycles; back-to-back pending ones skip the 12 + 12 unstack and restack and cost 30 cycles total for entry, tail-chain and exit instead of 48. Timing analysis that multiplies a fixed 24 by the number of interrupts overestimates the cost in a busy system and underestimates the variance.

**ISR code runs in handler mode with its own rules.** It cannot use blocking calls, it shares the stack with the nest, and if the RTOS owns the stack for threads then handlers use the main stack while tasks use the process stack. Mixing those up is a common source of subtle crashes.

> [!UNCERTAIN]
> The AVR cycle counts depend on the compiler's prologue and which registers the handler touches. The Cortex-M figures are for M3/M4 with zero wait states (exit is quoted as 10–12 cycles depending on the source; this page uses 12). Flash wait states, bus contention and a stacked FPU frame all add to them. Treat the comparison as a model for counting, and read the compiler's generated assembly and the core manual for exact numbers.

## Verifying on the bench

1. **Count the cycles.** Use the core's cycle counter (DWT on Cortex-M) or a timer to measure entry-to-first-instruction and last-instruction-to-return. Compare against the table above, and note anything extra from wait states or a stacked FPU frame.
2. **Look at the generated code.** Disassemble the handler and check its prologue. A handler that touches more registers than you expected, or calls a library function, costs far more than the counter increment suggests.
3. **Try to break the buffer.** Send data at the maximum rate while the main loop is deliberately stalled for a long operation, and check the overrun status and buffer-full counters. The test finds the stall time at which the buffer fails, which should be well above the longest real stall.
4. **Provoke the torn read.** Write a test that increments a multi-byte counter in an ISR at a high rate while the main code reads it in a tight loop, then check whether any reading ever goes backward or jumps by an unexpected amount. A race that appears in minutes under stress would have appeared in the field in weeks.

::: applications
- **Low-latency control loops**: ADC end-of-conversion ISR at 20 kHz for a motor current loop (10-20 µs budget).
- **UART/USB drivers**: byte-level ISRs feeding ring buffers.
- **RTOS context switch**: PendSV is the lowest-priority exception that performs the switch after the other ISRs finish.
- **Fault diagnostics**: HardFault handlers decode the stacked frame to report the failing address.
- **Real-time scheduling analysis**: using entry/exit cycle counts in worst-case response time calculations.

::: assumptions
- The main example is Armv7-M (Cortex-M3/M4). Armv6-M (M0/M0+) uses a similar 8-word frame but different timing; Armv8-M adds security states with extra stacking. RISC-V cores (CLIC) generally do **not** auto-stack, so ISRs need a software prologue.
- Cycle numbers assume zero wait states for the vector fetch and stack; real systems with flash accelerators or caches have non-deterministic variation.
- A bare-metal view: with an RTOS, interrupt entry may be wrapped by kernel code, and some RTOS APIs may only be called from ISRs at certain priorities.
- Mode names (handler/thread) and EXC_RETURN values are Arm specific.
:::

::: followups
### Why can a Cortex-M ISR be a normal C function but an AVR ISR needs a special macro?
Cortex-M hardware stacks the AAPCS caller-saved registers and uses EXC_RETURN so a plain `BX LR` returns correctly. AVR hardware only pushes the PC, and the interrupt must end with `RETI` rather than `RET`, so the compiler needs the `ISR()` attribute to emit register saves/restores and the correct return.

### What is tail-chaining and why does it matter?
When an ISR finishes and another is already pending, the core skips the unstack/stack pair and branches straight to the next handler in about 6 cycles instead of about 24. It reduces latency and bus traffic under load, and it is automatic.

### How much stack does an ISR use?
At least 32 bytes for the hardware frame (104 bytes with an active FPU context) plus the compiler's saved registers and local variables. With nesting, add one frame per level. Estimate worst-case depth from the priority levels that can preempt each other ([[q0803]]).

### How can you measure the real interrupt latency?
Toggle a GPIO at the event source (or use a timer capture) and toggle another GPIO as the first instruction in the ISR; measure the delay on a scope. Do it with realistic background load to see the worst case rather than the 12-cycle ideal. A DWT cycle counter can also timestamp entry on Cortex-M parts that have it.

### Why might a handler appear to run twice for one event?
Because the flag clear didn't reach the peripheral before exception return (write buffering), or because a second event arrived between the status read and the flag clear and the clear wiped it. Read back to flush, and clear only the flag bits you handled.
