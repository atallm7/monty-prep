::: testing
Whether you can talk about performance as a **measured, multi-dimensional quantity** and not just "GHz". The interviewer is checking that you can:

1. State the Iron Law, $T=IC\times CPI\times T_{clk}$, and say which layer controls each term.
2. Distinguish latency (time for one task) from throughput (tasks per second), and know why clock speed alone is a poor metric.
3. Use benchmarks properly (representative workloads, geometric means) and know the problems with MIPS and peak FLOPS.
4. Bring in memory behavior, Amdahl's law, and power/thermals, since modern performance is limited by all three.
:::

::: why
Every architecture decision is justified with a performance number, and every performance number can be misleading if you do not know what it measures. A hardware engineer has to read a claim like "20% faster" and ask: on what workload, at what power, with what baseline, single-thread or aggregate? In design reviews this is the language used to decide whether a bigger cache or a wider core is worth its area. See [[q0924]] for the GPU version of the same question.
:::

::: concepts
- **Execution time**: the ultimate metric, $T=IC\times CPI\times T_{clk}$.
- **CPI / IPC**: average cycles per instruction and its reciprocal. See [[q0908]].
- **Latency vs throughput**: one task's response time versus aggregate rate.
- **Benchmarks**: standard programs (for example SPEC CPU, CoreMark) used for comparison.
- **Amdahl's law**: speedup limited by the unimproved fraction.
- **Memory hierarchy effects**: cache misses add stall cycles to CPI.
- **Power and frequency**: dynamic power $\propto CV^2f$ ties performance to thermals. See [[q0945]].
:::

::: answer
"The fundamental measure is execution time for a real workload. The Iron Law breaks it down: time equals instruction count times cycles per instruction times clock period. The compiler and ISA mostly set instruction count, the microarchitecture sets CPI, and the circuit design and process set the clock. So frequency on its own tells you very little. A 3 GHz chip with a CPI of 2 loses to a 2 GHz chip with a CPI of 1.

Beyond that, I'd separate latency from throughput. Latency is how long one task takes, which matters for responsiveness. Throughput is how many tasks per second, which matters for servers. You have to say which one you care about.

To compare machines I'd use benchmarks that look like the real workload, such as SPEC CPU for general compute, and summarize with a geometric mean of speedup ratios. I'd stay away from MIPS or peak FLOPS as headline numbers because they ignore what the instructions do.

Then I'd look at what limits performance: memory stalls from cache misses, branch mispredictions, and Amdahl's law for parallel code. Finally, performance per watt and thermals, since a chip that throttles after ten seconds doesn't deliver its peak."
:::

::: technical
**Iron Law.**
$$T_{CPU}=IC\times CPI\times T_{clk}=\frac{IC\times CPI}{f}$$
- $IC$: dynamic instruction count, set by algorithm, compiler and ISA.
- $CPI$: average cycles per instruction, set by microarchitecture and memory system.
- $T_{clk}=1/f$: set by circuit design, pipeline depth and process.

CPI is often decomposed: $CPI=CPI_{base}+\text{stalls per instruction}$, for example
$$CPI = CPI_{base} + f_{mem}\,m\,P_{miss} + f_{br}\,r_{mp}\,P_{mp}$$
with memory-access fraction $f_{mem}$, miss rate $m$, miss penalty $P_{miss}$ (cycles), branch fraction $f_{br}$, mispredict rate $r_{mp}$, penalty $P_{mp}$.

**Worked example.** $CPI_{base}=1$, 30% of instructions access memory, 5% miss in the cache, 100-cycle miss penalty: $CPI=1+0.3\times0.05\times100=2.5$. Halving the miss rate to 2.5% gives 1.75, a 1.43x speedup, which is more than a 40% faster clock would give if memory time doesn't scale.

**Metrics and their pitfalls.**
- **MIPS** $=f/(CPI\times10^6)$ depends on the ISA and instruction mix. A machine with simpler instructions has higher MIPS but not higher speed.
- **Peak FLOPS** is a ceiling you rarely reach. Achieved performance depends on memory bandwidth and utilization.
- **Speedup** $=T_{old}/T_{new}$; summarize over several benchmarks with the **geometric mean**, because ratios must be averaged multiplicatively.
- **Amdahl's law**: if fraction $p$ of time is improved by factor $s$, overall speedup $=1/\big((1-p)+p/s\big)$.
- **Throughput vs latency**: multicore improves throughput but not single-thread latency.
- **Tail latency** (99th percentile) matters for servers more than average.

**Efficiency metrics.** Performance per watt, energy per task (joules), energy-delay product, and performance per area/cost.

**Measurement hygiene.** Same compiler flags, warm-up and caches, multiple runs, report variance, fixed thermal state, and note frequency scaling (turbo and throttling).
:::

"For me, CPU performance is how long it takes to finish the work I actually care about. The Iron Law gives a clean breakdown: execution time equals instruction count times cycles per instruction times clock period. Instruction count is set by the algorithm, compiler and ISA. CPI is set by the microarchitecture and memory system. Clock period depends on the circuit design and process. For comparison across machines I'd use benchmarks that resemble the real workload, like SPEC CPU for general compute, and combine the per-benchmark speedups with a geometric mean. I'd avoid MIPS or peak FLOPS because they depend on instruction mix and ignore memory behavior.

To understand why a number is what it is, I'd build a CPI stack: base CPI plus stalls from cache misses, branch mispredictions and so on. For example, with 30% memory instructions, a 5% miss rate and a 100-cycle penalty, memory adds 1.5 cycles to a base CPI of 1. Amdahl's law tells me the ceiling for any improvement or parallelization.

Last, performance isn't free: I'd quote performance per watt or energy per task, and check whether the chip can sustain its frequency or thermally throttles."
:::

::: terms
- **Iron Law**: $T=IC\times CPI\times T_{clk}$.
- **CPI / IPC**: cycles per instruction and its inverse.
- **Latency / throughput**: time per task versus tasks per unit time.
- **Speedup**: ratio of old to new execution time.
- **Geometric mean**: the correct average for ratios such as speedups.
- **Amdahl's law**: speedup bounded by the unimproved fraction.
- **MIPS / FLOPS**: instruction and floating-point operation rates; easy to mislead.
- **CPI stack**: breakdown of CPI into base and stall components.
- **Tail latency**: high-percentile response time.
- **Performance per watt**: efficiency measure for power-limited systems.
:::

::: exceptional
**An average answer** lists clock speed, cores and cache size.

**An exceptional answer**:
- Starts from execution time and the Iron Law, and assigns each term to a design layer.
- Distinguishes latency from throughput and names the metric to match the use case.
- Builds a small **CPI stack** with real numbers (for example 1 + 0.3 x 0.05 x 100 = 2.5).
- Explains why geometric mean is used and why MIPS and peak FLOPS mislead.
- Applies Amdahl's law with a number and warns about the unimproved fraction.
- Closes with energy: performance per watt, sustained vs peak frequency, throttling.
:::

::: mistakes
- **Using GHz as performance.** Two chips can have the same frequency and very different CPI.
- **Averaging speedups arithmetically.** Use the geometric mean (arithmetic means of ratios depend on the baseline).
- **Quoting MIPS across different ISAs.** Instruction work differs, so MIPS is not comparable.
- **Ignoring memory.** Many workloads are memory-bound, so a faster core barely helps.
- **Reporting peak, not sustained.** Turbo and thermal limits change real performance.
- **Forgetting the baseline and workload.** "30% faster" needs a "than what, running what".
:::

::: deep
## Starting from time

All performance metrics are ultimately about time. Say machine A runs a program in $T_A$ and B in $T_B$. "A is $n$ times faster than B" means $T_B/T_A=n$. Everything else (IPC, MIPS, FLOPS) is a proxy that is valid only when other factors are held fixed.

The Iron Law is useful because each factor is controlled by a different team:

| Factor | Controlled by | Typical levers |
|---|---|---|
| Instruction count | Algorithm, compiler, ISA | better algorithm, vectorization, ISA extensions |
| CPI | Microarchitecture, memory system | wider issue, better predictor, bigger/faster caches, prefetch |
| Clock period | Circuits, process, pipeline depth | deeper pipeline, better process, careful circuit design |

They interact. A deeper pipeline lowers $T_{clk}$ but raises the branch mispredict penalty, increasing CPI. A larger cache lowers miss rate but lengthens hit latency. Performance engineering is mostly managing these couplings.

## Building a CPI stack

Take a core with base CPI 1.0 (ideal pipeline). Instruction mix: 20% branches, 30% memory accesses. Branch predictor mispredicts 8% of branches with a 15-cycle flush. L1 misses on 5% of memory accesses to L2 with a 12-cycle penalty; 1% of memory accesses also miss L2 and cost 150 cycles total to DRAM (approximately 50 ns at 3 GHz).

- Branch stalls $=0.20\times0.08\times15=0.24$
- L2 hit stalls $=0.30\times(0.05-0.01)\times12=0.144$
- DRAM stalls $=0.30\times0.01\times150=0.45$
- $CPI=1.0+0.24+0.144+0.45=1.834$

Figure: Each extra 1% of memory accesses that go to DRAM adds 0.45 to CPI. Beyond about 0.85% the DRAM term is bigger than the branch and L2 stalls combined (0.384). This is why memory behavior, not core width, is often the first thing to examine.

DRAM contributes $0.45/1.834\approx25\%$ of CPI even at 1% miss rate. Doubling the core width would only attack the base 1.0 (and by assumption can reduce it below 1), while halving the DRAM miss rate removes 0.225 cycles. Which is worth more depends on how much a wider core costs. That is the kind of trade a CPI stack makes explicit.

## Frequency is not free: connecting to power

Dynamic power is $P\approx\alpha CV^2f$, and raising $f$ typically requires raising $V$, so power grows roughly with $f^3$ in the voltage-scaling regime. Take a core at 1.0 V and 2 GHz versus 0.7 V and 1 GHz:

$$\frac{P_2}{P_1}=\frac{0.7^2\times1}{1.0^2\times2}=0.245$$

Half the performance for about a quarter of the power, and energy per instruction drops to $0.7^2=0.49$ of the original. That is why mobile chips use DVFS and many slower cores, and why you quote performance per watt. Explore it:

## Energy-delay: which operating point is better?

Take the two DVFS points above. Point B has half the speed, so a fixed job takes $2T$ instead of $T$, at 0.245 of the power. Energy $E=P\,t$ scales by $0.245\times2=0.49$. The energy-delay product $ED$ scales by $0.49\times2=0.98$, essentially a tie, while $ED^2$ scales by $0.49\times4=1.96$, so B is worse if latency is weighted heavily. So "the efficient point" depends on the metric: a battery-limited sensor wants minimum energy (run slow), a latency-sensitive phone UI wants the high point briefly (race to idle), and a datacenter often optimizes throughput per watt. There is also a floor: leakage power keeps flowing while the job stretches out, so below some voltage running slower stops saving energy.

## Reading CPI from real counters

On real hardware you do not guess the CPI stack, you measure it. Performance counters report cycles, retired instructions, branch mispredicts and cache misses per level. IPC is retired instructions over cycles. Top-down analysis methods then classify every issue slot as retiring, front-end bound, back-end bound (memory or core) or bad speculation. A low IPC with a high back-end-memory fraction points at the cache and DRAM terms above; a high bad-speculation fraction points at the predictor. The trap is that counters count events, not their cost: an out-of-order core overlaps several misses, so ten L2 misses do not cost ten times the penalty. That overlap is called memory-level parallelism, and it is why the additive stack above is an upper bound for an out-of-order core.

## Amdahl's law

If a fraction $p$ of runtime can be sped up by $s$:
$$S=\frac{1}{(1-p)+p/s}$$
With $p=0.9$ and $s=8$ (eight cores): $S=1/(0.1+0.1125)=4.7$. With infinite cores: 10. With $p=0.95$ and 16 cores: 9.14. Sequential 5 to 10 percent dominates quickly. For real parallel programs add synchronization and memory-bandwidth limits, so scaling is usually worse.

## Benchmarks and how to summarize them

Single benchmarks are easy to game, so suites such as SPEC CPU (integer and floating-point sets) are used. Each program's score is a ratio versus a reference machine, and the overall score is the **geometric mean**:
$$\text{GM}=\Big(\prod_i r_i\Big)^{1/n}$$
Why geometric? Suppose machine X is 2x faster than Y on program 1 and 0.5x on program 2. Arithmetic mean of ratios says 1.25 (X "wins"); but swapping which is baseline gives the same 1.25 for Y, an absurd result. Geometric mean gives $\sqrt{2\times0.5}=1$ either way: a tie, as it should be. Small microcontroller benchmarks (CoreMark, Dhrystone) are quick but narrow, and Dhrystone in particular is known to be gameable by compilers.

## Real hardware behavior

- **Turbo and throttling**: advertised boost frequency is available for short bursts; sustained performance is set by cooling and the power limit. A laptop and a desktop with the same chip can differ by 20% or more on long jobs.
- **SMT**: simultaneous multithreading raises throughput by filling idle issue slots, but does not make one thread faster, and shares caches.
- **Measurement noise**: OS jitter, frequency changes, and cache warm-up mean you should run repeated trials and report distributions.
- **Tail latency**: in services, p99 response time is dominated by rare events (cache misses to DRAM, page faults, interrupts), which averages hide.

> [!UNCERTAIN]
> Real-machine penalties (L2 latency, DRAM latency, mispredict flush length) vary by microarchitecture. The numbers here are representative for a 3 GHz class core, not a specific product.
:::

::: applications
- **Choosing a CPU for a product**: compare benchmark results on the workload type, performance per watt and sustained thermal limits.
- **Architecture design reviews**: CPI stacks decide whether to spend area on caches, predictors or width.
- **Compiler and software tuning**: reducing instruction count and cache misses using profilers and performance counters.
- **Server capacity planning**: throughput and tail latency under load rather than single-thread speed.
- **Embedded benchmarking**: CoreMark/MHz and energy per operation when comparing microcontrollers.
:::

::: assumptions
- The Iron Law gives *single-thread* execution time. For multithreaded programs add parallel efficiency, synchronization and shared-resource contention.
- CPI is workload-dependent; there is no single CPI for a processor.
- The worked CPI stack assumes penalties add without overlap. Out-of-order cores overlap some stalls, so real CPI contributions are smaller than the simple product suggests.
- Power-frequency scaling ($f^3$) holds only in the range where voltage must rise with frequency; near minimum voltage it becomes closer to linear in $f$.
- Interviewers may want metrics specific to a domain (latency in real-time systems, frames per second in graphics).
:::

::: followups
### Why can a 2 GHz CPU beat a 3 GHz CPU?
Time is IC x CPI / f. If the 2 GHz chip has half the CPI or needs fewer instructions (better ISA or vectorization) it wins. For example CPI 1.0 at 2 GHz gives 0.5 ns per instruction versus CPI 2.0 at 3 GHz giving 0.67 ns.

### You double the number of cores and the speedup is only 1.4x. What do you check?
Amdahl's law (serial fraction), synchronization overhead, memory bandwidth saturation, cache contention and false sharing, load imbalance, and thermal or power limits reducing frequency when more cores are active. Profile each.

### Why do we use the geometric mean for benchmark speedups?
Because speedups are ratios, and arithmetic means of ratios depend on which machine you choose as baseline. The geometric mean is baseline-independent and treats a 2x gain and a 2x loss as canceling.

### A new design lowers CPI from 1.5 to 1.2 but its clock drops from 3.0 to 2.6 GHz. Net effect?
Time per instruction: old $1.5/3.0=0.5$ ns; new $1.2/2.6=0.4615$ ns. Speedup $=1.083$, about 8% faster. Check power and area too: a lower clock often saves power.

### How would you decide whether a workload is memory-bound or compute-bound?
Use performance counters: high cache-miss rates and low IPC with the core stalled on loads indicate memory-bound; high IPC near the issue limit and low miss rates indicate compute-bound. A quick experiment is to lower the core clock: a memory-bound program slows far less than proportionally.
:::
