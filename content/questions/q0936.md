::: testing
Whether you understand **why** computers have a hierarchy at all, rather than reciting "registers, cache, RAM, disk". The interviewer is looking for:

1. The core trade-off: fast, small and expensive vs slow, large and cheap, with no single technology that wins on all three.
2. **Locality** (temporal and spatial) as the reason the hierarchy works.
3. Typical numbers for latency and capacity at each level, and what is stored there.
4. The ability to quantify: average memory access time (AMAT) and how hit rates change it.
5. Awareness of the technology behind each level (flip-flops, 6T SRAM, 1T1C DRAM, NAND flash).
:::

::: why
Memory, not compute, is the bottleneck of almost every modern system. A core can do an add in a fraction of a nanosecond but a DRAM access costs a hundred or more cycles. Understanding the hierarchy is what lets you reason about why a loop order change makes code 10x faster, why a GPU has huge register files, why an MCU has no cache but a prefetch buffer, and how to size on-chip SRAM in an SoC. It is the backbone of the whole memory section ([[q0937]] caches, [[q0938]] registers, [[q0939]] RAM, [[q0943]] MMU).
:::

::: concepts
- **Speed vs capacity vs cost**: a bigger memory has longer wires, more decode logic and slower access; faster cells are bigger and cost more per bit.
- **Temporal locality**: data used recently is likely to be used again soon.
- **Spatial locality**: data near recently used data is likely to be used soon.
- **Hit rate, miss penalty, AMAT**: $\text{AMAT} = t_{hit} + m \cdot t_{miss}$.
- **SRAM vs DRAM vs flash cells**: 6T latch, 1T1C capacitor, floating-gate/charge-trap. See [[q0939]].
- **Inclusion and coherence**: a level holds copies of the level below; copies must stay consistent.
:::

::: answer
"The memory hierarchy is a stack of storage levels where each level is bigger, slower and cheaper per bit than the one above it: registers, then L1, L2 and L3 cache, then main memory, which is DRAM, then storage like an SSD or disk. The reason is that no single memory technology is fast, big and cheap at once. The hierarchy fakes it by exploiting locality: programs reuse recent data and touch nearby data, so a small fast memory can hold the working set and satisfy most accesses.

Registers sit inside the core, hold a few dozen values, and are accessed in under a cycle. L1 cache is tens of kilobytes of SRAM at about 1 ns. L2 and L3 get bigger, up to tens of megabytes, at maybe 4 to 15 ns. DRAM is gigabytes at 50 to 100 ns. SSDs are hundreds of gigabytes at tens of microseconds, and spinning disks are milliseconds.

What's stored: registers hold the operands being computed on right now. Caches hold copies of recently used instructions and data. DRAM holds the running programs and their data. Storage holds everything persistently.

And you can quantify it: if L1 hits 95 percent at 1 ns and the rest goes through to 80 ns DRAM, average access time is 5 ns instead of 80."
:::

::: technical
**Levels, with typical (order-of-magnitude, process-dependent) figures.**

| Level | Technology | Capacity | Latency | Managed by | Holds |
|---|---|---|---|---|---|
| Registers | flip-flops / latches | 0.1 to 4 KB | <1 cycle | compiler | live operands |
| L1 cache | 6T SRAM | 16 to 64 KB per core | ~1 ns (3 to 5 cycles) | hardware | hot instructions/data |
| L2 cache | SRAM | 256 KB to 2 MB | ~3 to 5 ns (12 to 20 cycles) | hardware | working set |
| L3 / LLC | SRAM / eDRAM | 8 to 64+ MB shared | ~10 to 20 ns | hardware | shared data |
| Main memory | DRAM (1T1C) | 4 to 512+ GB | ~50 to 100 ns | OS + MMU | active program state |
| Storage | NAND flash / HDD | 100 GB to TBs | ~20 to 100 µs (SSD), ~5 to 10 ms (HDD) | OS | files, swapped pages |

**Why trade-offs are forced.**
- *Latency grows with capacity*: more bits means longer word- and bit-lines (more RC delay), larger decoders and wires to cross the die.
- *Cell size*: a 6T SRAM cell is roughly 100 to 150 F² (F = feature size) vs about 6 F² for a DRAM cell, so SRAM costs tens of times more area per bit; NAND is cheaper still per bit.
- *Volatility and endurance*: SRAM/DRAM are fast and unlimited-endurance but volatile; NAND is non-volatile but slow to write and wears out.
- *Power*: SRAM leaks (static power scales with bits), DRAM needs refresh; the core's register file switches every cycle.

**AMAT.** For a multi-level hierarchy, recursively:
$$\text{AMAT} = t_{L1} + m_{L1}\left(t_{L2} + m_{L2}\left(t_{L3} + m_{L3}\,t_{DRAM}\right)\right).$$
With $t_{L1} = 1$ ns, $m_{L1} = 5\%$, $t_{L2} = 4$ ns, $m_{L2} = 20\%$, $t_{L3} = 12$ ns, $m_{L3} = 30\%$, $t_{DRAM} = 80$ ns:
$$\text{AMAT} = 1 + 0.05\,(4 + 0.2\,(12 + 0.3\times 80)) = 1.56\ \text{ns},$$
about $51\times$ faster than going to DRAM every time.
:::

::: short
"The memory hierarchy stacks storage levels, each bigger, slower and cheaper than the last: registers, L1/L2/L3 SRAM caches, DRAM main memory, then SSD or disk. No one technology is fast, large and cheap, so we exploit locality: keep the working set in small fast levels and most accesses never reach the slow ones. Registers hold live operands, caches hold copies of hot code and data, DRAM holds running programs, storage holds everything persistently. With a 95 percent L1 hit rate and 80 ns DRAM, average access time drops from 80 ns to a few ns."
:::

::: long
"The hierarchy exists because of a physical trade-off. Fast memory is small and expensive: a register or an SRAM cell is built from several transistors and has to sit close to the core, while big memory has long wires and lots of decoding, so it's slower, and cheap memory like DRAM or NAND packs a bit into one transistor or less but pays in latency. There's no technology that gives all three, so the system layers them.

Starting from the top: registers, a few hundred bytes to a few kilobytes, accessed in under a cycle, hold what the instruction is operating on right now, and the compiler manages them. L1 cache is 32 to 64 KB per core of SRAM at around a nanosecond, split into instruction and data. L2 is a few hundred KB to a couple of MB, maybe 4 ns. L3 is shared and tens of MB at 10 to 20 ns. These hold copies of recently used instructions and data, managed entirely by hardware. Below that is DRAM, gigabytes at 50 to 100 ns, which holds the running programs and their data; the OS and MMU manage it. And then storage: SSD at tens of microseconds, hard disk at milliseconds, holding files and anything swapped out.

It works because of locality. Temporal locality says a loop counter or a hot function gets reused; spatial locality says if you touched array element i you'll touch i plus one, so we fetch whole cache lines of 64 bytes.

You can put numbers on it. If L1 takes 1 ns and hits 95 percent of the time, L2 takes 4 ns and hits 80 percent of what's left, L3 12 ns and hits 70 percent, and DRAM is 80 ns, the average access time is about 1.6 ns. Without caches every access would cost 80, over fifty times worse. That's why a miss rate that looks small, like 5 percent, still matters, because the miss penalty is 50 to 100 times the hit time."
:::

::: terms
- **Locality of reference**: temporal (reuse) and spatial (neighbors) clustering of memory accesses.
- **Cache line (block)**: unit of transfer between levels, typically 64 bytes.
- **Hit rate / miss rate**: fraction of accesses found / not found at a level.
- **Miss penalty**: extra time to fetch from the next level.
- **AMAT**: average memory access time, $t_{hit} + m\,t_{miss}$.
- **Working set**: the data a program actively uses over a short window.
- **Inclusive / exclusive hierarchy**: whether a lower level contains (or excludes) everything in the one above.
- **Memory wall**: the growing gap between CPU speed and DRAM latency.
:::

::: exceptional
An average answer names the levels in order. An exceptional answer:

- Explains the **physical reason** (wire delay and cell area) that capacity and speed trade off, and gives cell sizes (6T SRAM vs 1T1C DRAM).
- Ties the hierarchy to **locality** and shows it works only because programs have it; a random-access pattern over a huge array defeats it.
- Gives **AMAT with numbers**, including a multi-level calculation.
- Says who manages each level (compiler, hardware, OS) and what is stored.
- Mentions embedded variants: MCUs with no cache but tightly-coupled memory, GPUs with huge register files and scratchpads, and the memory wall.
:::

::: mistakes
- **"Cache is just faster RAM."** It holds copies, is managed by hardware, and is built from SRAM at a different point in the hierarchy.
- **Quoting exact latencies as universal.** They vary by process, clock and design; give ranges and say they are typical.
- **Ignoring locality**, so the answer reads as a list rather than an explanation.
- **Averaging hit rates additively.** Miss rates compound through the levels (local miss rates multiply), as the nested AMAT formula shows.
- **Forgetting storage and registers** or saying registers are "memory managed by hardware". The compiler allocates them.
- **Thinking more cache is always better.** Bigger caches are slower, use more area and leak more power.
:::

::: deep
## Why no single memory wins

A memory array is a grid of cells with a word-line per row and a bit-line per column. To read a bit, a decoder activates one word-line, the selected cells drive their bit-lines, and a sense amplifier detects a small voltage difference. Delay has three parts:

1. **Decode**: grows like $\log_2 N$ gate delays.
2. **Word-line and bit-line RC**: a line of length $L$ has resistance $\propto L$ and capacitance $\propto L$, so its Elmore delay grows like $L^2$. Doubling rows or columns more than doubles that part.
3. **Sensing**: the bit-line swing is $\Delta V \approx I_{cell} t / C_{BL}$; bigger $C_{BL}$ means slower development of the signal.

So access time rises with capacity. Designers fight it by splitting a big array into banks and sub-arrays, but the wire distance across a 32 MB L3 or a 64 GB DRAM module is still much larger than across a 32 KB L1. Hence capacity and speed are tied by physics, not just by cost.

Cost is tied to cell design. A 6T SRAM cell is two cross-coupled inverters plus two access transistors; a DRAM cell is one access transistor plus a capacitor; NAND flash stores charge in a floating or trap layer in a string of series transistors. Rough area per bit: SRAM ~120 to 150 F², DRAM ~6 F², NAND a few F² per bit before stacking layers. That roughly 20:1 area ratio between SRAM and DRAM (146/6 ≈ 24) is the reason caches are MBs and main memory is GBs.

## Locality is the other half

A hierarchy is a bet on program behavior:

- *Temporal*: loop variables, stack frames, hot functions, and lookup tables are reused.
- *Spatial*: instructions are sequential; arrays and structs are traversed in order. When you miss on a byte, the cache fetches the entire 64-byte line, so the next 63 bytes are free.

Example: summing an array of 4-byte ints sequentially. A 64-byte line holds 16 ints, so the first access misses and the next 15 hit: miss rate 1/16 = 6.25% even with a cold cache. Walking the same array with a stride of 64 bytes touches a new line every access: 100% miss rate, 16x the traffic for the same number of loads. Try this in the cache simulator ([[q0937]]).

## Putting numbers on AMAT

Using the figures above ($t_{L1}$=1 ns, 5% L1 miss, L2 4 ns / 20% miss, L3 12 ns / 30% miss, DRAM 80 ns):

| Configuration | AMAT | Relative to all-DRAM |
|---|---|---|
| No cache | 80 ns | 1x |
| L1 only (5% miss) | $1 + 0.05\times 80 = 5.0$ ns | 16x faster |
| L1 only (1% miss) | $1 + 0.01\times 80 = 1.8$ ns | 44x faster |
| L1 + L2 + L3 | 1.56 ns | 51x faster |

Observations: (1) Even a 5% L1 miss rate leaves the average dominated by the miss term (4 of 5 ns). (2) Intermediate levels exist because the gap between L1 and DRAM is too wide for one level: adding L2 and L3 cuts the effective miss penalty seen by L1 from 80 ns to $4+0.2(12+0.3\times80)=11.2$ ns. (3) To reach AMAT ≤ 2 ns with only L1 and DRAM, the miss rate must be at most $(2-1)/80 = 1.25\%$.

## What lives where, and who decides

- **Registers**: the compiler's register allocator decides which variables live in them; excess spills to the stack (memory).
- **L1/L2/L3**: hardware decides using replacement policies (LRU approximations). Software can only hint (prefetch instructions, non-temporal stores).
- **DRAM**: the OS decides which virtual pages reside in physical frames ([[q0943]]).
- **Storage**: the filesystem and OS decide; swap space extends DRAM.

Embedded variants: many MCUs omit caches for determinism and instead provide **tightly-coupled memory (TCM)** or scratchpad that software manages explicitly, so worst-case latency is known (important for real-time interrupt handlers). GPUs expose **shared memory** and giant register files because their latency-hiding strategy is thousands of threads, not big caches.

## Real hardware behaviors worth knowing

- **Line size** (64 B): DRAM has a long fixed latency, then streams bytes cheaply, so moving 64 bytes is only slightly more expensive than 1 byte.
- **Row buffer in DRAM**: an open row acts like a mini cache; row-buffer hits are faster than misses ([[q0940]]).
- **Prefetchers** detect streams and fetch ahead, turning spatial locality into hidden latency.
- **Bandwidth vs latency**: DRAM bandwidth per channel may be tens of GB/s even though latency is ~80 ns; with 64-byte lines, the memory-level parallelism needed to saturate 25 GB/s at 80 ns latency is $25\times10^9\times 80\times10^{-9}/64 \approx 31$ outstanding misses.
- **Coherence**: with multiple cores each L1/L2 may hold a copy of the same line; MESI-style protocols keep them consistent, and false sharing (two cores writing different words of one line) can silently cost 10x.

> [!UNCERTAIN]
> All capacities and latencies here are typical ranges for current desktop/server-class parts. Specific processors differ by a factor of 2 or more, and cycle counts depend on clock speed. State them as "on the order of" in an interview.

::: applications
- **Desktop/server CPUs**: three cache levels (L1 per core, L2 per core or cluster, shared L3) over DDR DRAM and NVMe storage.
- **Microcontrollers (Cortex-M0/M3)**: no cache, a flash prefetch buffer, SRAM, and optionally TCM for deterministic real-time code.
- **GPUs**: huge register files, small shared memories/L1, an L2, and high-bandwidth GDDR/HBM instead of deep latency-hiding caches.
- **Smartphone SoCs**: system-level cache shared by CPU, GPU and NPU to reduce power-hungry LPDDR accesses.
- **Databases and OS page cache**: software-managed layer using DRAM as a cache for SSD/disk, the same hierarchy idea one level up.
:::

::: assumptions
- The numbers are typical of mainstream 2020s desktop/mobile parts; embedded MCUs, FPGAs and exotic memories (HBM, 3D XPoint, FRAM) shift individual levels.
- Hit rates are workload dependent; the 95%/80%/70% figures are illustrative.
- AMAT assumes serial lookups and ignores overlap (out-of-order execution, prefetch, multiple outstanding misses), which hide a lot of latency in real CPUs.
- "Hierarchy" can also be taught as including network storage and cloud tiers; the same locality trade-off applies.
- An embedded interviewer may mainly want flash / SRAM / registers; the principle is the same with fewer levels.
:::

::: followups
### Why are there multiple cache levels instead of one big cache?
A single big cache would be slow (long wires) and so would hurt the common hit case. A small L1 is fast for most accesses, and L2/L3 reduce the miss penalty to DRAM. With the earlier numbers, L1-only at 5% miss gives 5.0 ns while the three-level hierarchy gives 1.56 ns.

### How does the hierarchy behave if a program has no locality?
It degrades toward DRAM speed, or worse. Random accesses over a 10 GB array have almost 0% hit rate in any cache, and every access pays about 80 ns plus a TLB miss. Throughput is then bounded by memory-level parallelism, not by caches.

### Why is SRAM used for caches but DRAM for main memory?
SRAM (6T) is fast and needs no refresh but occupies about 20x the area per bit, so it is limited to MBs. DRAM (1T1C) is dense and cheap but slower and needs periodic refresh. Splitting the roles gives speed where it counts and capacity where it is cheap. See [[q0939]].

### Estimate the miss rate needed so that DRAM misses add less than 10% to a 1 ns L1 hit time.
We need $m\times 80\ \text{ns} \le 0.1$ ns, so $m \le 0.125\%$ (about 1 miss per 800 accesses). That is why L2/L3 matter: they cut the effective penalty, so the required L1 miss rate is looser (with 11.2 ns effective penalty, $m \le 0.9\%$).

### A loop gets 10x faster when you swap its two nested loops. Explain with the hierarchy.
In row-major C, `a[i][j]` with `j` innermost walks memory sequentially, using all 16 ints of each 64-byte line (6.25% miss). With `i` innermost you stride by a full row, so each access touches a different line and, for large rows, evicts it before reuse (near 100% miss). The hierarchy rewards spatial locality, and the miss penalty dominates runtime.
