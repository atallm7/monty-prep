::: basics
### In plain words
A program and its data are both just patterns of bits, so they can sit in any memory in the system. Memories differ in speed, size, and whether they keep their contents with the power off. The program is usually stored in memory that survives power loss. Values that change while it runs live in fast memory that forgets.

### Picture it
Think of an office. The filing cabinet holds everything permanently, but digging through it is slow. Your desk holds what you are working on, and it is cleared when you leave for the night. Your hands hold the one or two things you are using this second. The cabinet is flash or disk, the desk is RAM, and your hands are the CPU's registers.

### Words you need
- **Non-volatile**: keeps its contents with the power off. **Volatile** memory forgets them.
- **Flash**: non-volatile memory that holds the program and constants. It reads fast but is slow to rewrite.
- **SRAM**: fast, volatile memory for variables that change.
- **Register**: a tiny storage slot inside the CPU that holds the value being worked on right now.
- **Startup code**: the first code to run after reset, which prepares memory.

### The simplest example
A small chip has 64 KB of flash and 20 KB of SRAM. The program code is 38 KB, constants such as lookup tables are 6 KB, and the starting values of variables are 1 KB. Flash holds $38+6+1=45$ KB. At power-up, the startup code copies those 1 KB of starting values into SRAM. SRAM then holds 4 KB of variables, which leaves 16 KB for the stack (scratch space for function calls) and the heap (memory a program asks for while running). That is the whole idea. The rest of this page covers how a program image is laid out, flash speed, and sharing one path for code and data versus separate paths.
:::


::: testing
Whether you can draw the whole map of "places a bit can live" and match each place to what it is good for, instead of just saying "RAM and the hard drive". The interviewer is listening for:

1. Both **data and instructions** are just bits, so they can live in the same kinds of memory. What differs is how the machine is wired to fetch them.
2. You know the layers: registers, caches, on-chip SRAM, off-chip DRAM, non-volatile flash/ROM, and storage.
3. You can describe a real program image: code in flash, constants in flash, initialized variables copied to RAM at boot, stack and heap in RAM.
4. You separate **volatile vs non-volatile** and **von Neumann vs Harvard** without being prompted.
:::

::: why
Every embedded and SoC bug eventually becomes "where is this thing actually stored and who can touch it?" Stack overflow, a variable that resets after power cycle, code that runs slowly because it executes out of external flash, a DMA that cannot reach a buffer in tightly-coupled memory: all of these are memory-placement problems. For hardware interviews it is also the entry point to the memory section: once you can say where bits live, the follow-ups on hierarchy ([[q0936]]), caches ([[q0937]]), RAM ([[q0939]]) and MMUs ([[q0943]]) all hang off the same picture.
:::

::: concepts
- **Volatile vs non-volatile**: SRAM/DRAM lose contents without power; flash, ROM, EEPROM keep them. See [[q0826]].
- **Address space**: the CPU sees one (or two) flat numbered range(s); each region of addresses is routed to a different physical memory or peripheral.
- **Von Neumann vs Harvard**: one shared path for code and data, or two separate ones. See [[q0935]].
- **Registers and caches**: the fastest, smallest storage, holding copies of what the CPU is using right now. See [[q0938]], [[q0937]].
- **Program image sections**: `.text` (code), `.rodata` (constants), `.data` (initialized variables), `.bss` (zero-initialized), stack, heap.
- **Memory-mapped I/O**: peripheral registers also sit in the address space, so "memory" includes things that are not storage at all. See [[q0829]].
:::

::: answer
"Both data and program are just bits, so they can sit in any of the memories in the system; what changes is speed, size, and whether it survives power-off.

On a microcontroller, the program normally lives in on-chip flash, which is non-volatile. Constants like lookup tables and strings live there too. Variables live in SRAM. Initialized globals are a nice example: their starting values are stored in flash, and the startup code copies them into SRAM before main runs, and the uninitialized ones in .bss are just zeroed. The stack and heap are regions of SRAM.

On a bigger system, like a phone or a PC, the program is stored on disk or flash storage, which is non-volatile and huge but slow. When you run it, the OS loads it into DRAM. The CPU then pulls the pieces it is actively using into the caches, which are small fast SRAM, and into registers, which are the fastest of all.

You can also run code from RAM if you want speed, like copying an interrupt handler into fast on-chip RAM. And peripherals are memory-mapped, so some addresses aren't storage at all.

The architectural twist is that a von Neumann machine uses one memory and one bus for code and data, while a Harvard machine has separate ones. Most chips are a hybrid: separate L1 instruction and data caches, but one shared main memory."
:::

::: technical
**Storage classes by role.**

| Place | Volatile? | Typical size | Typical access | Holds |
|---|---|---|---|---|
| Registers | yes | 16 to 32 words (+ vector/FP) | sub-cycle to 1 cycle | operands, results, pointers |
| L1/L2/L3 cache (SRAM) | yes | 10s of KB to 10s of MB | ~1 ns to ~15 ns | copies of recently used code and data |
| On-chip SRAM / TCM | yes | KBs to MBs | 1 to few cycles | stack, hot data, ISR code |
| External DRAM | yes | MBs to GBs | ~50 to 100 ns | OS, programs, large data |
| On-chip / external flash, ROM | no | 10s of KB to GB | tens of ns (NOR, XIP) to µs (NAND) | firmware, constants, boot code |
| SSD / disk / SD card | no | GBs to TBs | µs to ms | files, installed programs |

**A real microcontroller image.** At link time the program is split into sections. With 64 KB of flash and 20 KB of SRAM, say `.text` = 38 KB, `.rodata` = 6 KB, `.data` = 1 KB, `.bss` = 3 KB. Flash holds 38 + 6 + 1 = 45 KB (the `.data` initial values are stored at their *load address* in flash). SRAM holds 1 + 3 = 4 KB static, leaving 16 KB for the stack and heap. At reset, startup code copies `.data` flash to SRAM, zeroes `.bss`, then calls `main`.

**Address-space view (ARMv7-M style).** The architecture reserves `0x0000_0000` to `0x1FFF_FFFF` for code, `0x2000_0000` for SRAM, `0x4000_0000` for peripherals, `0x6000_0000` for external RAM, and `0xE000_0000` for core/system registers. A load to a peripheral address reads a hardware register, not a stored value.

**Where *can* each go?** Data: registers, any RAM, flash (read-only), disk. Program: flash/ROM/disk at rest, DRAM or SRAM when running, caches in flight. Only RAM-like memories can be written quickly and indefinitely; flash writes need erase blocks and have limited endurance.

**Bus view.** In a Harvard core the instruction fetch and the data access happen in the same cycle on two buses. In a von Neumann core they contend for one bus (the "von Neumann bottleneck").
:::

::: short
"Program and data are both just bits, so they can live in registers, caches, SRAM, DRAM, flash and disk. At rest the program sits in non-volatile memory like flash or an SSD. When it runs, instructions and data are brought into RAM and then into caches and registers. On a microcontroller, code and constants stay in flash, variables and the stack live in SRAM, and the startup code copies initialized globals from flash into RAM. Von Neumann machines share one memory for both, Harvard machines keep them separate."
:::

::: long
"I'd split it into 'at rest' and 'while running'.

At rest, the program has to survive power-off, so it's in non-volatile memory: flash or ROM on a microcontroller, an SSD or SD card on a bigger system. Constants like lookup tables and strings are stored with it. Data that has to persist, like calibration values, goes in flash or EEPROM too.

While running, things move closer to the CPU. On a microcontroller, the CPU can execute directly out of flash, which is called execute-in-place, and variables live in on-chip SRAM. The linker lays the image out in sections: .text for code, .rodata for constants, .data for initialized globals, .bss for zero-initialized globals. The initial values for .data are stored in flash and copied to SRAM at startup, .bss is zeroed, then the stack and heap use whatever SRAM is left. If a function needs to be fast, I can place it in RAM or a tightly-coupled memory.

On a bigger system, the OS loads the program from storage into DRAM. As the CPU runs it, hot instructions and data are copied into the L1, L2 and L3 caches, which are SRAM, and the values being operated on right now sit in registers.

There's one more thing that looks like memory but isn't: memory-mapped peripherals. Reading a certain address reads a hardware register.

And architecturally, von Neumann machines put code and data in one address space on one bus, while Harvard machines keep them apart so you can fetch an instruction and access data in the same cycle. Most real CPUs are modified Harvard: split L1 caches, unified main memory."
:::

::: terms
- **Volatile memory**: loses its contents when power is removed (SRAM, DRAM, registers).
- **Non-volatile memory (NVM)**: retains contents without power (flash, ROM, EEPROM, disk).
- **Execute-in-place (XIP)**: the CPU fetches instructions directly from flash instead of copying them to RAM first.
- **Linker sections**: `.text`, `.rodata`, `.data`, `.bss`, plus stack and heap regions.
- **Load address vs run address (LMA/VMA)**: where `.data` is stored in flash vs where it lives while running in SRAM.
- **Von Neumann architecture**: single memory and bus for instructions and data.
- **Harvard architecture**: separate instruction and data memories/buses.
- **Memory-mapped I/O**: peripheral registers accessed with ordinary loads and stores at fixed addresses.
:::

::: exceptional
An average answer lists "RAM, ROM, hard drive, cache". An exceptional answer:

- Organizes it by **role and lifetime**: at rest (non-volatile) vs running (volatile, hierarchical).
- Walks through a concrete image: `.text`/`.rodata` in flash, `.data` copied at boot, `.bss` zeroed, stack/heap in SRAM, and does the size arithmetic.
- Points out that the same bits can be code or data depending only on which bus fetches them (and mentions self-modifying code, JIT, and bootloaders writing code as data).
- Mentions memory-mapped I/O and that not every address is storage.
- Brings in von Neumann vs Harvard and the "modified Harvard" reality of split L1 caches over unified DRAM.
- Notes flash write limits (erase blocks, endurance), which is why variables do not live in flash.
:::

::: mistakes
- **"Program is in ROM, data is in RAM, end of story."** Modern firmware sits in flash (rewritable), constants also sit in flash, and big systems load the program into DRAM at run time.
- **Forgetting the `.data` copy.** Initialized globals are stored in flash *and* live in RAM; the startup code does the copy. Skipping this in a custom linker script or bare-metal bring-up gives garbage initial values.
- **Treating flash as ordinary RAM.** Flash is read at RAM-like speed but written in pages after an erase, and survives only ~10^4 to 10^6 cycles depending on type.
- **Saying cache is a separate place you "store" things.** A cache holds *copies*; the programmer does not choose to store data there.
- **Ignoring memory-mapped I/O**, then being surprised that reading an address twice can give different values (a status register).
:::

::: deep
## Bits do not know if they are code or data

An instruction is a 16-, 32- or 64-bit word the control unit decodes; an integer is a word the ALU adds. The memory cell cannot tell the difference. What makes a word "program" is only that the **program counter (PC)** pointed at it and the fetch path decoded it. This is the stored-program idea: the same memory can hold both, and the machine can load new programs by writing them as data. Compilers' output, JIT-generated code, and bootloaders that write a new firmware image into flash all rely on this.

Two consequences:

1. Security features such as W^X (write xor execute) and the NX bit exist because "data" overwritten by an attacker can be executed if the hardware does not forbid it.
2. When code is modified (JIT, self-loading), caches need explicit maintenance: the instruction cache may hold stale copies of what the data cache just wrote.

## Walking through a power-up

1. **Reset.** The core loads the initial stack pointer and reset vector from the first words of the vector table in flash. A boot ROM may run first on bigger SoCs, copying a bootloader from external flash into on-chip SRAM, because external flash is slow and cannot be executed from until its controller is configured.
2. **Startup code.** Copies `.data` (e.g. 1 KB) from its flash load address to SRAM, zeroes `.bss` (3 KB), sets up clocks, then calls `main`.
3. **Running.** Instruction fetches go to flash (often through a small prefetch buffer or "ART accelerator"-style cache, because flash is slower than the core clock); data reads/writes go to SRAM; stack pushes and pops move the stack pointer within SRAM.

Why does flash need caching at all? Flash read time is typically tens of ns, but a 100+ MHz core wants an instruction every 10 ns or less. Vendors insert wait states (extra cycles) and a prefetch buffer. At 168 MHz (5.95 ns per cycle) a flash with 30 ns access needs $30/5.95 = 5.04$, so 6 cycles per fetch (5 wait states), and without prefetch the CPU would run at roughly a sixth of its potential on straight-line code. That is the practical reason to put hot code in zero-wait-state RAM.

> [!TIP]
> "Where does the code run from?" is a great follow-up to volunteer. If asked about a 200 MHz MCU whose flash needs wait states, you can say: hot ISRs go in ITCM/SRAM, the rest executes from flash via the prefetch cache.

## Big-system view: from disk to register

On a laptop or phone, the executable file sits on an SSD (NAND flash). When you launch it:

1. The OS maps the file's pages into a process's virtual address space ([[q0943]]). Nothing is read yet.
2. On first touch of each 4 KB page, a page fault makes the OS read it from storage into a DRAM frame (tens of µs from an SSD).
3. The CPU fetches instructions through L1-I; data goes through L1-D. A miss at each level walks down to L2, L3, DRAM ([[q0936]]).
4. The operands for the current instruction are in registers.

So any given byte can exist simultaneously in storage, DRAM, one or more cache levels, and a register. The levels hold **copies**; coherence hardware and the OS keep them consistent.

## Von Neumann, Harvard and what you really find

| Style | Code and data | Pro | Con | Example |
|---|---|---|---|---|
| Von Neumann | one memory, one address space, one bus | simple, flexible, can load code as data | fetch and data access compete for the bus | classic PC main memory; many small cores |
| Harvard | two memories/buses, often separate address spaces | fetch and data access in the same cycle | cannot trivially treat code as data; need special instructions to read flash constants (AVR `LPM`) | PIC, AVR, many DSPs |
| Modified Harvard | separate L1 I/D caches (or buses), unified lower levels | most of Harvard's bandwidth, von Neumann's flexibility | cache coherence between I and D when code changes | Cortex-M and nearly every application CPU |

See [[q0935]] for the head-to-head comparison.

## A quick sizing exercise

A sensor node has 256 KB flash and 64 KB SRAM. The firmware has 180 KB code, 20 KB constants, 4 KB initialized and 10 KB zero-initialized variables. Flash used = 180 + 20 + 4 = 204 KB (80% of flash, leaving 52 KB for an OTA second image or logs). SRAM static = 14 KB, leaving 50 KB for stack and heap. If a 32 KB receive buffer is placed statically, SRAM static grows to 46 KB, leaving 18 KB, which is where stack overflow ([[q0941]]) starts to become a real risk.
:::

::: applications
- **STM32 / Cortex-M firmware**: code in internal flash at `0x0800_0000`, variables in SRAM at `0x2000_0000`, ISRs optionally relocated to ITCM RAM for zero-wait-state execution.
- **AVR / PIC (Harvard)**: program in flash, data in SRAM, with dedicated instructions to read constants out of program memory.
- **Smartphone SoC**: boot ROM, then bootloader from UFS/eMMC flash, OS and apps loaded into LPDDR DRAM, hot code and data in on-chip caches.
- **FPGA soft cores**: program in block RAM initialized from the bitstream, which makes "ROM" and "RAM" the same physical resource configured differently.
- **Server CPUs**: instruction and data residing in DRAM with split L1 I/D caches and large shared L3.
:::

::: assumptions
- I am answering for a conventional stored-program computer. Exotic architectures (dataflow, in-memory compute) change the picture.
- On a microcontroller I assume internal flash and SRAM; many parts also have external QSPI/OctoSPI flash executed in place, which is slower, or external SDRAM for data.
- Sizes and speeds are typical orders of magnitude, not product specs.
- "Program" means machine code in memory; with interpreted languages (Python), the interpreter's code is the program and your script is data to it. That is a valid alternative reading and worth mentioning if the interviewer is software-minded.
:::

::: followups
### What is the difference between where a variable's initial value is stored and where the variable lives?
For an initialized global like `int gain = 5;`, the value 5 is stored in flash (at the `.data` load address) so it survives power-off. The variable itself lives in SRAM at its run address, because it must be writable. The startup code copies the initial values over before `main`. A `const` global may be left only in flash (`.rodata`) and read from there.

### Can code run from RAM? Why would you want that?
Yes. Instruction fetches can come from any executable memory. Reasons: RAM has zero wait states so it is faster than flash; you must run from RAM while erasing/writing that same flash (the flash is busy); and bootloaders and JITs generate code at run time. The cost is RAM space and having to load the code first.

### What is the difference between volatile and non-volatile memory, and which would you use for a counter updated every second?
Volatile loses data without power; non-volatile keeps it. Updating a counter every second in flash would wear it out: at $10^5$ cycles of endurance, one write per second is gone in $10^5/86400 \approx 1.2$ days if you hit the same cell. Keep it in RAM and write to non-volatile memory only on power-fail or every N minutes, use wear-leveling, or use FRAM/EEPROM with higher endurance.

### How does a CPU fetch an instruction and a data word in the same cycle in a Harvard design?
It has two independent memories (or ports) with their own address and data buses: one fed by the PC for instructions, one by the load/store unit for data. Both transfer in parallel. Modified Harvard CPUs get the same effect with split L1 I and D caches.

### A function runs 5x slower when I move it to a different source file. Memory could explain it. How?
The linker may have placed it in a different region: external QSPI flash instead of internal, or outside the instruction cache's cacheable window, or with a different number of wait states. Check the map file for the function's address and see which memory region and attributes cover it. Alignment relative to cache lines and flash prefetch width can also matter.
:::
