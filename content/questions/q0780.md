::: basics
### In plain words
GPIO stands for General-Purpose Input/Output. It is a pin on a microcontroller whose job you choose in software. As an output, the pin drives itself high or low, for example to light an LED. As an input, the pin reads whether the voltage on it is high or low, for example from a button.

### Picture it
Picture a hose fitting on a control panel that you can set to one of two modes. In output mode it is a small pump outlet, which pushes water out. In input mode it is a pressure gauge, which only reads. The small pump can fill a small cup but cannot run a big machine. For the machine you use the pump to flip a valve, and the valve controls the large flow. A GPIO pin works the same way: it signals a transistor, and the transistor switches the big load.

### Words you need
- **Direction**: whether the pin is set as an input (read) or an output (drive).
- **Current limit**: how much current a pin can supply or absorb, typically a few to a few tens of milliamps.
- **Pull-up resistor**: a resistor that holds an unused input high, so it never drifts between high and low. See [[q0786]].
- **Transistor**: an electrically controlled switch that lets a small pin current control a bigger one.

### The simplest example
To light a green LED from a 3.3 V output, you need a series resistor. The LED drops about 2.0 V, so the resistor must drop the other 1.3 V. For 5 mA, $R = 1.3/0.005 = 260$ Ω. A standard 270 Ω resistor gives about 4.8 mA. For a button, you set a pin as an input with a pull-up and wire the button to ground. The pin reads high when the button is open and low when it is pressed. That is the whole idea. The rest of this page covers the pin's internal circuit, and driving relays and motors.
:::

::: testing
Whether you can unpack the acronym **and** show you have used one: that a GPIO is a pin whose direction and function are chosen in software, how you read and write it (registers), and what it is and is not good for. The best answers give concrete use cases with a number or two (LED current, how many mA a pin can drive) and mention the limits.

Hidden sub-skills: electrical limits of a pin (source/sink current, logic thresholds), pull-ups, interrupts on pin change, and when to add a driver or use a dedicated peripheral instead of bit-banging.
:::

::: why
GPIOs are the first peripheral you ever use on a microcontroller (blink an LED) and the last one you stop debugging (chip selects, resets, enables, boot straps, interrupt lines). Nearly every embedded design uses dozens. Interviewers ask it to see if you treat a pin as a real electrical circuit with limits, not just a variable in software. A candidate who says "I'd put a transistor between the pin and the relay because the pin can only source about 20 mA" shows they have built things.
:::

::: concepts
- **Digital I/O pin**: a pad connected to an output driver and an input buffer, controlled by registers. See [[q0783]].
- **Direction**: configured as input (read the pin level) or output (drive it high or low).
- **Logic levels**: $V_{IL}$, $V_{IH}$, $V_{OL}$, $V_{OH}$ define what counts as 0 and 1 and what the pin drives. See [[q0020]].
- **Pull-up / pull-down**: internal or external resistors that set the default level of an input. See [[q0786]].
- **Drive limits**: maximum source and sink current per pin and per package (typically a few mA to tens of mA; vendor-specific).
- **Alternate function**: the same pin may be handed to a peripheral (UART TX, SPI, PWM) instead of software control. See [[q0781]].
- **Interrupt on edge**: input pins can raise an interrupt on rising or falling edges, rather than being polled.
:::

::: technical
**Name.** General-Purpose Input/Output: a digital pin that software can configure and control, as opposed to a pin dedicated to a fixed function (supply, oscillator, analogue input).

**Hardware per pin (typical).** An output driver (push-pull or open-drain, [[q0785]]), an input buffer (often with a Schmitt trigger), optional pull-up and pull-down resistors, ESD protection diodes, and a multiplexer that connects the pad to either the GPIO block or a peripheral (alternate function). Registers: mode (input/output/analog/alternate), output type, pull, speed/slew, input data, output data, and atomic set/reset. See [[q0787]].

**Electrical limits.** For 3.3 V CMOS parts, representative values: $V_{IL}\approx 0.3 V_{DD}$, $V_{IH}\approx 0.7V_{DD}$; $V_{OL}$ and $V_{OH}$ specified at a stated current (for example within 0.4 V of the rails at a few mA); source/sink 4 to 25 mA per pin (varies, and the pin drive is configurable in many parts); a total per-port and per-package limit.

**LED example.** Green LED at 5 mA, forward voltage about 2.0 V, supply 3.3 V: $R = (3.3-2.0)/5\text{ mA} = 260\ \Omega$, so 270 Ω gives 4.8 mA.

**Switching a bigger load.** An NPN with $h_{FE}\approx 50$ driving 100 mA needs base current $\approx 100/50 = 2$ mA, so $R_B\approx (3.3-0.7)/2\text{ mA}\approx 1.3$ kΩ (use 1 kΩ for margin). Or use a logic-level NMOS with a gate resistor and a pull-down ([[q0786]]).

**Inputs.** Reading a button: switch to ground with a pull-up (internal or external). Pin reads 1 when open and 0 when pressed. Mechanical contacts bounce for about a millisecond or more, so debounce in hardware or software.

**Speed.** Toggling a pin from software takes a few CPU cycles via the set/reset register, so a few MHz of toggle rate is typical on a 48 to 100 MHz core; hardware timers or SPI/PWM peripherals do better.
:::

::: long
"GPIO stands for General-Purpose Input/Output. It's a pin on a microcontroller that isn't permanently assigned to one job. In software I pick the direction: as an output, I write a bit and the pin goes to high or low, and as an input, I read a bit that tells me the voltage on the pin. Behind each pin there's a small block with a direction control, an output latch, an input buffer, and usually settings for pull-up or pull-down resistors, drive strength and speed. Many pins can also be handed over to a peripheral, like UART or SPI, instead of being controlled by software.

The use cases are the glue of any embedded system. On the output side: LEDs, enable and reset lines for other chips, chip selects for SPI devices, driving the gate of a MOSFET or the base of a transistor to switch loads like relays, motors or buzzers, and bit-banging a simple protocol when I run out of peripherals. On the input side: buttons and switches, status flags from other ICs, sensor outputs like data-ready lines, and external interrupts so the MCU can sleep until an edge arrives, instead of polling.

The electrical side is where people slip. A pin can typically drive only a few to maybe 25 milliamps, and there's a total budget per package. So a 5 milliamp LED is fine with a series resistor, about 270 ohms from 3.3 volts. A relay coil or motor is not; the pin should drive a transistor or MOSFET that switches the load from its own supply, plus a flyback diode. For inputs I'd make sure there's a defined default with a pull-up or pull-down so a floating pin doesn't read random values, and I'd debounce mechanical switches.

So GPIO is simple, but it's where software meets the real world, and the datasheet limits matter."
:::

::: terms
- **GPIO**: General-Purpose Input/Output, a software-configurable digital pin.
- **Direction register**: selects whether a pin is an input or output.
- **Source / sink current**: current a pin supplies when high / absorbs when low.
- **$V_{OH}$, $V_{OL}$**: guaranteed output high and low voltages at a given load current.
- **$V_{IH}$, $V_{IL}$**: input thresholds for reading a 1 or a 0.
- **Pull-up / pull-down**: resistor setting the default level of an undriven pin.
- **Alternate function**: routing the pin to a peripheral instead of the GPIO block.
- **Bit-banging**: implementing a protocol by toggling GPIOs in software.
- **Debounce**: filtering the contact bounce of a mechanical switch.
:::

::: exceptional
**An average answer** gives the acronym and says "you can use it as input or output, for LEDs and buttons".

**An exceptional answer**:
- Describes the pin as hardware: direction, output latch, input buffer, optional pulls, protection, alternate-function mux.
- Gives use cases with numbers: LED resistor (270 Ω at 3.3 V gives 4.8 mA), transistor base current for a 100 mA load.
- States the **limits** (per-pin and per-package current, 5 V tolerance) and the fix (driver transistor, flyback diode, buffer).
- Mentions pulls, debounce and interrupts for inputs; mentions atomic set/reset registers.
- Knows when not to bit-bang: use a hardware peripheral (SPI, PWM, timer) when speed or timing matters.
:::

::: mistakes
- **Driving a relay or motor straight from a pin.** Coil current is usually tens to hundreds of mA, and the inductive kick can destroy the pin. Use a transistor and a flyback diode ([[q0429]]).
- **No series resistor on an LED.** The pin would try to force current into a low-impedance LED, exceeding its limit.
- **Leaving inputs floating.** A floating CMOS input picks up noise and can read random values or oscillate; set a pull.
- **Exceeding the package-level current budget** by summing many pins that each seem within limits.
- **Connecting 5 V signals to a non-5V-tolerant 3.3 V pin.** Check the datasheet.
- **Using read-modify-write on the output register** when an interrupt also changes the port, creating a race; use the atomic set/reset register instead.
:::

## A GPIO is a small circuit, not just a bit

From software a GPIO looks like one bit in a register. From the pin it looks like this: a pad connected to an output stage that can pull high or low, and to an input buffer that converts the pin voltage into a bit, with ESD protection diodes and optional pull resistors in parallel. ## Output: what the pin can really do

When a pin drives high it connects through a PMOS to $V_{DD}$; when low, through an NMOS to ground. Each transistor has an on-resistance, so the output voltage droops under load: $V_{OH} = V_{DD} - I\,R_{p}$, $V_{OL} = I\,R_{n}$. If the datasheet says $V_{OL} < 0.4$ V at 8 mA, the NMOS looks like at most 50 Ω. At 3.3 V into a short, the pin would try to deliver $3.3/50 = 66$ mA, which is why shorting a pin to the opposite rail destroys it and why [[q0788]] matters.

**LED.** $R = (V_{DD}-V_F)/I_F$. For a red LED with $V_F \approx 1.8$ V, 3.3 V and 5 mA: 300 Ω. The pin's own $R_p$ (tens of ohms) adds slightly. Modern LEDs are bright at 1 to 2 mA, which saves current and pin budget.

**Bigger loads.** Pins source or sink only milliamps, so for a motor, solenoid or relay the pin switches a transistor:

| Load | Pin drives | Why |
|---|---|---|
| LED, 2 to 10 mA | directly via resistor | within pin budget |
| Piezo buzzer, about 10 to 30 mA | directly or via small transistor | check limit |
| Relay coil, about 70 mA at 5 V | NPN or logic-level NMOS | pin cannot supply it; flyback diode needed |
| Motor, 1 A | MOSFET driver or H-bridge | pin only provides the gate drive |

For an NPN switching 70 mA with $h_{FE}\approx 100$ the base current is 0.7 mA; a 2.2 kΩ base resistor from a 3.3 V pin gives about 1.2 mA, plenty. Always put a flyback diode across the coil.

## Input: reading the world

An input pin presents a high-impedance CMOS gate (leakage typically nA). That means it will read whatever the outside world gives it, including nothing at all. A pin connected to an open switch floats and picks up noise from every nearby trace, so inputs need a defined default: pull-up (switch to ground), pull-down (switch to supply). Internal pulls are weak (tens of kΩ; vendor-specific); external ones are stiffer. Sizing is on [[q0786]].

**Debounce.** A mechanical contact bounces for roughly 1 to 10 ms (varies by switch) and one press can produce a dozen edges. Software debounce samples the pin every 5 to 10 ms and requires the same value several times; hardware debounce uses an RC filter into a Schmitt-trigger input. The GPIO simulation below has a debounce view.

**Interrupts.** Instead of polling, configure the pin to interrupt on a rising or falling edge. The MCU can sleep (microamps) until a button press or a sensor's data-ready line wakes it.

## What the firmware looks like

Whatever the vendor, the pattern is the same four steps: enable the port's clock, set the pin mode (input or output, plus pull and speed), then read or write the data register. In pseudo-C:

```c
gpio_enable_clock(PORTB);
gpio_mode(PORTB, 0, OUTPUT);       // PB0 drives the LED
gpio_mode(PORTA, 0, INPUT_PULLUP); // PA0 reads the button
if (gpio_read(PORTA, 0) == 0) gpio_set(PORTB, 0);   // pressed: LED on
```

A frequent first-day bug is forgetting the clock-enable step, in which case writes silently do nothing. Another is leaving the pin in its reset state, which on many parts is a high-impedance input (so the LED never lights) or, on pins shared with a debug port, an alternate function. On power-up most MCUs also hold every pin as an input until firmware runs, so any load wired to a GPIO must be safe in that state: a MOSFET gate with no pull-down can float on and switch a motor at boot. That is the reason for the 100 kΩ gate pull-down you see on almost every board.

## What GPIO is not good at

Software toggling is limited by instruction time and interrupt latency. A 48 MHz core takes several cycles per write, so a GPIO bit-banged signal has jitter of tens of ns to microseconds if interrupts intervene. For precise waveforms, use a hardware timer (PWM), SPI, I2C, UART or DMA-driven GPIO. GPIO is for control signals and slow interfaces. Also a GPIO is a digital pin: to measure an analogue voltage, use an ADC pin.

## Registers you will meet

Almost every MCU has the same few: a **direction/mode** register, an **output data** register, an **input data** register, and a way to **set or clear individual bits atomically** (STM32 has BSRR; AVR has PINx toggle; others have SET/CLR registers). The atomic form matters: writing `PORT |= bit` is a read-modify-write that an interrupt can corrupt if it also changes the same port, whereas one write to a set/reset register cannot.
:::

::: applications
- **Status LEDs** on every board: heartbeat, error, link activity.
- **Chip selects, enables and resets** for external ICs (SPI flash, sensors, radio modules).
- **Button and switch inputs** with pull-ups and debounce.
- **Wake-up and interrupt lines**: accelerometer INT pin waking a sleeping MCU.
- **Transistor/MOSFET drive** for relays, solenoids, backlights and small motors.
- **Bit-banged protocols**: one-wire sensors (DHT-type), WS2812-style LEDs on a spare pin, a software I2C when no peripheral is free.
- **Boot-mode and configuration straps** read at reset.
:::

::: assumptions
- 3.3 V CMOS microcontroller with push-pull-capable pins and optional internal pulls; other families (5 V AVR, 1.8 V parts) change the numbers but not the ideas.
- Source/sink limits of 4 to 25 mA per pin and a package total are typical ranges; read your device's datasheet, since limits depend on part, pin group and configured drive strength.
- LED forward voltages: about 1.8 V (red), 2.0 V (green), 3.0 V and above (blue/white); the exact value varies by LED.
- Debounce time estimates are typical and depend on the switch.
- GPIO terminology differs slightly across vendors (port, pin, pad, bank); the structure is the same.
:::

::: followups
### Can I power an LED directly from a GPIO?
Yes, with a series resistor, as long as the current is within the pin limit. At 5 mA and 3.3 V a green LED needs about 260 Ω (use 270 Ω). Without the resistor the LED limits nothing and the pin tries to deliver tens of mA, potentially damaging it.

### How do I drive a 12 V relay or motor from a 3.3 V GPIO?
Use the pin only as a control signal: GPIO to the gate (through a gate resistor) of a logic-level NMOS, or to the base of an NPN via a resistor, with the load on its own 12 V supply and a flyback diode across the coil. Make sure $V_{GS(th)}$ is well below 3.3 V. See [[q0429]].

### What happens if I read an input pin that isn't connected to anything?
It floats; the value is undefined and noisy, and a CMOS input in the linear region can draw extra current. Enable an internal pull or add an external resistor. Unused pins should be configured as outputs (low) or inputs with pulls, to avoid wasting power and picking up noise.

### How fast can I toggle a GPIO?
It depends on the core clock and the bus path to the port: from a few MHz (software loop on a 48 MHz Cortex-M) to tens of MHz for the fastest MCU ports, limited by the pin's slew-rate setting and load capacitance. For precise high-rate signals use a timer or SPI.

### Harder: sink 15 mA on each of 12 pins at once. Any issue?
Perhaps. Even if each pin is within its rating, the package has a total current limit (often 80 to 150 mA through VDD/VSS pins, vendor-dependent). 12 x 15 mA = 180 mA could exceed it, cause supply droop and ground bounce ([[q0788]]), and heat the die. Spread loads, use LED drivers, or reduce current per LED.
:::

::: interpretations
"GPIO" is a *role* a pin plays, not a distinct hardware type: the same physical pin can be a GPIO, a UART TX or an ADC input, depending on configuration. The "GP" in the name is discussed on [[q0781]], running out of pins on [[q0782]], and the internal circuit on [[q0783]].
:::
