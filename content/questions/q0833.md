::: testing
Whether you stay productive when the convenient tool is missing. The interviewer is looking for **resourcefulness with a ranked toolbox**: UART/printf logging, GPIO toggling with a scope or logic analyzer, LEDs as a last resort, simulation and host-side unit tests, bootloader-based development, a cheap probe you can build or buy, and post-mortem data captured in RAM. Strong candidates also know the cost of each method (timing disturbance, pins, code size) and pick the least intrusive one that answers the question.
:::

::: why
Many real situations lack a debug port: cost-reduced boards without a header, field units, MCUs in tiny packages that sacrifice pins, parts with readout protection, or old 8-bit families with limited tools. Even where a debugger exists, it may not help (timing-sensitive code, remote devices). Showing a broad, disciplined toolbox signals that you can make progress in any environment. It follows naturally from [[q0832]] and complements [[q0831]].
:::

::: concepts
- **Serial logging (printf over UART)**: simplest visibility; cost is CPU time and a pin.
- **GPIO as a probe**: toggle a pin at events; measure with a scope or logic analyzer.
- **Logic analyzer / scope**: observe external effects independent of the CPU.
- **Host-side simulation and unit tests**: run logic on a PC where a full debugger exists.
- **Bootloader and DFU**: reprogram over UART/USB without a probe.
- **Post-mortem state**: fault handlers saving registers and logs to RAM or flash.
:::

::: answer
"I'd fall back on instrumenting the code and observing from the outside.

The first thing is serial output. Send status messages over a UART to a terminal, ideally lightweight and buffered so it doesn't disturb timing. That's printf debugging, and it works on almost anything. If the UART isn't free or timing is tight, I toggle GPIO pins at key points, like the start and end of an ISR, and watch them on an oscilloscope or logic analyzer. That gives me nanosecond-level timing with almost no overhead. For buses like SPI or I2C, a logic analyzer with a protocol decoder shows exactly what the chip sent. Even an LED can show which state the program reached.

Beyond that, I'd keep a small log in RAM, like a ring buffer of event codes, and dump it later, and I'd write a fault handler that saves the registers when something goes wrong. I'd also run as much logic as possible on the PC as unit tests, and use a simulator for the rest.

And I'd consider getting a debugger anyway: a cheap probe costs about the price of a lunch, and some dev boards turn into one. A Raspberry Pi Pico can run open-source probe firmware, for example. The point is to pick the least intrusive method that answers the question."
:::

::: technical
**Ranked toolbox.**

| Method | Needs | Intrusiveness | Best for |
|---|---|---|---|
| LEDs / GPIO state | 1 pin | negligible | "did we reach here" |
| GPIO toggle + scope/LA | 1 pin + instrument | negligible (2-5 cycles) | timing, ISR duration |
| UART printf | 1 TX pin + terminal | high if blocking | state, values |
| Binary ring-buffer log in RAM | RAM | very low | long traces, read at the end |
| Logic analyzer on buses | probes | none | SPI/I2C/UART protocol bugs |
| Fault handler dump | some RAM/flash | none until fault | crashes |
| Host-side unit tests | build setup | n/a | algorithm bugs |
| Simulator/emulator (QEMU, vendor sim) | tool support | n/a | logic, not timing |
| Bootloader (UART/USB DFU) | bootloader in flash | n/a | programming without probe |

**Cost of UART printf.** At 115200 baud, 8N1, each character takes $10/115200 = 86.8\ \mu s$. A line like `T=23.5\r\n` (8 characters including CR and LF) takes about 0.69 ms if blocking. Use interrupt- or DMA-driven buffered output, or log binary codes (1-2 bytes per event) and decode on the PC.

**Cheap real debugger options.** Many dev boards have an on-board probe (ST-Link, CMSIS-DAP, J-Link OB). Open-source firmware can turn a spare MCU board (for example a Raspberry Pi Pico running the "debugprobe" firmware) into a CMSIS-DAP SWD probe; Black Magic Probe is another open design. Boards without a header can be reached with spring-pin (Tag-Connect) connectors.

**Fault handler.** In the hard-fault handler, copy stacked registers (PC, LR, xPSR) and fault status registers to retained RAM, then reset; read them after reboot over UART.
:::

::: short
"Without a hardware debugger I rely on observability from the outside: UART or buffered printf logging, GPIO toggles measured on a scope or logic analyzer for timing, LEDs for state, and a logic analyzer for buses. I also log events to a RAM ring buffer, save registers in a fault handler, and test algorithms on the PC. I'd pick the least intrusive method, and consider a cheap probe, since SWD adapters are inexpensive."
:::

::: long
"If there's no hardware debugger, I switch from controlling the chip to observing it, and I use a ladder of techniques from cheapest to most informative.

The simplest is output pins. I toggle a GPIO or light an LED at key points, which tells me which state the code reached, and it costs a couple of CPU cycles. With a scope or logic analyzer on that pin I can also measure timing precisely: for example, set the pin high on entering an interrupt and low on exit, and the pulse width is the ISR duration.

Next is serial logging. A UART printf gives me values and messages on a terminal. I have to be careful because at 115200 baud each character takes about 87 microseconds, so a 20-character line is nearly 2 milliseconds. In time-critical code I'd buffer the output and send it from a low-priority task or DMA, or log short binary event codes into a RAM ring buffer and dump it afterward.

For communication problems, a logic analyzer with a decoder on the SPI or I2C lines shows exactly what went over the wire, independent of my firmware.

For crashes, I install a fault handler that saves the stacked PC and the fault status registers somewhere that survives reset, and print them on the next boot. That gives me a post-mortem.

I also shift work off the target: I keep algorithms hardware-independent and run unit tests on the PC, where I have a full debugger, and I can use a simulator or emulator for the logic.

Finally, I'd ask whether a debugger is really unavailable. A probe costs very little, many dev boards include one, and open-source firmware can turn a spare board into one. Reflashing is also solvable without it, through a UART or USB bootloader."
:::

::: terms
- **printf debugging**: tracing program state by printing messages.
- **Ring buffer**: fixed-size circular log that overwrites oldest data.
- **Logic analyzer**: instrument capturing many digital channels over time.
- **Bootloader / DFU**: resident code that reprograms flash over a communication interface.
- **Semihosting**: debugger-provided I/O (needs a debugger, so not an option here).
- **Fault handler**: exception routine that records state on a crash.
- **Retained RAM**: memory that survives a soft reset.
- **Emulator / simulator**: software model of the CPU or board.
:::

::: exceptional
**An average answer**: "Use printf over serial and LEDs."

**An exceptional answer**:
- Ranks methods by intrusiveness and quantifies the cost of printf (87 µs per character at 115200).
- Uses GPIO toggles with a scope to measure ISR timing non-intrusively.
- Brings up binary RAM logs, fault handlers saving registers, and logic-analyzer protocol decoding.
- Moves logic to host-side unit tests and simulation.
- Mentions practical alternatives: on-board probes, DIY probes, bootloaders for flashing.
- Recognises limits: no breakpoints means more design for observability (asserts, counters, status registers).
:::

::: mistakes
- **Printing from an ISR over a blocking UART**, which breaks real-time behaviour or deadlocks.
- **Long, human-readable logs in tight loops**; the log itself becomes the bug.
- **Forgetting to flush or wait** so the last message before a crash never appears.
- **Using the LED for everything** and missing intermittent timing issues; no history to look at.
- **Leaving debug code enabled in the release build**: wasted flash, time and security exposure. Use compile-time flags.
- **Assuming no debugger means no flashing.** A UART/USB bootloader or DFU mode can program the part.
- **Not confirming the UART baud rate and clock**; garbage output often means a wrong clock, which is itself a diagnosis ([[q0834]]).
:::

::: deep
## Making the system observable

Without breakpoints, observability must be designed in. The principle: record **what happened and when** cheaply, and look at it later.

### Level 0: one bit of information (LED or GPIO)

A single pin can encode a lot over time. Patterns: toggle at the top of each loop (the frequency tells you the loop rate and whether it is stuck); pulse high during a critical region; blink codes for error states (1 long + 3 short = sensor failure). A scope on the pin shows frequency, duty cycle and jitter.

### Level 1: GPIO timing with an instrument

Measure an ISR: set a pin at entry, clear at exit. Capture with infinite persistence, and read the maximum width.

Worked example. An ISR is expected to take 20 µs. On the scope the pulses are normally 18-22 µs, but occasionally 140 µs. That tells you: (a) the ISR is sometimes long, (b) by how much, and (c) with a second channel on the input signal, whether the long ones correlate with an event. If the interrupt rate is 10 kHz (period 100 µs), a 140 µs ISR means the next interrupt is missed or delayed: a real bug found in a minute.

### Level 2: UART logging, done right

Naive blocking printf at 115200 baud:

$$t_{char} = \frac{10\ \text{bits}}{115200\ \text{bit/s}} = 86.8\ \mu\text{s}.$$

| Message | Chars | Blocking time |
|---|---|---|
| `OK\r\n` | 4 | 0.35 ms |
| `T=23.5\r\n` | 8 | 0.69 ms |
| `adc=2048 v=1.650 state=3\r\n` | 27 | 2.34 ms |

Compare with a 1 kHz control loop that has a 1 ms period: one message already blows the deadline. Improvements:

1. **Buffered, interrupt-driven TX.** `printf` writes into a ring buffer (a few CPU cycles per character); the UART TX interrupt drains it. Cost per message becomes microseconds, but the buffer can overflow if you log faster than the line can drain: 115200 baud = 11.5 kB/s maximum.
2. **Faster baud rate.** 921600 baud gives 92 kB/s and 10.9 µs per character (check your UART and USB-serial adapter support it).
3. **Binary logging.** Write a 1-byte event ID and a 2-byte value, 3 bytes instead of 27. Decode on the PC with a script using a table.
4. **DMA output** so the CPU does not wait at all.

### Level 3: RAM ring buffer and post-mortem

```c
typedef struct { uint32_t t; uint8_t id; uint16_t val; } log_t;
static log_t ring[256];
static volatile uint16_t head;
static inline void log_ev(uint8_t id, uint16_t v) {
    uint16_t h = head++ & 255;
    ring[h] = (log_t){ DWT_CYCCNT, id, v };
}
```
This takes about 10-20 cycles. 256 entries x 8 bytes = 2 KB of RAM. When something fails (assert, fault, watchdog about to reset), dump the buffer over UART or save to retained RAM. The buffer always holds the last 256 events leading up to the failure, a flight recorder. Timestamps come from a cycle counter or a timer.

### Level 4: crash capture

A hard-fault handler written to save the stacked frame:

```c
void HardFault_Handler(void) {
    __asm volatile("tst lr, #4; ite eq; mrseq r0, msp; mrsne r0, psp;"
                   "b hardfault_c");
}
void hardfault_c(uint32_t *frame) {
    saved.pc  = frame[6];  saved.lr = frame[5];
    saved.cfsr = SCB->CFSR; saved.bfar = SCB->BFAR;
    NVIC_SystemReset();     // after boot, print `saved` if its magic is set
}
```
`frame[6]` is the stacked PC on a Cortex-M exception frame (R0, R1, R2, R3, R12, LR, PC, xPSR), so the PC is word 6. Use the map file or `arm-none-eabi-addr2line` to convert the PC to a source line. The saved data must live in a RAM section that startup code does not clear (`.noinit`).

> [!UNCERTAIN]
> Exact register names, intrinsics and the `.noinit` mechanism differ by toolchain and core (M0 vs M3/M4/M7, RISC-V and others have different exception frames).

### Level 5: move work off the target

Write algorithms (filters, protocol parsers, state machines) as portable C with no register access, and compile them on the PC with unit tests. Hardware-dependent code stays thin. Bugs in the logic are then found with a full debugger, sanitizers and a test framework. Emulators (QEMU supports several Cortex-M boards; vendor simulators and Renode exist) let you run firmware images with some peripherals modelled. These do not reproduce analog behaviour or tight timing.

## Programming without a debug probe

You can still load firmware:
- **UART bootloader** in ROM (many MCUs have one; entered via a boot pin) or a custom one in flash.
- **USB DFU** or mass-storage bootloader (UF2).
- **OTA updates** over wireless.
- **A spare MCU board as a programmer.** Some boards expose SWD of a target through their own on-board probe; others can run open-source probe firmware to act as one.

## Is a debugger really unavailable?

Often the best answer is to get one. A CMSIS-DAP-class probe costs on the order of a few to tens of USD, and Tag-Connect or pogo-pin connectors let you debug a board with no header fitted. The cost of an hour of engineer time often exceeds the cost of the probe. The design lesson: always route SWD pins and add test points, even if you plan to ship without a header.

::: assumptions
- I assume the question means "no **on-chip debug probe/connection**" rather than "no IDE" at all; if the IDE lacks a debugger but the chip has SWD, you can use command-line GDB with OpenOCD.
- The **UART or at least one GPIO** is available; if not, even the LED tricks need a pin.
- **Timing figures** use 115200 baud 8N1 for illustration.
- Some tiny MCUs (such as 6-pin parts) only offer one-wire programming/debug interfaces; the methods here still apply.
- Fault handler code is for **Cortex-M**; other cores differ.
- **Security**: removing debug interfaces on shipping products is a reason you may have none in the field.

::: followups
### What do you do if the UART is already used by the application?
Use a spare GPIO for a bit-banged transmit-only debug output (software UART, timing-sensitive), a different UART or LPUART/USB CDC, or SWO if available. Or switch to the GPIO-toggle method, or a RAM log you dump on demand. A single pin driven by a timer-compare interrupt can emit bits at 115200 baud with low CPU load.

### How do you find an intermittent crash with no debugger?
Make it leave evidence. Install a fault handler and watchdog handler that save the stacked PC, LR and fault registers (and the last N entries from a ring log) into retained RAM or flash, then reset and report on the next boot. After a few crashes, the PC values cluster at the failing function.

### How do you measure how long a function takes without a debugger?
Toggle a GPIO around it and measure on a scope, or read a free-running cycle counter (DWT_CYCCNT on Cortex-M3/M4/M7) before and after and log the difference. At 48 MHz one cycle is 20.8 ns, so a count of 2400 cycles is 50 µs.

### How would you get firmware onto a board that has no debug header?
Use the MCU's built-in ROM bootloader over UART or USB (pull the boot pin), or a pogo-pin/Tag-Connect cable to the SWD pads, or an already-loaded custom bootloader. Plan for this at PCB design time with test pads.

### Harder: printf makes the bug disappear. What does that tell you, and what next?
It suggests a timing-dependent bug (a race, an uninitialised variable, or a missed interrupt) or memory layout change (the extra code or stack usage moved things). Replace printf with the least intrusive instrumentation, such as a RAM event log with cycle-counter timestamps and GPIO markers, and look at the ordering of events. Also look for stack overflows, since printf uses a lot of stack and could also reveal a nearly-full stack.
:::
