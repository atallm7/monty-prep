::: testing
Whether you can turn a raw integer from `analogRead()` into a physical voltage without hesitating, and whether you know the conventions hiding behind the formula. The core is $V = V_{ref-} + \text{code}\cdot(V_{ref+}-V_{ref-})/2^N$. The interviewer is looking for four things: you ask what the reference (the "ADC supply voltages") actually is, you know the resolution $N$, you mention the $2^N$ versus $2^N-1$ ambiguity, and you remember to undo any divider or gain in front of the pin to get back to the real signal.
:::

::: why
This is the most common ADC task in firmware: read a number, report volts, amps, degrees or percent. Getting the scale wrong by a factor of 4096/4095 is minor, but forgetting that the reference is a noisy 3.3 V rail, or forgetting the 3:1 divider on a battery sense line, gives readings that are wrong by tens of percent. It also tests basic calculation fluency with a worked number in front of someone, which is exactly how this question is asked.
:::

::: concepts
- **LSB size**: $V_{LSB}=(V_{ref+}-V_{ref-})/2^N$. See [[q0808]].
- **Reference range**: for most MCUs $V_{ref-}$ is analog ground and $V_{ref+}$ is the analog supply or a reference pin.
- **Ratiometric measurement**: the code is a ratio to $V_{ref}$, so reference error becomes reading error.
- **Voltage divider**: the voltage at the pin is a scaled version of the real signal. See [[q0008]].
- **Number formats**: unsigned, offset binary and two's complement for bipolar converters.
:::

::: answer
"I'd start by pinning down three things: how many bits the ADC has, what the low and high reference voltages are, and whether the code is unsigned. Say it's a 12-bit ADC with the reference at the 3.3 V supply and ground as the low end, and I read 3000.

Each code is worth the full range divided by $2^N$, so 3.3 over 4096, which is 0.806 millivolts. The voltage is the code times that: 3000 times 0.806 mV is 2.417 V. In general it's $V = V_{low} + \text{code}\cdot(V_{high}-V_{low})/2^N$, so if the ADC's reference range were 0.5 to 3.3 V, I'd add the 0.5 V offset and scale by 2.8 V instead.

Two things I'd flag. Some datasheets divide by $2^N-1$ so that the top code reads exactly $V_{ref}$; the difference is 0.024%, so about 0.6 mV here. And that's the voltage at the pin. If there's a divider in front, say 200 k over 100 k to measure a battery, I multiply back by 3. Also, if the reference is just the supply, the reading is only as accurate as that supply, so I'd calibrate it or use an internal reference."
:::

::: technical
**General conversion (unsigned, single-ended).**

$$V_{in}=V_{ref-}+\text{code}\cdot\frac{V_{ref+}-V_{ref-}}{2^N}$$

Common case $V_{ref-}=0$: $V_{in}=\text{code}\cdot V_{ref}/2^N$.

**Bin centre.** A code $k$ represents inputs from $kV_{LSB}$ to $(k+1)V_{LSB}$. The unbiased estimate is $(k+\tfrac12)V_{LSB}$, which removes a systematic half-LSB bias. For 12 bits and 3.3 V that is 0.4 mV, usually below the noise.

**The $2^N-1$ convention.** Some libraries use $V=\text{code}\cdot V_{ref}/(2^N-1)$ so full-scale code maps to exactly $V_{ref}$. The two differ by a factor $2^N/(2^N-1)$, 0.0244% at 12 bits, up to 0.8 mV at the top. Neither is "wrong"; check what your datasheet's transfer function says, and note real gain error is typically larger than this.

**Bipolar and differential.** Two's complement 16-bit with $\pm V_{ref}$: $V=\text{code}\cdot V_{ref}/2^{15}$ with code as a signed integer. Offset binary: $V=(\text{code}-2^{N-1})\cdot V_{ref}/2^{N-1}$.

**Undoing front-end scaling.** For a divider $R_1$ (top), $R_2$ (bottom): $V_{sig}=V_{pin}\frac{R_1+R_2}{R_2}$. For a current-sense chain: $I=V_{pin}/(G\,R_{sense})$ after removing any offset.

**Worked numbers.**

| Case | Code | Result |
|---|---|---|
| 12-bit, 3.3 V, divide by 4096 | 3000 | 2.4170 V |
| same, divide by 4095 | 3000 | 2.4176 V |
| 12-bit, $V_{ref-}$=0.5 V, $V_{ref+}$=3.3 V | 1000 | $0.5+1000\cdot2.8/4096=1.1836$ V |
| 16-bit two's complement, ±2.5 V | −12000 | $-12000\cdot2.5/32768=-0.9155$ V |
| 12-bit, 3.3 V, 3:1 divider | 1850 | pin 1.4905 V, battery 4.471 V |

> [!UNCERTAIN]
> Whether a given MCU's datasheet defines full scale as $V_{ref}$ or $V_{ref}\cdot(2^N-1)/2^N$, and whether the reference is the supply or a separate pin, varies by part. Always read the transfer-function section.

::: long
"First I'd confirm what the converter is: the resolution N, the low and high reference voltages, and whether the output is unsigned or signed. Those are what the question means by the ADC supply voltages, since on most microcontrollers the reference is tied to the analog supply and ground.

The formula is $V_{in} = V_{low} + \text{code}\cdot(V_{high}-V_{low})/2^N$. Example: 12 bits, 0 to 3.3 V, reading 3000. The LSB is 3.3 over 4096, which is 0.806 mV, so the voltage is 2.417 V. That's half of full scale at code 2048, which gives 1.65 V, a handy sanity check.

If the reference range doesn't start at zero, say 0.5 V to 3.3 V, I add the 0.5 V and scale by 2.8 V: code 1000 gives 1.18 V. For a bipolar two's complement converter, I treat the code as signed and scale by the reference over $2^{N-1}$.

There are some subtleties. Datasheets sometimes use $2^N-1$ in the denominator so the top code equals the reference exactly. At 12 bits the difference is about 0.6 mV at code 3000, below typical noise but worth knowing. The true center of a bin is code plus a half LSB.

Then there's the physical meaning. This is the voltage at the pin. If I put a 200 k and 100 k divider ahead of it to measure a battery, I multiply by 3, so 1850 counts is 1.49 V at the pin and 4.47 V at the battery.

Finally, accuracy: the ratio is only as good as the reference. If it's the supply and the supply is 3.0 V instead of 3.3 V, every reading is 10% high unless I measure the supply with an internal reference and correct."
:::

::: terms
- **Code / counts**: the integer the ADC returns.
- **LSB (volts per count)**: $(V_{ref+}-V_{ref-})/2^N$.
- **$V_{ref+}$, $V_{ref-}$**: the top and bottom of the conversion range.
- **Full scale**: the span $V_{ref+}-V_{ref-}$; the top code is one LSB below it in the ideal case.
- **Ratiometric**: output depends on the ratio $V_{in}/V_{ref}$, so reference drift cancels if the signal derives from the same reference.
- **Two's complement / offset binary**: encodings for signed ADC outputs.
- **Gain / offset error**: deviations of the real transfer line from the ideal.
:::

::: exceptional
**An average answer** says "code divided by 4096 times 3.3".

**An exceptional answer**:
- Asks or states **N, $V_{ref+}$, $V_{ref-}$** and signedness before computing.
- Gives the general formula with offset, then a **numeric result** with units and a sanity check at mid-scale.
- Mentions the **$2^N$ vs $2^N-1$** convention and quantifies it.
- Brings up **the reference as the accuracy limit** and a fix (internal reference, ratiometric design, calibration).
- Reverses **front-end scaling** (divider, gain) to report the real signal.
- Uses integer math in firmware to avoid float cost, for example millivolts $=\text{code}\cdot3300/4096$ with 32-bit intermediates.
:::

::: mistakes
- **Dividing by 4096 when the code is 10-bit** (or the reverse). Check the resolution setting; many MCUs default differently from what the library assumes.
- **Forgetting the divider.** The pin voltage is not the battery voltage.
- **Assuming $V_{ref}$ is exactly 3.3 V.** A USB-powered board may sit at 3.2 to 3.4 V, a 3% error.
- **Integer overflow.** In 16-bit C, $3000\cdot3300$ overflows. Use `uint32_t`.
- **Treating signed data as unsigned.** A two's complement −12000 read as unsigned is 53536.
- **Reporting more digits than the ADC supports.** 2.41699 V from a 12-bit ADC implies 10 µV resolution when the LSB is 806 µV ([[q0819]]).
:::

::: deep
## The formula from first principles

An ideal $N$-bit ADC splits its range into $2^N$ equal bins. Code $k$ means the input was in $[k\,V_{LSB},(k+1)V_{LSB})$ above the bottom reference. So the reverse mapping is just "code times bin width", plus the bottom reference:

$$V_{in}\approx V_{ref-}+k\,V_{LSB},\qquad V_{LSB}=\frac{V_{ref+}-V_{ref-}}{2^N}$$

The reading is a ratio to the reference, which is the key physical point: the converter never "knows" volts. If $V_{ref+}$ drops 10%, the same input voltage gives a code 11% larger, and your firmware, which assumed 3.3 V, reports a voltage that is too high.

## Worked example: 12-bit, 3.3 V

Reading: 3000.
$$V=3000\cdot\frac{3.3}{4096}=2.4170\text{ V}$$
Using the bin centre: $3000.5\cdot3.3/4096=2.4174$ V. Using 4095: 2.4176 V. All three sit within 0.6 mV of each other, under one LSB, so any is acceptable unless the spec says otherwise.

Sanity checks: code 0 is 0 V, code 2048 is 1.65 V, code 4095 is 3.2992 V (not 3.3). If your conversion gives 3.3 V at 4095 you are using the $2^N-1$ convention.

## Worked example: offset reference

Some converters (and external ADCs) let $V_{ref-}$ differ from ground. With $V_{ref-}=0.5$ V and $V_{ref+}=3.3$ V, the span is 2.8 V and $V_{LSB}=2.8/4096=0.684$ mV. Code 1000 gives $0.5+1000\cdot0.684\text{ mV}=1.1836$ V. Any input below 0.5 V clips at code 0.

## Worked example: battery through a divider

Battery sense with $R_1=200$ kΩ (top) and $R_2=100$ kΩ (bottom): the pin sees one third of the battery voltage ([[q0008]]). Reading 1850 on a 12-bit, 3.3 V ADC:

$$V_{pin}=1850\cdot\frac{3.3}{4096}=1.4905\text{ V},\qquad V_{bat}=3\cdot1.4905=4.471\text{ V}$$

A fully charged Li-ion cell is 4.2 V, so 4.47 V should make you suspicious: either the supply isn't 3.3 V, the resistors are off, or this is a 2-cell pack. The check against physical expectation is part of the job.

## Signed converters

For a differential 16-bit ADC with $\pm2.5$ V full scale and two's complement output, $V_{LSB}=2.5/32768=76.3$ µV. A raw code of 0xD120 is $-12000$ as a signed 16-bit value, so $V=-12000\cdot76.3\text{ µV}=-0.9155$ V. Casting to a signed type before multiplying is the entire trick; otherwise you read 53536 and report +4.08 V.

## Doing it in firmware

```c
// 12-bit, 3.3 V reference, result in millivolts, integer math only
uint32_t mv = ((uint32_t)code * 3300u + 2048u) >> 12;   // rounds to nearest
// battery through a 3:1 divider
uint32_t vbat_mv = mv * 3u;
```
Shifting by 12 replaces division by 4096, and adding 2048 before the shift rounds to the nearest millivolt instead of truncating.

## When the reference isn't 3.3 V

If $V_{ref}$ is the supply, measure it. Many MCUs have an internal fixed reference (around 1.2 V on some families; the value and its factory-calibrated code differ per part). Reading it gives $V_{DDA}=V_{int}\cdot2^N/\text{code}_{int}$, which you then use in the formula. Example: if the internal 1.2 V reads 1638 counts on a 12-bit ADC, the supply is $1.2\cdot4096/1638=3.0$ V. A reading of 1850 then means $1850\cdot3.0/4096=1.355$ V rather than the 1.490 V you'd compute assuming 3.3 V, a 10% difference.

## How good is the number you just computed?

The conversion gives a nominal voltage. The true uncertainty comes from four places, and you should be able to name them when asked "how accurate is that 2.417 V?":

1. **Quantization**: ±0.4 mV (half an LSB) at 12 bits and 3.3 V.
2. **Noise**: a few LSB of rms noise is normal on a microcontroller ADC, so a single sample is good to maybe ±1 to 3 mV. Averaging 16 samples cuts uncorrelated noise by 4.
3. **Offset and gain error**: datasheets quote these in LSB or percent; several LSB of offset and 0.1 to 1% gain error are common. A two-point calibration removes the repeatable part.
4. **Reference**: a 1% supply error is 33 mV, about 41 LSB, which usually dwarfs all of the above.

So a firmware routine that prints "2.41699 V" is claiming a precision the hardware does not have. Round to what the error budget supports ([[q0819]]), and if accuracy matters more than cost, add a precision reference, which turns the dominant error into a 0.05 to 0.1% effect.

## Worked example: a two-point calibration, step by step

Nominal conversion assumes ideal gain and zero offset. Real converters have both errors, and a two-point calibration measures and removes them. Feed the ADC from a bench supply at two precisely known voltages, read each with a multimeter, and record the raw codes. Suppose at 0.500 V the 12-bit ADC (3.3 V reference) returns code 627, and at 3.000 V it returns 3711. The ideal codes would be $0.5/3.3\times4096=621$ and $3.0/3.3\times4096=3724$, so this converter has a few counts of offset and a gain slightly under unity.

The line through the two points is $V=g\,k+b$ with

$$g=\frac{3.000-0.500}{3711-627}=0.81064\ \text{mV/count},\qquad b=0.500-627\times0.00081064=-8.27\ \text{mV}.$$

The nominal LSB was $3.3/4096=0.80566$ mV, so the real gain is 0.6% above the nominal step width and the offset is $-8.3$ mV, about 10 counts. Apply it to the earlier reading of 3000:

$$V=0.81064\ \text{mV}\times3000-8.27\ \text{mV}=2.4236\ \text{V}$$

compared with 2.4170 V from the uncalibrated formula, a 6.6 mV difference, equal to about 8 LSB. That is a bigger error than the quantization step and illustrates why "volts = code × Vref / 4096" is only a starting point. The two readings used to calibrate should be near the ends of the range of interest (not at 0 V and full scale, where the converter clips and the ends are the least linear).

In firmware, store $g$ and $b$ in non-volatile memory as integers, for example gain in nanovolts per count, so the run-time cost is one multiply and one add: `uint32_t uv = code * gain_nv / 1000 + offset_uv;` with attention to overflow (next section).

## Integer overflow and rounding in the fixed-point formula

The fixed-point expression from earlier, `(code * 3300 + 2048) >> 12`, is safe for 12-bit codes: the largest product is $4095\times3300=13{,}513{,}500$, which fits easily in 32 bits but would overflow a 16-bit `unsigned`, whose limit is 65,535. On an 8-bit or 16-bit MCU where `int` is 16 bits, an unadorned `code * 3300` silently wraps, and the symptom is a voltage that looks right at low codes and garbage above code 19. Cast to `uint32_t` first. For a 16-bit ADC the product reaches $65{,}535\times3{,}300=216{,}265{,}500$, still under $2^{32}=4{,}294{,}967{,}296$, but a result in microvolts ($\times3{,}300{,}000$) would exceed 32 bits and needs a 64-bit intermediate.

Rounding matters less than people expect. Truncation gives an average bias of half a millivolt downward, rounding to nearest removes it, and neither is large compared with the 0.806 mV LSB and the noise. What matters more is not compounding steps: convert to millivolts once from the code, not to a rounded intermediate that is then scaled again.

## Oversampling arithmetic: how many extra bits do you really get?

Summing 16 consecutive 12-bit readings gives a 16-bit-range number (maximum $16\times4095=65{,}520$). Shifting it right by 2 produces a 14-bit result, and the common rule says 16 samples buy 2 extra bits if the noise is roughly white and at least about 1 LSB rms, because the averaged noise falls by $\sqrt{16}=4$. For example, if the single-sample noise is 3 counts rms (2.4 mV), averaging 16 samples reduces it to $3/4=0.75$ counts, or 0.60 mV. Convert the 16-sample sum with `(sum * 3300 + 32768) >> 16` to get millivolts (the product of 65,520 and 3,300 is 216,216,000, which fits in 32 bits).

Two caveats are worth saying out loud. Oversampling reduces random noise but does not remove offset, gain error or reference drift, so the extra bits are resolution, not accuracy. And if the input is perfectly quiet (less than about 0.5 LSB of noise), averaging returns the same code 16 times and gains nothing; adding a small amount of dither noise is how designers make oversampling work on very clean signals.

## Using the internal reference to correct the supply

The page already describes measuring the internal reference to infer $V_{DDA}$. Here is a fully worked version with a factory calibration word, as some families provide. Suppose the device stores a value of 1489 measured at a 3.3 V supply (this matches $1.2/3.3\times4096=1489.5$ for a 1.2 V internal reference). Today the ADC reads the internal reference as 1638. Since the reference voltage is constant, the supply is

$$V_{DDA}=3.3\ \text{V}\times\frac{1489}{1638}=3.000\ \text{V}.$$

Then convert the pin: $1850\times3.000/4096=1.355$ V. This approach turns a supply-referenced converter into a reasonably accurate one, limited by the internal reference's own tolerance and temperature drift, typically in the range of 0.5% to a few percent depending on the part; read the datasheet for the exact figure.

> [!UNCERTAIN]
> Whether a factory calibration word exists, its test voltage (commonly 3.3 V, sometimes 3.0 V), and the internal reference's nominal value and accuracy are vendor- and part-specific. The numbers here (1489 at 3.3 V and a 1.2 V reference) illustrate the method.

## Common real-hardware errors in the reading itself

- **Source impedance.** If the source resistance is high relative to the sample time, the sampling capacitor does not settle and readings sag. For a 12-bit conversion the source must settle to within half an LSB, which takes roughly $\ln(2^{13})\approx9$ time constants of $R_sC_S$.
- **Reference noise.** Switching supply ripple on the reference appears directly in the readings, so a 20 mV ripple on a 3.3 V reference modulates every reading by $20/3300=0.6\%$, which is 20 mV at full scale and about 25 counts.
- **Ground bounce.** A shared ground that carries digital return currents shifts the apparent input by the voltage drop along the trace.
- **Temperature.** Offset and gain drift with temperature, and the datasheet specifies it in ppm per kelvin or LSB over the range. A calibration done at 25 °C is not exact at 80 °C.
- **Channel crosstalk.** After switching a multiplexer from a high to a low voltage, the first sample may carry some memory of the previous one; discard the first conversion or add settling time.

## How to verify the conversion on the bench

1. **Apply a known voltage** from a bench supply and read it with a meter whose accuracy is at least 10 times better than the ADC. Compare the firmware voltage with the meter at five or more points across the range. Plot error versus input; a straight tilted line means gain error, a vertical shift means offset, a wavy line means nonlinearity.
2. **Test the ends.** Apply exactly 0 V and a value just under full scale to confirm that code 0 and the maximum code 4095 occur as expected, and that an input above the reference clips rather than wraps.
3. **Measure the noise.** Short the input (or hold it at a clean DC value), log a thousand samples, and compute the standard deviation in counts. If it is much larger than a few counts, look at the reference decoupling and the analog layout.
4. **Vary the supply** by plus and minus 5% with the signal source ratiometric (derived from the same rail) and confirm whether your reported voltage tracks the supply, which would reveal a ratiometric error, or stays constant.
5. **Check types in firmware** by feeding the maximum code through the conversion in a unit test on the target compiler, to catch the overflow described above.

- **Battery voltage monitoring** through a divider, reported as percent charge or millivolts.
- **Thermistor temperature**: code to volts, volts to resistance, resistance to temperature ([[q0008]]).
- **Current sensing**: code to volts, then divide by gain and sense resistance ([[q0446]]).
- **Potentiometer and joystick positions**: code as a fraction of full scale, no volts needed (ratiometric).
- **Supply self-measurement** using the internal reference to compute VDDA.
- **Production calibration**: store offset and gain constants so reported millivolts match a reference meter.

::: assumptions
- Ideal ADC: no offset, gain error, INL or noise. Real parts can be off by several LSB, so the formula gives the nominal value ([[q0819]]).
- Unsigned, single-ended unless stated; $V_{ref-}$ is ground unless the part has a separate pin.
- $V_{ref}$ is known. If it's the supply, the answer's accuracy is the supply's accuracy.
- "ADC supply voltages" is read as the reference range $V_{ref+}$ and $V_{ref-}$, usually AVDD and AGND. If the interviewer means a part where the reference differs from the supply, use the reference pin.
- Resolution is stated or known. If it isn't, ask. A "12-bit" ADC may return left-justified or oversampled data.
:::

::: followups
### Reading is 512 on a 10-bit ADC with a 5 V reference. What voltage?
$512\cdot5/1024=2.5$ V, half of full scale. LSB is 4.88 mV.

### What if the reference is only 3.0 V because the battery sagged, but firmware assumes 3.3 V?
Every reading is high by 10%. A true 1.35 V input gives code $1.35/3.0\cdot4096=1843$, which firmware reports as $1843\cdot3.3/4096=1.485$ V. Fix: measure the supply with the internal reference and rescale, or use a separate precise reference.

### How would you convert to millivolts without floating point?
$\text{mV}=(\text{code}\cdot3300+2048)\gg12$ with a 32-bit intermediate. The max product $4095\cdot3300=13.5$ million fits easily in 32 bits and overflows 16 bits.

### How do you convert if the ADC is differential with two's complement output?
Treat the code as a signed integer and multiply by $V_{ref}/2^{N-1}$. For 16 bits and ±2.5 V, code −12000 is −0.9155 V. The sign bit is the MSB, so a cast to the signed type must happen first.

### Harder: your readings are 1.5% too high at one end of the range but exact at the other. What is it?
A gain error: either the reference voltage differs from what the firmware assumes, or a divider resistor is off. An offset error would move all readings by the same amount. Two-point calibration (measure two known voltages, fit $V=a\cdot\text{code}+b$) removes both.
:::

::: interpretations
"Given the value and the ADC supply voltages" most likely means the reading plus the ADC's reference range, $V_{ref+}$ and $V_{ref-}$ (typically AVDD and AGND on a microcontroller). I've treated "supply voltages" as that range. If the ADC reference is a separate precision pin, use it instead of the supply. The unstated resolution is the other missing piece, so state your assumption (12-bit) or ask.
