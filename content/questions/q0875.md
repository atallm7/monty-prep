::: basics
### In plain words
A computer stores numbers bigger than one byte across several memory locations, one byte per location. Endianness is the rule for which byte goes in the lowest location. Big-endian puts the most significant byte first. Little-endian puts the least significant byte first. Both store the same number, and the order only matters when data moves between systems.

### Picture it
Imagine writing the number 1234 into four numbered mailboxes. One convention puts the biggest place first: 1, 2, 3, 4. The other puts the smallest place first: 4, 3, 2, 1. Same number, different layout. Computers do this with bytes, not digits. The mailbox picture misses one thing: the order of bits inside each byte does not change, because endianness only reorders whole bytes.

### Words you need
- **Byte**: eight bits. Memory is a row of byte-sized boxes.
- **Address**: the number that labels each box in memory.
- **Most significant byte (MSB)**: the byte holding the largest part of the number. See [[q0876]].
- **Big-endian**: the most significant byte is stored at the lowest address.
- **Little-endian**: the least significant byte is stored at the lowest address.

### The simplest example
Take the 32-bit value 0x12345678, which is four bytes: 12, 34, 56 and 78 in hexadecimal (base 16, marked by 0x). Store it starting at address 0x1000. Big-endian memory reads 12 34 56 78. Little-endian memory reads 78 56 34 12. Now a sensor sends a 16-bit reading as two bytes, FF then 38, high byte first. Put together correctly, that is 0xFF38, which as a signed number is minus 200. Swap the order by mistake and you get 0x38FF, which is 14,591, a plausible but wrong value. That is the whole idea. The rest of this page covers where it bites and how to write code that never depends on it.
:::

::: testing
Whether you know that endianness is about **byte order in memory (or on a wire)** and not bit order, and whether you can show it with a concrete multi-byte value. The interviewer is also checking that you know where it bites in real hardware work: reading a 16-bit sensor register over I²C/SPI, parsing a packet, sharing memory between two processors, or casting a byte array to a 32-bit integer in C.
:::

::: why
Almost every embedded bug story involves a byte-order mix-up at least once: an IMU that reports 8,448 instead of 33, an MCU and a host disagreeing about a struct, a checksum that is right on one chip and wrong on another. Endianness is simple to define but easy to get wrong in practice, so interviewers use it as a quick test of whether you have ever actually moved data between devices. It pairs naturally with [[q0876]] (MSB/LSB) and [[q0893]] (hex and base conversion).
:::

::: concepts
- **Byte**: eight bits, the smallest addressable unit in nearly all systems. Hex shows one byte as two digits ([[q0893]]).
- **Most/least significant byte**: the byte holding the highest or lowest powers of two ([[q0876]]).
- **Byte-addressable memory**: each address holds one byte, so a 32-bit word occupies four consecutive addresses.
- **Endianness**: which byte of a multi-byte value is stored at the lowest address (big: MSB first; little: LSB first).
- **Wire order versus memory order**: serial protocols specify their own byte order, independent of the CPU.
:::

::: answer

In big-endian, the most significant byte, 0x12, goes at the lowest address, so memory reads 12 34 56 78, which looks the same as how you'd write the number. In little-endian, the least significant byte goes first, so memory reads 78 56 34 12.

Both store exactly the same number. Which one a system uses is basically a convention. x86 is little-endian, ARM cores are normally run little-endian, and RISC-V is little-endian. Network protocols use big-endian, which is why we have functions like htonl to swap.

Where it bites you is at boundaries. If I read a 16-bit sensor value as two bytes over I²C, I need to check the datasheet for which byte comes first and combine them correctly, something like high shifted left eight, OR low. If I cast a byte buffer to a uint32_t pointer in C, I get the machine's endianness, which could be different from the packet format. And note it's byte order, not bit order: within a byte, the MSB is still bit 7 on both."
:::

::: technical
**Definition.** For a $w$-byte value $X=\sum_{i=0}^{w-1} b_i\,256^{i}$, where $b_0$ is the least significant byte:
- **Little-endian**: address $A+i$ holds $b_i$ (LSB at lowest address).
- **Big-endian**: address $A+i$ holds $b_{w-1-i}$ (MSB at lowest address).

**Example.** $X=\texttt{0x12345678}$ stored at address $\texttt{0x1000}$:

| Address | 0x1000 | 0x1001 | 0x1002 | 0x1003 |
|---|---|---|---|---|
| Big-endian | 12 | 34 | 56 | 78 |
| Little-endian | 78 | 56 | 34 | 12 |

**Reassembling a 16-bit register read** (high byte first on the wire, big-endian wire order):
`value = (uint16_t)(buf[0] << 8) | buf[1];` For a signed sensor, cast to `int16_t`. Bytes `0xFF 0x38` give `0xFF38` $=65336-65536=-200$.

**Detecting endianness in C.** Store `uint16_t x = 1;` and read the first byte through a `uint8_t*`; a result of 1 means little-endian. Better practice is to avoid caring: use shifts and masks, which are defined on *values*, not on memory layout.

**Where each is used.** Little-endian: x86/x64, most ARM Cortex-M and Cortex-A deployments, RISC-V. Big-endian: network byte order (TCP/IP headers), many file formats, older SPARC and PowerPC (PowerPC is bi-endian). Several architectures are bi-endian (ARM, MIPS, PowerPC) and can be configured.

**Advantage claims.** Little-endian: the address of a value is the address of its LSB regardless of width, so narrowing a 32-bit to 8-bit is a no-op in memory, and multi-precision arithmetic starts at the low byte. Big-endian: memory dumps and hex read naturally, and comparisons of byte strings sort numerically.
:::

::: short

Little-endian puts the least significant byte first: 78 56 34 12. Same number, different layout. x86, ARM-in-practice and RISC-V are little-endian, network order is big-endian. It matters whenever bytes cross a boundary, like sensor registers, packets or shared memory, and it's about bytes, not bits."

::: long
"Endianness is the byte order of a multi-byte number in memory. Say I have the 32-bit value 0x12345678 at address 0x1000. A big-endian machine stores the most significant byte first: 0x12 at 0x1000, then 34, 56, 78. A little-endian machine stores the least significant byte first, so 0x78 at 0x1000 and 0x12 at 0x1003. The number is identical either way; only the layout in memory differs.

In terms of who uses what: x86 and RISC-V are little-endian, and ARM is bi-endian but virtually always run little-endian. Network protocols are big-endian, which is why TCP/IP code uses htons and htonl to convert. A few older processors like classic SPARC and PowerPC were big-endian.

The practical rule is that endianness only matters when bytes cross a boundary. If I'm reading a 16-bit accelerometer reading over I²C, the datasheet tells me whether the high byte or the low byte is at the lower register address, and I combine them with a shift and an OR. Get it backwards and a reading of 33 turns into 8,448. If I'm sending a struct between an MCU and a PC, or memcpy-ing a byte buffer into a uint32_t, I'm relying on both sides agreeing, plus struct padding. The safe approach is to define the wire format explicitly and build values with shifts and masks, which don't depend on the host.

The last thing I'd say is to keep it separate from bit order. Endianness is about bytes. Within a byte, bit 7 is the MSB on either system. Serial protocols like UART send LSB first, which is an unrelated bit-order choice."
:::

::: terms
- **Endianness**: byte ordering of multi-byte values in memory or on a link.
- **Big-endian (BE)**: MSB at the lowest address.
- **Little-endian (LE)**: LSB at the lowest address.
- **Network byte order**: big-endian, used by TCP/IP headers.
- **Byte swap (bswap, htonl, ntohl)**: operation or function that reverses byte order.
- **Bi-endian**: hardware that can be configured for either order.
- **MSB/LSB**: most/least significant bit or byte ([[q0876]]).
- **Word**: the natural data width of a processor (8/16/32/64 bits).
:::

::: exceptional
**An average answer** gives the definition and says x86 is little-endian.

**An exceptional answer**:
- Shows 0x12345678 laid out byte by byte for both orders, unprompted.
- Separates **byte order** from **bit order** and from **wire order**, and mentions that UART sends LSB first regardless of endianness.
- Gives the real failure case: reading a 16-bit register over I²C, with the 33 versus 8,448 example, or casting a buffer to `uint32_t*`.
- Recommends the portable fix: shifts and masks, explicit wire formats, `htonl`, never struct overlays.
- Mentions alignment/padding and `memcpy` as related traps, and knows some parts are bi-endian.
:::

::: mistakes
- **Confusing endianness with bit order.** Endianness reorders *bytes*; bit 7 of a byte is still the MSB in both. Bit-banged serial order (UART LSB-first, SPI usually MSB-first) is a separate setting.
- **Saying "big-endian is more significant first so it is better".** Neither is better; each is a convention with minor advantages.
- **Casting a `uint8_t` buffer to `uint32_t*`.** The result depends on host endianness, can break alignment rules, and violates strict aliasing. Use shifts or `memcpy` plus a swap.
- **Assuming a sensor's byte order matches the MCU.** Registers are defined by the sensor datasheet. Some devices put the high byte at the lower address, others the low byte. Read the datasheet.
- **Believing endianness affects arithmetic.** Inside the CPU a register is just a number. Order only matters in memory or on a link.
:::

::: deep
## What is really being decided

Memory is a row of byte-sized boxes with increasing addresses. A 32-bit number does not fit in one box, so it has to be split across four, and somebody has to decide which byte goes where. There is no physics behind the choice. It is a layout convention, and both options were picked by different hardware families early on.

The number is a positional sum. In hex, 0x12345678 means
$$0x12\cdot256^3+0x34\cdot256^2+0x56\cdot256+0x78 = 305{,}419{,}896.$$
Each pair of hex digits is one byte ([[q0893]]), so byte values are $b_3=0x12$ (most significant), $b_2=0x34$, $b_1=0x56$, $b_0=0x78$ (least significant).

## Reading a sensor register, the classic case

Suppose an accelerometer returns its X reading in two 8-bit registers: `0x3B` (high byte) and `0x3C` (low byte), with the datasheet saying the value is a signed 16-bit two's-complement number. You read the two bytes over I²C in one burst and get `buf[0]=0xFF`, `buf[1]=0x38`.

Correct: `int16_t x = (int16_t)((buf[0] << 8) | buf[1]);` gives $0xFF38=-200$.

Wrong order: `(buf[1] << 8) | buf[0]` gives $0x38FF=14{,}591$. The error is not subtle but it is not obviously wrong either, since 14,591 is a plausible-looking number. That is why the mistake can survive a quick test and only show up when you tilt the board.

Another real trap is the 33 versus 8,448 case: the 16-bit value 0x0021 (33) with bytes swapped is 0x2100, which equals $0x21\cdot256=8448$. Swapping bytes multiplies by 256 whenever the original high byte is zero, so a small reading suddenly becomes a large one. Debugging tip: if values are consistently off by a factor of 256 or look like multiples of 256, suspect byte order.

For signed values, sign-extend *after* assembling the full width. Assemble in an unsigned type, then cast to the signed type of the same width. Doing `buf[0] << 8` on a signed `char` can sign-extend into the upper bits and corrupt the result.

## Portable code: shifts, not casts

The reliable way to handle multi-byte values is to operate on **values**, not memory layout.

```c
// Parse a big-endian 32-bit field from a packet, regardless of host order
uint32_t be32(const uint8_t *p) {
    return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16)
         | ((uint32_t)p[2] << 8)  |  (uint32_t)p[3];
}
```
This compiles to correct code on any machine, and modern compilers recognize it and emit a single load-and-byte-swap instruction on little-endian hardware. The alternative, `*(uint32_t*)p`, silently gives the wrong number on a mismatched host, may fault on cores that require aligned accesses (a 32-bit load from an odd address traps on some Cortex-M0 devices), and is technically undefined behavior due to aliasing.

## Wire order, memory order and bit order are three different things

| Concept | What is ordered | Example |
|---|---|---|
| Memory endianness | Bytes of a word at increasing addresses | x86 LE, SPARC BE |
| Protocol byte order | Bytes of a field on a bus or packet | TCP/IP big-endian; many sensors high byte first |
| Bit order on a serial line | Bits of each byte | UART sends LSB first; SPI typically MSB first |

Consider a UART sending the 16-bit value 0x1234. A little-endian MCU might transmit bytes `34` then `12` if it just sends memory in order, and each byte is sent LSB first at the bit level. The receiver needs to agree on both. A protocol spec should always state both explicitly.

## Floats, 24-bit samples and other awkward widths

Floating-point numbers are also multi-byte, so they carry byte order too. The IEEE 754 single-precision value 1.0 is the 32-bit pattern 0x3F800000. A little-endian host stores it as `00 00 80 3F`; a big-endian host as `3F 80 00 00`. If you receive those four bytes from a big-endian device and `memcpy` them into a `float` on a little-endian MCU, you do not get 1.0. You get the pattern 0x0000803F, which as a float is a denormal around $4.6\times10^{-41}$. A useful diagnostic: values that are bizarrely tiny or huge, but stable, usually mean byte order rather than a bad sensor.

Many precision ADCs (24-bit delta-sigma parts) return three bytes. There is no native 24-bit type, so the code assembles them into a 32-bit integer. For a raw reading `0x80 0x00 0x01` in offset-binary format the code is $0x800001$, which is $+1$ LSB above mid-scale, whereas the same bytes interpreted as two's complement would be a large negative number ($0x800001-2^{24}=-8{,}388{,}607$). So you need both pieces of information from the datasheet: byte order *and* number encoding.

## What a byte swap costs

Swapping a 32-bit word is cheap. ARM Cortex-M3/M4 have a `REV` instruction that reverses the four bytes in one cycle, and x86 has `BSWAP`. Compilers recognize the shift-and-mask pattern in `be32()` and emit these instructions. So there's no reason to avoid the portable form for performance. The costs that do matter are at the system level: a DMA engine copying a big-endian packet buffer to a little-endian structure either needs a swap pass in software or hardware support for byte swapping (some DMA controllers and peripherals have a byte-swap option).

## Comparison and sorting

Little-endian layouts break `memcmp`-style comparison of numbers: `memcmp` compares the lowest address first, which is the *least* significant byte on a little-endian machine, so it does not sort integers numerically. Big-endian byte strings do sort numerically with `memcmp`, which is why key encodings for databases and some hash/UUID formats use big-endian.

## Real hardware: crossing the boundary

- **Shared memory between two processors** (for example a Cortex-M co-processor and a big-endian DSP, or an MCU and an FPGA soft core): the same word is read with different byte orders unless you swap.
- **FPGAs and HDL**: in Verilog a vector `[31:0]` has no address, so endianness appears only where you map it onto a byte-wide bus; when you wire a 32-bit register to an 8-bit SPI slave, you choose which slice goes first.
- **Files and protocols**: BMP and many x86-native formats are little-endian; PNG and TIFF-big (MM) or network headers are big-endian. Always check the spec rather than assuming.
- **Debuggers**: a memory view showing `78 56 34 12` for a `uint32_t` is correct on a little-endian MCU, not corrupted.
:::

::: applications
- **Sensor drivers**: assembling 16-bit and 24-bit ADC or IMU readings from register pairs over I²C/SPI.
- **Networking**: IP, TCP and UDP headers are defined in network (big-endian) byte order; firmware uses `htons`/`ntohs`.
- **Firmware updates and file formats**: image headers with length and CRC fields need a defined byte order.
- **FPGA to MCU interfaces**: matching register maps and DMA buffers between a little-endian CPU and HDL logic.
- **Debugging with logic analyzers**: protocol decoders let you choose byte order so the decoded value is right.
:::

::: assumptions
- Byte-addressable memory with 8-bit bytes. Some DSPs have 16-bit "bytes", which changes the picture.
- "Big" and "little" refer to byte order only; mixed or "middle-endian" layouts (PDP-11 style) exist historically but are not relevant to modern hardware.
- Statements about which CPUs use which order describe common configurations. ARM, MIPS and PowerPC can be configured either way, though ARM Cortex deployments are overwhelmingly little-endian.
- Sensor register order is device-specific and must come from the datasheet; do not infer it from the MCU.
:::

::: followups
### A 16-bit sensor reading comes through as 8,448 when it should be 33. What happened?
The bytes were assembled in the wrong order. 33 is 0x0021; swapped it is 0x2100, which is $0x21\cdot256=8448$. Check the datasheet for which register holds the high byte and fix the shift: `(hi << 8) | lo`.

### How can you check endianness at runtime in C?
Put `uint16_t x = 1;` in memory and read its first byte through a `uint8_t*` (or `memcpy` into a byte array). If it is 1, the machine is little-endian; if 0, big-endian. Compilers also provide macros like `__BYTE_ORDER__`. But better to write code that doesn't need to know, using shifts.

### Why does the network use big-endian?
Convention from early protocol design (it is called network byte order). Having a single wire format lets machines with different native orders talk, at the cost of a swap on little-endian hosts, which is cheap: most CPUs have a one-cycle byte-reverse instruction.

### What changes in a struct passed between two MCUs with different endianness?
Every multi-byte field is byte-reversed, and padding can differ because of different alignment rules. Serialize field by field to an explicit format instead of sending the raw struct. For floats, also check IEEE 754 layout and byte order match.

### What if you received a 24-bit ADC sample and it's two's complement?
Assemble `(b0<<16)|(b1<<8)|b2` in a 32-bit type, then sign-extend: if bit 23 is set, subtract $2^{24}$ (or OR with 0xFF000000). A raw 0xFFFF38 becomes $0xFFFF38-2^{24}=-200$.
:::

::: interpretations
"Big and small endian" is a slight misnomer. The standard term is **little-endian** ("small" is not wrong, but the opposite of big is little). I interpret the question as byte order of multi-byte values. If asked in the context of bit order (for example for a serial protocol), I would clarify that endianness refers to bytes and answer the MSB-first/LSB-first question separately ([[q0876]]).
:::
