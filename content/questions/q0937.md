::: basics
### In plain words
A cache is a small, very fast memory between the processor and the slow main memory. It keeps copies of data the processor used recently, plus the data stored next to it. The processor is far faster than main memory, so without a cache it would mostly wait. Programs reuse recent data and read neighbors, so a small cache answers most requests.

### Picture it
Think of the speed-dial list on a phone. It holds a few numbers, while the full phone book holds thousands. Most calls go to people you called recently, so the short list usually has the number. When it does not, you search the big book, add the number, and drop the one you used longest ago. The list is a copy of part of the book.

### Words you need
- **Cache line**: the chunk of memory, usually 64 bytes, that the cache copies in one go.
- **Hit / miss**: a hit finds the data in the cache. A miss does not, so the line must come from main memory.
- **Locality**: programs tend to reuse recent data and read data next to it.
- **Tag**: a label stored with each line, saying which memory address it copies.
- **Eviction**: throwing out an old line to make room for a new one.

### The simplest example
A program adds up an array of 4-byte numbers in order. A 64-byte line holds 16 numbers. The first read misses, and the cache copies the whole line. The next 15 reads hit. So the miss rate is $1/16 = 6.25\%$. Say a hit takes 1 ns and each miss costs 80 ns extra. The average is $1 + 0.0625\times80 = 6$ ns per read, instead of 80 ns with no cache. That is the whole idea. The rest of this page shows how the cache finds a line, what happens when addresses collide, and how writes work.
:::

::: testing
Whether you can explain a cache beyond "a small fast memory". The interviewer wants to see:

1. **Why** caches exist (the processor-memory speed gap) and **why they work** (locality).
2. The mechanics: lines, tag/index/offset, hit vs miss, associativity, replacement, write policy.
3. That a cache holds **copies**, is managed by hardware, and is invisible to the programmer's logical view of memory.
4. A feel for numbers: hit time, miss penalty, AMAT, and what causes misses.
5. Awareness that caches create new problems: coherence, non-determinism for real-time code.
:::

::: why
A modern core can issue several instructions per nanosecond, but a DRAM access takes 50 to 100 ns. Without caches, almost every CPU would idle over 95% of the time. Caches also dominate area and power on chips (often over half of a CPU's transistors), so hardware engineers size, partition and verify them constantly. In embedded work, cache behavior explains why timing varies, why DMA buffers need cache maintenance, and why real-time systems sometimes disable the cache or use tightly-coupled memory instead.
:::

::: concepts
- **Locality of reference**: temporal and spatial reuse is what makes a cache effective. See [[q0936]].
- **SRAM cell**: caches are built from fast 6T SRAM. See [[q0939]].
- **Cache line / block**: the fixed-size chunk (e.g. 64 B) moved between levels.
- **Address decomposition**: tag | index | offset locate a line.
- **Associativity**: how many places a given line may go (direct-mapped, N-way, fully associative).
- **Write policy**: write-through vs write-back, write-allocate vs no-write-allocate.
- **Pipeline stalls**: a miss stalls IF or MEM. See [[q0908]].
:::

::: answer
"A cache is a small, fast memory that sits between the processor and main memory and holds copies of the data and instructions the CPU is likely to need next. It exists because the CPU is much faster than DRAM, and it works because programs have locality: they reuse recent data, which is temporal locality, and they use data near what they just touched, which is spatial locality.

Mechanically, the cache stores memory in lines, typically 64 bytes. When the CPU asks for an address, hardware splits it into tag, index and offset. The index picks a set, the tags in that set are compared with the address's tag, and if one matches and is valid, that's a hit and the data comes back in a few cycles. If not, it's a miss: the line is fetched from the next level, which may take tens to hundreds of cycles, and it replaces an older line, usually least-recently-used.

Writes can be write-through, updating memory immediately, or write-back, where you mark the line dirty and write it out on eviction.

The payoff is average access time: with a 1 ns hit and a 5% miss rate to an 80 ns DRAM, the average is 5 ns instead of 80. The cost is area, power, and complexity like coherence between cores and less predictable timing."
:::

::: technical
**Organization.** A cache of capacity $C$ bytes, line size $B$ bytes and associativity $N$ ways has
$$S = \frac{C}{B\,N}\ \text{sets},\qquad \text{offset bits} = \log_2 B,\quad \text{index bits} = \log_2 S,\quad \text{tag bits} = A - \log_2 S - \log_2 B.$$
Example: 32 KB, 64 B lines, 8-way, 32-bit addresses: $S = 32768/(64\times 8) = 64$ sets, 6 offset bits, 6 index bits, 20 tag bits.

**Lookup.** Index selects a set; all $N$ tags in the set are compared in parallel with the address tag; valid && match = hit; the offset selects the bytes in the line. Direct-mapped is $N=1$ (fast, simple, conflict-prone); fully associative has one set (flexible, expensive comparators).

**Miss types (the 3 C's).** *Compulsory* (first touch), *capacity* (working set > cache), *conflict* (too many lines map to the same set). A fourth, *coherence*, appears in multicore systems.

**Replacement.** LRU (or pseudo-LRU), random, FIFO. Random is surprisingly close to LRU for high associativity and much cheaper.

**Write policies.**
- *Write-through*: every store goes to the next level (simple, consistent, more traffic; used with write buffers).
- *Write-back*: store updates the line and sets a dirty bit; memory is updated on eviction (less traffic).
- *Write-allocate* (fetch on write miss) usually pairs with write-back; *no-write-allocate* with write-through.

**Performance.** $\text{AMAT} = t_{hit} + m\,t_{miss}$. With $t_{hit}=1$ ns, $m=5\%$, $t_{miss}=80$ ns, AMAT $=5$ ns; with $m=1\%$, 1.8 ns. Tag overhead: a 48-bit physical address, 64 B lines, 64 sets gives $48-6-6=36$ tag bits per line, plus valid/dirty/LRU bits: about 7 to 8% extra storage over the 512-bit data line.
:::

The address is split into tag, index and offset; the index selects a set, tags are compared, and a match is a hit in a cycle or few; otherwise it's a miss and a 64-byte line is fetched from the next level. With a 95 percent hit rate and 80 ns DRAM, average access time falls from 80 ns to about 5 ns."

::: long
"A cache is a small, fast memory that sits between the CPU and a bigger, slower memory, and automatically keeps copies of the data you're likely to need again. It exists because a core can execute an instruction in under a nanosecond while DRAM takes 50 to 100 ns, and it works because of locality. Temporal locality: if you used something, you'll probably use it again. Spatial locality: if you used an address, you'll probably use the next one.

The cache stores data in lines, usually 64 bytes. When the CPU issues an address, the low bits, the offset, say which byte in the line. The next bits, the index, select a set. The remaining high bits are the tag, which is compared against the tags stored in that set. If one matches and its valid bit is set, it's a hit and the data returns in a few cycles. Otherwise it's a miss: the controller fetches the whole line from the next level and evicts something to make room, typically least-recently-used.

Associativity controls where a line may go. Direct-mapped has exactly one spot, so it's fast but two hot addresses mapping to the same index keep kicking each other out, a conflict miss. N-way set-associative allows N spots. Fully associative allows anywhere, which is flexible but needs a comparator per line.

For writes there are two policies. Write-through sends every write to memory, simple but chatty. Write-back just marks the line dirty and writes it out on eviction, which saves bandwidth.

The performance model is average memory access time: hit time plus miss rate times miss penalty. A 1 ns hit with a 5 percent miss rate to 80 ns DRAM gives 5 ns, versus 80 with no cache. The costs are area and power, coherence between cores, and timing that depends on history, which is why real-time designers sometimes use scratchpad memory instead."
:::

::: terms
- **Cache line (block)**: unit of transfer and storage, typically 64 bytes.
- **Tag / index / offset**: address fields used to find a line within the cache.
- **Hit / miss**: whether the requested line is present.
- **Associativity**: number of ways, the places a given line may reside.
- **LRU**: replace the least recently used line.
- **Write-back / write-through**: update memory on eviction / on every write.
- **Dirty bit**: marks a line modified relative to the next level.
- **Coherence**: keeping copies of the same line consistent across cores.
- **Compulsory / capacity / conflict miss**: the 3 C's.
:::

::: exceptional
An average answer says "small fast memory that stores frequently used data". An exceptional answer:

- Starts from the **speed gap** and **locality**, not the definition.
- Breaks an address into tag/index/offset with **actual numbers** for a given size, line, and associativity.
- Classifies misses (compulsory/capacity/conflict) and shows how associativity or line size fixes each.
- Gives **AMAT** and notes miss rate matters multiplied by a 50-100x penalty.
- Mentions write policies, coherence, and the **embedded caveats**: unpredictable timing, DMA coherence (clean/invalidate), cache-disable for real-time code.
:::

::: mistakes
- **"Cache stores frequently used data."** More precisely, *recently* used data and its neighbors, kept by LRU-like policies; frequency is only approximated.
- **Treating cache as architecturally visible storage.** Programs do not address it; it must be transparent (except for explicit maintenance instructions).
- **Mixing up index and tag.** The index chooses where to look; the tag verifies what is there.
- **Saying a bigger cache is always faster.** Hit time grows with size, and associativity adds comparator delay and power.
- **Forgetting writes.** Without a write policy, the cache and memory disagree.
- **Ignoring DMA on embedded parts:** a CPU may read stale cached data after a peripheral DMAs fresh data into RAM, unless the line is invalidated.
:::

::: deep
## The problem a cache solves

Suppose a core runs at 3 GHz and wants one instruction and 0.3 data accesses per cycle. If every access went to DRAM at 80 ns, that is $80\,\text{ns}\times 3\,\text{GHz} = 240$ cycles per access. The core would stall for 240 cycles for every ~1.3 accesses it wants. A cache with 98 to 99% hit rate at ~4 cycles turns the average into $4 + 0.02\times 240 \approx 8.8$ cycles, and an out-of-order core hides much of the rest.

**Direct-mapped is the special case $N = 1$.** There is only one tag compare and the data can be read speculatively while the compare finishes, so it is the fastest. But every address with the same index fights for one slot.

## Why associativity matters: a conflict worked example

A 4 KB direct-mapped cache has 16-byte lines, so $4096/16 = 256$ lines and the index is bits [11:4]. A loop does `c[i] = a[i] + b[i]` with 4-byte ints, `a` at `0x0000` and `b` at `0x1000` (exactly 4 KB apart). Addresses `a[i]` and `b[i]` have identical index bits, so they map to the same line. Each access evicts the other's line before its neighboring elements are used:

- Direct-mapped: every `a[i]` and `b[i]` access misses: **100% miss rate** (compulsory + conflict), even though the working set (a few lines) is tiny.
- 2-way set-associative of the same size: `a` and `b` lines coexist in the two ways of a set. Each 16-byte line holds 4 ints, so only the first of every 4 accesses misses: **25% miss rate**.

That 4x difference in misses is pure conflict. Raising associativity gives diminishing returns past about 4 to 8 ways, which is why L1s are typically 4 to 8-way (every extra way adds compare and mux delay to the hit time). L3s are often 12 to 16-way because their hit time is less critical while each L3 miss costs a full DRAM access, so removing conflict misses there is worth the extra comparators.

## Line size trade-off

Bigger lines exploit spatial locality and amortize the DRAM latency (the first word is slow, the rest stream), but:
- They waste bandwidth and capacity when only part of the line is used.
- They increase the miss penalty (more bytes to transfer) and raise the chance of conflict, since fewer lines fit.
64 B is the common sweet spot today (128 B in some GPUs and POWER designs).

## Write policies, concretely

Consider a loop that increments a counter 1,000 times in a write-back write-allocate cache: the first write misses and allocates the line (one fill), the following 999 writes hit and only mark the line dirty; one write-back occurs at eviction: 1 fill + 1 write-back total. A write-through cache would send 1,000 writes to the next level (mitigated by a write buffer or write-combining). That is why L1s in application CPUs are write-back (or write-through to a write-back L2) and why embedded write-through caches are simpler to keep coherent with DMA.

## Real hardware behavior

- **Parallel tag and data access**: the L1 compares tags while reading the data of all ways, then muxes the winning way. This costs power (reading 8 ways to use 1) and is why some designs use way prediction.
- **Virtually indexed, physically tagged (VIPT)**: L1 uses virtual-address bits for the index (so lookup overlaps with TLB translation, [[q0943]]) and physical tag for compare. To avoid aliasing, index+offset bits must fit inside the 12-bit page offset: $32\,\text{KB}/8\text{ ways} = 4\,\text{KB}$, which is exactly why 8-way 32 KB L1s are so common with 4 KB pages.
- **Non-blocking caches** keep servicing hits while earlier misses are outstanding (miss-status holding registers, MSHRs).
- **Prefetchers** detect sequential or strided streams and fetch ahead of the demand.
- **Coherence**: each core has private L1/L2; a protocol (MESI and variants) invalidates or updates copies on writes. A shared counter bouncing between cores' caches can be 10x slower than a private one.
- **MCUs**: Cortex-M7 has optional I/D caches (e.g. 4 to 64 KB); smaller M0/M3/M4 parts have none, and use a flash prefetch/accelerator and optionally TCM. DMA buffers in cacheable regions require clean (before DMA read) and invalidate (after DMA write) operations, or an uncached MPU region.

> [!INTERVIEW]
> If asked "how would you shrink miss rate?", organize by miss type: compulsory (bigger lines, prefetch), capacity (bigger cache, better algorithms/blocking), conflict (more associativity, victim cache, changing data layout or padding).

## Worked miss accounting

A 2-way 8 KB cache with 32 B lines has $8192/(32\times 2) = 128$ sets (7 index bits, 5 offset bits). A program streams through a 64 KB array once. Number of lines touched $=65536/32 = 2048$; each is a compulsory miss: 2048 misses. If each byte is read once sequentially, accesses = 65536; miss rate $=2048/65536 = 3.1\%$ (1 miss per 32 bytes). Reading the array a second time, the cache (8 KB) cannot hold 64 KB, so the second pass misses again: capacity misses. Blocking the loop into 4 KB tiles that fit in the cache turns the second pass into hits. This is the essence of cache-aware algorithm design (matrix tiling).
:::

::: applications
- **CPU L1/L2/L3 caches** in laptops, servers and phones, all built from SRAM with 64-byte lines.
- **Flash accelerators/prefetch caches** in MCUs (e.g. STM32 ART-style) to hide flash wait states.
- **TLBs** are caches of address translations ([[q0943]]).
- **Operating system page cache and database buffer pools**: DRAM as a cache for storage.
- **CDNs and browsers** use the same idea at a bigger scale: replicate hot data nearer the consumer.
- **GPU texture and L2 caches** exploit 2D spatial locality.
:::

::: assumptions
- I assume a conventional CPU data/instruction cache with 64-byte lines and LRU-like replacement; other caches (TLB, branch target buffer, disk cache) share the idea but differ in details.
- Numbers are typical, not tied to a specific product.
- A cache can also mean a **software** cache (memoization, page cache), which follows the same locality logic.
- Real-time engineers sometimes prefer **scratchpad (TCM)** over cache for determinism; an interviewer from automotive or aerospace may expect that mention.
- For multicore systems I assume hardware coherence; some embedded multicore or accelerators require software-managed coherence.

::: followups
### What is the difference between direct-mapped, set-associative and fully associative?
Direct-mapped: each address maps to exactly one line, so lookup is one tag compare, but conflicts are common. N-way: a set contains N lines, and an address may be in any of them; one set lookup, N parallel compares. Fully associative: one set, any line can hold any address; maximum flexibility but needs a comparator per line, so only small structures like TLBs use it.

### Write-back vs write-through: which would you choose and why?
Write-back for performance and power on the main CPU path because repeated writes to a line cost one eviction. Write-through when simplicity or consistency matters, e.g. a small embedded cache shared with DMA, or an L1 backed by a write-back L2. Write-through needs a write buffer so stores do not stall the pipeline.

### How many tag bits for a 32 KB, 4-way cache, 64 B lines, 40-bit physical addresses?
Sets $=32768/(64\times 4)=128$, so index = 7 bits, offset = 6 bits, tag $=40-7-6=27$ bits per line. With 512 lines that is $512\times 27=13{,}824$ bits (1.7 KB) of tags, plus valid/dirty/LRU bits.

### Your code runs fine, but after adding DMA from an ADC into a buffer the CPU reads stale samples. What happened and how do you fix it?
The CPU read the buffer earlier, so lines were cached. The DMA wrote fresh data directly to RAM, bypassing the cache, and the CPU keeps hitting the stale lines. Fix: invalidate the cache lines for that buffer after DMA completes (and clean before DMA reads from a buffer the CPU wrote), or place the buffer in a non-cacheable MPU/MMU region, or use a coherent DMA path. Align buffers to the line size, or neighboring variables get invalidated too.

### Harder: why do 32 KB, 8-way L1 caches with 4 KB pages show up so often?
VIPT lookup wants the index and offset bits inside the page offset so that virtual and physical indexes are identical and no aliasing exists. With 4 KB pages (12 offset bits), cache size per way must be at most 4 KB: $32\text{ KB}/8 = 4$ KB. To grow the L1, you must add ways (or use larger pages or more complex alias handling).
:::
