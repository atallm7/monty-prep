::: basics
### In plain words
An interrupt lets a peripheral make the CPU pause its work and run a short handler right away. That is very useful, but it is not free. Interrupts add delay, can be lost, use CPU time, and can corrupt data the main code is using. Knowing these limits is how you use interrupts safely.

### Picture it
Picture a cook who also answers the doorbell. Every ring stops the cooking. If a second ring comes before the cook reaches the door, the cook remembers only "someone rang", not how many times. If the bell rings every few seconds, no cooking gets done. A real CPU resumes exactly where it stopped, but data shared with the handler can still be left half updated.

### Words you need
- **Interrupt** ([[q0795]]): a hardware signal that makes the CPU pause the main code and run a handler.
- **ISR** ([[q0801]]): the short handler function that runs in response.
- **Latency**: the delay between the event and the first handler instruction.
- **Jitter**: how much that latency changes from one event to the next.
- **Pending flag**: one bit that records "an event happened". It cannot count events.
- **Race condition**: a bug where the result depends on whether the interrupt lands before or after a step of the main code.

### The simplest example
A sensor sends events at least 100 µs apart. The handler takes 8 µs. The main code sometimes switches interrupts off for 12 µs. Worst case, an event waits 12 µs and then the handler runs 8 µs: 20 µs in total, well under 100 µs, so nothing is lost. Now switch interrupts off for 150 µs instead. A second event arrives while the first is still pending, and the two merge into one.

That is the whole idea. The rest of this page lists each limit and its standard fix.
:::

::: testing
Whether you understand interrupts as a **trade-off** rather than a free lunch. The interviewer wants a structured list: latency and jitter, nondeterminism, event loss (single pending bit), CPU overhead at high rates, shared-data races, stack usage and nesting, priority inversion and starvation, limited number of sources and priorities, difficulty of testing and debugging, and the restrictions on what an ISR may do. Even better is pairing each limitation with the standard mitigation.
:::

::: why
Most field failures in embedded systems that "work on the bench" trace back to one of these limits: a rarely-hit race, a missed event under load, a stack overflow from nesting, a latency spike from a long critical section. Knowing the limitations is what lets you design interrupt handling that is robust rather than merely functional ([[q0802]], [[q0803]]).
:::

::: concepts
- **Latency and jitter**: delay and its variation, set by masked sections and higher-priority ISRs ([[q0794]]).
- **Single pending bit**: multiple events can merge into one interrupt.
- **Shared data hazards**: ISR and main access the same data asynchronously.
- **Overhead**: entry/exit and ISR body consume CPU at high rates ([[q0798]]).
- **Stack usage**: each active ISR needs a frame; nesting multiplies it ([[q0797]]).
- **Priority/starvation**: low-priority work can starve; priority inversion with locks.
- **Restrictions**: no blocking, limited library use, small time budgets ([[q0802]]).
:::

::: answer
"Interrupts are great, but they come with limits I'd always keep in mind.

First, latency isn't zero and isn't constant. There's the entry overhead, but the real problem is jitter: if main code disables interrupts for a critical section, or a higher-priority ISR is running, my response waits. So worst case matters, not average.

Second, events can be lost. A peripheral has one pending bit, so if two events occur before I service the first, I only get one interrupt. And an ISR that's too long causes the next event to be missed.

Third, there's overhead. Every interrupt costs entry and exit, a few hundred nanoseconds, so at hundreds of kilohertz the CPU is swamped. That's when I switch to DMA or timer hardware.

Fourth, concurrency. The ISR can run between any two instructions of main code, so shared variables need volatile and atomic access, and bugs are intermittent and hard to reproduce.

Fifth, resources: each ISR uses stack, and nesting multiplies it, and you only have a limited number of priorities and vectors.

Finally, ISRs have restrictions: no blocking, no malloc or printf, and long ISRs hurt everything else. Debugging is also hard because breakpoints change the timing.

The mitigations are short ISRs, deferred processing, careful priorities, DMA for high rates, and hardware paths for hard deadlines."
:::

::: technical
**1. Latency and jitter.** $t_{worst}=t_{entry}+\max(t_{CS})+\sum_{j\in hp}t_{ISR,j}\cdot n_j+\ldots$ where $t_{CS}$ is the longest interrupts-disabled section and the sum covers higher-priority ISRs that can run first. Jitter $\approx t_{worst}-t_{best}$. Cortex-M entry is 12 cycles; AVR 4+3 cycles (typical figures).

**2. Event loss.** One pending bit per source (edge latches once). If $t_{service}>$ inter-arrival time, events are lost. Condition for no loss at event period $T$: worst-case response plus ISR duration must be less than $T$ (and $T_{min}$ between consecutive events):

$$t_{latency,worst}+t_{ISR}\le T_{min}$$

Overrun in peripherals (UART data register overwritten) follows the same logic.

**3. CPU overhead and rate ceiling.** Load $U=r(t_{ISR}+t_{entry}+t_{exit})$. For sets of ISRs, total $\sum U_i$ must be below 1 and ideally below about 0.5 to retain margin. Above about 100 kHz per source on typical MCUs, use DMA/hardware.

**4. Race conditions.** Non-atomic read-modify-write and multi-word accesses between ISR and main (or between ISRs) produce lost updates or torn reads. Use `volatile`, atomic types, short critical sections (`__disable_irq()` or BASEPRI), or lock-free single-producer/single-consumer structures.

**5. Stack.** Worst-case depth: $S=S_{main}+\sum_{k\in\text{nest chain}}(32+S_{locals,k}+\text{saved regs})$ for the longest chain of preempting priorities. With 4 priority levels nesting and 100 bytes each, 400 bytes of stack just for ISRs, and more with FPU context (an extended frame is 104 bytes instead of 32).

**6. Priority issues.** Starvation of low-priority sources by a busy high-priority source; priority inversion if a low-priority context holds a resource (a lock or a masked-interrupt section) that a high-priority ISR needs.

**7. Finite resources.** Limited interrupt lines (e.g. one pin per EXTI line), limited priority bits (as few as 2-4 bits on small parts, so 4-16 levels), shared vectors.

**8. Non-determinism for verification.** Interleavings are numerous; bugs are timing-dependent and appear rarely. Breakpoints and `printf` perturb the timing.

**9. ISR restrictions.** Cannot block, wait, or use non-reentrant or slow library calls; the RTOS API subset is limited to FromISR variants; floating point enlarges the stack frame.

**10. Power.** Frequent interrupts keep the CPU from sleeping; each wake-up has a time and energy cost.
:::

::: short
"The main limits are latency and jitter, since masked sections and higher-priority ISRs delay response, so worst case matters. Events can be lost because there's only one pending bit and a long ISR misses the next event. Entry and exit overhead makes very high rates infeasible, so those need DMA or timer hardware. Shared data between ISR and main creates race conditions, nesting uses stack, and ISRs can't block or do heavy work. I mitigate with short ISRs, deferred processing, careful priorities and hardware offload."
:::

::: long
"I'd organise the limitations by what goes wrong.

Timing first. Interrupt latency has a floor, 12 cycles on a Cortex-M, but more importantly a variable part: any time the main code masks interrupts, or a higher-priority ISR is running, my response waits. So for a hard deadline I compute the worst case, which is entry plus the longest critical section plus any higher-priority ISRs. The ISRs also add jitter to the main code and to each other.

Second, missed events. There's one pending flag per source, so if two events arrive before the first is serviced, one is lost. The rule is that worst-case latency plus ISR time has to be shorter than the minimum gap between events. For a UART, that's why you need buffers or FIFOs: if the data register is overwritten before you read it, you get an overrun.

Third, overhead. Each interrupt costs a few hundred nanoseconds of entry and exit before any real work. At 100 kilohertz that's already tens of percent, so high-rate streams should use DMA or timer hardware rather than per-event interrupts.

Fourth, concurrency. An ISR runs between any two instructions of the main program, so shared variables must be volatile, updates must be atomic, and multi-byte data can tear. These bugs are intermittent, and debugging changes timing, so they're hard.

Fifth, resources: stack for each active ISR and every nested level, limited priority levels, and sometimes a limited number of interrupt lines.

And there are behavioural limits: an ISR can't block, shouldn't call slow or non-reentrant library functions, and long ISRs starve everything below them.

So the design response is short ISRs with deferred processing, a deliberate priority scheme, buffers sized for the worst case, DMA and hardware shortcuts for high rates, and critical sections kept to a few microseconds."
:::

::: terms
- **Interrupt latency**: delay from request to first ISR instruction.
- **Jitter**: variation in latency.
- **Critical section**: code with interrupts disabled.
- **Overrun**: a new data item arrives before the previous one is read.
- **Race condition**: result depends on the relative timing of ISR and main code.
- **Atomic operation**: indivisible with respect to interrupts.
- **Priority inversion**: a high-priority task is blocked by a lower-priority one holding a resource.
- **Starvation**: a low-priority task never gets CPU time.
:::

::: exceptional
An average answer names two or three issues. An exceptional answer:

- States the **no-loss condition** $t_{latency}+t_{ISR}\le T_{min}$ and computes it for an example.
- Differentiates **latency from jitter** and names their causes (critical sections, higher-priority ISRs, flash wait states).
- Explains the **single pending bit** limit and mitigations (FIFO, DMA, counters).
- Quantifies **overhead** and sets a load budget.
- Covers **stack depth** with nesting and **priority inversion/starvation**.
- Pairs each limit with a **mitigation** and knows the **hardware alternative** (DMA, timers).
:::

::: mistakes
- **"Interrupts make the system real-time."** They make it responsive; determinism requires bounding worst-case latency and load.
- **Disabling all interrupts around long operations** (for example a flash write or a 500 µs routine), which blows latency for every other source.
- **Sizing buffers for the average rate** rather than worst-case burst and worst-case service delay.
- **Assuming the ISR will always run before the next event.** If the next event comes while the ISR runs, it is lost or deferred.
- **Ignoring stack** for nested or FPU-using ISRs, so a rare overflow corrupts memory.
:::

::: deep
## Latency budget in numbers

Suppose a sensor produces a data-ready pulse every 100 µs ($T_{min}$). The MCU is a Cortex-M4 at 72 MHz. Contributions:

| Item | Time |
|---|---|
| Entry (12 cycles) | 0.17 µs |
| ISR body to read the sensor over SPI (assume 40 cycles setup + transfer 8 µs) | 8.6 µs |
| Longest critical section in main (disabled interrupts) | 12 µs |
| Higher-priority motor ISR (10 µs, 20 kHz, may run once in the window) | 10 µs |

Worst-case total latency to *finish* servicing: $0.17+12+10+8.6\approx30.8\ \mu s<100\ \mu s$: there is margin. If the critical section were 80 µs it would be $0.17+80+10+8.6=98.8$ µs, nearly at the limit, and any additional higher-priority ISR would make the system lose a sample. The point of the exercise is that *one* long critical section anywhere in the firmware determines the worst-case latency for *every* interrupt.

## Why the single pending bit loses events

A peripheral has one flag per event type. Sequence:
1. Event 1 sets the flag.
2. ISR starts, reads status.
3. Event 2 arrives while the ISR is running; the flag is already set (or is set again).
4. ISR clears the flag (a blanket clear removes event 2's contribution too).
5. Return. No pending. Event 2 is lost.

The standard defences:
- Clear only the bits you handled and re-read status before returning.
- Use hardware counters (an input capture FIFO, a UART FIFO with 8-16 entries, a DMA buffer).
- Make the ISR short so the window is small.

## Overhead at high rates

At 72 MHz a minimal round trip is about 24 cycles = 0.33 µs. For a 250 kHz event rate that's 8% before any ISR body; an ISR body of 1 µs raises it to 33%. For a 1 MHz event the overhead alone is 33% and with body 1 µs it exceeds 100% (1.33 µs per event at a 1 µs period). That's the rate ceiling: $r_{max}=1/(t_{ISR}+t_{overhead})$, and a design should operate at under about half of it.

## Concurrency and atomicity

Consider `count++` on a 32-bit variable updated in both ISR and main. The compiler emits LDR, ADD, STR. If the ISR fires between LDR and STR in main and increments `count`, main's STR overwrites it with the stale-plus-one value: one count lost. On an 8-bit AVR, a 16-bit variable is accessed in two steps so the ISR can fire between the low and high byte read and the main code reads a "torn" value (for example 0x00FF then 0x0100 gives 0x01FF).

Mitigations:
- Make exactly one side the writer of each variable.
- Use `volatile` for visibility, and atomic operations or short critical sections for read-modify-write.
- Double-buffering or SPSC ring buffers for multi-word data.
- On Cortex-M use `LDREX/STREX` or `__atomic` builtins where supported, or BASEPRI to mask only up to the needed priority.

## Priorities, starvation and inversion

If a high-priority ISR fires at 80% load, everything below it has 20% of the CPU and its latency stretches. If a low-priority context takes a lock (or masks interrupts at some level) that a high-priority ISR needs, the high-priority work is delayed by the lock holder: priority inversion. In ISRs the usual fix is to avoid locks and use lock-free structures or short masked sections instead.

## Stack with nesting

With priority levels $P_1>P_2>P_3>P_4$ able to preempt each other, the worst case is all four active at once: frames of 32 bytes each (hardware) plus compiler saves and locals, say 80 bytes each: 4 x 112 = 448 bytes plus the main stack. On a part with 2 kB of RAM, that is 22% of memory. Measure with stack painting (fill with a pattern, run, check the high-water mark) rather than guessing ([[q0803]]).

## Debugging limitations

A breakpoint inside an ISR stops the system and ruins timing; `printf` from an ISR changes it further. Better tools: GPIO toggles on entry/exit viewed on a scope or logic analyser, cycle counters (DWT), trace (ITM/ETM) where available, and logging events in a RAM ring buffer with timestamps.

## What interrupts are *not* good at

| Need | Better tool |
|---|---|
| High-rate data (above about 100 kHz) | DMA |
| Exact timestamps | Timer input capture ([[q0790]]) |
| Nanosecond protection | Hardware comparator to break input |
| Hard analysable timing | Polling with a static schedule, or a time-triggered design |
| Complex processing | Deferred to a task |

::: assumptions
- Numbers assume a Cortex-M4 at 72 MHz with zero-wait-state memory and are illustrative. Real parts with caches and wait states have more jitter.
- Single core. On multi-core systems interrupts can run truly in parallel with other cores, adding cross-core synchronisation issues.
- "Limitations" here are inherent to the interrupt mechanism; some are mitigated by hardware features (tail-chaining, FIFOs, DMA).
- Different candidates may emphasise either timing or concurrency; both should be covered.

::: followups
### How do you calculate worst-case interrupt latency?
Add the entry time, the longest interrupts-disabled section anywhere in the code, and the execution time of every higher-priority ISR that can run first (times the number of occurrences in the window). For a hard deadline compare that sum plus your own ISR time with the deadline. In practice you measure with a scope and a worst-case workload and add margin.

### An ISR sometimes misses a button press. Why, and how do you fix it?
Likely a long critical section or a long higher-priority ISR delays service past the event, or the pulse is shorter than the sampling. An edge-latched interrupt should capture even a short press; if it still misses, debounce logic may be discarding it, the flag may be cleared incorrectly, or the interrupt is masked. Measure with GPIO toggles, shorten masked sections, and use edge-latching hardware.

### How do you make a shared 32-bit counter safe between ISR and main on an 8-bit MCU?
In main, disable interrupts (or use an atomic block), copy the 4 bytes to a local, re-enable. Alternatively read twice until two reads match. Make the ISR the only writer so no read-modify-write races occur.

### Why can't you use `printf` or `malloc` in an ISR?
They are slow (hundreds of µs or more), may block or take locks, are often non-reentrant, and `malloc` can fragment or deadlock if main code was interrupted mid-allocation. Log to a buffer and print from the main loop.

### What's the downside of letting ISRs nest freely?
Each nested ISR adds a stack frame and the interleavings multiply: more shared-data hazards and harder verification. It improves the latency of urgent sources but should be used with explicit priority design and stack analysis ([[q0803]]).
