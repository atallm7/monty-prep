::: testing
Whether you can define setup and hold times precisely (a window around the **active clock edge** during which the data input must be stable), explain *what physically goes wrong* when it's violated (metastability or capturing the wrong value), and tie both to a **timing budget** with real terms: clock-to-Q, propagation delay, skew, jitter. This version sits in the signal-integrity section, so the best answers also show how ringing, slow edges, crosstalk and jitter eat into the window. The key insight: setup violations can be cured by slowing the clock; hold violations cannot.
:::

::: why
Timing closure is the central discipline in digital hardware. Every synchronous interface (SPI, DDR, parallel buses, FPGA I/O) is ultimately specified by setup and hold windows. A marginal setup or hold shows up as bit errors that appear with temperature, voltage and board-to-board variation: some boards pass, some fail. SI issues change the effective window, so a design that closes in static timing analysis can still fail in hardware. The same concept appears as [[q0880]] in the digital section; here the emphasis is on how signal quality affects the window.
:::

::: concepts
- **Edge-triggered flip-flop**: samples D at the active clock edge. See [[q0884]].
- **Setup time ($t_{su}$)**: data must be stable for this long *before* the edge.
- **Hold time ($t_h$)**: data must stay stable this long *after* the edge.
- **Clock-to-Q ($t_{cq}$)** and propagation delay: how long the launching flop and the path take to deliver new data. See [[q0885]].
- **Metastability**: the flop's output hangs between 0 and 1 and resolves after a random time. See [[q0887]].
- **Skew and jitter**: static and random differences in clock arrival that subtract from the window. See [[q0695]].
:::

::: answer
"A flip-flop samples its input at the active clock edge, and internally it needs the data to be stable for a short window around that edge. Setup time is how long the data must be stable before the edge, and hold time is how long it must stay stable after the edge. Together they define the window where the data may not change.

If the data changes inside that window, the flop can't reliably decide between 0 and 1. It may capture the old value, the new value, or go metastable, where the output sits at an in-between voltage for a random amount of time before settling. That can propagate garbage into downstream logic, and it's very hard to debug because it's intermittent.

For a path between two flops the timing budget is: clock period must be at least clock-to-Q plus logic and wire delay plus setup plus clock skew and jitter. If that fails, I can lower the clock frequency or shorten the path. Hold is the other direction: the fastest path must be longer than hold time plus skew; and that doesn't depend on clock period, so slowing the clock doesn't help. I'd fix hold by adding delay. In signal-integrity terms, ringing, slow edges, crosstalk or jitter near the capture edge shrink the window."
:::

::: technical
**Definitions.** For an edge-triggered flip-flop capturing at $t_{clk}$: data must be stable from $t_{clk} - t_{su}$ to $t_{clk} + t_h$. Datasheets define them at specified input levels (often 50% or $V_{IH}$/$V_{IL}$) and slews.

**Setup constraint** (data path from launching flop to capturing flop):

$$T_{clk} \ge t_{cq,max} + t_{logic,max} + t_{wire,max} + t_{su} + t_{skew} + t_{jitter}$$

**Hold constraint:**

$$t_{cq,min} + t_{path,min} \ge t_h + t_{skew}$$

(skew taken in the unfavourable direction for each check). Note $T_{clk}$ does not appear in the hold constraint.

**Worked example (100 MHz).** $t_{cq,max} = 1.2$ ns, combinational 5.8 ns, wire 1.0 ns, $t_{su} = 0.8$ ns, skew 0.3 ns, jitter 0.2 ns. Sum = 9.3 ns, so setup slack at $T = 10$ ns is $+0.7$ ns, and the maximum clock is $1/9.3$ ns = 107.5 MHz. Hold: $t_{cq,min} + t_{path,min} = 0.5 + 0.3 = 0.8$ ns versus $t_h + t_{skew} = 0.4 + 0.3 = 0.7$ ns: slack $+0.1$ ns, thin but passing.

**Violation behavior.** Inside the window the internal regenerative latch is driven near its balance point; the output takes longer than $t_{cq}$ to resolve, and which value it resolves to is random. The mean time between failures is

$$MTBF = \frac{e^{t_r/\tau}}{T_w\,f_c\,f_d}$$

where $t_r$ is the resolution time available, $\tau$ the flop's regeneration time constant, $T_w$ its metastability window, $f_c$ the clock and $f_d$ the data-change rate. Using the illustrative values $\tau = 100$ ps, $T_w = 100$ ps, $f_c = 100$ MHz, $f_d = 10$ MHz: $t_r = 1$ ns gives 0.22 s; $t_r = 3$ ns gives about 3.4 years. Real values come from the vendor's metastability characterization.

**Fixes.** *Setup*: slower clock, shorter or faster logic, pipelining, lower skew/jitter. *Hold*: add delay (buffers) to the data path, reduce clock skew; no clock-frequency fix. *Asynchronous inputs*: 2-flop synchronizer to give time for resolution.

**Signal-integrity effects.** Slow data or clock edges lengthen the effective setup (datasheet numbers assume a stated slew); ringback near the threshold at the capture instant looks like a data change; crosstalk and ground bounce add noise-induced timing shifts; jitter and skew subtract directly.
:::

::: long
"A flip-flop doesn't sample instantaneously. Internally it needs the input to be stable for a small window around the active clock edge. Setup time is how long before the edge the data must already be stable. Hold time is how long after the edge it must stay put. Think of a camera: setup is holding still before the shutter, hold is not moving right after it.

If the data changes inside that window, the flop can capture the old value, the new value, or go metastable. In metastability the output sits at some in-between voltage for a random time, which can exceed the clock period and then resolves to a random 0 or 1. That can cause downstream logic to see different values, which is hard to debug since it's intermittent and depends on temperature and voltage.

For a path between two flops, the setup budget is: the period must be at least clock-to-Q plus the logic and wire delay plus setup plus skew and jitter. With a 10 nanosecond period, 1.2 for clock-to-Q, 5.8 of logic, 1.0 of wire, 0.8 setup, 0.3 skew and 0.2 jitter, I have 0.7 nanoseconds of slack. If it fails I can slow the clock or shorten the path.

Hold is the opposite check: the fastest possible data arrival, clock-to-Q min plus the shortest path, has to exceed hold time plus skew. The clock period doesn't appear, so slowing the clock doesn't help. I'd add delay to the data path.

From the signal-integrity side, anything that moves the threshold crossing near the capture edge eats into this window: slow edges, ringback, crosstalk, ground bounce and jitter. And for asynchronous inputs I use a two-flop synchronizer to let metastability resolve."
:::

::: terms
- **Setup time ($t_{su}$)**: minimum time data must be stable before the active clock edge.
- **Hold time ($t_h$)**: minimum time data must remain stable after the active clock edge.
- **Clock-to-Q ($t_{cq}$)**: delay from the clock edge to a new output at Q.
- **Slack**: margin; positive means the constraint is met.
- **Clock skew**: difference in clock arrival time between two flops.
- **Metastability**: the flop output hangs at an intermediate level and resolves after a random delay.
- **Synchronizer**: chain of flops that gives metastability time to resolve for asynchronous inputs.
- **Recovery/removal**: setup/hold equivalents for asynchronous set/reset deassertion.
:::

::: exceptional
An average answer defines both times and says "violations cause errors". An exceptional answer draws the **window around the edge**, writes the two inequalities and notes the asymmetry (**hold doesn't depend on the clock period**, so slowing the clock fixes setup only), gives a numerical budget, and explains **metastability** with the MTBF form $e^{t_r/\tau}/(T_w f_c f_d)$ and the 2-flop synchronizer. In this SI context it adds how slew rate, ringback near threshold, crosstalk, ground bounce, skew and jitter shrink the effective window, and that datasheet $t_{su}$/$t_h$ are specified for a given input slew.
:::

::: mistakes
- **Believing a slower clock fixes any timing failure.** It only fixes setup; hold is independent of period and needs added delay or less skew.
- **Defining hold as "time data is held before the edge".** Setup is before, hold is after.
- **Treating the flop as sampling at a perfect instant.** The effective window has width and is slew-dependent.
- **Forgetting skew and jitter in the budget.** They subtract directly from the window; clock distribution matters.
- **Assuming metastability is a rare lab curiosity.** At high clock and data rates the MTBF can be minutes; synchronizers and enough resolution time are required for asynchronous inputs.
- **Using nominal numbers for checks.** Setup uses the slowest corner (max delays), hold uses the fastest corner (min delays).
:::

## Where the numbers come from: a path budget

Launch flop → logic → wire → capture flop. The data launches at the clock edge plus $t_{cq}$, then travels, and must arrive at least $t_{su}$ before the *next* capture edge ($T$ later):

$$\underbrace{t_{cq,max} + t_{logic,max} + t_{wire,max}}_{\text{latest arrival}} + t_{su} + t_{skew} + t_{jitter} \le T$$

| Term | Value | Notes |
|---|---|---|
| $t_{cq,max}$ | 1.2 ns | launching flop |
| combinational logic | 5.8 ns | slowest path |
| wire/flight time | 1.0 ns | about 6 inches of FR4 at 170 ps/in |
| $t_{su}$ | 0.8 ns | capture flop |
| skew | 0.3 ns | clock arrival difference, unfavourable direction |
| jitter | 0.2 ns | clock period/cycle jitter ([[q0695]]) |
| **Total** | **9.3 ns** | slack = $+0.7$ ns at $T = 10$ ns; $f_{max}=107.5$ MHz |

Hold check at the *fastest* corner: the earliest new data arrives at $t_{cq,min} + t_{path,min} = 0.5 + 0.3 = 0.8$ ns. It must exceed $t_h + t_{skew} = 0.4 + 0.3 = 0.7$ ns for the data launched at this edge not to overwrite the data the capture flop is still holding. Slack $+0.1$ ns.

> [!TIP]
> Setup is checked at the **slow** corner (high temperature, low voltage, slow process). Hold is checked at the **fast** corner. They are different corners and they fail in different ways.

If hold had slack of $-0.2$ ns, changing $T$ from 10 ns to 20 ns would not change it. You'd insert about 0.3 ns of delay into the data path (a buffer or a longer route) or reduce skew. Doing that eats into setup slack, so you re-check both.

## Metastability: what a violation really does

A flop's master latch is a pair of cross-coupled inverters. Normally the input pushes it firmly to one state before the clock closes the loop. If the input changes right at the closing moment, the latch is left balanced near its unstable midpoint. It will roll to one side, but the escape time grows exponentially as it starts closer to the balance point:

$$MTBF = \frac{e^{t_r/\tau}}{T_w\,f_c\,f_d}$$

## How signal integrity moves the window

The datasheet defines $t_{su}$ and $t_h$ relative to where the input crosses a threshold, at a stated slew. Anything that changes *when* the data crosses, or *whether* it crosses cleanly, changes the real window:

- **Slow data edge**: crosses later by half the ramp time; also datasheets show setup growing with input slew. Compare a 10 ns and a 1 ns 10–90% edge: the 50% point of a linear ramp arrives about 5.6 ns later (6.25 ns versus 0.63 ns after the edge starts), enough to fail a 100 MHz bus ([[q0689]]).
- **Ringing/ringback**: a dip back toward the threshold close to the capture edge looks like data moving inside the window ([[q0691]]).
- **Crosstalk and ground bounce**: add voltage noise, which turns into time shifts $\sigma_t = \sigma_v/SR$ at the crossing.
- **Clock jitter and duty cycle**: subtract from the period or the window directly.
- **Skew between clock and data** (trace-length mismatch): at 170 ps/inch, 0.5 inch of mismatch is 85 ps, which matters for DDR-class interfaces.

## Source-synchronous example

An SPI or parallel bus launched by a master with clock on the same connector: the receiver samples at a clock edge half a period after the data changes (or on the opposite edge). With a 25 MHz clock (40 ns period), half period is 20 ns and setup slack is huge; at 100 MHz it's 5 ns; at 400 MHz it's 1.25 ns, where a 0.4 ns skew plus 0.3 ns jitter plus 0.5 ns of setup suddenly matter. That's why faster interfaces use calibration and training: they move the sampling instant to the center of the data eye ([[q0698]]).

## Quick sanity checks in the lab

1. Scope the data and clock at the receiver pin, trigger on the clock, and measure the time from the data's 50% crossing to the clock's 50% crossing. Compare with the datasheet's $t_{su}$/$t_h$.
2. Repeat at hot and cold and low and high supply: both margins move.
3. If the capture is intermittent, look for data moving close to the clock edge, or ringback near the threshold at the capture moment.

::: applications
- **FPGA I/O timing constraints**: input delay and output delay constraints are setup/hold budgets at the pins.
- **DDR memory interfaces**: write-leveling and read training set the data-to-strobe timing to keep the sample at the middle of the eye.
- **SPI/parallel buses at high clock rates**: choosing clock polarity/phase (modes) shifts the capture edge relative to data change.
- **ADC and DAC interfaces**: data and clock skew and jitter set the achievable sample timing.
- **Clock domain crossing**: 2-flop synchronizers and handshake/FIFO structures manage metastability.
- **Board design**: length matching and termination to preserve skew and monotonic edges at clock-sensitive nets.
:::

::: assumptions
- **Positive-edge-triggered D flip-flop** with a single clock; latches and multi-edge schemes (DDR) have analogous but different windows.
- **Worst-case (corner) numbers**: setup with max delays, hold with min delays. Typical numbers give false confidence.
- **Skew treated as a single number**; in reality on-chip variation and clock-tree uncertainty add statistical terms.
- **Metastability model** is the standard exponential-resolution model with illustrative constants.
- **Data and clock arrive as clean edges**; the SI section emphasises that this is not guaranteed, so the effective window is smaller than the datasheet's.
:::

::: followups
### Why can't you fix a hold violation by lowering the clock frequency?
Hold is a race between the *same* clock edge and the new data launched by it. The period does not appear in the inequality $t_{cq,min} + t_{path,min} \ge t_h + t_{skew}$. Lowering the frequency moves the next edge farther away but the current edge still races its own launched data. The fix is delay in the data path (buffers, longer route) or reducing the clock skew.

### What does the output of a flop look like when it goes metastable?
Q sits at an intermediate voltage (near the threshold) or oscillates, for a random time that can exceed a clock period, then falls to 0 or 1 at random. If downstream logic samples during that time, different gates may interpret the level differently, so the error spreads. That's why synchronizers are used.

### A bus works at room temperature but fails cold. Setup or hold?
Cold silicon is faster, so propagation delays shrink: that helps setup but threatens **hold** (min-delay paths get shorter). I'd suspect hold. (One caveat: in advanced low-voltage processes "temperature inversion" can make cold the *slow* corner, so check which corner is fast for the parts involved.) I'd confirm by measuring data-to-clock timing at the capture pin at cold, then add delay or adjust the sampling phase.

### How does a slower input edge change the setup requirement?
Datasheet setup is defined for a specified input slew. A slower edge crosses the receiver's internal threshold later, and the flop's internal comparator is less decisive, so the required setup grows. Many datasheets give $t_{su}$ vs slew curves. If you don't derate, you can fail at the slow-edge corner of the driver.

### Design a synchronizer for an asynchronous button into a 100 MHz domain. How many stages and why?
Two flip-flops in series clocked by the destination clock, with the first stage's output feeding only the second. The first can go metastable; the second gets a full period (about 10 ns minus setup) to see it resolved. With $\tau \approx 100$ ps that's $e^{80}$-scale resolution, an MTBF astronomically larger than the product lifetime. For very high frequencies or safety-critical systems, add a third stage. The button also needs debouncing and a Schmitt input ([[q0692]]).
:::
