::: basics
### In plain words
To characterize GPU performance, you measure three things: compute (how many operations per second it can do), memory (how many bytes per second it can move), and efficiency (work per watt). Then you check which limit your workload actually hits. For graphics, you also look at frame time. Peak numbers say what the chip could do, not what your program gets.

### Picture it
Picture a factory with fast workers inside and one narrow loading door for materials. If each product needs little material, the workers are the limit. If each product needs a lot, the door is the limit, and hiring more workers changes nothing. A GPU is like that. Kernels that do little arithmetic per byte are limited by the memory "door".

### Words you need
- **FLOPS**: floating-point operations per second. A fused multiply-add counts as 2.
- **Memory bandwidth**: bytes per second between the GPU and its memory.
- **Arithmetic intensity**: operations done per byte of memory traffic.
- **Roofline model**: attainable speed is the smaller of peak compute and bandwidth times intensity.
- **Frame time**: time to draw one frame. Worst-case frames show stutter that average FPS hides.

### The simplest example
Take 80 clusters of 128 lanes at 1.7 GHz. Peak is $80 \times 128 \times 2 \times 1.7\text{ GHz} \approx 34.8$ TFLOPS. A 256-bit memory bus at 16 Gb/s per pin gives $256 \times 16 / 8 = 512$ GB/s. Now run $y = ax + y$: it does 2 operations per 12 bytes moved, which is 1/6 operation per byte. The memory limit gives $512 \times 10^9 / 6 \approx 85$ GFLOPS, about 0.24% of peak.

That is the whole idea: find which limit binds. The rest of this page covers the ridge point where the two limits meet (about 68 operations per byte here), graphics rates, sustained clocks and power, and counting data copies.
:::

::: testing
Whether you can turn "how fast is this GPU?" into numbers and, more importantly, say **what limits it**. The interviewer is looking for:

1. Peak compute (FLOPS) derived from cores, lanes and clock, not just quoted from a spec sheet.
2. Memory bandwidth and the **roofline** idea: arithmetic intensity decides whether you are compute-bound or memory-bound.
3. Graphics-specific rates (pixel/texel fill rate, triangles per second) and **frame time**, not just average FPS.
4. Efficiency metrics: performance per watt, utilization/occupancy, achieved versus peak.
5. Awareness that benchmarks must match your workload, and that transfer over PCIe can dominate.
:::

::: why
GPU purchasing, kernel tuning and architecture decisions all start with "what is the bottleneck?". A hardware engineer who can say "this kernel does 2 FLOP per 12 bytes, so it will never beat bandwidth" saves months of misdirected optimization. The CPU version of this question is [[q0918]]; the GPU version adds massive parallelism, memory bandwidth as a first-class limit and graphics throughput metrics. It also feeds directly into SoC power and area budgeting ([[q0933]]).
:::

::: concepts
- **Peak throughput**: lanes $\times$ 2 FLOP (a fused multiply-add counts as two) $\times$ clock. See [[q0920]].
- **Memory bandwidth**: bus width $\times$ data rate $/ 8$. Often the real limit.
- **Arithmetic intensity**: FLOP performed per byte moved to or from DRAM. The x-axis of a roofline plot.
- **Occupancy and utilization**: how much of the machine the workload actually fills. See [[q0923]].
- **Graphics rates**: pixel fill rate (ROPs $\times$ clock), texel rate (texture units $\times$ clock), triangle/primitive rate. See [[q0921]].
- **Latency vs throughput metrics**: average FPS versus frame-time percentiles; kernel time versus end-to-end time including transfers.
- **Performance per watt**: the metric that decides datacenter and mobile designs. See [[q0918]] for the CPU analog.
:::

::: answer
"I'd characterize it on three axes: compute, memory and efficiency, and then check which one the workload actually hits.

Compute first. Peak FLOPS is the number of FP32 lanes times two, because a fused multiply-add is two operations, times the clock. A GPU with 80 SMs, 128 lanes each at 1.7 GHz is about 35 TFLOPS. Then memory bandwidth: a 256-bit GDDR6 bus at 16 Gb/s per pin is 512 GB/s. Divide the two and you get the ridge point, about 68 FLOP per byte. A kernel below that intensity is memory-bound, so a vector add or SAXPY gets under one percent of peak no matter how many cores you have. A big matrix multiply with good tiling is far above it and can approach peak.

For graphics I'd add pixel and texel fill rates and, importantly, frame time, so I'd look at the 99th-percentile frame, not just average FPS, because stutter is what people notice.

Then efficiency: performance per watt, and achieved versus peak, meaning occupancy, divergence, coalescing. And I'd always measure on my own workload, including host-to-device transfers, because a synthetic benchmark number can be nowhere near what my application sees."
:::

::: technical
**Peak compute.**
$$P_{peak} = N_{SM}\times N_{lane}\times 2\times f$$
For 80 SMs $\times$ 128 FP32 lanes $\times$ 2 $\times$ 1.7 GHz $= 34.8$ TFLOPS. (Lower-precision modes and tensor units multiply this for FP16/INT8 matrix work.)

**Memory bandwidth.** $BW = \text{bus width}\times\text{data rate}/8$. A 256-bit bus at 16 Gb/s per pin is $256\times16/8=512$ GB/s.

**Roofline model.** For arithmetic intensity $I$ (FLOP/byte), attainable performance is
$$P(I)=\min\left(P_{peak},\; BW\times I\right)$$
The ridge point is $I^*=P_{peak}/BW = 34.8\text{ TFLOPS}/512\text{ GB/s}=68$ FLOP/B.
- SAXPY ($y=ax+y$, FP32): 2 FLOP, 12 bytes (read $x$, read $y$, write $y$), $I=0.167$, so $P=85$ GFLOPS, which is 0.24% of peak.
- Tiled $N\times N$ matrix multiply: $2N^3$ FLOP over at best $3N^2\times4$ bytes, $I=N/6$. For $N=4096$ that is 683 FLOP/B, well past the ridge, so compute-bound.

**Graphics rates.**
- Pixel fill rate = ROPs $\times f$: 64 $\times$ 1.7 GHz = 109 Gpixel/s.
- Texel rate = texture units $\times f$: 320 $\times$ 1.7 GHz = 544 Gtexel/s.
- Frame budget: 60 fps is 16.7 ms, 120 fps is 8.3 ms. 4K is 8.29 Mpixel; at 60 fps with an average overdraw of 3 that is 1.5 Gpixel/s, far below the raw fill rate, which shows that real games are limited by shading, bandwidth and geometry rather than fill alone.

**Efficiency.** Performance per watt (for example FLOPS/W), utilization $=P_{achieved}/P_{peak}$, and energy per frame or per inference.

**Latency and end to end.** Report kernel time and total time including PCIe copies. PCIe 4.0 x16 gives about 31.5 GB/s theoretical.
:::

::: short
"I'd look at compute, memory and efficiency. Peak FLOPS is SMs times lanes times two times clock, about 35 TFLOPS for a typical card. Memory bandwidth is bus width times data rate over eight, say 512 GB/s. The ratio, the ridge point of the roofline, tells me whether a kernel is compute- or memory-bound. For graphics I add fill rate and frame-time percentiles. Then performance per watt and achieved versus peak, measured on my real workload including transfers."
:::

::: long
"There's no single GPU performance number, so I characterize it along a few axes and then work out which one limits my workload.

Start with raw capability. Peak compute is the number of SMs times FP32 lanes per SM times two, since a fused multiply-add counts as two operations, times the clock. Eighty SMs with 128 lanes at 1.7 GHz is about 35 TFLOPS. Peak memory bandwidth is bus width times data rate over eight: a 256-bit GDDR6 bus at 16 gigabits per pin is 512 GB/s.

The way I connect those is the roofline model. Attainable performance is the smaller of peak compute and bandwidth times arithmetic intensity, where intensity is FLOP per byte of DRAM traffic. The ridge point here is 35 TFLOPS over 512 GB/s, about 68 FLOP per byte. A SAXPY does two FLOP for twelve bytes, so it tops out around 85 GFLOPS, a quarter of one percent of peak, and no amount of extra cores helps. A big tiled matrix multiply is hundreds of FLOP per byte and can get close to peak.

For graphics I'd add pixel fill rate, which is ROPs times clock, texel rate and geometry throughput, but the number that matches what a user feels is frame time. I'd report the 99th percentile frame, not just average FPS.

Then efficiency: performance per watt, and achieved versus peak. Low achieved numbers point to occupancy, divergence or uncoalesced memory access.

Finally, I'd benchmark my actual application, including host-to-device copies over PCIe, because a kernel that's ten times faster can still lose end to end if the transfer takes longer than the compute."
:::

::: terms
- **FLOPS**: floating-point operations per second; an FMA counts as 2.
- **Memory bandwidth**: bytes per second between the GPU and its DRAM.
- **Arithmetic intensity**: FLOP per byte of DRAM traffic.
- **Roofline model**: performance bound $\min(P_{peak}, BW\cdot I)$.
- **Ridge point**: the intensity where the memory and compute bounds meet.
- **Fill rate**: pixels (ROPs $\times f$) or texels (texture units $\times f$) per second.
- **Occupancy**: resident warps divided by the maximum an SM supports.
- **Frame time / 1% lows**: time per frame and the worst-percentile frames that show stutter.
- **Performance per watt**: throughput divided by power; the key efficiency metric.
:::

::: exceptional
**An average answer** lists "number of cores, clock speed, memory size, FPS".

**An exceptional answer**:
- Derives peak FLOPS and bandwidth from the architecture and states the FMA = 2 convention.
- Uses the **roofline** to say which workloads are memory- or compute-bound, with a worked SAXPY versus GEMM comparison.
- Separates **peak** from **achieved** and names the usual losses: occupancy, divergence, uncoalesced access, small kernels, launch overhead.
- Reports frame-time percentiles for graphics and end-to-end time (with transfers) for compute.
- Includes power: performance per watt and thermal throttling, because sustained clocks are lower than boost clocks.
- States that no benchmark replaces measuring your own workload.
:::

::: mistakes
- **Quoting core count or clock as "performance".** A GPU with more lanes can be slower if it is bandwidth-bound.
- **Forgetting FMA counts as two FLOPs**, giving half the right peak.
- **Comparing FLOPS across precisions.** FP32, FP16 and tensor-core numbers are different units of work.
- **Treating average FPS as the whole story.** Two GPUs with the same average can feel very different if one has frame-time spikes.
- **Ignoring memory bandwidth** and assuming adding cores speeds up any kernel.
- **Ignoring transfers.** The PCIe copy can exceed the kernel time (see [[q0925]]).
- **Using boost clock numbers for sustained loads.** Thermal and power limits throttle real clocks.
:::

::: deep
## Peak numbers: where they come from

A GPU is an array of streaming multiprocessors (SMs), each with many lanes. If each lane can issue one fused multiply-add per cycle, then the lane produces $a\cdot b+c$ (two floating-point operations) every clock:

$$P_{peak}=N_{SM}\times N_{lane/SM}\times 2\times f_{clk}$$

Plugging in 80 SMs, 128 lanes and 1.7 GHz gives 34.8 TFLOPS. Two things quietly change this number in real life. First, the quoted clock is usually a boost clock; under sustained load the power and thermal limits pull it lower. Second, the peak assumes every lane is issuing useful FMAs every cycle, with no stalls, no divergence and no integer or address instructions competing for the same issue slots.

Memory bandwidth is the other pillar:

$$BW=\frac{\text{bus width (bits)}\times\text{data rate (Gb/s per pin)}}{8}$$

256 bits at 16 Gb/s is 512 GB/s. Notice the ratio: 34.8 TFLOPS against 0.512 TB/s means the machine can do 68 FLOP in the time it takes to fetch one byte from DRAM. That imbalance is the whole story of GPU performance tuning.

## The roofline model

Take a kernel that performs $W$ FLOP and moves $Q$ bytes to and from DRAM. Its arithmetic intensity is $I=W/Q$. The execution time is at least $\max(W/P_{peak},\,Q/BW)$, so the attainable rate is

$$P(I)=\min\left(P_{peak},\;BW\cdot I\right)$$

On a log-log plot this is a sloped line (memory-bound) that hits a flat roof (compute-bound) at the ridge point $I^*=P_{peak}/BW$.

**How to move a kernel right.** Reuse data in shared memory or registers (tiling), fuse kernels so intermediates never touch DRAM, use lower-precision formats (FP16 halves the bytes), compress, or restructure the algorithm. Moving right is usually worth more than micro-optimizing instructions.

**Worked example: SAXPY.** For $N$ elements: reads $x$ (4 B), reads $y$ (4 B), writes $y$ (4 B) = 12 B per element; 2 FLOP per element. $I=1/6$ FLOP/B. At 512 GB/s: $512\times10^9/12=42.7\times10^9$ elements/s, i.e. 85 GFLOPS. A CPU with 50 GB/s of DRAM bandwidth would manage about 8 GFLOPS on the same kernel, so the speed-up is about the bandwidth ratio (10x), not the FLOPS ratio (which could be 30x or more).

**Worked example: GEMM.** Multiplying two $4096\times4096$ FP32 matrices is $2N^3=137$ GFLOP. At ideal peak that is $137/34{,}800=3.9$ ms. A CPU at 1 TFLOPS peak needs at least 137 ms. Realistic libraries reach perhaps 70 to 90% of peak on large GEMM, but the exact figure is hardware- and library-dependent.

> [!UNCERTAIN]
> Achieved fractions of peak (for example 70 to 90% for large GEMM) vary by architecture, library version and clocks. Treat them as typical ranges, not specifications.

## Graphics metrics

Compute-style numbers do not capture rendering. The graphics pipeline ([[q0921]]) has fixed-function stages with their own rates:

| Metric | Formula | Example |
|---|---|---|
| Pixel fill rate | ROPs $\times f$ | 64 $\times$ 1.7 GHz = 109 Gpixel/s |
| Texel rate | texture units $\times f$ | 320 $\times$ 1.7 GHz = 544 Gtexel/s |
| Triangle setup rate | setup units $\times f$ (often 1 per clock per raster engine) | architecture-specific |
| Memory bandwidth | as above | 512 GB/s |

Real games rarely hit the fill-rate roof. A 4K frame is 8.29 Mpixel. At 60 fps and overdraw 3, that is $8.29\times10^6\times60\times3=1.49$ Gpixel/s of shaded pixels, only 1.4% of the raw ROP rate. What limits you is shader arithmetic per pixel, texture and framebuffer bandwidth, and geometry or draw-call overhead on the CPU side. Profile each stage to find which one saturates first.

**Frame time, not just FPS.** Average FPS hides spikes. A frame budget of 16.7 ms at 60 fps means a single 50 ms frame is a visible hitch. Report the average, the 99th percentile (or "1% low") frame time and the maximum.

## Efficiency and sustained performance

- **Performance per watt.** 34.8 TFLOPS at 250 W is 139 GFLOPS/W. This matters for datacenters (power and cooling cost) and phones (a few watts).
- **Utilization / occupancy.** Profilers report achieved occupancy, warp execution efficiency (divergence), memory-coalescing efficiency and which unit is the limiter. A kernel at 20% of peak with 90% memory-bus utilization is bandwidth-bound; one at 20% of peak with 30% bus utilization and low occupancy is latency- or launch-bound. See [[q0923]].
- **Thermal and power limits.** GPUs boost until they hit a power or temperature limit. A 5-minute benchmark may sustain different clocks from a 5-second one.
- **Launch overhead and small kernels.** A kernel launch costs on the order of several microseconds. A kernel that only does 20 µs of work spends a visible fraction of its time in overhead. Batch work or fuse kernels.

## End-to-end measurement

For compute offload the relevant time is total, not kernel-only:

$$t_{total}=t_{H\to D}+t_{kernel}+t_{D\to H}$$

For the GEMM above, moving three 67 MB matrices (201 MB) at 25 GB/s effective PCIe 4.0 x16 takes 8.1 ms, double the 3.9 ms of compute. The GPU "is 35x faster than the CPU" in the kernel, but the end-to-end speed-up is $137/(3.9+8.1)\approx11\times$ at best. Keeping data resident on the GPU across many kernels (or using larger problems whose compute grows as $N^3$ while transfer grows as $N^2$) is the standard fix.

> [!INTERVIEW]
> A great closing line: "peak numbers tell you what the machine could do, the roofline tells you what the kernel can do, and a profiler tells you why it doesn't."
:::

::: applications
- **Choosing a GPU for a workload**: compare FP32 or FP16 TFLOPS for compute-bound jobs, memory bandwidth and capacity for bandwidth-bound ones.
- **Tuning CUDA/OpenCL/compute-shader kernels**: roofline analysis to decide between tiling for reuse versus occupancy tuning.
- **Game performance work**: per-stage profiling (vertex, pixel, ROP, bandwidth) and frame-time capture.
- **ML training and inference**: tokens/s or images/s per watt, plus memory capacity and interconnect bandwidth.
- **SoC GPU sizing**: mobile architects set lanes and bandwidth within a watt budget, see [[q0933]].
:::

::: assumptions
- Peak FLOPS counts FP32 FMAs at a fixed (boost) clock; real sustained clock may be lower.
- The roofline uses DRAM traffic only. Caches and shared memory change the effective $I$; a more detailed model adds cache levels as extra roofs.
- The example GPU (80 SMs, 128 lanes, 1.7 GHz, 256-bit GDDR6 at 16 Gb/s) is illustrative, not a specific product.
- Triangle and rasterizer rates are architecture-specific; check the vendor documentation.
- If the workload is latency-bound (tiny kernels, dependent chains, CPU-side draw-call limits), neither roof applies.
:::

::: followups
### Why does a GPU with twice the TFLOPS sometimes run a program no faster?
The program is probably memory-bound: intensity below the ridge point, so bandwidth sets the speed. Doubling lanes without raising bandwidth does nothing. Check by comparing achieved bandwidth with peak. If it is near peak, the kernel needs more reuse, not more cores.

### How would you tell if a kernel is memory-bound or compute-bound?
Compute its arithmetic intensity (FLOP over DRAM bytes) and compare with the ridge point. Confirm with a profiler: memory-bound kernels show high DRAM bandwidth utilization and low ALU utilization; compute-bound ones show the opposite. A quick experiment is to lower the memory clock or the core clock and see which one changes the run time.

### Why report 99th-percentile frame time for games?
Perception is driven by the worst frames. A game averaging 100 fps with one 60 ms frame every second feels worse than a steady 60 fps. Percentile frame time captures the spikes from shader compilation, streaming or thermal throttling that averages hide.

### An FP16 tensor-unit GPU claims 300 TFLOPS. Does it train a model 10x faster than a 30 TFLOPS FP32 part?
Not automatically. The 300 is a peak for dense matrix operations in low precision. Real models also spend time on memory-bound operations (normalization, activations, data loading), communication, and precision conversions. The end-to-end gain is bounded by Amdahl: if 90% of the time is accelerated by 10x, the total is $1/(0.1+0.09)=5.3\times$.

### Your kernel takes 4 ms on the GPU but the application only improved from 130 ms to 90 ms. Why?
The kernel is not the whole time. Likely suspects are PCIe transfers (hundreds of MB at about 25 GB/s is milliseconds), launch and synchronization overhead, serial CPU code that remains, or pageable-memory copies. Profile the timeline, use pinned memory and asynchronous copies, and keep data resident.
:::
