::: basics
### In plain words
A UART receiver has no clock wire, but it knows how long one bit should last because both sides agreed on the speed. The line rests high, so a falling edge can only mean "a byte starts now". From that edge the receiver counts time with its own clock. It reads the line once per bit time, near the middle of each bit.

### Picture it
Picture stepping stones across a stream. You spot the edge of the first stone. You step half a stone in, so you stand in the middle of it. Then you take strides exactly one stone long, and each lands in the middle of the next stone. The middle is the safest spot, because it is far from both edges. If your stride is slightly off, the error adds up over ten stones. But once you cross, you restart at the next bank.

### Words you need
- **Start edge**: the falling edge that begins a byte. It is the receiver's only timing reference.
- **Bit time**: the length of one bit, which is 1 divided by the baud rate. See [[q0775]].
- **Mid-bit sampling**: reading the line at the middle of each bit, where the signal is steadiest.
- **Framing error**: the stop bit was read low, which usually means the two speeds do not match.

### The simplest example
Take 115200 baud, so one bit lasts about 8.68 µs. The receiver sees the line fall at time zero. It waits half a bit, about 4.34 µs, and checks the line is still low. If so, it is a real start bit. Then it reads the line every 8.68 µs: at about 13.0 µs, 21.7 µs, and so on for the eight data bits. The stop bit is read at 9.5 bit times, about 82.5 µs, and should be high. That is the whole idea. The rest of this page shows the tick-by-tick counting, derives the tolerance of about 5%, and explains what framing errors reveal.
:::

::: testing
Whether you can explain **how a receiver recovers data from a single wire with no clock**: start-edge detection, local timing from the agreed baud rate, mid-bit sampling, and re-synchronisation every frame. It tests understanding, not memory: you should be able to say *where* the receiver samples and *why*, and how much clock error that tolerates.

Hidden sub-skills: reasoning about timing budgets, the role of the idle level and stop bit, noise rejection (glitch filtering, majority vote), and linking to oversampling ([[q0779]]).
:::

::: why
This is the heart of UART. Once you can explain it, you can debug garbled serial output: you know the sampling point is the middle of the bit, that error accumulates linearly across the frame, and that the start edge is the only reference. Interviewers like it because the answer is a small, complete piece of engineering reasoning: a protocol design constraint, the derived tolerance, and a hardware mechanism. It also leads naturally into oversampling and clock-and-data recovery in faster links.
:::

::: concepts
- **Idle level and start edge**: the line idles high, so a start bit is a falling edge the receiver can hunt for. See [[q0771]].
- **Agreed bit time**: both sides know $T_b = 1/\text{baud}$ in advance; see [[q0775]].
- **Mid-bit sampling**: sample at $T_b/2$ after each bit begins, where the signal is farthest from both edges.
- **Free-running local clock**: the receiver counts ticks of its own oscillator (usually 16 per bit). See [[q0779]].
- **Re-synchronisation per frame**: timing restarts from each start edge, so error cannot accumulate beyond one frame. See [[q0777]].
- **Stop-bit check**: confirms that the frame lined up; a low stop bit gives a framing error.
:::

::: answer
"The receiver doesn't get a clock, but it knows how long a bit should last because both sides agreed on the baud rate. The line idles high, so the receiver just watches for a falling edge. That edge is the start bit and it's the only synchronisation it gets.

From that edge, it starts counting with its own clock. It waits half a bit time, so it lands in the middle of the start bit, and checks the line is still low, which filters out glitches. Then it waits one full bit time at a time, and each time it samples the line, so each sample lands in the middle of a data bit. Sampling in the middle matters because that's the point farthest from both edges, where the signal is steadiest, so it has the most margin against clock error and noise.

After the data bits it samples the stop bit, which should be high. If it isn't, that's a framing error. Then it goes back to waiting for the next falling edge, and everything restarts.

The reason this works without a clock is that errors only accumulate over one frame. Even if my clock is a couple of percent off, over ten bits the sampling point only slides a fraction of a bit, and then the next start edge resets it. The limit is about 5% total mismatch for 8N1."
:::

::: technical
**Receiver algorithm (8N1, $N$ ticks per bit, typically $N=16$).**

1. Idle: sample the RX line every tick. Wait for a high-to-low transition.
2. On the first low sample at tick 0, start counting. At tick $N/2$ ($=8$) the sample should still be low: if not, treat it as a glitch and return to idle.
3. At tick $N/2 + kN$ ($k = 1\ldots8$) sample data bit $D_{k-1}$ (LSB first) and shift into the register.
4. At tick $N/2 + 9N$ (bit-time 9.5) sample the stop bit. High is valid; low sets the framing error flag.
5. Return to idle immediately (some UARTs return at the middle of the stop bit so they can catch an early next start edge).

**Why the middle.** Each bit cell is $T_b$ wide, with transitions at its ends. Edges are where the signal is changing, where jitter and slow rise times blur it. Sampling at the centre puts the decision $T_b/2$ from each edge, so the sample can move by up to $\pm T_b/2$ before it hits a neighbouring bit.

**Error budget.** If the receiver's bit time is $T_b(1+\varepsilon)$, the sample for bit $k$ (start = 0) is displaced by $(k+0.5)T_b\varepsilon$. At the stop bit: $9.5\,T_b\varepsilon < 0.5\,T_b \Rightarrow \varepsilon < 5.26\%$. With 16x oversampling the start-edge detection has $\pm 1/16$ bit uncertainty, so $\varepsilon < (0.5-0.0625)/9.5 = 4.6\%$. Edge slew, jitter and noise justify budgeting 3 to 4%.

**Noise rejection.** The half-bit check on the start bit rejects narrow glitches. Many UARTs take three samples around the centre (ticks 7, 8, 9) and use the majority; a single noisy sample does not change the result, though it may set a noise flag.

**What a framing error means.** At the stop bit the receiver expects 1. A 0 means the sampling was misaligned (baud mismatch), a break condition, or an incorrectly configured frame length.
:::

::: short
"The line idles high, so the receiver waits for the falling start edge. From that edge it counts its own bit times using the agreed baud rate. It waits half a bit to land in the middle of the start bit and confirms it's still low, then samples once per bit time, so every sample lands in the middle of a bit, where the signal is steadiest. After the data it checks the stop bit is high. Because it re-syncs on every start edge, clock error only builds up over one frame, so up to a few percent mismatch is tolerable."

::: long
"Even though there's no clock wire, the receiver has three things to work with: the line idles high, both sides agreed on the bit time, and each byte begins with a start bit that's a guaranteed falling edge.

So the receiver sits there sampling the line with its own fast clock. Usually it's sixteen times the baud rate. When it sees the line go low, that's the start of a frame, and it begins counting its own ticks. It waits half a bit, eight ticks, and checks again that the line is still low. If it's high again, it was a glitch and the receiver goes back to idle. If it's low, it's a real start bit and now it's sitting in the middle of that bit.

From there, it waits a whole bit time, sixteen ticks, and samples. That's the middle of the first data bit. Wait sixteen more, sample the next bit, and so on, shifting the bits into a register, least significant bit first. After the data and optional parity, it samples the stop bit, which has to be high. If it is, the byte is good and a flag goes up. If not, it's a framing error, and that's the classic sign that the baud rates don't match.

Why the middle of the bit? It's the point farthest from both edges, so it tolerates the most clock error and noise. How much error? The stop bit sample is 9.5 bit times after the start edge, and it has to stay within half a bit of the true centre, so the total mismatch limit is half over nine and a half, about 5%, and I'd design for three to four. And because the next start edge re-aligns everything, errors never accumulate beyond one frame.

Some UARTs take three samples around the middle and do a majority vote to reject noise."
:::

::: terms
- **Start edge**: the falling transition from idle that begins a frame; the receiver's only sync event.
- **Bit time ($T_b$)**: $1/\text{baud}$.
- **Mid-bit sampling**: sampling at $T_b/2$ into each bit cell.
- **Oversampling clock**: receiver tick running at $N\times$ baud ($N$ = 8 or 16).
- **Framing error**: stop bit read as 0 instead of 1.
- **Glitch rejection**: re-checking the start bit at half a bit to discard noise spikes.
- **Majority vote**: using the most common of three samples near the bit centre.
- **Clock tolerance**: allowed frequency mismatch, about 5% theoretical for 8N1.
:::

::: exceptional
**An average answer** says "it samples in the middle of each bit using the baud rate".

**An exceptional answer**:
- Walks the whole sequence: idle high, falling edge, half-bit confirmation, one sample per bit, stop-bit check, back to idle.
- Explains *why* mid-bit and *why* half-bit confirmation (centre alignment plus glitch rejection).
- Derives the tolerance: $9.5\varepsilon<0.5$ gives 5.26%, and says what it reduces to in practice.
- Mentions oversampling (16x) and majority voting without being asked, and links to what a framing error means.
- Shows awareness that the same idea scales up: clock-and-data recovery in high-speed links is the continuous version.
:::

::: mistakes
- **"The receiver syncs once and keeps time forever."** It re-syncs every frame; if it only synced once, even a 0.01% error would eventually fail.
- **"It samples on the edge of the bit."** Sampling at the edge is the worst place; the centre is best.
- **"The start bit is the clock."** It's a single edge reference per frame, not a periodic clock.
- **Forgetting the glitch check.** Without it, any noise spike on an idle line starts a bogus frame.
- **Believing 5% means any error below 5% is fine.** That limit is the theoretical edge with zero jitter and perfect edge detection; budget 3 to 4%.
- **Believing the stop bit carries data.** It is a check that alignment was right, and it restores the idle level.
:::

::: deep
## The three facts the receiver exploits

The receiver does not know the transmitter's clock, but it knows:

1. **The idle level is high.** So a falling edge can only be the start of a frame.
2. **The nominal bit time** (from the baud rate setting).
3. **The frame length** (10 bits in 8N1), which is short.

Because the frame is short, the receiver's own clock only has to stay accurate for about 10 bit times. For a quartz-referenced clock this is trivial, and even for an RC oscillator it is easy. Contrast with a continuous stream where the clock must be tracked indefinitely.

The samples are half a bit from every transition.

## Where exactly does the counting happen?

Take 16x oversampling at 115200 baud. The receiver's tick period is $1/(16\times115200) = 0.5425\ \mu s$.

| Event | Tick count after the start edge | Time |
|---|---|---|
| Start edge detected | 0 | 0 |
| Confirm start low (centre of start bit) | 8 | 4.34 us |
| Sample D0 | 24 | 13.0 us |
| Sample D1 | 40 | 21.7 us |
| ... Sample D7 | 136 | 73.8 us |
| Sample stop bit | 152 | 82.5 us |

The general formula is tick $=8 + 16k$ for bit $k$ (start = 0), so the stop bit is at tick $8+16\times 9 = 152$, i.e. 9.5 bit-times, 82.5 us at 115200 (computed: $152 \times 0.5425 = 82.5$ us).

A detail: the receiver detects the edge only when it next samples the line, which can be up to one tick (1/16 of a bit) late. That is a built-in offset of up to $-1/16$ bit, taken out of the tolerance budget.

## What error does to the sampling

Plug in a receiver that is 3% slow: all its tick times scale by 1.03. The stop-bit sample falls at $82.5 \times 1.03 = 84.97$ us while the true stop bit centre is at $82.5$ us ($9.5\times8.68$). The displacement is $2.5$ us or $0.285$ bit. Still within the stop bit, which spans $\pm 4.34$ us around its centre.

## Noise handling and the majority vote

A noise spike less than half a bit wide does very little damage: on an idle line, the half-bit re-check turns a false start into an ignored glitch. Inside a frame, if the sample lands on a spike, the bit is misread; with majority voting on three samples (ticks 7, 8 and 9 around the centre) a single bad sample is out-voted. Some UARTs flag this as a **noise error** even when the majority gives the right value. Parity can catch residual single-bit errors.

## A bit-banged receiver, step by step

If you ever have to write one in firmware (a spare pin, no UART peripheral left), the same algorithm drops out directly. Configure a pin-change interrupt on the falling edge of RX. In the ISR, disable that interrupt and start a timer that fires 1.5 bit-times later: 0.5 to reach the centre of the start bit and 1.0 more to reach the centre of D0. Each timer tick samples the pin, shifts the bit into a byte (LSB first, so shift right and insert at the top), and re-arms for one bit-time. After eight data bits, one more tick samples the stop bit; if it is high, the byte is good, and you re-enable the edge interrupt. At 9600 baud the bit time is 104 us and a modest MCU copes easily; at 115200 the 8.68 us bit leaves almost no room for interrupt latency, and the jitter of the sample points eats into the tolerance budget. That is exactly why hardware UARTs do the sampling themselves with a dedicated oversampling counter.

## Reading a framing error like a detective

A framing error is a measurement, not just a flag. If it appears on every byte, the receiver's baud is wrong by more than the budget: measure one bit on a scope. If it appears only on some bytes, the mismatch is marginal and only certain bit patterns fail. With a fast receiver, a byte whose D7 is 0 is the most sensitive, because the early stop-bit sample lands in D7 and reads a 0. With a slow receiver, the late stop-bit sample lands in the next frame's start bit when bytes are sent back to back, so dense traffic fails while isolated bytes pass. If it appears only at start-up or after sleep, the clock was still settling. If it appears as one framing error followed by a burst of garbage, a break or line glitch put the receiver out of step, and it needs one idle period to recover.

## Why this generalises

High-speed serial links (PCIe, USB, Ethernet, SATA) also have no clock wire, but they cannot rely on a short frame, so they transmit enough transitions (via line coding such as 8b/10b or scrambling) for a **clock-and-data-recovery (CDR)** circuit, a PLL, to keep tracking the phase continuously. UART's start-edge re-sync is the same idea reduced to the minimum: re-align at the start of every short frame, and then free-run.
:::

::: applications
- **Any MCU UART peripheral**: the receive state machine implements exactly this algorithm in hardware.
- **Software (bit-banged) UART**: a timer interrupt or cycle-counted delay samples the pin at 1.5 bit-times after the start edge, then at 1-bit intervals.
- **Auto-baud detection**: measure the time between edges of a known first character (0x55) to set the divisor.
- **Logic analyser decoders**: use the same mid-bit sampling to decode UART traces.
- **Debugging**: a scope measurement of bit width tells whether a framing error is due to baud mismatch.
:::

::: assumptions
- 8N1 frame and 16x oversampling unless stated; 8x or 3x oversampling changes the granularity but not the idea.
- The receiver's local clock is free-running and unrelated in phase to the transmitter's.
- "Error" means a constant relative frequency difference between the two baud generators; real links also have jitter, finite rise time and noise.
- Hardware designs vary: some sample once, some three times, some begin counting at the first low sample and some at a synchronised tick.
- Parity adds one bit, moving the stop sample to 10.5 bit-times and reducing the tolerance to about 4.8%.
:::

::: followups
### Why does the receiver wait half a bit after the falling edge?
To put its first sample in the middle of the start bit, so every subsequent one-bit-time step is also centred in a bit. It also re-checks the line is still low there, which rejects short glitches that would otherwise start a false frame.

### What is the maximum baud-rate mismatch before data is corrupted?
The stop-bit sample at 9.5 bit-times must stay within half a bit: $0.5/9.5 = 5.26\%$ total (sum of both ends). With 16x oversampling about 4.6%; practical budget 3 to 4%.

### How would you implement a software UART receiver?
Wait for the falling edge (interrupt on pin change). Start a timer for 1.5 bit-times so the first sample lands in the middle of D0 (start edge + 0.5 bit to the start-bit centre + 1 bit). Then sample every 1 bit-time, shift in 8 bits LSB first, check the stop bit. At 9600 baud that is 104 us per bit; at 115200 it is 8.68 us, which is tight for a software loop, and interrupt latency becomes the dominant error.

### What if the first byte after power-up is garbage?
The receiver may have started in the middle of a frame, mistaking a data 0 for a start. It recovers on the next idle period and start edge. Systems that need clean starts hold the line idle for a few frame times first, or the protocol begins with a sync character.

### Harder: how does the scheme change if the data contains a long run of zeros?
Nothing, because the receiver uses the start edge only once per frame and counts time afterwards, not data edges. A long run of zeros (up to 8 data zeros after the start bit, 9 low bits in total) is fine as long as the clock error stays within budget. This is different from links that recover the clock from data edges, which need transition-density guarantees.
:::
