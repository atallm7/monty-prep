::: basics
### In plain words
A GPU (graphics processing unit) is a processor built to do a huge number of simple, similar calculations at the same time. A CPU has a few powerful cores that each run one task fast. A GPU has thousands of small, simple arithmetic units, called lanes. It was made to color the millions of pixels on a screen, and the same design now also speeds up science and AI.

### Picture it
Imagine painting a giant mural made of 8 million tiny squares. One master painter works fast but still does one square at a time. A crowd of 10,000 helpers, each painting one square at a time from the same simple instructions, finishes far sooner, even though each helper is slower. A GPU is that crowd.

### Words you need
- **Throughput**: total work finished per second, as opposed to how fast one task finishes.
- **Thread**: one independent stream of work, such as the program for one pixel.
- **Shader**: the small program run for each pixel, each triangle corner (vertex) or each compute thread.
- **SIMT**: single instruction, multiple threads. Groups of threads run the same instruction together.
- **Memory bandwidth**: how many bytes per second can move between memory and the chip.

### The simplest example
A 4K frame is $3840 \times 2160 = 8{,}294{,}400$ pixels, about 8.3 million. At 60 frames per second that is about 498 million pixels per second. Assume 300 arithmetic operations per pixel, counting extra drawing and effects. That is roughly 150 billion operations per second. Each pixel can be shaded without waiting for its neighbors. A modern GPU delivers tens of trillions of operations per second, so this is a modest share.

That is the whole idea: independent work spread across many lanes. The rest of this page shows how a GPU spends its silicon differently from a CPU, how it hides memory delays with many threads, and why memory bandwidth matters as much as raw speed.
:::

::: testing
Whether you can define a GPU by **what it is optimized for**, not just "the chip that draws graphics". The interviewer wants you to:

1. Say it is a massively parallel, throughput-oriented processor with thousands of simple lanes.
2. Explain why graphics maps well to this design: millions of independent pixels and vertices doing the same program.
3. Mention that it has its own high-bandwidth memory system and fixed-function graphics hardware.
4. Recognize that modern GPUs are general-purpose parallel accelerators (compute, ML), not only display chips.
:::

::: why
GPUs are in every phone SoC, game console, laptop and datacenter, and they now drive most AI compute. A hardware engineer is expected to explain what makes them different from a CPU and why that difference exists, because it shapes chip architecture, memory design, power budget and software. This is the definition question that the next six GPU questions build on: [[q0920]] (how it works), [[q0921]] (the pipeline), [[q0922]] (versus CPU), [[q0923]] (optimizations and trade-offs), [[q0924]] (performance) and [[q0925]] (other uses).
:::

::: concepts
- **CPU**: latency-optimized general-purpose processor. See [[q0900]].
- **Throughput computing**: maximizing total work per second rather than speed of one task.
- **Data parallelism**: the same operation applied to many data elements, as with pixels.
- **SIMD/SIMT**: one instruction controls many lanes or threads at once.
- **High-bandwidth memory**: wide, fast DRAM interfaces (GDDR, HBM, or shared LPDDR in SoCs).
- **Fixed-function hardware**: rasterizer, texture units, ray-tracing units, video encoders.
:::

::: answer
"A GPU, or graphics processing unit, is a processor built for massively parallel, throughput-oriented work. Where a CPU has a handful of big, complex cores designed to run one thread as fast as possible, a GPU has hundreds to many thousands of small, simple processing lanes grouped into clusters, and it hides memory latency by switching between thousands of threads rather than by big caches and speculation.

It exists because graphics is embarrassingly parallel. A 4K frame has about eight million pixels, each shaded by the same small program, and every pixel is independent of the others. So you design hardware that runs the same instruction across many pixels at once, with a very wide, high-bandwidth memory system to feed it, plus fixed-function units for things like rasterization and texture filtering.

Today GPUs are really general-purpose parallel accelerators. The same architecture that shades pixels is great at dense linear algebra, so they run scientific computing, video processing and most machine learning training and inference. You'll find them as discrete cards, or as integrated blocks inside SoCs in phones and laptops."
:::

::: technical
**Definition.** A GPU is a throughput-oriented, many-core processor with a SIMT (single instruction, multiple threads) execution model, designed originally for the graphics pipeline and now widely used for general parallel computation (GPGPU).

**Architecture at a glance.**
- **Streaming multiprocessors / compute units**: tens to over a hundred clusters, each containing many ALU lanes (for example 64 to 128 FP32 lanes), a register file, a scheduler, and local shared memory/L1.
- **Warps/wavefronts**: threads are grouped (32 on NVIDIA, 32 or 64 on AMD) and execute in lockstep.
- **Massive multithreading**: thousands of resident threads per cluster hide memory latency; a context switch costs essentially nothing because every thread keeps its registers on chip.
- **Memory system**: wide buses and high-bandwidth DRAM (GDDR6/6X, HBM) giving hundreds of GB/s to multiple TB/s; on integrated GPUs, shared system memory (LPDDR/DDR).
- **Fixed-function units**: rasterizer, texture mapping units, render output units (ROPs), and in recent GPUs ray-tracing and tensor/matrix units.

**Why graphics fits.** A 3840 x 2160 frame has 8.29 million pixels. At 60 frames per second that is about 498 million pixels per second. With, say, 300 floating-point operations per pixel (including overdraw and post-processing) that is roughly 150 GFLOP/s of shading work before geometry, well above one CPU core's capability but a modest share of a modern GPU's tens of TFLOP/s.

**Key figures of merit.** Peak FLOP/s (cores x 2 x clock for FMA), memory bandwidth (GB/s), memory capacity, and power. A representative discrete GPU has on the order of 10,000 FP32 lanes at around 2 GHz giving tens of TFLOP/s, with several hundred GB/s to over 1 TB/s of memory bandwidth.

**Programming model.** Graphics APIs (Vulkan, DirectX, Metal, OpenGL) with shader languages, and compute APIs (CUDA, OpenCL, ROCm/HIP, compute shaders). The programmer writes a kernel for one thread; the hardware runs it on a grid of thousands or millions of threads.
:::

::: short
"A GPU is a throughput-oriented parallel processor with thousands of small lanes that run the same program on many threads at once, backed by very high memory bandwidth and fixed-function graphics units. Graphics is perfect for it because millions of pixels are independent. It hides memory latency with massive multithreading instead of big caches. Today the same hardware also runs compute and machine learning."
:::

::: long
"A GPU is a processor designed for throughput. A CPU is built to finish one task as quickly as possible, so it has a few big cores with deep out-of-order machinery, branch predictors and big caches. A GPU takes the opposite bet: use the silicon for hundreds or thousands of small, simple ALU lanes and run a massive number of threads at once.

The reason is graphics. A 4K frame has about eight million pixels, and at 60 frames per second you shade roughly half a billion pixels a second. Each pixel runs the same small program and doesn't depend on its neighbors, so it's an ideal match for hardware that applies one instruction to a group of threads, say 32 at a time. That's the SIMT model. The GPU is organized into many clusters, each with its own schedulers, register file and shared memory, and the chip has fixed-function blocks for things graphics always needs: rasterization, texture sampling, blending and now ray-tracing.

Memory is the other half of the story. Feeding thousands of lanes needs enormous bandwidth, so GPUs use wide, fast memory like GDDR or HBM, hundreds of GB/s up to terabytes per second. Latency is hidden by keeping thousands of threads resident: when one group stalls on a load, the scheduler switches to another in zero cycles because all the registers are already on chip.

In the last 15 years people realized that the same machine is excellent at any data-parallel work, especially dense linear algebra. That's why GPUs now run scientific simulation, video, crypto and most deep-learning workloads. You see them as discrete cards, or as integrated blocks in phone and laptop SoCs where they share memory with the CPU."
:::

::: terms
- **SIMT**: single instruction, multiple threads; a group of threads runs one instruction stream in lockstep.
- **Warp / wavefront**: the hardware group of threads (32 or 64) that execute together.
- **Streaming multiprocessor (SM) / compute unit (CU)**: a cluster of lanes with scheduler, registers and shared memory.
- **Shader**: a small program run per vertex, pixel or compute thread.
- **Throughput**: total work completed per unit time.
- **GDDR / HBM**: high-bandwidth graphics and stacked memory technologies.
- **ROP / TMU**: render output unit (blending) and texture mapping unit.
- **GPGPU**: general-purpose computing on a GPU.
:::

::: exceptional
**An average answer** says "a GPU is a chip for graphics with many cores".

**An exceptional answer**:
- Frames it as a **design philosophy**: throughput over latency, using area for lanes rather than caches and speculation.
- Explains *why* graphics maps to it, with a number (8.3 million pixels x 60 fps).
- Names the key mechanisms: SIMT/warps, latency hiding by multithreading, high-bandwidth memory, fixed-function blocks.
- Makes the point that bandwidth, not only FLOPS, defines a GPU.
- Notes the generalization to GPGPU and AI, and distinguishes discrete GPUs from integrated ones in SoCs.
:::

::: mistakes
- **"A GPU is just a CPU with more cores."** The cores are simpler, execute in lockstep groups, and rely on multithreading to hide latency.
- **"GPU cores are faster."** Each lane is typically slower than a CPU core; the win comes from parallelism.
- **Only mentioning graphics.** Compute and AI are major uses.
- **Ignoring memory bandwidth.** Many GPU workloads are limited by memory, not FLOPS.
- **Equating CUDA cores with CPU cores.** A "CUDA core" is one FP32 lane, closer to one SIMD lane than a full core.
- **Thinking GPUs run any code well.** Branchy, serial or pointer-chasing code performs poorly.
:::

## Why does graphics map so well?

Look at the work in one frame.

- Pixels per 4K frame: $3840\times2160=8{,}294{,}400$.
- At 60 fps: $8.29\times10^6\times60=4.98\times10^8$ pixels per second.
- With overdraw of 2 and about 150 FP operations per shaded pixel: $4.98\times10^8\times2\times150\approx1.5\times10^{11}$ FLOP/s = 150 GFLOP/s.

A single CPU core with 256-bit SIMD (8 FP32 lanes, FMA on two ports) peaks around $2\times8\times2\times4\text{ GHz}=128$ GFLOP/s, and in practice reaches a fraction of it. A GPU with 10,000 FP32 lanes at 2 GHz has a peak of $10{,}000\times2\times2\times10^9=40$ TFLOP/s. The workload is a few percent of the GPU's capability, which leaves headroom for geometry, lighting, ray tracing and post-processing at high quality.

The important property is independence. Pixel $(x,y)$ can be shaded without waiting on pixel $(x+1,y)$, so you can assign each to a separate thread and the hardware can schedule them in any order. Vertices likewise. That is why the programming model is "write the program for one pixel."

## The latency-hiding trick

A DRAM access takes on the order of 300 to 800 GPU clock cycles. A CPU reduces this pain with caches and out-of-order execution. A GPU instead keeps many warps resident. Suppose each warp executes 10 arithmetic instructions between memory loads and a load takes 400 cycles. To keep the ALUs busy you need enough other warps to fill the 400 cycles. If the SM issues one warp-instruction per cycle per scheduler, each warp supplies about 10 cycles of work per load, so you need roughly $400/10=40$ warps in flight per scheduler to cover the latency. Registers are the constraint: a warp using 64 registers per thread uses $64\times32=2048$ 32-bit registers, so a 64K-register SM holds at most 32 such warps in total, only 8 per scheduler on a four-scheduler SM. That is well short of 40, so real kernels also lean on instruction-level parallelism: each warp issues several independent loads before it needs the first result, which multiplies the latency each warp can cover. Balancing registers per thread against resident warps is the **occupancy** trade-off that GPU programmers tune.

> [!UNCERTAIN]
> DRAM latency in cycles, warp sizes, registers per SM and lanes per SM differ by vendor and generation. Values here are representative orders of magnitude.

## Bandwidth: the other half

FLOPS alone mean nothing without data. A 40 TFLOP/s GPU doing an operation that needs 4 bytes per FLOP would need 160 TB/s, far beyond any memory system. Real GPUs have 0.5 to 3 TB/s (GDDR6X and HBM), so a streaming kernel such as vector add (one FLOP per 12 bytes moved) tops out around $1\times10^{12}/12\approx83$ GFLOP/s at 1 TB/s, which is a tiny fraction of peak. Only operations with high reuse (matrix multiply, convolution, shading with textures cached on chip) get close to peak. This is why GPU architecture is as much about caches, shared memory and memory controllers as ALUs. Compare the CPU/GPU comparison in [[q0922]] and the roofline in [[q0924]].

## Little's law: how much parallelism does a GPU need?

The reason a GPU wants thousands of threads falls out of Little's law: sustained throughput equals the amount in flight divided by latency, $\text{throughput}=\text{concurrency}/\text{latency}$. Rearranged, the data that must be in flight to saturate memory is

$$\text{bytes in flight}=B\times L$$

For $B=1$ TB/s and a loaded memory latency of 400 ns, that is $10^{12}\times4\times10^{-7}=400$ KB outstanding at all times. If each thread has one 4-byte load outstanding, you need $400{,}000/4=100{,}000$ threads in flight across the chip. A CPU with 8 cores and about 10 outstanding misses per core (64-byte lines) has only $80\times64=5$ KB in flight, so at 80 ns latency it can sustain at most about $5120/80\text{ ns}=64$ GB/s no matter how wide its memory bus is. That is a clean explanation of why a GPU needs 100,000 threads and a CPU does not: they are provisioned for different bandwidth-latency products. It also explains why a GPU launched with too few threads (a tiny kernel) leaves most of its bandwidth unused.

## Memory budget of a frame

Even simple display output costs bandwidth. A 4K frame at 4 bytes per pixel is $8.29\times10^6\times4=33$ MB; writing the final color once at 60 fps is 2.0 GB/s. Real rendering reads and writes color with blending (read plus write, so 2x), touches a depth buffer (another 2x to 3x), and samples textures, easily reaching 10 to 20 GB/s or more before geometry and post-processing. On a phone SoC sharing roughly 50 GB/s of LPDDR bandwidth with the CPU, camera and display, that is a big slice of the budget, which is why mobile GPUs render in on-chip tiles and write each pixel to DRAM once (see [[q0921]]). A discrete card with 500 to 1000 GB/s does not have the same pressure, so it uses immediate-mode rendering with large caches.

## Real hardware flavors

- **Discrete GPU cards**: own dedicated memory (GDDR or HBM), connected by PCIe, 100 to 450 W or more.
- **Integrated GPUs in SoCs**: share system memory with the CPU, tens of watts or less down to a watt or two in a phone. Bandwidth is much lower (for example 50 to 100 GB/s of LPDDR shared), so these GPUs use tile-based rendering to save bandwidth.
- **Datacenter accelerators**: GPUs (or GPU-derived chips) with HBM, matrix units and high-speed interconnect, used for AI training. Graphics hardware may be absent.
- **Fixed-function extras**: video encode/decode engines, display controllers, ray-tracing cores, tensor cores. These are not "shader" lanes but part of the GPU block.
:::

::: applications
- **Real-time rendering**: games, CAD, VR on desktop, console and mobile GPUs.
- **Machine learning**: training and inference with matrix-multiply accelerators on GPUs.
- **Scientific simulation**: molecular dynamics, fluid dynamics, weather and finite-element solvers.
- **Video**: hardware encode/decode, image processing in cameras and phones.
- **Display and UI composition**: every smartphone and laptop uses the GPU to composite the screen.
- **Crypto and signal processing**: massively parallel hashing, FFTs and filtering.
:::

::: assumptions
- Numbers for lane counts, clock rates and bandwidth are representative of recent consumer and datacenter GPUs and change every generation.
- "GPU" here covers discrete, integrated and mobile GPUs. Some accelerators (TPU-like chips) are not GPUs even though they share the throughput philosophy.
- The 150 operations per pixel and overdraw of 2 are illustrative; real titles vary from tens to thousands of operations.
- Vendor terminology differs (CUDA core vs stream processor, warp vs wavefront, SM vs CU). Interviewers will usually accept either if you define it.
:::

::: followups
### Is a GPU core the same as a CPU core?
No. A GPU "core" or lane is a simple ALU that executes one thread's arithmetic in a warp's lockstep; it has no independent branch prediction or out-of-order engine. The comparable unit to a CPU core is an SM/CU, which contains many lanes sharing a scheduler and instruction fetch.

### Why do GPUs use such high-bandwidth memory?
Because thousands of lanes need data every cycle, and throughput scales with how fast you can feed them. Bandwidth is delivered by wide buses (256 to 512 bits for GDDR, thousands of bits with HBM) and high data rates. Many kernels are bandwidth-limited, so memory sets performance more than FLOPS.

### Why can't a GPU just run my operating system?
OS and typical application code is branch-heavy, serial and latency-sensitive, with irregular memory access, which GPUs handle poorly. GPUs also lack the same support for privileged operations, interrupts and fine-grained synchronization. They work as co-processors under a CPU.

### What happens to performance if half the threads in a warp take a different branch?
The warp executes both paths serially with the inactive lanes masked off, so the cost is the sum of both paths. In the worst case 32 different paths give 1/32 efficiency. This is branch divergence, covered in [[q0920]] and [[q0923]].

### You are choosing between an integrated GPU and a discrete GPU for a laptop product. What matters?
Performance target, power and thermal budget, battery life, memory bandwidth (shared LPDDR vs dedicated GDDR), board area, cost, and software needs. Integrated saves power and cost; discrete gives much higher bandwidth and compute but needs cooling and an extra memory system.
