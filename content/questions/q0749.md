::: testing
Whether you can describe the two kinds of frame precisely: the **address frame** (7 address bits MSB first, one R/W bit, then an ACK clock) and the **data frame** (8 bits MSB first then an ACK clock), and who drives each bit. A good answer also covers the practical traps: 7-bit versus 8-bit address notation (0x48 versus 0x90), the reserved addresses, the 10-bit extension, and the fact that "register address" is a *convention carried in the first data byte*, not part of the I2C protocol itself. Quick arithmetic with hex addresses is a good sign.
:::

::: why
Every I2C bug report starts with "the address is wrong" or "the byte order is wrong", and every logic-analyzer decode is a list of address and data frames. If you can read a frame, you can tell in seconds whether a failure is addressing (no ACK on the address frame), a register mistake (ACK on address but NACK on the data frame), or a direction mistake (R/W bit wrong). The 7-bit versus 8-bit confusion alone wastes hours for newcomers because datasheets and libraries disagree on conventions.
:::

::: concepts
- **Byte + ACK framing**: every frame on the bus is 8 bits followed by a 9th clock for ACK/NACK ([[q0745]], [[q0751]]).
- **MSB-first transmission**: bit 7 (or address bit 6) goes out first.
- **R/W bit**: 0 = controller writes, 1 = controller reads.
- **Reserved addresses**: 0x00 to 0x07, 0x78 to 0x7F ([[q0747]]).
- **10-bit addressing**: a two-byte address scheme with a 11110xx prefix.
- **Register conventions**: the first data byte after the address often selects a register ([[q0746]]).
- **Hex arithmetic**: shifting a 7-bit address left by one and OR-ing the R/W bit gives the byte on the wire.
:::

::: answer
"There are two kinds of frame on an I2C bus, and both are nine clocks long.

The address frame comes right after START. It has eight bits clocked out MSB first: seven address bits and then a read/write bit, where 0 means the controller will write and 1 means it will read. On the ninth clock the target whose address matches pulls SDA low to ACK. For example, a target at 0x48 is addressed with the byte 0x90 for a write and 0x91 for a read, since 0x48 shifted left by one is 0x90.

Data frames follow. Each is eight bits, MSB first, then a ninth clock for the ACK. During a write the controller drives the 8 bits and the target drives the ACK; during a read the target drives the 8 bits and the controller does the ACK, with a NACK on the last byte. There's no length field in the protocol, so a transfer just continues until the controller sends STOP.

What those data bytes mean is up to the target. Typically the first byte after a write address is a register pointer, and the rest are values.

There's also a 10-bit addressing option where the first byte is the prefix 11110, two address bits and R/W, followed by a second byte with the remaining eight address bits."
:::

::: technical
**Address frame (7-bit):**

| Bit | 7 | 6 | 5 | 4 | 3 | 2 | 1 | 0 | 9th clock |
|---|---|---|---|---|---|---|---|---|---|
| Content | A6 | A5 | A4 | A3 | A2 | A1 | A0 | R/W | ACK |
| Driven by | controller | controller | controller | controller | controller | controller | controller | controller | target |

Byte on the wire = (address ≪ 1) | R/W. For address 0x48: write byte 0x90 (1001 0000), read byte 0x91 (1001 0001). For 0x50: 0xA0/0xA1. For 0x68: 0xD0/0xD1.

**Data frame:** D7 … D0 (MSB first) then ACK. Direction set by the R/W bit of the address frame: write = controller drives data, target ACKs; read = target drives data, controller ACKs (NACK on the final byte).

**10-bit address (write):** first byte 1 1 1 1 0 A9 A8 R/W (the 0x78 to 0x7B prefix region), target ACK, second byte A7 to A0, ACK, then data. Example: 10-bit address 0x25A: A9A8 = 10, first byte 11110 10 0 = 0xF4 (write), second byte 0x5A. For a read, the controller sends the 10-bit address with W, then a repeated START and just the first byte again with R/W = 1.

**Reserved 7-bit addresses:** 0x00 general call (and START byte), 0x01 CBUS compatibility, 0x02 and 0x03 other formats, 0x04 to 0x07 Hs-mode master codes, 0x78 to 0x7B 10-bit prefix, 0x7C to 0x7F reserved (device ID uses 0x7C). 112 addresses are usable.

**Overhead:** one address frame + 3 data frames = 36 clocks for 24 payload bits, 66.7% efficiency.

**No length or CRC in the base protocol.** SMBus adds an optional packet error code: a CRC-8 (polynomial $x^8+x^2+x+1$, init 0) over all bytes including the address byte. For [0xA0, 0x01, 0xA5] it is 0x2F.
:::

::: short
"Each frame is nine clocks. The address frame is 7 address bits MSB first plus a read/write bit, with the target pulling SDA low on the ninth clock to ACK; address 0x48 becomes 0x90 for a write and 0x91 for a read. Data frames are 8 bits MSB first plus an ACK, driven by the controller on a write and by the target on a read. There's no length field: bytes continue until STOP. What the bytes mean, such as a register pointer, is defined by the target."
:::

::: long
"Everything on the bus is made of 9-clock frames: eight bits and one acknowledge.

The address frame comes first, right after START. The controller sends seven address bits, MSB first, and then the R/W bit, so zero means the controller is going to write and one means it will read. On the ninth clock the controller releases SDA and the target that recognised its address pulls SDA low: that's the ACK. A useful trick for debugging: the byte you see on the logic analyzer is the 7-bit address shifted left by one. So a target at 0x48 shows up as 0x90 for a write and 0x91 for a read, and a datasheet that says its address is '0x90' is quoting the 8-bit write byte, which is the 7-bit address 0x48. That mismatch is behind a lot of 'my sensor doesn't ACK' problems.

Data frames come next, each eight bits MSB first and then an ACK. The R/W bit decides who drives. On a write the controller drives the bits and the target ACKs. On a read the target drives the bits and the controller ACKs every byte except the last, which it NACKs. The protocol has no length field and no checksum, so the transfer simply continues until the controller issues a STOP or repeated START.

The meaning of the data bytes is not part of I2C. By convention, for register-based devices, the first byte after the write address selects a register, and any bytes after it are values for that register and the following ones.

There are two variations: reserved addresses, 0x00 to 0x07 and 0x78 to 0x7F, which leaves 112 usable, and 10-bit addressing, where the first byte is 11110, two address bits and R/W, and a second byte carries the other eight address bits."
:::

::: terms
- **Address frame**: START + 7-bit address + R/W + ACK.
- **Data frame**: 8 data bits + ACK/NACK.
- **R/W bit**: direction bit: 0 write, 1 read.
- **MSB-first**: most significant bit is sent first.
- **General call (0x00)**: address that all devices that support it acknowledge.
- **10-bit addressing**: extension using 11110 + A9 A8 as the first byte.
- **Register pointer**: first data byte after a write address, selecting the register.
- **Packet error code (PEC)**: SMBus CRC-8 appended to a message.
- **Frame**: here, a 9-clock unit: byte plus acknowledge.
:::

::: exceptional
**An average answer** says "the address frame has 7 bits plus read/write, and data frames have 8 bits plus ACK".

**An exceptional answer**:
- Gives the **bit-by-bit structure**, MSB first, and **who drives each bit** (including the ACK).
- Works the **7-bit vs 8-bit conversion** with a number (0x48 → 0x90/0x91) and mentions the datasheet confusion.
- Notes that the protocol has **no length field**, and **no CRC** (except SMBus PEC).
- Distinguishes **protocol** from **convention**: the register pointer is a device-level agreement.
- Mentions **reserved addresses** and the **10-bit** two-byte format with the 11110 prefix.
- Gives an **efficiency number** (36 clocks for 24 payload bits).
:::

::: mistakes
- **Treating the R/W bit as part of the address.** The 7-bit address is the upper seven bits; the LSB is direction.
- **Passing 0x90 to a library that expects a 7-bit address.** It will shift it again and send 0x20/0x21 (0x90 ≪ 1 truncated to 8 bits), so the target never ACKs.
- **Assuming the target ACKs the *data* because it ACKed the address.** Each byte gets its own ACK; a NACK on a register byte means the target rejected it.
- **Assuming a fixed frame length.** I2C has none; devices define how many bytes to expect.
- **Sending LSB first (bit-banged driver).** I2C is MSB first.
- **Thinking the first data byte is always a register address.** Some devices (EEPROMs use two address bytes; some sensors use command codes or none).
:::

::: deep
## The unit of the bus: eight bits and a handshake

I2C has exactly one framing rule: after every eight data bits there is a ninth clock for the receiver to acknowledge. Everything else is *what you put in the bytes*. That makes the address frame and the data frame the same shape; they differ in who speaks and what the bits mean.

```timing
{"signals":[{"name":"SCL","wave":"11010101010101010101010101010101010101"},{"name":"SDA","wave":"10110011000000000000110011000011001100"},{"name":"field","wave":"=.3.............4.5.2...............5.","data":["S","ADDR = 0x50 (1010000)","W","ACK","DATA = 0xA5","ACK"]}],"hscale":0.55}
```
Figure: A write to address 0x50 with data 0xA5. Read the SDA row left to right: the bits after START are 1010000 (0x50), then 0 for write, then the target pulls SDA low for the ACK. The next eight bits, 10100101, are the data byte 0xA5, and the target ACKs again. SDA changes only while SCL is low.

### Address frame in detail

Seven address bits are sent MSB first, A6 first:

$$\text{wire byte} = (\text{address} \ll 1)\ |\ R/\overline{W}$$

| 7-bit address | binary | write byte | read byte |
|---|---|---|---|
| 0x48 | 1001000 | 0x90 | 0x91 |
| 0x50 | 1010000 | 0xA0 | 0xA1 |
| 0x68 | 1101000 | 0xD0 | 0xD1 |
| 0x3C | 0111100 | 0x78 | 0x79 |

Any datasheet figure showing the address byte with R/W (like 0xA0) is the 8-bit form. Libraries differ: Arduino-style `Wire` and Linux's `i2c-dev` take the 7-bit form (0x50), while some vendor HALs take the shifted 8-bit form and ask you to pass `0xA0`. Always check which one your driver expects, and confirm with a bus scan or a logic analyzer.

The ACK on the ninth clock is the only information the controller gets from the address phase: "a device with this address exists and is listening". If no one answers, SDA stays high = NACK.

```sim
{"id":"i2c-bus","address":"0x50","rw":"w","data":["0x01","0xA5"],"stretch":false}
```
Figure: Try address 0x50 write with two data bytes: the first is the register pointer, the second the value. Switch to read and check which fields the simulator says the target drives.

### Reserved addresses and why

| Address (7-bit) | Use |
|---|---|
| 0x00 | General call (R/W = 0), START byte (R/W = 1) |
| 0x01 | CBUS compatibility |
| 0x02, 0x03 | Reserved for other bus formats |
| 0x04 to 0x07 | High-speed mode master codes |
| 0x78 to 0x7B | 10-bit addressing prefix |
| 0x7C to 0x7F | Reserved (device ID) |

That leaves 0x08 to 0x77 = 112 usable addresses ([[q0747]]).

### 10-bit addressing

The 10-bit scheme uses two bytes so it can coexist with 7-bit devices: the first byte 11110 A9 A8 R/W looks like a reserved 7-bit address, which no 7-bit device claims.

```timing
{"signals":[{"name":"Controller drives","wave":"==z=z=z=","data":["S","0xF4","0x5A","0x3A","P"],"color":"accent"},{"name":"Target drives","wave":"zz=z=z=z","data":["ACK","ACK","ACK"],"color":"orange"}],"hscale":1.8}
```
Figure: A 10-bit write (address 0x25A): the first byte 0xF4 is 11110, A9A8 = 10, R/W = 0; the second byte 0x5A holds A7 to A0. Both are ACKed by the matching target, then data follows (0x3A here). A read repeats the first byte after a repeated START with R/W = 1.

Because it spends an extra byte (9 clocks) per transaction and few devices support it, 10-bit addressing is rare.

### Data frames and direction

After the address frame, direction is fixed for the whole transaction (until a repeated START):

- **Write:** controller drives D7 to D0; target pulls SDA low for ACK. A NACK from the target means it rejected the byte, and the controller should stop.
- **Read:** target drives D7 to D0; controller pulls SDA low to ACK ("send more") or leaves it high to NACK ("last byte") ([[q0751]]).

There's no field that says how many bytes follow. A write of N bytes ends when the controller sends STOP; a read of N bytes ends when the controller NACKs the Nth byte and STOPs.

### What the data bytes mean: convention, not protocol

I2C says nothing about registers. Most sensors adopt the pointer-register convention: **the first data byte after a write address is a register address**, and the pointer auto-increments (or not) for subsequent bytes:

- **Register write:** S, addr+W, **reg**, value₁, value₂, …, P
- **Register read:** S, addr+W, **reg**, Sr, addr+R, value₁, …, P

Others differ: EEPROMs use a two-byte memory address; some ADCs use a single command byte; some devices have no register pointer at all (reading just returns the latest conversion). Always check the datasheet's timing diagram.

### Efficiency

Overhead per transaction: 1 address frame + 1 register frame + data frames. A single 1-byte register write is 3 frames = 27 clocks for 8 payload bits (30% efficiency). Writing 16 bytes to consecutive registers is 18 frames = 162 clocks for 128 payload bits (79%). That's why burst access matters ([[q0746]]).

### Error detection

I2C itself has only the ACK. There is no CRC. SMBus adds an optional **PEC** byte: a CRC-8 with polynomial 0x07 over every byte of the message including the address byte. For a Write Byte to 0x50 of command 0x01, data 0xA5, the PEC is CRC-8([0xA0, 0x01, 0xA5]) = 0x2F (computed here with init 0). Some sensors (e.g. many humidity sensors) define their own CRC byte after each data word; that is again device convention.

### Decoding a capture in your head

Given a logic-analyzer list: `S 0x90 W A 0x00 A Sr 0x91 R A 0x0C A 0x80 N P`:

1. 0x90 is 1001000 + W → target at 0x48, write.
2. 0x00: register pointer 0.
3. Sr then 0x91 → same target, read.
4. Two data bytes 0x0C, 0x80; the controller ACKed the first, NACKed the second, then STOP.

A decode like "S 0x90 W N" tells you immediately: address phase failed, nobody answered.
:::

::: applications
- **Logic-analyzer decoding** of captures into `S addr W A reg A data A P` lines.
- **EEPROM writes** (24-series): address frame, two address-byte data frames, then page data ([[q0751]] for ACK polling).
- **Sensor register configuration**: address frame, register pointer, value bytes.
- **General-call reset** (0x00 followed by 0x06 on devices supporting it) to reset all supporting targets at once.
- **Bus scanners** that send only an address frame to each of 0x08 to 0x77 and record which ones ACK.
- **SMBus devices with PEC** in batteries and PMBus regulators.
:::

::: assumptions
- 7-bit addressing is the default; 10-bit is described as the extension.
- Register-pointer behaviour is **convention**, device-specific; the examples use typical sensor patterns.
- Reserved address details follow the NXP I2C-bus specification table; consult UM10204 for exact assignments (the 0x7C to 0x7F range includes the device-ID address).
- The PEC example uses CRC-8 polynomial 0x07 with init 0 over the listed bytes, computed with a small script; other implementations and byte coverage differ.
- Libraries differ on 7-bit vs 8-bit address arguments; examples here use the 7-bit form for the address and the shifted form for wire bytes.
:::

::: followups
### Your datasheet says the write address is 0xD0 and read address 0xD1. What do you pass to a library that wants a 7-bit address?
0x68: shift right by one (0xD0 ≫ 1 = 0x68). The datasheet quotes the 8-bit wire bytes. If you pass 0xD0 to a 7-bit library it shifts again to 0xA0 and probably gets a NACK.

### How does a 10-bit read work?
The controller sends the first byte (11110 A9 A8 with R/W = 0), the second byte (A7 to A0), then a repeated START and the first byte again with R/W = 1. The addressed target then sends data. The initial write phase sets the address, the second first-byte with R = 1 switches direction.

### What is the general call address and when would you use it?
0x00 with R/W = 0 addresses all devices that support general call: the second byte can be a command such as a software reset (commonly 0x06 on parts that implement it) or "write slave address". Not all devices respond; check the datasheet.

### How would you detect which addresses are present on an unknown bus?
Send START + address + W + STOP for each 7-bit address from 0x08 to 0x77 and record which ones ACK. At 100 kHz it takes roughly 12 ms. Caution: a write to an address with an unexpected device can have side effects, and some devices respond to read probes differently; many scanners use a quick-write with no data byte.

### What if the target ACKs its address but NACKs the first data byte?
It heard the address but rejected the byte: invalid register address or command, device busy (for example an EEPROM in an internal write cycle), or a locked register. Check the datasheet's register map and timing, and retry after the busy time if applicable.
:::
