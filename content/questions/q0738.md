::: basics
### In plain words
I2C and SPI both move bytes between a controller and peripheral chips using a shared clock. The real difference is how a device is picked and how the wires are driven. SPI gives each device its own select wire and drives every wire hard, so it is fast but uses more pins. I2C puts the device's address on the data wire and lets a resistor pull the wires high, so it uses two wires but is slower.

### Picture it
Imagine talking to people in a room. SPI is tapping one person on the shoulder and then speaking quickly. It is fast, but you need a separate tap for each person, and an empty chair never answers. I2C is calling out a name to the whole room and waiting for that person to say "yes." It is slower, but needs no private line, and silence means the person is missing.

### Words you need
- **Chip select**: a dedicated wire that wakes up one SPI device. Each device needs its own.
- **Address**: a number sent on the shared wires that picks one I2C device ([[q0737]]).
- **ACK**: the receiver's reply bit meaning "I got that." SPI has none.
- **Pull-up resistor**: a resistor that lifts an I2C wire to high when no device pulls it low. It makes the climb from low to high slow.
- **Full duplex**: data flows both ways at once, as in SPI.

### The simplest example
Read 14 bytes from a sensor. On I2C at 400 kHz, that is 14 data bytes plus 3 overhead bytes (the address, the register number, the address again; a register is a numbered slot), at 9 clock ticks each. So 17 × 9 = 153 ticks, about 382 µs. On SPI at 10 MHz, it is 1 command byte plus 14 data bytes at 8 ticks each, 120 ticks, which is 12 µs. That is about 30 times faster, at the cost of a select wire per device. That is the whole idea. The rest of this page covers why I2C is slow and which bus to pick.
:::

::: testing
Whether you can compare two buses **on engineering axes** instead of reciting pin names. The interviewer wants to hear wires and pin cost, how a device is selected, speed and why, duplex, error detection, electrical style (open-drain vs push-pull), and multi-master support. They are also checking that you can turn the comparison into a decision: given a part list and a pin budget, which bus do you choose and what do you check? Bonus points for noticing that I2C is a formal, versioned spec while SPI is a convention, so SPI parts disagree about modes, bit order and command formats.
:::

::: why
Choosing a bus is one of the first design decisions on any board with more than one chip, and the wrong choice shows up late: an I2C sensor that cannot keep up with a sample-rate requirement, or an SPI design that runs out of MCU pins when the fifth peripheral gets added. The comparison also explains symptoms you see on the bench: why an I2C bus needs pull-ups and SPI does not, why a missing SPI device reads back all ones while a missing I2C device produces a NACK, and why I2C edges look like slow ramps and SPI edges look square.
:::

::: concepts
- **Selection scheme**: SPI uses a dedicated chip-select pin per target; I2C sends a 7-bit address in-band ([[q0746]], [[q0766]]).
- **Push-pull vs open-drain**: determines speed limits and whether pull-ups are needed ([[q0761]]).
- **Synchronous serial clocking**: both buses have a controller-driven clock, so neither needs baud-rate agreement ([[q0741]]).
- **Duplex**: SPI shifts data in both directions on every clock; I2C uses one data wire so it is half duplex.
- **Acknowledge**: I2C acknowledges every byte; SPI has no handshake, so errors are invisible at the protocol level ([[q0751]]).
- **Bus capacitance and pull-up sizing**: sets the I2C speed limit ([[q0756]], [[q0755]]).
:::

::: answer
"The big differences are pins, speed and who gets selected how.

SPI uses four wires at minimum: clock, MOSI, MISO and a chip-select, and every extra device needs its own chip-select pin. It's full duplex, since every clock shifts a bit out and a bit in, and the outputs are push-pull, so edges are crisp and you can run at tens of MHz.

I2C uses just two wires, SCL and SDA, shared by everything. Devices are selected by a 7-bit address sent on the bus, so adding a device costs zero pins. The price is speed: the lines are open-drain with pull-up resistors, so rising edges are slow RC curves and you're limited to 100 kHz, 400 kHz, or 1 MHz on a good day. It's half duplex, and it has more protocol overhead: a start, an address byte, and an ACK bit after every byte.

I2C does give you a few things SPI doesn't: acknowledgement, so you know if a device is actually there, multi-master support with arbitration, and clock stretching. So I'd pick I2C for lots of slow devices like sensors and EEPROMs, and SPI for anything that needs bandwidth, like flash, displays or fast ADCs."
:::

::: technical
| Property | I2C | SPI |
|---|---|---|
| Signals | SCL, SDA (+ GND) | SCLK, MOSI, MISO, one CS per target |
| Controller pins for $n$ targets | 2 | $3 + n$ (or 4 if daisy-chained) |
| Selection | 7-bit (or 10-bit) address, in-band | Dedicated CS line |
| Duplex | Half | Full |
| Output stage | Open-drain + pull-up | Push-pull |
| Typical clock | 100 k, 400 k, 1 MHz (3.4 MHz HS-mode) | 1 to 50+ MHz |
| Handshake / error detect | ACK/NACK each byte | None |
| Multi-master | Yes (arbitration) | Not defined |
| Clock stretching | Yes | No |
| Specification | Formal (NXP UM10204) | De facto convention (modes 0 to 3) |
| Bits on wire per data byte | 9 (8 + ACK), plus ~9 for address | 8 |

**Why I2C is slower.** A rising edge is an RC exponential through $R_p$ into the bus capacitance $C_b$. The 30% to 70% rise time is $t_r = 0.8473\,R_pC_b$. Fast mode (400 kHz) requires $t_r \le 300$ ns; with $C_b = 100$ pF that bounds $R_p \le 3.54$ kΩ. A push-pull SPI output charges the line through a driver of tens of ohms, so rise time is nanoseconds.

**Throughput example.** Reading 14 bytes from a register-mapped sensor: I2C at 400 kHz needs $9\times(3+14) = 153$ clocks = 382 µs (address+W, register, address+R, 14 data bytes). SPI at 10 MHz needs $8\times(1+14) = 120$ clocks = 12 µs, about 32 times faster for the same payload.

**Power.** An I2C line held low sinks $(V_{DD}-V_{OL})/R_p$ from the pull-up. At 3.3 V, 4.7 kΩ and $V_{OL}=0.4$ V that is 0.62 mA whenever the line is low. SPI has no static current, but its CS and clock lines toggle with CMOS dynamic power $CV^2f$.

**Robustness.** I2C's ACK lets firmware detect a missing or hung device. SPI has no such feedback, so a disconnected target leaves MISO floating or pulled to a constant value; you need your own CRC, ID-register read or status check.
:::

::: short
"SPI is four-plus wires, push-pull, full duplex and fast, but every extra device costs a chip-select pin. I2C is two shared open-drain wires with pull-ups, devices selected by address, half duplex and slower, but it adds ACK, multi-master and clock stretching. So I2C scales better in pins, SPI scales better in speed. I'd use I2C for many slow sensors and SPI for flash, displays, or high-rate ADCs."
:::

::: long
"I'd compare them on five axes: pins, selection, speed, handshake and electrical style.

On pins, SPI needs clock, MOSI, MISO, plus one chip-select per device, so $n$ devices cost $3+n$ pins. I2C needs two wires no matter how many devices share the bus. On selection, SPI uses the physical chip-select line, while I2C sends a 7-bit address on the data wire at the start of each transaction and only the matching device responds. That means I2C devices need unique addresses, and SPI devices don't care about each other as long as only one CS is low.

On speed, SPI wins by a large margin. Its outputs are push-pull, so both edges are driven hard and clocks of 10 to 50 MHz are normal. I2C uses open-drain outputs with pull-up resistors, so the rising edge is an RC curve of roughly $0.85 R_p C_b$, and the standard limits are 100 kHz, 400 kHz and 1 MHz. On top of that, I2C spends 9 clocks per byte plus address overhead, so for a 14-byte read at 400 kHz I'm looking at about 380 microseconds versus about 12 microseconds on 10 MHz SPI.

On handshake, I2C acknowledges every byte, so the controller knows if a device is missing, busy or full. SPI has none. A dead SPI target just reads back zeros or ones, so I add an ID register check at boot.

The extras: I2C supports multiple controllers with arbitration and clock stretching. SPI is simpler silicon and more flexible in data format. So I'd choose I2C for sensors, EEPROMs and housekeeping parts, and SPI when the data rate matters or when I have only a few devices."
:::

::: terms
- **Chip select (CS)**: dedicated line enabling one SPI target.
- **7-bit address**: in-band device identifier that I2C targets recognise; 112 usable values out of 128 ([[q0747]]).
- **Push-pull**: output that actively drives high and low through a pair of transistors (SPI).
- **Open-drain**: output that only pulls low; high comes from a pull-up resistor (I2C).
- **Duplex**: full duplex = both directions simultaneously (SPI); half duplex = one direction at a time (I2C).
- **ACK / NACK**: I2C's per-byte acknowledge or not-acknowledge ([[q0751]]).
- **Arbitration**: I2C's way of resolving two controllers starting at once ([[q0748]]).
- **Daisy chain**: SPI wiring where target outputs feed the next target's input and all share one CS ([[q0768]]).
:::

::: exceptional
**An average answer** lists "I2C has 2 wires, SPI has 4, SPI is faster".

**An exceptional answer**:
- Gives the **pin formula**: $3+n$ vs 2, and mentions daisy-chaining or a decoder as an SPI pin-saver.
- Explains **why** SPI is faster (push-pull edges vs RC rise through a pull-up), with $t_r = 0.8473\,R_pC_b$, not just "it is".
- Computes **real throughput including overhead**: 9 clocks per I2C byte plus address versus 8 per SPI byte.
- Names the **features only I2C has**: ACK/NACK, multi-master arbitration, clock stretching, and a formal spec; and the **features only SPI has**: full duplex and no addressing overhead.
- Finishes with a **decision rule** and one thing to verify, e.g. "check the sample rate fits the bus time" or "check the address map has no collisions".
:::

::: mistakes
- **Saying SPI is always faster in practice.** The *bus* is faster, but a slow SPI target (say 1 MHz max) can be slower than a 1 MHz I2C part. Always take the minimum of bus and device limits.
- **Claiming SPI is "simpler" so it is better.** Pin cost is real: ten SPI devices need 13 pins. I2C needs 2.
- **Forgetting SPI has no acknowledge.** A disconnected device is invisible; you need your own presence check.
- **Thinking I2C supports multiple devices with the same address.** It does not; both would respond at once. Use address pins, a multiplexer or a second bus ([[q0750]]).
- **Saying I2C is full duplex because it can "read and write".** There is only one data wire, so only one side drives at a time.
- **Ignoring pull-ups when comparing electrical behaviour.** I2C's open-drain nature is the root of both its flexibility (wired-AND, multi-master) and its speed limit ([[q0761]]).
:::

::: deep
## The same job, two different wire contracts

Both buses move bytes between a controller and peripherals using a clock so that the receiver doesn't need baud agreement. The differences come from two design choices that ripple through everything else:

1. **How is a device selected?** SPI uses one physical wire per device (CS). I2C puts the selection in the data stream as an address.
2. **How are outputs driven?** SPI uses push-pull drivers. I2C uses open-drain drivers and pull-up resistors so that many devices can share the same wire without fighting.

### Why the clock ceiling differs

On SPI, the controller's push-pull output drives the clock line through tens of ohms, so edges are limited by trace and package parasitics, not by a resistor. A 25 MHz SPI clock has a 40 ns period; it works because rise times are a few ns.

On I2C, the rising edge is not driven at all; the pull-up resistor charges the bus capacitance. For a first-order RC, the time to go from 30% to 70% of $V_{DD}$ is

$$t_r = t_{70\%} - t_{30\%} = R_pC_b\ln\frac{0.7}{0.3} = 0.8473\,R_pC_b$$

(from $V(t) = V_{DD}(1-e^{-t/R_pC_b})$, which reaches 30% at $0.357\,R_pC_b$ and 70% at $1.204\,R_pC_b$.) The I2C-bus spec limits $t_r$ to 1000 ns in Standard mode, 300 ns in Fast mode, and 120 ns in Fast-mode Plus. So at a given $C_b$ the pull-up must be small enough; and a smaller pull-up means more current when the line is low, bounded by the 3 mA sink rating in Standard and Fast modes. That squeeze is why I2C stalls near 1 MHz.

> [!NOTE]
> With 4.7 kΩ and a modest 100 pF bus, $t_r = 0.8473\times 4700\times 100\text{ pF} = 398$ ns. That works at 100 kHz but already violates the 300 ns Fast-mode limit. See [[q0759]] and [[q0755]].

Figure: Even for a single byte, I2C pays for address, register pointer and repeated START (3 bytes of overhead, 27 clocks). SPI pays one command byte. For 14 bytes the gap is 382 µs vs 12 µs, about 32 times. Reasoning about bus time like this is how you check whether a sensor sample rate fits.

Reading from I2C typically uses a **repeated START**: write the register pointer, then re-address the device in read mode without releasing the bus (see [[q0746]]). That is the 3-byte overhead above. SPI typically uses a single command byte with a read bit.

### What I2C gives you back

The extra overhead buys real features:

- **ACK/NACK** per byte: firmware sees immediately whether a device exists or accepted the data ([[q0751]]).
- **Multi-master with arbitration**: two controllers can share the bus safely because open-drain wired-AND lets the one sending a 0 win ([[q0748]]).
- **Clock stretching**: a slow target can hold SCL low to ask for more time ([[q0752]]).
- **A formal spec**: all I2C devices follow one electrical and timing spec, so vendor A's controller works with vendor B's sensor without negotiating modes.

SPI instead trades those for flexibility: no address overhead, arbitrary frame length, any bit order or word size, and the ability to stream continuously. But because it is a convention, each datasheet defines its own mode (CPOL/CPHA), bit order, command format and maximum clock.

### Design decision: a worked scenario

You have a 3.3 V MCU and need an IMU sampling 14 bytes at 1 kHz, a temperature sensor at 1 Hz, a small EEPROM, and a 128×64 OLED refreshed at 30 fps.

- **IMU at 1 kHz on I2C 400 kHz**: 382 µs per sample is 38% of the bus every millisecond. It works, but leaves little room for anything else on that bus. On SPI at 10 MHz it is 1.2%.
- **OLED framebuffer**: 128×64 monochrome = 1024 bytes per frame; ×30 = 30,720 bytes/s. On I2C that is $30720\times 9 = 276{,}480$ clocks/s, 69% of a 400 kHz bus before the IMU. On SPI at 10 MHz it is 2.5% of capacity.
- **Temperature sensor and EEPROM**: tiny, rare transfers. I2C is perfect and costs no pins.

A sensible split: IMU and OLED on SPI, temperature and EEPROM on I2C. Total controller pins: SCLK, MOSI, MISO + 2 CS + SCL, SDA = 7.

### Real-world physical limits

- **I2C length and load**: the 400 pF bus-capacitance limit caps length to roughly a board or a short cable. Typical sensor pins add 3 to 10 pF each and PCB traces about 1 pF per cm (rough rule; depends on stackup).
- **SPI length**: with 10+ MHz clocks and fast edges, a long unterminated trace can ring; keep clock traces short or add series damping resistors (~22 to 33 Ω).
- **Both are single-ended** and not meant for long cables. For off-board runs use differential buses (RS-485, CAN, or I2C bus extenders).

## Scope picture

On a scope, SPI looks like clean square waves with fast edges. I2C looks like fast falling edges (the device pulls low hard) and slow rounded rising edges (the RC charge). If someone shows you "I2C" with square rising edges, they have a very small pull-up or very little capacitance; if the rising edges are barely reaching the top before the next fall, the bus is too slow for its pull-up.
:::

::: applications
- **Sensor hub**: a dozen environmental, light and magnetometer parts on one I2C bus.
- **Serial NOR flash / SD card**: SPI (or quad-SPI) for fast reads and fast boot from external flash.
- **Small OLED/LCD**: I2C versions for status screens; SPI for animated or larger displays.
- **IMUs, ADCs and DACs**: many support both. High-rate designs pick SPI; low-power designs pick I2C to save pins.
- **PMICs and battery fuel gauges**: typically I2C (configuration and telemetry, low rate).
- **Audio codecs**: I2C or SPI for the control path, a separate I2S for the audio stream.
:::

::: assumptions
- "Speed" means **maximum achievable bus clock and effective throughput**, not the maximum clock of any one device. The slowest device on a shared bus limits it.
- SPI numbers assume standard four-wire push-pull SPI. Dual/quad SPI use extra data lines and are faster still.
- I2C numbers assume Standard, Fast and Fast-mode Plus speeds with a 7-bit address. High-speed mode (3.4 MHz) needs active pull-up circuitry and a special header, and the newer I3C uses push-pull in data phases to go faster.
- I3C's top data rate varies by mode; check the MIPI I3C specification if asked.
- The pins formula $3+n$ assumes one CS per target. Daisy-chaining, GPIO expanders or decoders change it.

> [!UNCERTAIN]
> Datasheet maximums for SPI clock (and which I2C modes a part supports) are vendor dependent. Always read the target's datasheet before assuming a speed.
:::

::: followups
### Why does a disconnected SPI sensor return 0xFF (or 0x00) but a disconnected I2C sensor returns an error?
SPI has no acknowledge, so MISO just sits at whatever the pin floats or is pulled to, commonly all ones with a pull-up. I2C's ninth-clock ACK makes the missing device visible: nobody pulls SDA low, so the controller sees a NACK. That's also why I read a WHO_AM_I register at boot on SPI parts. See [[q0751]].

### Can you put two I2C devices with the same address on one bus?
Not on the same segment, because both would ACK and drive data at the same time. Fixes: use the device's address-select pins if it has any, put one behind an I2C multiplexer (channel select), or use a second I2C peripheral on the MCU. See [[q0750]].

### An IMU needs 14 bytes at 1 kHz. Does 400 kHz I2C work?
It fits but only just: 153 clocks per sample is 382 µs, so 38% bus utilisation, before any other traffic or clock stretching. SPI at 10 MHz needs 12 µs per sample. If the IMU supports both, SPI leaves headroom and lower latency.

### Can you share MISO between multiple SPI devices without chip-selects fighting?
Yes, MISO is a shared line, so the targets must tri-state MISO when their CS is high. Some older parts don't, which causes contention; add a buffer or analog switch, or use separate MISO lines.

### What if you only have two MCU pins left and need five SPI devices?
Use a different bus for some devices, or use a GPIO expander / decoder for chip-selects, or choose devices that support daisy-chaining. Bit-banging SPI on GPIOs also works at modest speeds. The cleanest answer is usually to check whether parts also offer I2C versions.
:::

::: interpretations
"Difference" is answered here as a **side-by-side engineering comparison**. Some interviewers use "slaves/masters" in the follow-up; modern documents say **controller/target** (I2C spec) and **controller/peripheral** (SPI), and the question list keeps the older wording. If asked "which is better", the right reply is "it depends on pin budget, data rate and device count", followed by the decision rule above. See [[q0739]] for the speed side in depth and [[q0740]] for how chips choose among all buses.
:::
