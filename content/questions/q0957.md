::: basics
### In plain words
A clock divider makes a slower clock from a faster one, for example 1 MHz from 100 MHz. The usual design is a counter that counts the fast ticks and flips the output every N/2 of them, giving a clock at 1/N of the speed. Even ratios are easy. Odd ratios need a trick to keep the high and low times equal. Often a better design makes a single "now" pulse every N ticks instead of a new clock.

### Picture it
Think of a gear train. A gear with twice as many teeth turns half as fast, like a toggle that flips on every tick. For other ratios, picture a person counting metronome beats and flipping a switch every 50 beats. The switch is exactly as steady as the metronome. The picture breaks down for odd counts. Flipping after a whole number of beats cannot give equal on and off times when the total is odd.

### Words you need
- **Counter**: a circuit that counts clock ticks and wraps back to 0.
- **Flip-flop**: a circuit that stores one bit and updates it on a clock tick.
- **Duty cycle**: the share of each period that the clock is high. 50% means equal high and low times.
- **Clock enable (tick)**: a one-cycle pulse that means "act now", used with the original clock.
- **Glitch**: a very short, unwanted pulse. On a clock line it acts as a false clock edge.

### The simplest example
Divide 100 MHz by 100 to get 1 MHz. A counter counts 0 to 49, which takes 50 input cycles, or 500 ns. Each time it reaches 49, it resets and flips the output flip-flop. The output is high for 500 ns and low for 500 ns, so the period is 1 µs and the duty cycle is 50%. For divide-by-3 with only rising-edge logic, the output can be high for 1 cycle and low for 2, a 33% duty cycle. A true 50% needs the falling edge too. That is the whole idea. The rest of this page covers the odd-N design, why a clock enable is often better, and safe ratio changes.
:::

::: testing
Whether you can turn a vague hardware request into a clean, correct RTL design **and** show you know where clock dividers go wrong. Hidden sub-skills:

1. **Asking clarifying questions**: divide ratio, even or odd, required duty cycle, fixed or programmable, how the output is used.
2. Writing a counter-based divider with correct reset and wrap-around.
3. Knowing the **odd-N 50% duty cycle** trick, which uses both clock edges.
4. Knowing the *engineering* answer: dividing a clock in logic creates a new clock for timing analysis, so often you should generate a **clock enable** instead.
5. Glitch-free behavior when the ratio changes, and when a PLL is the better tool.
:::

::: why
Almost every chip needs slower clocks than its source: a UART baud tick from 50 MHz, a 1 kHz scheduler tick, a slow peripheral bus, a PWM carrier. A clock divider is also the standard "design something small in RTL" question because it touches counters, resets, duty cycle, edge sensitivity and timing constraints in a dozen lines. The failure modes (a glitchy clock, a duty cycle that breaks downstream logic, a clock that the timing tool cannot see) are exactly the issues real teams chase in clock-domain bugs.
:::

::: concepts
- **Flip-flop as a divide-by-2**: a D flip-flop with $\bar Q$ fed back to $D$ toggles every clock edge, so the output frequency is half. See [[q0882]].
- **Counters**: a modulo-$N$ counter wraps every $N$ clocks; its terminal count marks the divided period.
- **Duty cycle**: the high-time fraction. Even divisors give 50% easily; odd divisors need both edges.
- **Clock enable versus divided clock**: a one-cycle pulse every $N$ clocks used with the original clock, versus a new clock net. See [[q0884]].
- **Glitches**: combinational decoding that can produce short spurious pulses on a clock line.
- **Clock-domain implications**: a divided clock is a new clock for CTS and STA, and crossing to it needs care. See [[q0887]].
:::

::: answer
"First I'd ask a few questions: what's the divide ratio, is it fixed or programmable, does the output need a 50% duty cycle, and is this going to drive real flip-flop clock pins or just be a periodic tick?

For the basic case, divide by N with N even: I use a counter clocked by the input clock. It counts from 0 to N/2 minus 1, and when it hits the end it resets to zero and toggles the output register. So the output is high for N/2 input cycles and low for N/2, which is a 50% duty cycle and a frequency of f over N. Divide by 2 is just a flip-flop with its inverted output fed back to D.

For odd N, a single-edge counter gives an uneven duty cycle, like 2 high and 1 low for divide by 3. To get 50% I run one counter on the rising edge and an identical one on the falling edge, each producing a pulse that's high for N minus 1 over 2 cycles, and OR them together, which lengthens the high time by half a cycle.

One thing I'd mention is that in a real design I'd prefer a clock-enable pulse once every N cycles and keep everything on the original clock. A logic-generated clock needs generated-clock constraints and clock-tree handling, and it's easy to get glitches or skew."
:::

::: technical
**Even divisor ($N = 2M$).** A modulo-$M$ counter on the rising edge; toggle the output when the counter reaches $M-1$. Output frequency $f/N$, duty 50%. All outputs come directly from flip-flops, so the output is glitch-free.

```verilog
module clk_div_even #(parameter integer N = 4) (
  input  wire clk, input wire rst_n, output reg clk_out);
  localparam integer HALF = N/2;
  reg [$clog2(HALF)-1:0] cnt;
  always @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin cnt <= 0; clk_out <= 1'b0; end
    else if (cnt == HALF-1) begin cnt <= 0; clk_out <= ~clk_out; end
    else cnt <= cnt + 1'b1;
  end
endmodule
```

(For $N=2$, `HALF` is 1 and `$clog2(1)` is 0 which gives a zero-width counter, so special-case it as a plain toggle flip-flop.)

**Odd divisor ($N = 2H+1$) with 50% duty.** Two counters, one on each edge. Each phase signal is high for $H=(N-1)/2$ input cycles of every $N$; the falling-edge copy is shifted by half a cycle; the OR is high for $H + 0.5 = N/2$ cycles, a 50% duty cycle.

```verilog
module clk_div_odd #(parameter integer N = 3) (
  input  wire clk, input wire rst_n, output wire clk_out);
  localparam integer H = (N-1)/2;
  reg [$clog2(N)-1:0] cp, cn;
  reg qp, qn;
  wire [$clog2(N)-1:0] cp_nx = (cp == N-1) ? 0 : cp + 1'b1;
  wire [$clog2(N)-1:0] cn_nx = (cn == N-1) ? 0 : cn + 1'b1;
  always @(posedge clk or negedge rst_n)
    if (!rst_n) begin cp <= 0; qp <= 1'b0; end
    else begin cp <= cp_nx; qp <= (cp_nx < H); end
  always @(negedge clk or negedge rst_n)
    if (!rst_n) begin cn <= 0; qn <= 1'b0; end
    else begin cn <= cn_nx; qn <= (cn_nx < H); end
  assign clk_out = qp | qn;
endmodule
```

Both modules were simulated (divide by 3 and divide by 5 give equal high and low times, 15 ns and 15 ns of a 30 ns period for a 100 MHz input divided by 3). The first output pulse after reset is shortened because the two phases start up out of step; real designs hold the output low until the phases settle.

**Clock enable version (preferred for internal logic).**

```verilog
reg [$clog2(N)-1:0] cnt;
always @(posedge clk or negedge rst_n)
  if (!rst_n) cnt <= 0; else cnt <= (cnt == N-1) ? 0 : cnt + 1'b1;
wire tick = (cnt == N-1);       // one-cycle pulse, f/N rate
// downstream:  always @(posedge clk) if (tick) state <= next;
```

Everything stays in one clock domain, so no new clock constraints are needed.
:::

Odd N needs a rising-edge and a falling-edge counter whose pulses are ORed to fix the duty cycle. :::

::: long
"Before drawing anything I'd ask: is the ratio fixed or programmable, does it need to be 50% duty, and is the output driving flip-flop clock pins, or is it just a periodic tick?

The simplest case is a power-of-two divider: a flip-flop with its inverted output tied to D toggles on every rising edge, so it divides by two, and chaining them divides by four, eight and so on. That's cheap, though in the chained version each stage is clocked by the previous one, so delays accumulate.

For a general even N, I use a synchronous counter on the input clock that counts to N over 2 minus 1, then resets and toggles an output flip-flop. The output is high for N/2 input cycles and low for N/2, and it comes straight from a register, so it is glitch-free.

For odd N, a plain counter can only give something like two cycles high and one low for divide by three, which isn't 50%. The standard fix is to make two signals, one clocked on the rising edge and one on the falling edge, each high for N minus 1 over 2 cycles. The falling-edge one is shifted by half a cycle, so OR-ing them gives a high time of N over 2, which is exactly 50%.

Then I'd bring up the practical points. A logic-generated clock is a new clock as far as clock-tree synthesis and static timing are concerned, so it needs a generated-clock constraint, and any crossing between it and the source clock needs care. If the consumer is just fabric logic, I'd generate a one-cycle enable pulse every N cycles instead and keep everything on the original clock. If the ratio is programmable, I'd update it only at the terminal count so the output never gets a runt pulse. And if I need a non-integer ratio with good jitter, I'd use a PLL rather than logic."
:::

::: terms
- **Clock divider**: a circuit that produces a clock (or enable) at $f_{in}/N$.
- **Modulo-$N$ counter**: a counter that counts $0$ to $N-1$ and wraps.
- **Duty cycle**: the fraction of the period the clock is high; 50% is typical.
- **Clock enable (tick)**: a one-cycle pulse used with the main clock instead of a separate slower clock.
- **Generated clock**: a clock derived in logic, which needs an explicit constraint in timing analysis.
- **Glitch**: a short unwanted pulse, often from combinational logic on a clock path.
- **Ripple (asynchronous) counter**: stages clocked by the previous stage's output; simple but with accumulating delay.
- **Fractional divider**: alternates between two integer ratios to approximate a non-integer average, giving jitter.
- **Clock gating cell (ICG)**: a latch plus AND that safely enables or disables a clock.
:::

::: exceptional
**An average answer** draws a toggle flip-flop and a counter and says "divide by N".

**An exceptional answer**:
- Starts with clarifying questions and explicitly lists the cases (even, odd, programmable).
- Gets the **odd-N 50%** design right, with the justification: two phases of $(N-1)/2$ cycles, half a cycle apart, OR-ed give $N/2$.
- Insists on glitch-free outputs: registered outputs only, no combinational decode feeding a clock.
- Raises the **clock enable vs generated clock** choice and its timing-tool consequences.
- Handles reset and run-time ratio changes safely.
- Mentions fractional dividers and PLLs as the answer for non-integer ratios, and verifies with a testbench that measures high and low times.
:::

::: mistakes
- **Decoding a counter combinationally and using it as a clock.** `assign clk_out = (cnt == 3);` glitches whenever bits change at slightly different times. Register the output.
- **Wrong high/low split.** For a toggle at terminal count $N/2-1$ you get $N/2$ cycles each way. Counting to $N-1$ and toggling gives a divide-by-$2N$ instead.
- **Claiming 50% duty for odd N from a single-edge counter.** It is impossible: the high time would be a non-integer number of cycles.
- **Ignoring reset.** Without reset the counter and output start unknown in simulation (X) and may never recover.
- **Treating the divided clock as free.** It needs clock-tree balancing and a generated-clock constraint; without them the timing tool may not check paths in that domain.
- **Changing N on the fly with no care.** Loading a new divisor mid-count can produce a runt pulse or a very long period. Update at the terminal count.
:::

::: deep
## Step 0: ask the right questions

The interviewer's phrase "design a clock divider" hides several choices. In a real conversation I would ask:

| Question | Why it changes the design |
|---|---|
| Divide ratio: fixed, small power of two, arbitrary, programmable? | Power of two is a chain of toggle flip-flops. Arbitrary needs a counter. Programmable needs safe loading. |
| Even or odd? | Even is easy; odd with 50% duty needs both edges. |
| Does the output need 50% duty? | If not, a one-cycle pulse is simpler. |
| Is the result a *clock* feeding flip-flops, or an event? | Events should be clock enables; clocks need clock-tree and constraint care. |
| Input frequency and tolerance for jitter or phase relationship? | Decides whether logic is enough or a PLL is needed. |

## Divide by 2: the building block

A D flip-flop with $D = \bar Q$ changes state at every rising edge of the clock, so its output has half the frequency and exactly 50% duty cycle, regardless of the input duty.

Figure: The inverted output feeds back to D, so every rising clock edge flips the state. The output period is twice the input period. Chaining N of these divides by $2^N$ (each stage is clocked by the one before).

A chain of these toggle stages is an **asynchronous (ripple) counter**. It uses very little logic, but each stage adds its clock-to-Q delay to the next stage's clock, so the outputs are not aligned with each other and cannot safely be used together as a synchronous bus.

## Even divide by $N$: counter and toggle

Counting to $M = N/2$ and toggling gives equal high and low times. Worked example: divide 100 MHz by 100 gives 1 MHz. $M=50$, the counter counts 0 to 49, the output toggles every 50 input cycles (500 ns), the output period is 1 µs. Resource use: a 6-bit counter and one flip-flop.

## Odd divide by $N$: both edges

For divide-by-3, a single-edge counter gives a waveform high for 1 cycle and low for 2 (33% duty) or 2 and 1 (67%). To get 50% we need a period of three cycles with 1.5 high and 1.5 low, so the output must switch on both clock edges.

The scheme:
- Rising-edge phase $Q_p$: high for $H=(N-1)/2 = 1$ cycle, low for 2.
- Falling-edge phase $Q_n$: identical, but updated on falling edges, so shifted by half a cycle.
- Output $= Q_p \lor Q_n$: high for 1 + 0.5 = 1.5 cycles.

Generalizing: the OR of two phases with high time $H$ cycles gives $H + 0.5 = N/2$ cycles, which is exactly half of $N$ only when $H = (N-1)/2$, so this works for every odd $N \ge 3$. In simulation, the divide-by-5 circuit above gave 25 ns high and 25 ns low for a 100 MHz source (period 50 ns).

> [!WARNING]
> Combining two clocks with an OR gate is exactly the sort of thing that is fine on the whiteboard and needs care in silicon: the OR is on the clock path, so the two phases must overlap (they do here, by half a cycle) and the structure must be recognized by clock-tree synthesis and static timing. Many teams avoid it and use enables instead.

## Clock enable instead of a slower clock

Often what you actually want is "do this once every $N$ cycles". Generate a one-cycle pulse:

$$\text{tick} = (\text{cnt} == N-1)$$

and use `if (tick)` in downstream registers, which all stay on the original clock. Benefits: one clock domain, no clock-tree for the divided signal, no generated-clock constraint, no clock-domain crossing. The costs: the flops still receive the fast clock (so clock-tree power is not saved unless you add a clock gate) and the enable adds a mux or enable-flop in front of each register.

Worked example, a UART oversampling tick. For 115200 baud with 16 times oversampling from 50 MHz: $50\times10^6/(16\times115200) = 27.13$. With $N=27$ the tick rate gives 115741 baud, an error of $+0.47\%$; $N=28$ gives $-3.1\%$, which is worse. A fractional approach alternates 27 and 28 so that the average is 27.13 (28 for about 13% of the ticks), reducing the long-term error at the cost of tick-to-tick jitter of one input cycle (20 ns), tiny compared with a bit time of 8.7 µs. See [[q0779]].

## Programmable ratio and glitch-free updates

If $N$ is a register, three rules keep the output clean:

1. **Load the new value only at the terminal count** (or when the output phase is known), so a period is never cut short or doubled.
2. **Synchronize the control input** if it comes from another clock domain.
3. **Keep the output on a register**, never on combinational decode of the count.

A related problem is **switching between two different clocks** (a clock mux). That needs a glitch-free clock mux with handshakes, because an AND-OR mux can clip a pulse when the select changes in the middle of a high phase. The classic solution latches each select on the falling edge of its own clock and waits for the other clock to be disabled first.

## Timing and physical design implications

- A logic-derived clock is a **generated clock**. The constraint tells the timing tool the source, the divide ratio and where the new clock appears; without it, flip-flops on the divided net may be unconstrained.
- **Clock-tree synthesis** must balance the divided clock against the source, or the paths between them have large skew.
- **Hold risk**: a divided clock launches data a flip-flop's clock-to-Q after the source edge, and the capturing clock comes through additional delay; hold violations are common at boundaries between the domains.
- For small fabric logic on an FPGA, prefer the **enable** method or the device's dedicated clock manager (MMCM/PLL or clock divider primitive), which use the global clock network.

## Non-integer ratios and PLLs

Dividing by 2.5 requires toggling on both edges with alternating phases, or a **fractional-N** scheme that alternates between $N$ and $N+1$ using an accumulator (a first-order delta-sigma). Average frequency is right but there is deterministic jitter of one input period, and dither spurs in the spectrum. For clean non-integer ratios, a PLL multiplies and divides. See [[q0946]] for why chips need several clocks.

## Verification

A short self-checking test: after reset, record the time between consecutive rising edges (period) and falling-to-rising (low time), then assert period $= N\,T_{in}$ and high time $= N\,T_{in}/2$ within one half input period. Test $N = 1, 2, 3, 5, 8$, and apply reset in the middle to check it recovers. For programmable dividers also assert that no period is shorter than $\min(N_{old},N_{new})\,T_{in}$.
:::

::: applications
- **UART baud-rate and oversampling ticks** derived from a system clock (see the worked example).
- **Slow peripheral clocks**: SPI/I2C clock generators divide a system clock by a programmable ratio.
- **Timers and watchdogs**: a prescaler divides the CPU clock before the main counter.
- **PWM carriers** and LED dimming derived from a single oscillator.
- **Low-power domains**: peripheral clocks run at a fraction of the core clock to save dynamic power.
- **Serializer/deserializer and DDR interfaces**: divided clocks align parallel data to a fast serial clock.
:::

::: assumptions
- **Synchronous design with a clean input clock** of known frequency and roughly 50% duty. The toggle-flip-flop divide-by-2 does not depend on input duty, but the odd-N both-edge scheme assumes a clock whose duty cycle is close to 50%, otherwise the "half cycle" shift is not exact.
- **Reset is available** and asserted at start-up.
- **ASIC or FPGA with standard flip-flops.** On an FPGA, vendor clock primitives are normally better than fabric dividers.
- **Integer ratio.** Fractional ratios have jitter that may or may not be acceptable.
- A valid alternative is to answer with a *clock enable* design even when the question says "clock"; say so and explain why.
:::

::: followups
### Design a divide-by-3 with 50% duty cycle. Draw the waveforms.
Two counters, one on each edge, each counting 0 to 2 and producing a phase signal high for one input cycle. The falling-edge phase lags by half a cycle. OR them: high for 1.5 cycles, low for 1.5 cycles, period 3 cycles. Rising edges of the output align with rising edges of the input, falling edges with falling edges.

### Why not just decode the counter and use that as a clock?
Counter bits do not all change at exactly the same time, so a decode like `cnt == 3` can briefly glitch high or low for a gate delay. A glitch on a clock pin is a spurious clock edge, so a flop captures wrong data. Register the decoded signal (a flip-flop output changes cleanly once per edge) or avoid using it as a clock at all.

### What is the difference between a divided clock and a clock enable, and which do you prefer?
A divided clock is a separate clock net with its own edges; an enable is a pulse sampled by the original clock. I prefer enables for logic inside one design: single clock domain, simpler timing, no crossing logic. A true divided clock is needed when an external device needs a physical slower clock (an SPI clock pin) or when saving clock-tree power matters, and then it needs a generated-clock constraint.

### How would you make the divisor programmable and safe?
Hold the new value in a shadow register and load it into the working register only when the counter reaches terminal count. Use a reset-safe default, synchronize the control signal, and keep the output a registered signal. Guard against $N=0$ or $1$ with explicit handling (N=1 passes the clock through, which should be handled with a mux or by disallowing it).

### Scenario: a divided clock works in simulation but your FPGA board shows random data errors on the slow domain. What do you check?
First the timing report: is the divided signal on a global clock buffer, and is it constrained as a generated clock? If the logic output drives flop clock pins through ordinary routing, skew can break hold. Then check crossings between the fast and slow domains (they are not synchronous to each other), reset release, and whether a combinational path drives the clock. The fix is usually to switch to a clock-enable scheme or the vendor clock primitive.

### What if the input clock duty cycle is not 50%? Does your odd-N design still give 50%?
Not exactly. The falling-edge phase is shifted by the input's high time $t_{high}$ rather than by half a period, so the OR is high for $H\,T_{in} + t_{high}$. For divide-by-3 with a 40% duty input that is $1.4\,T_{in}$ out of $3\,T_{in}$, a 46.7% output duty instead of 50%. If an exact 50% matters, use a PLL or double the clock first and divide by $2N$.
:::
