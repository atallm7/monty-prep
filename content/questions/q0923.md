::: basics
### In plain words
GPU designers assume the work is millions of independent, similar pieces, and every optimization uses that. One instruction front end serves 32 lanes, many threads hide memory delays, and the memory is very wide and fast. Dedicated hardware handles common jobs. Each of these gives up flexibility for efficiency, so a GPU is poor at single tasks, branchy code and small jobs.

### Picture it
Think of a bottling plant. It is superbly efficient at filling millions of identical bottles: one control system runs a hundred filling heads, and the conveyor never stops. But ask it to make one custom jar, or to handle bottles that each need different treatment, and it wastes most of its machinery. The speed comes from giving up flexibility.

### Words you need
- **Amortization**: spreading a fixed overhead, such as fetching and decoding an instruction, across many operations.
- **Fixed-function unit**: dedicated hardware for one job, such as texture filtering, that beats general code.
- **Divergence**: lanes in a warp wanting different branches, which leaves lanes idle ([[q0920]]).
- **Memory bandwidth**: bytes per second between memory and the chip.

### The simplest example
Use the page's illustrative energy numbers. Fetching and scheduling one instruction costs 40 pJ, and the arithmetic itself costs 4 pJ. A scalar machine pays both for every operation: 44 pJ. A GPU sharing one instruction across 32 lanes pays $40/32 + 4 = 5.25$ pJ per operation. That is about 8.4 times less energy. The trade-off: if branches leave lanes only 60% useful, the cost per useful operation is $5.25/0.6 = 8.75$ pJ. That is still about 5 times better.

That is the whole idea: each trick trades generality for efficiency. The rest of this page covers the cost of the huge register file, memory width and texture compression, fixed-function rigidity, a list of when the tricks fail, and heat.
:::

::: testing
Whether you can list the architectural optimizations **and** attach a cost to each. The interviewer wants:

1. Specific mechanisms: massive parallelism, SIMT amortization of fetch/decode, latency hiding, high-bandwidth memory, fixed-function units, texture caches and compression, on-chip tiles.
2. The logic of "specialize for the common case" and why it makes graphics so efficient.
3. Honest trade-offs: poor single-thread performance, divergence, need for huge parallelism, programming difficulty, inflexible hardware, power density, memory capacity.
4. A sense of numbers: energy per operation, bandwidth, compression ratios.
:::

::: why
This is a classic "design trade-off" question: every optimization is a bet on a workload, and it pays only while the bet holds. Being able to say "here is the optimization, here is what it assumes, here is when it breaks" is the skill used in real architecture reviews. It also connects CPU/GPU differences ([[q0922]]) to power and area decisions that later show up at SoC level ([[q0932]]).
:::

::: concepts
- **Specialization**: hardware tuned to a workload's common case. See [[q0921]].
- **SIMT amortization**: one fetch/decode drives many lanes. See [[q0920]].
- **Latency hiding by multithreading**: more threads, bigger register file.
- **Memory bandwidth**: wide buses, GDDR/HBM, compression.
- **Fixed-function units**: rasterizer, texture units, ROPs, ray-tracing and matrix engines.
- **Energy per operation**: voltage, frequency and data-movement costs. See [[q0945]].

::: answer
"The big picture is that GPUs specialize for a workload where there are millions of independent, similar pieces of work, and every optimization exploits that.

First, massive parallelism and SIMT: instead of a complex front end per thread, one fetch and decode feeds 32 lanes, so the overhead per operation is tiny. Second, latency hiding by multithreading: tens of thousands of threads and a huge register file mean no need for big caches or speculation. Third, very high memory bandwidth, with wide GDDR or HBM buses, plus texture caches and compression of color, depth and textures to cut traffic. Fourth, fixed-function hardware for rasterization, texture filtering and blending, which is much more energy-efficient than doing it in shaders. And they run at lower clock and voltage, which gives much better energy per operation.

The trade-offs follow directly. Single-thread performance is poor. Branch divergence and uncoalesced memory accesses waste lanes and bandwidth. You need huge amounts of parallel work to hit peak. The big register file and wide memory interface cost area and power, and memory capacity is limited compared with system RAM. Fixed-function blocks are inflexible if the workload changes. And programming is harder, because you have to think about warps, memory patterns and occupancy."
:::

::: technical
**Optimizations and the cost of each.**

| Optimization | What it buys | What it costs / assumes |
|---|---|---|
| Thousands of simple lanes in SIMT groups | Fetch/decode/schedule amortized over 32 lanes; high FLOP/mm² | Lockstep: divergence wastes lanes; weak single-thread speed |
| Massive multithreading, zero-cost switch | Hides 400+ cycle memory latency without big caches or speculation | Huge register files (hundreds of KB per SM), need >10⁴ threads |
| High-bandwidth memory (GDDR6/6X, HBM) | Hundreds of GB/s to TB/s feeds the lanes | Cost, power, pin count or interposer; limited capacity |
| Texture caches, color/depth compression | Cuts DRAM traffic (for example block texture compression 8:1) | Lossy formats; compression logic area; unpredictable ratios |
| Fixed-function raster, texture, ROP | 10 to 100x better energy/area than shaders on those tasks | Inflexible; idle when the workload doesn't use them |
| Tile-based rendering / on-chip tiles | Overdraw and blending in SRAM; one DRAM write per pixel | Binning overhead, geometry buffering |
| Early-Z / hierarchical-Z | Skips shading hidden pixels | Disabled by `discard` or depth writes in shaders |
| Lower clock and voltage | Lower energy per op ($\propto CV^2$) | Each thread slower |
| Reduced-precision datapaths (FP16/INT8, tensor units) | 2 to 16x more throughput per area/watt | Accuracy limits; special-purpose |
| Shared memory (software-managed) | Deterministic fast reuse within a block | Programmer must manage, bank conflicts |

**SIMT amortization, quantified.** Let the per-instruction overhead (fetch, decode, schedule, operand collect) be $E_o$ and the arithmetic energy $E_a$. A scalar machine spends $E_o+E_a$ per operation. A $W$-lane SIMT machine spends $E_o/W+E_a$. With illustrative $E_o=40$ pJ and $E_a=4$ pJ: scalar 44 pJ; $W=32$: $1.25+4=5.25$ pJ, an 8.4x improvement.

**Voltage and frequency.** Dynamic energy per operation scales with $V^2$. A lane at 0.8 V instead of a CPU's 1.1 V uses $(0.8/1.1)^2=0.53$ of the energy per op, and a lower clock permits a simpler, smaller, lower-leakage design.

**Main trade-offs.** Poor latency per thread, divergence penalty (down to 1/32), sensitivity to memory access patterns, high peak power and power density (cooling), limited device memory, PCIe transfer cost, restricted programming model.
:::

Compression and on-chip tiles cut bandwidth. The costs are weak single-thread speed, divergence and memory-pattern sensitivity, huge register files and power, limited memory, and harder programming."

::: long
"Every GPU optimization is a bet that the workload has lots of independent, similar work, like pixels.

The first is SIMT. Instead of every thread carrying its own fetch, decode and scheduling machinery, one instruction stream drives 32 lanes. If the overhead per instruction is something like ten times the arithmetic itself, spreading it over 32 lanes makes the overhead almost vanish. That's a big part of why GPUs are efficient per operation.

Second, latency hiding. Instead of big caches, branch predictors and out-of-order windows, the GPU keeps tens of thousands of threads resident and switches to another when one stalls. The price is a very large register file, hundreds of kilobytes per SM, and a requirement that you give it enough parallel work.

Third, memory. GPUs use wide, fast memory, GDDR or HBM, giving hundreds of GB/s to terabytes per second. They then work to cut traffic: texture caches, block texture compression with ratios like 8 to 1, color and depth compression, and tile-based rendering so blending happens in on-chip memory.

Fourth, fixed-function blocks: the rasterizer, texture filtering and ROPs. These do the same operation on every pixel, so dedicated logic is far more efficient than shader code. Modern GPUs add ray-tracing and tensor units for the same reason. Finally they run at lower voltage and frequency, which saves energy per operation quadratically in voltage.

The trade-offs are the flip side. A single thread is slow. Divergence serializes branches and can cut efficiency to one thirty-second. Uncoalesced memory access wastes bandwidth. You need huge parallelism to reach peak. The register file and memory interface are area- and power-hungry, device memory is limited compared with host RAM, fixed-function units are inflexible if the workload changes, and software has to be written carefully for warps and memory layout. So the GPU wins big when the bet holds and can lose badly when it doesn't."
:::

::: terms
- **Amortization**: spreading a fixed overhead (fetch/decode) over many operations.
- **Zero-overhead context switch**: switching warps with no state save because registers stay resident.
- **Texture compression**: block formats (such as BCn, ASTC) that shrink texture memory and bandwidth.
- **Early-Z / Hi-Z**: depth tests before shading, per pixel or hierarchical.
- **Tile-based rendering**: render in on-chip tiles to avoid DRAM round trips.
- **Tensor / matrix unit**: fixed-function matrix multiply-accumulate hardware.
- **Divergence**: warp lanes taking different branches.
- **Power density**: watts per mm², a thermal limit.
:::

::: exceptional
**An average answer** says "lots of cores, fast memory, specialized hardware".

**An exceptional answer**:
- Organizes optimizations as **bets on workload properties** and states the property each assumes.
- Quantifies one or two (SIMT amortization 44 pJ to 5 pJ; texture compression 8:1; $V^2$ scaling).
- Distinguishes **energy** optimizations from **performance** optimizations.
- Names the specific failure mode for each (divergence, uncoalesced access, `discard` disabling early-Z, small kernels not filling the machine).
- Notes the cost side in silicon and power: register file size, memory interface, power density.
- Mentions that the boundary is moving (CPUs adding SIMD/matrix, GPUs adding caches and flexible scheduling).
:::

::: mistakes
- **Listing optimizations without trade-offs.** The question explicitly asks for both.
- **"Higher clock speed"** as a GPU optimization: GPUs generally run slower clocks than CPUs.
- **Claiming GPUs have no caches.** They have texture caches, L1/L2, and constant caches.
- **Mixing up latency and throughput.** Multithreading raises throughput, not per-thread speed.
- **Forgetting energy.** Many choices (SIMT, low voltage, fixed-function) are about joules per operation, not just speed.
- **Saying fixed-function is always better.** It is only efficient while the workload matches; it wastes area otherwise.
:::

::: deep
## The efficiency argument in joules

An operation on a processor costs the arithmetic itself plus all the overhead to decide *what* to do and *where the data is*. Published circuit-level measurements (for example Horowitz's ISSCC 2014 energy table at 45 nm) show arithmetic energy of a few picojoules but instruction and data-movement overhead in the tens to hundreds of picojoules, with a DRAM access far above that. Specialization attacks the overhead.

> Absolute picojoule values depend on process node and design and are from older nodes in the literature. Use ratios and orders of magnitude, not exact values. The numbers below are illustrative.

Figure: The dashed line is the arithmetic floor E_a = 4 pJ. With overhead 10x the arithmetic cost, widening the group from 1 to 32 lanes cuts energy per operation by 8.4x. Beyond about 16 lanes the gains flatten near the arithmetic floor, which is why going wider than 32 to 64 buys little but costs divergence.

The curve also shows the **cost** side: widening further would increase divergence waste. If the average warp runs at 60% lane efficiency because of branches, the effective energy per *useful* op is $E/0.6$, so $W=32$ gives $5.25/0.6=8.75$ pJ and the benefit relative to scalar falls from 8.4x to 5x.

## Latency hiding and its price in silicon

The register file is the key enabler. With 2048 resident threads and 32 registers each, an SM holds $2048\times32\times4\text{ B}=256$ KB. Across 80 SMs that is 20 MB of register file, more than many CPUs' L3 cache, and it must be multi-ported or banked and read every cycle by many lanes. It's a significant share of area and a large source of static power. A CPU instead puts a few hundred registers (physical register file) per core and relies on a cache hierarchy. Both are paying SRAM area to hide latency; the GPU pays it in registers and gets the benefit only when there is enough parallelism. Run a tiny kernel of 1000 threads on that machine and you use under 1% of it.

## Memory-system optimizations, with numbers

**Wide, fast memory.** A 256-bit GDDR6 interface at 16 Gb/s per pin gives $256\times16/8=512$ GB/s. One HBM2E stack at 1024 bits and 3.2 Gb/s gives $1024\times3.2/8=410$ GB/s per stack, and several stacks reach multiple TB/s. Cost: GDDR needs many pins and careful PCB signal integrity at high data rates, while HBM needs a silicon interposer and advanced packaging, raising cost and limiting capacity per stack.

**Texture compression.** A 4x4 block of RGBA8 texels is 64 bytes. Block compression BC1 stores it in 8 bytes, 8:1. Textures stay compressed in memory and caches and are decompressed by the texture unit. The cost is fixed lossy quality and encoder time, but sampling bandwidth and cache footprint drop up to 8x. Mobile uses ASTC with selectable block sizes for bits-per-pixel trade-offs.

**Color/depth compression and tiling.** Lossless compression on regions with uniform or smoothly varying values commonly saves around 2x on typical content, with no guarantee: worst-case content gets no gain, so the memory system must still be provisioned for full traffic in the worst case.

## Fixed function: efficiency and rigidity

A bilinear texture sample needs four texels, addressing, format conversion, filter-weight computation and four multiply-adds per channel. In shader instructions that is dozens per sample; a texture unit does it in a pipelined fixed path with dedicated caches and filtering. The same logic holds for rasterization (incremental edge functions with adders) and blending. The cost is area and design commitment: if the workload shifts (say, toward compute with no textures) the texture units sit idle but still take area and leak. This is why recent datacenter accelerators drop graphics hardware and add matrix engines instead. Tensor units are the same idea: an FP16 matrix-multiply-accumulate array does many times the operations per watt of general lanes, but only helps matrix-shaped code.

## When the optimizations fail: a failure catalog

1. **Divergent branches**: lanes idle, warp time = sum of paths.
2. **Scattered memory access**: coalescing fails, effective bandwidth drops 8x or more (see [[q0920]]).
3. **Too little parallelism**: a kernel with 1000 threads on 160,000-thread hardware.
4. **`discard`/depth-write in shaders**: early-Z disabled, overshading.
5. **Tiny triangles**: quad overshading and setup limits ([[q0921]]).
6. **Working-set exceeding on-chip storage**: 37 bytes of L2 per thread means no cache help.
7. **Transfer-bound jobs**: PCIe dominates ([[q0922]]).
8. **Thermal/power limits**: sustained clocks below the boost clock.

## Power density: the thermal cost

A GPU die of 600 mm² dissipating 300 W has an average power density of $300/600=0.5$ W/mm², or 50 W/cm², with hotspots higher. Hence large heat sinks, vapor chambers, liquid cooling in datacenters, and aggressive power management (clock gating idle SMs, DVFS). A phone GPU, with passive cooling of a few watts total, must use tile-based rendering and low clocks to stay inside the budget. So the thermal budget, not peak FLOPs, often sets sustained GPU performance.

> Close with a one-sentence principle: "each optimization trades generality for efficiency, so the GPU is brilliant when the workload is wide, regular and bandwidth-friendly and mediocre when it is narrow, branchy or irregular."

::: applications
- **Gaming GPUs**: rely on fixed-function raster/ROP/RT cores plus large shader arrays and GDDR.
- **Mobile GPUs**: tile-based rendering, texture compression (ASTC) and low clocks for sub-5 W budgets.
- **AI accelerators**: HBM, tensor units, reduced precision (FP16, BF16, INT8) for matrix workloads.
- **Video encode/decode engines**: separate fixed-function blocks next to the GPU for far lower energy per frame than shaders.
- **Professional visualization**: large framebuffer memory and ECC options traded against cost.
:::

::: assumptions
- Energy figures are illustrative ratios; absolute values vary by process, design and clock.
- "GPU" covers consumer, mobile and datacenter parts. Not every optimization exists in all (for example tile-based rendering is typical in mobile GPUs).
- Compression ratios depend on content; BC1's 8:1 is a fixed format ratio, whereas color/depth compression is content-dependent.
- Trade-off severity depends on the workload; a regular compute kernel hardly sees the fixed-function trade-off at all.

::: followups
### Why does SIMT save energy compared with giving each thread its own pipeline?
Instruction fetch, decode, scheduling and operand collection are paid once per warp rather than per thread. If those cost 10x the arithmetic, a 32-lane warp spends roughly an eighth of the energy per operation (illustratively 5.25 vs 44 pJ), as long as lanes stay active.

### What is the downside of a very large register file?
Area and leakage, plus access energy and wiring. It also caps occupancy: more registers per thread means fewer resident threads, less latency hiding. Compilers trade register use against spilling, and programmers tune this per kernel.

### Why not use fixed-function units for everything?
They are efficient only for the exact operation they implement and cannot adapt to new algorithms. The industry keeps graphics fixed-function where operations are stable (raster, texture filtering, blending) and uses programmable shaders for the parts that change (lighting models). Matrix engines are a newer stable pattern.

### If compression gives an average 2x bandwidth saving, can I halve the memory interface?
Not safely. Compression ratio is content-dependent and worst-case frames compress poorly, so you have to size for the worst case or accept stutters. Compression is best viewed as lower average power and extra headroom, not a reason to under-provision.

### A kernel with heavy branching runs at 15% of peak on a GPU. What do you try?
Sort or bin data so neighboring threads follow the same path, restructure to predicated or branch-free math, split into separate kernels per case (stream compaction), reduce the work inside divergent regions, or move the part to the CPU if it is inherently irregular.
