::: testing
Whether you understand that "real-time" means **predictable, bounded response, not "fast"**. The interviewer is looking for the definition (correctness depends on when a result is produced, not just what it is), the hard/firm/soft distinction, the mechanisms that deliver it (priority-based preemptive scheduling, bounded interrupt and kernel latencies, deterministic primitives), and the classic pitfalls: priority inversion, long critical sections, and the fact that an RTOS makes real-time possible but does not guarantee it. Showing a schedulability calculation distinguishes a strong candidate.
:::

::: why
Anything that controls a physical process (motors, brakes, airbags, power converters, medical pumps, audio streams) has deadlines. Missing one is not "slow", it is wrong, sometimes dangerous. RTOSes are the standard way to organise such software on microcontrollers, and real-time reasoning (priorities, worst-case execution times, utilisation, blocking) is a core part of embedded design. It is the culminating question of the OS section, building on [[q0835]], [[q0837]] and [[q0839]].
:::

::: answer
"A real-time operating system is an OS designed so that the timing of its behaviour is predictable. Real-time doesn't mean fast; it means that tasks meet their deadlines reliably, because the worst-case response time is bounded and known.

The way it works is usually a preemptive, priority-based scheduler. Each task has a priority, and the scheduler always runs the highest-priority task that's ready. If a more urgent task becomes ready, say because an interrupt gave it a semaphore, it preempts the current task straight away, after a context switch of a few microseconds. Interrupt latency and the kernel's critical sections are kept short and bounded, and the primitives, like queues, mutexes and timers, have predictable behaviour.

There are different strictness levels. Hard real-time means a missed deadline is a failure, such as an airbag controller or a motor control loop. Soft real-time means occasional misses just degrade quality, like dropped video frames.

Examples are FreeRTOS, Zephyr, ThreadX, VxWorks and QNX.

A real-time OS doesn't guarantee that my system meets its deadlines. I still need to assign priorities sensibly, bound execution times, avoid priority inversion with mutexes that support priority inheritance, and check schedulability, for example with rate-monotonic analysis or response-time calculations."
:::

::: technical
**Definition.** An RTOS provides services with bounded, documented worst-case timing so that application tasks can be shown to meet their deadlines.

**Deadline classes.**
- *Hard*: miss = system failure (airbag, ABS, pacemaker pacing).
- *Firm*: late result is useless but system survives (a missed sensor sample).
- *Soft*: late result is degraded (UI, streaming).

**Key RTOS properties.**
1. Fixed-priority preemptive scheduler (also round-robin among equal priorities, optionally EDF).
2. Bounded interrupt latency and kernel critical sections (interrupts disabled for only a few µs).
3. Deterministic primitives: queues, semaphores, mutexes with **priority inheritance** or ceiling, event flags, timers.
4. Small, static or bounded memory allocation (avoid `malloc` in time-critical paths).
5. Timing services with sub-tick or hardware-timer resolution.

**Response-time analysis (fixed priority, deadlines = periods, independent tasks).** For task $i$ with execution time $C_i$ and higher-priority tasks $j$:
$$R_i^{(k+1)} = C_i + \sum_{j<i}\left\lceil \frac{R_i^{(k)}}{T_j}\right\rceil C_j,$$
iterate from $R_i^{(0)}=C_i$ until it converges. Schedulable if $R_i \le D_i$.

**Example.** Tasks (C, T) = (1, 5), (2, 10), (3, 20) ms, RMS priorities: $R_1 = 1$, $R_2 = 2 + \lceil 3/5\rceil\cdot 1 = 3$, $R_3 = 3 + \lceil 7/5\rceil\cdot1 + \lceil 7/10\rceil\cdot2 = 3+2+2 = 7$ ms. All $\le$ periods. Utilisation 0.55 versus the $n=3$ bound 0.780.
:::

::: long
"A real-time OS is an operating system built so that its timing is predictable. The important point is that real-time doesn't mean fast, it means a result is only correct if it arrives by its deadline, and the worst-case time is bounded and known in advance.

Deadlines come in classes. Hard real-time: missing one is a system failure, like a motor controller or an airbag. Firm: a late result is useless but the system carries on. Soft: late is just degraded, like UI or streaming.

The core mechanism is a preemptive, fixed-priority scheduler. Every task has a priority and the highest-priority ready task always runs. When an interrupt makes a higher-priority task ready, say by giving a semaphore, the kernel switches to it after a few microseconds. To keep that bound, the RTOS keeps interrupt-disabled sections extremely short, offers primitives with deterministic behaviour, and encourages static memory allocation, because malloc can take unbounded time.

The big hazard is priority inversion. A low-priority task holds a mutex that a high-priority task needs, and a medium-priority task preempts the low one, so the high-priority task is stuck behind the medium one. The fix is a mutex with priority inheritance, so the low-priority task runs at the high task's priority until it releases the lock. That's famously what hit the Mars Pathfinder lander in 1997.

An RTOS makes real-time achievable but doesn't guarantee it. I'd do the analysis. For periodic tasks I'd assign rate-monotonic priorities, shortest period highest, and check utilisation against the bound, or compute response times directly. For tasks of 1 ms every 5, 2 ms every 10 and 3 ms every 20, the worst-case response times work out to 1, 3 and 7 ms, all within their periods. Then I'd measure with a scope to confirm."
:::

::: terms
- **Deadline**: time by which a result must be produced.
- **Hard / firm / soft real-time**: severity of a missed deadline.
- **Latency / jitter**: delay from event to response / its variation.
- **WCET**: worst-case execution time of a piece of code.
- **Preemptive scheduling**: higher-priority ready task interrupts the running one.
- **Rate-monotonic (RMS)**: priority assignment by period (shorter = higher).
- **Priority inversion / inheritance**: hazard and fix when tasks share a lock.
- **Response time ($R_i$)**: worst-case time from task release to completion.
- **Tick**: periodic timer interrupt that drives kernel timekeeping.
:::

::: mistakes
- **"Real-time means fast."** A slow but predictable system can be real-time; a fast but unbounded one is not.
- **Assuming an RTOS guarantees deadlines.** It only provides the mechanisms; the design must be analysed.
- **Using binary semaphores as mutexes**, losing priority inheritance.
- **Calling `malloc`/`printf` from high-priority tasks**, whose execution time is unbounded.
- **Wrong priority assignment.** Priorities should follow deadlines/periods (RMS or deadline-monotonic), not "importance".
- **Long ISRs or critical sections** that destroy the latency guarantee.
- **Calling Linux a hard RTOS.** With PREEMPT_RT it gets close for some uses but is not typically certified hard real-time.
:::

::: deep
## What "real-time" really means

A real-time system is judged by two things: logical correctness and temporal correctness. Consider an anti-lock braking controller that needs to update wheel-slip every 5 ms. A perfectly computed answer at 7 ms is a wrong answer. The key quantity is not average speed but **worst-case** behaviour: the longest delay from an event to the response, and the variation (jitter).

| Class | Consequence of a missed deadline | Examples |
|---|---|---|
| Hard | failure, possibly harm | airbag firing, motor current loop, pacemaker, flight control |
| Firm | result discarded, system continues | video frame decode, sampled-data measurement |
| Soft | quality degrades | UI animation, audio buffering with margin, logging |

## Anatomy of latency

When an external event happens, the time until the responding task starts running is a sum of terms, each of which an RTOS must bound:

$$L = t_{\text{IRQ}} + t_{\text{ISR}} + t_{\text{sched}} + t_{\text{switch}} + t_{\text{block}}$$

- $t_{IRQ}$: interrupt latency. On Cortex-M, 12 cycles to start the ISR with zero-wait-state memory, plus the longest period where interrupts are disabled (kernel critical sections, application critical sections).
- $t_{ISR}$: the time the ISR itself runs (kept short; it does little work, then signals a task).
- $t_{sched}$: scheduler decision time (O(1) in good RTOSes, using a priority bitmap).
- $t_{switch}$: context switch (saving/restoring 16 or so registers).
- $t_{block}$: time the task is blocked by lower-priority tasks holding resources (priority inheritance bounds this).

Example for a 48 MHz Cortex-M: IRQ 0.25 µs + longest critical section 5 µs + ISR 3 µs + scheduler 2 µs + switch 5 µs + blocking 0 = about 15 µs. This is the number you verify on a scope with a GPIO toggle at the ISR entry and at the task's first line.

## Fixed-priority scheduling with a timeline

Take three periodic tasks with execution time $C$ and period $T$ (deadline = period): T1 = (1 ms, 5 ms), T2 = (2, 10), T3 = (3, 20). Rate-monotonic priorities: T1 > T2 > T3. All released at $t=0$.

```timing
{"signals":[
 {"name":"T1 (C1,T5)","wave":"10000100001000010000","color":"red"},
 {"name":"T2 (C2,T10)","wave":"01100000000110000000","color":"blue"},
 {"name":"T3 (C3,T20)","wave":"00011010000000000000","color":"green"}],
 "marks":[{"t":0,"label":"release"},{"t":5,"label":"T1 again"},{"t":10,"label":"T1, T2 again"},{"t":15,"label":"T1 again"}],
 "hscale":0.8}
```
Figure: Each column is 1 ms; a high level means the task is running. T1 always runs the moment it is released. T2 runs in the first gaps (1 to 3 ms). T3 gets the CPU only in the remaining gaps: 3 to 5 ms, then is preempted at 5 ms by T1, and finishes at 7 ms (its worst-case response time). The CPU is idle from 7 to 10 ms.

Response-time analysis confirms what the picture shows:

- $R_1 = C_1 = 1$ ms.
- $R_2$: start with $R=2$: $2 + \lceil 2/5\rceil\cdot1 = 3$; again with $R=3$: $2 + \lceil 3/5\rceil\cdot1 = 3$. Converged: $R_2 = 3$ ms.
- $R_3$: start $R=3$: $3 + \lceil 3/5\rceil\cdot1 + \lceil 3/10\rceil\cdot2 = 6$; then $3 + \lceil 6/5\rceil\cdot1 + \lceil 6/10\rceil\cdot2 = 3 + 2 + 2 = 7$; then $3 + \lceil 7/5\rceil\cdot1 + \lceil 7/10\rceil\cdot2 = 3+2+2 = 7$. Converged: $R_3 = 7$ ms.

All response times are below the periods (5, 10, 20 ms), so the set is schedulable, with margin: T3 finishes at 7 ms of its 20 ms deadline. Utilisation: $0.2+0.2+0.15 = 0.55$, below the RMS bound for three tasks of $3(2^{1/3}-1) = 0.780$.

Now add the OS's own load, such as a 1 kHz tick taking 25 µs per tick (2.5% of the CPU): the effective utilisation rises to about 0.575, still comfortable. A 4th task with $C=5$ ms, $T=20$ ms would raise $U$ to 0.80, above the $n=4$ bound of 0.757, so use exact response times: it would be the lowest priority, $R_4 = 5 + \lceil R/5\rceil + 2\lceil R/10\rceil + 3\lceil R/20\rceil$: try $R=5$: $5+1+2+3=11$; $R=11$: $5+3+4+3 = 15$; $R=15$: $5+3+4+3 = 15$. Converged at 15 ms $\le 20$: schedulable even though the utilisation bound was exceeded.

## Priority inversion, concretely

Three tasks: H (high), M (medium), L (low). H and L share a mutex. L takes the mutex at $t=0$. H becomes ready at $t=2$, tries to take the mutex and blocks. M becomes ready at $t=3$ and, being higher than L, preempts it. L cannot run to release the mutex until M finishes.

```timing
{"signals":[
 {"name":"L (low)","wave":"110000011000","color":"green"},
 {"name":"M (medium)","wave":"000111100000","color":"orange"},
 {"name":"H (high)","wave":"001000000110","color":"red"},
 {"name":"mutex held by L","wave":"111111111000","color":"muted"}],
 "marks":[{"t":2,"label":"H blocks"},{"t":3,"label":"M"},{"t":9,"label":"H resumes"}],
 "hscale":1.3}
```
Figure: Without priority inheritance, H (the most important task) waits from t=3 until t=9, while M, which does not even need the mutex, runs for 4 ms in between. Because M's run time is not bounded by anything in H's design, H's blocking time is unbounded in principle.

With **priority inheritance**, at $t=2$ L temporarily inherits H's priority, so M cannot preempt it. L finishes its critical section (2 more ms, $t=3$ to $5$), releases the mutex, drops back, and H runs at $t=5$. H's blocking is bounded by L's critical section length (2 ms of L's work) and M is delayed instead of H. **Priority ceiling** protocols go further: they also prevent deadlock and limit blocking to one critical section.

The Mars Pathfinder lander (1997) suffered repeated resets because a low-priority meteorological task held a mutex needed by a high-priority bus-management task, medium tasks preempted it, and a watchdog reset the system when the high-priority task missed its deadline. The VxWorks mutex had an option for priority inheritance that was not enabled, and enabling it fixed the issue. (This is a widely documented case; check the primary accounts if you quote the details.)

> Details of the Pathfinder anecdote are well known but secondhand here. Quote only the headline: priority inversion on a mutex, fixed by enabling priority inheritance.

## What makes a kernel "real-time"

1. **Bounded, documented worst-case timing** of kernel calls (queue send, semaphore give, context switch), usually independent of the number of tasks (O(1) scheduling).
2. **Priority-based preemption** in the kernel itself (a preemptible kernel, with only very short non-preemptible regions).
3. **Interrupt design**: ISRs signal tasks using "from ISR" APIs; deferred processing in tasks. Nested interrupts with priorities.
4. **Priority inheritance/ceiling mutexes.**
5. **Memory:** static allocation or bounded-time allocators (fixed-size block pools), no garbage collection pauses.
6. **Timers:** hardware timers with fine resolution; tick-less designs. A 1 kHz tick means a `delay(1)` can be anywhere from nearly 0 to 1 ms, so for tight timing use a hardware timer or `delay_until` with a periodic wake-up.

## Real hardware matters too

Software bounds sit on hardware that may not be deterministic: caches (hit vs miss), flash wait states, DMA contention on the bus matrix, and branch prediction on bigger cores all add jitter. Hard real-time designs on Cortex-M often place critical code in tightly coupled memory (TCM) or SRAM, lock cache lines, or choose cores without caches (Cortex-M0/M3/M4) for deterministic timing. Flash page erase on a single-bank device stalls instruction fetch for tens of milliseconds, which can break a 1 ms deadline unless the erase runs from RAM or a second bank.

## Verification in practice

- **WCET analysis:** measure with cycle counters under worst-case inputs (a stress test), or use static analysis tools for safety-critical work; add margin (20-30%).
- **Instrumentation:** GPIO toggles at task entry and exit on a scope/logic analyzer, or trace tools that show task timelines (SEGGER SystemView, Percepio Tracealyzer are examples).
- **Stress and fault injection:** run with maximum interrupt rates, full queues, and flash writes happening.
- **Monitoring in the field:** watchdog, deadline-miss counters, stack high-water marks.

- **Motor drives and power converters**: a top-priority control task or ISR at 10-50 kHz with lower-priority communication.
- **Automotive ECUs**: OSEK/AUTOSAR-style fixed-priority scheduling for engine control, braking and body electronics.
- **Medical devices**: infusion pumps, ventilators, pacemakers with certified kernels and analysed deadlines.
- **Avionics and space**: VxWorks, RTEMS, INTEGRITY on flight computers.
- **Audio/video pipelines**: DMA-fed streams with soft/firm real-time buffers.
- **Industrial control and robotics**: periodic I/O scans and motion control tasks.

::: assumptions
- I assume a **single-core, fixed-priority preemptive RTOS** on a microcontroller. Multicore real-time, EDF scheduling and mixed-criticality systems add complexity.
- Response-time analysis assumes **independent periodic tasks, deadline equals period** and ignores blocking and kernel overhead except where noted; real analyses add terms for blocking (resource sharing), jitter and interrupt load.
- Latency figures are **illustrative** for a 48 MHz Cortex-M with zero-wait-state memory.
- "Hard" real-time in a safety-critical product also requires **process evidence and certification** (for example DO-178C, ISO 26262, IEC 61508 or IEC 62304, depending on domain), not just a good scheduler.
- General-purpose OSes can be **soft real-time**; PREEMPT_RT Linux narrows the gap for many uses.

::: followups
### What's the difference between a real-time OS and a general-purpose OS?
A general-purpose OS (Windows, desktop Linux) optimises average throughput and fairness; its worst-case latency can be milliseconds and is unbounded under load (paging, long kernel sections). An RTOS optimises for bounded worst-case latency: priority preemption, short critical sections, deterministic primitives, and no paging. RTOSes are usually smaller, with fewer features.

### What is priority inversion and how do you prevent it?
When a low-priority task holds a resource a high-priority task needs, and a medium-priority task preempts the low-priority one, the high-priority task is delayed indefinitely. Prevention: mutexes with priority inheritance or priority ceiling, short critical sections, avoiding shared resources between tasks of very different priority (use queues and message passing), and designing for bounded blocking.

### How do you choose task priorities?
For periodic tasks with deadlines equal to periods, use rate-monotonic assignment: shortest period gets the highest priority. For deadlines shorter than periods, use deadline-monotonic. Importance is not the criterion; deadlines are. Then verify with utilisation and response-time analysis, and treat ISR-driven work and the tick as the highest priority load.

### How do you handle an interrupt in an RTOS?
Keep the ISR minimal: read the hardware, clear the flag, and signal a task through an interrupt-safe API (give a semaphore, send to a queue, or use a task notification), which makes the handler task ready. When the ISR returns, the kernel checks whether a higher-priority task became ready and switches to it immediately. The long processing runs in the task at its assigned priority, not in the ISR.

### Harder: three tasks (2 ms, 8 ms), (3 ms, 12 ms), (4 ms, 24 ms)? Is it schedulable under RMS?
Utilisation: $2/8 + 3/12 + 4/24 = 0.25+0.25+0.167 = 0.667 \le 0.780$, so yes by the bound. Exact: $R_1 = 2$; $R_2 = 3 + \lceil R/8\rceil\cdot 2$: $R=3 \to 5 \to 5$; so $R_2 = 5 \le 12$; $R_3 = 4 + \lceil R/8\rceil 2 + \lceil R/12\rceil 3$: $R=4 \to 4+2+3 = 9 \to 4 + 4 + 3 = 11 \to 4+4+3 = 11$. $R_3 = 11 \le 24$. Schedulable with ample margin.
