::: basics
### In plain words
You need an OS when the software must do several things at once with different timing needs, or when you need services that are hard to write yourself, such as a network stack, USB, or a file system. For a simple device with one or two jobs, a plain main loop is usually better. The choice should rest on numbers, not habit.

### Picture it
A cook with one dish needs no manager. A busy kitchen with many orders at once does. Someone has to decide who gets the stove, and an urgent order must not wait behind a slow one. The OS is that manager. But a manager costs wages, which is the memory and CPU time an OS uses, so a tiny kitchen does better without one.

### Words you need
- **Task**: one activity that the OS runs, with its own stack of working memory.
- **Scheduler**: the part of the OS that decides which task runs next.
- **Super-loop**: one endless loop that calls each job in turn. It is the usual no-OS design.
- **Preemption**: pausing a running task so a more important one can run at once.
- **Bare-metal** ([[q0838]]): firmware running directly on the hardware with no OS.

### The simplest example
A device has a control job that must run every 1 ms, and a display update that takes 50 ms. In a super-loop, the control job must wait for the display update to finish, so it can be up to 50 ms late. With an RTOS (a small real-time OS), you give the control task a higher priority. It preempts the display task and runs almost at once. The cost is RAM: four tasks with a 1 KB stack each use 4 KB, which matters on an 8 KB part.

That is the whole idea. The rest of this page covers the argument about managing waiting, a quick numeric check of whether the tasks fit, the costs, and where Linux comes in.
:::

::: testing
Whether you can make a **justified engineering decision**, not just say "when it's complex". The interviewer wants specific triggers: several concurrent activities with different timing, blocking I/O, a networking/USB/file-system stack that is itself multi-threaded, the need for memory protection or an MMU, team and code-reuse scale, and power management across many components. And the reverse: you know when *not* to use one (tiny, ultra-low-power, hard deterministic loops). Quantifying the decision (RAM, CPU overhead, schedulability) is the differentiator.
:::

::: why
"Should we use an RTOS?" is a real architecture review question, and the wrong answer is expensive both ways: adding an RTOS to a trivial product wastes memory and introduces concurrency bugs; skipping it in a complex product produces a fragile super-loop that nobody can extend. The question is phrased as "When is it needed?" in a sequence with [[q0835]] (what an OS is) and [[q0838]] (bare-metal), so the expected answer is a reasoned set of criteria.
:::

::: concepts
- **Concurrency**: multiple activities that must make progress independently ([[q0835]]).
- **Super-loop + interrupts**: the bare-metal alternative ([[q0838]]).
- **Timing requirements**: deadlines, jitter tolerance, periodic vs event-driven tasks.
- **Blocking and waiting**: tasks that wait for I/O without wasting CPU.
- **Utilisation and schedulability**: whether all deadlines can be met ([[q0840]]).
- **Resource cost**: RAM per task, tick overhead, flash for the kernel.
:::

::: answer
"I'd say you need an OS when the software has to do several things at once with different timing requirements, or when you need services that are painful to write yourself.

The signs are: multiple independent activities, like reading sensors, handling a network connection, updating a display and responding to buttons. In a bare-metal super-loop, a slow operation in one of them delays all the others. With an RTOS, each is a task, and the scheduler lets a high-priority task preempt a low-priority one, so a 1 ms control task is not held up by a 50 ms flash write.

Other triggers: using middleware that expects threads and blocking calls, like a TCP/IP stack, USB host or a file system; needing memory protection or process isolation, which pushes you to Linux with an MMU; wanting portable, modular code across a team; and complex power management.

When I wouldn't use one: simple devices with one or two jobs, hard memory limits, like 2 KB of RAM, ultra-low-power nodes that sleep most of the time, or very tight deterministic loops where a state machine and interrupts do the job with less overhead and fewer concurrency bugs.

I'd make the decision with numbers: the RAM for task stacks, a few percent CPU for the tick, and a simple schedulability check of the periodic tasks."
:::

::: technical
**Decision criteria.**

| Question | If yes | Lean |
|---|---|---|
| More than ~3 independent activities with different rates? | scheduler helps | RTOS |
| Must a long operation (flash write, display refresh) not delay a short deadline? | preemption needed | RTOS (or ISR split) |
| Using TCP/IP, USB, TLS, file system, BLE stacks? | these assume threads | RTOS / Linux |
| Needs process isolation, dynamic loading, virtual memory? | MMU | Linux |
| RAM < ~4 KB or ultra-low-power with long sleep? | overhead too high | bare-metal |
| Hard sub-microsecond deterministic response? | hardware (timer, DMA, PRU) | ISR/bare-metal |
| Certification or reuse across product line? | proven kernel | certified RTOS |

**Overheads.** Tick of 1 kHz with 1,200-cycle handler at 48 MHz: 2.5% CPU. Each task adds a stack (256-2048 bytes typical) plus a control block (~100 bytes, port-dependent). Kernel flash roughly 5-15 KB for a small RTOS.

**Schedulability (rate-monotonic).** For $n$ periodic tasks with execution times $C_i$ and periods $T_i$, utilisation $U=\sum C_i/T_i$. With rate-monotonic priorities the set is guaranteed schedulable if $U \le n(2^{1/n}-1)$ (sufficient, not necessary). For $n=3$ the bound is 0.780; the limit as $n\to\infty$ is $\ln 2 = 0.693$.

**Example.** Tasks $(C,T)$ = (1 ms, 5 ms), (2 ms, 10 ms), (3 ms, 20 ms): $U = 0.2+0.2+0.15 = 0.55 < 0.780$, so schedulable with RMS.
:::

::: short
"You need an OS when you have several concurrent activities with different timing, when a long task mustn't delay a short deadline, or when you use middleware like TCP/IP, USB or a file system that expects threads. You need Linux-class OS for memory protection and big ecosystems. Don't use one on tiny, ultra-low-power or very simple devices, where a super-loop plus interrupts is cheaper and simpler. I'd decide with RAM, tick overhead and a schedulability check."
:::

::: long
"My rule is that you add an OS when the cost of managing concurrency by hand becomes higher than the cost of the OS.

The classic trigger is multiple activities with different timing. Imagine a device that runs a 1 ms control loop, reads sensors every 10 ms, refreshes a display, and manages a network connection. In a bare-metal super-loop, the display refresh might take 8 ms and a flash write 50 ms, which would blow the 1 ms deadline unless I chop everything into little state machines. With an RTOS I give the control task the highest priority and it preempts everything else, so the long jobs can be written naturally with blocking calls.

The second trigger is middleware. A TCP/IP stack, TLS, USB host, a file system or a Bluetooth stack are usually written for threads and blocking APIs. Using them without an OS is possible but awkward.

Third, isolation and scale. If I need memory protection between components, or dynamic loading, or a big ecosystem, that's Linux on a processor with an MMU. And with a large team, an RTOS gives clean module boundaries and portability.

On the other side, an OS isn't free. A 1 kHz tick on a 48 MHz core with a 1200-cycle handler costs 2.5% CPU, every task needs its own stack, and you take on new bugs: priority inversion, deadlocks, races. So for a simple thermostat, a small sensor that sleeps almost all the time, or a part with 2 KB of RAM, I'd stay bare-metal.

I'd quantify it: stack RAM per task, tick overhead, and a quick rate-monotonic check. For tasks of 1 ms every 5, 2 ms every 10 and 3 ms every 20, the utilisation is 55%, well under the 78% bound for three tasks, so it's schedulable."
:::

::: terms
- **Super-loop**: `while(1)` main loop calling functions in sequence, with interrupts.
- **Preemption**: forcibly suspending a running task for a higher-priority one.
- **Utilisation ($U$)**: sum of $C_i/T_i$; fraction of CPU demanded.
- **Rate-monotonic scheduling (RMS)**: fixed priorities, shorter period = higher priority.
- **Blocking call**: call that waits for an event without consuming CPU.
- **Jitter**: variation in when a periodic action actually happens.
- **Middleware**: software layer (network stack, file system) between OS and application.
- **Idle task**: lowest-priority task that sleeps the CPU when nothing else is ready.
:::

::: exceptional
**An average answer**: "When the system is complex or needs multitasking."

**An exceptional answer**:
- Gives concrete triggers: concurrency with different timing, long operations vs short deadlines, thread-based middleware, isolation needs.
- Also gives the counter-cases: tiny RAM, ultra-low power, simplicity, hard deterministic loops.
- Quantifies: tick overhead, stack RAM per task, a schedulability test.
- Mentions the hybrid options (ISRs + state machines, run-to-completion schedulers, hardware offload).
- Connects to team and lifecycle factors: maintainability, certification, portability.
- Notes the new failure modes an OS introduces.
:::

::: mistakes
- **"Always use an OS, it's more professional."** It costs RAM, CPU and introduces concurrency bugs.
- **"Never use an OS, it's slower."** A super-loop with long blocking calls can have worse worst-case latency than an RTOS.
- **Confusing 'needs an OS' with 'needs Linux'.** Many cases only need a small RTOS.
- **Ignoring the stack budget.** Four tasks at 1 KB each is 4 KB; on an 8 KB part that matters.
- **Assuming an RTOS guarantees deadlines.** It only gives predictable scheduling; you still must check utilisation and bounded blocking.
- **Choosing by habit** instead of requirements; or forgetting that vendor middleware may mandate an OS.
:::

::: deep
## The core argument: managing waiting

Most embedded software spends most of its time waiting: for a timer, a sensor conversion, a UART byte, a network packet. Writing code that waits efficiently while doing other useful work is the real concurrency problem.

**In a super-loop:**

```c
while (1) {
    if (adc_done)   process_adc();      // fast
    if (rx_ready)   handle_uart();      // medium
    update_display();                    // 8 ms blocking SPI write
    if (flash_dirty) save_to_flash();    // up to 50 ms blocking!
}
```
The worst-case time from an event to its handling equals the longest path through the loop. Let the stages take 0.2 + 1 + 8 + 50 ms: then a button press might wait 59.2 ms. If you must respond within 1 ms, this architecture fails, however good the code is. The fixes in bare-metal are (a) interrupt handlers for the urgent work, (b) splitting long operations into small state-machine steps (display in 0.5 ms chunks), (c) DMA so that SPI transfers don't block. Each fix is manual, error-prone, and gets harder as features accumulate.

**With an RTOS:**
- Task A (priority 3): 1 ms control loop, blocked on a timer.
- Task B (priority 2): UART and sensor processing, blocked on queue/semaphore.
- Task C (priority 1): display and flash writes, blocked on events.
When the 1 ms timer fires, Task A preempts whatever is running (even the 50 ms flash write) after the context switch (say 10 µs). Worst-case latency becomes: context-switch time + longest interrupt-disabled/critical section in the kernel. The long jobs can be written as simple sequential code.

## Schedulability: a quick numeric check

If tasks are periodic, rate-monotonic analysis gives a test. Execution time $C_i$, period $T_i$; utilisation $U = \sum C_i/T_i$.

$$U \le n\left(2^{1/n}-1\right)$$

is sufficient for schedulability under RMS (deadline = period, independent tasks, negligible overhead).

| $n$ | Bound |
|---|---|
| 1 | 1.000 |
| 2 | 0.828 |
| 3 | 0.780 |
| 4 | 0.757 |
| $\infty$ | 0.693 |

**Example.** Tasks: T1 = (C 1 ms, T 5 ms), T2 = (2, 10), T3 = (3, 20).

$$U = 0.2 + 0.2 + 0.15 = 0.55 \le 0.780.$$ Schedulable. Add a fourth task (C 4 ms, T 20 ms): $U = 0.75 \le 0.757$ for $n=4$: still just inside the guaranteed region. If that fourth task were (5, 20): $U = 0.80 > 0.757$, not guaranteed by the bound, so you need exact analysis (response-time analysis, see [[q0840]]) or more CPU speed.

Don't forget the OS's own overhead: tick handling of 2.5% reduces available utilisation to roughly 97.5%, and context switches add small C values per preemption.

## The cost side, in numbers

For a Cortex-M0+ at 48 MHz and 8 KB of RAM:
- Kernel + stack-per-task: 4 tasks × (512 B stack + 100 B TCB) + 600 B kernel structures = 3,048 B (37% of RAM).
- Tick at 1 kHz with 1,200-cycle handler: 2.5% of CPU. Using a tickless idle mode the tick stops when all tasks sleep, which matters for battery life.
- Flash: 5-15 KB (10-25% of a 64 KB part).

The same system on 2 KB RAM is impossible with 4 tasks; there it's a state machine.

**Power.** On a battery node waking once a minute to read a sensor and send a packet, the bare-metal version is "wake, do one thing, sleep". Adding an RTOS adds a few µs of startup per wake and some µA of tick if not tickless. Often negligible, but on a 1 µA budget it isn't.

## Beyond tasks: middleware and ecosystem

Many libraries assume an OS:
- **TCP/IP stacks** (lwIP can run in a bare-metal "no-OS" mode with callbacks, but its sockets API needs threads).
- **TLS** with long handshakes (hundreds of ms of CPU) that must not starve a control loop.
- **USB host/device stacks, BLE controllers/hosts, FAT file systems** with blocking operations.
- **Vendor SDKs** (ESP-IDF, many Wi-Fi SDKs) are built on an RTOS; you get the OS whether you want it or not.

## Where Linux comes in

If the product needs process isolation (untrusted apps), a large driver base (cameras, GPUs), dynamic updates or high-level languages, you need an MMU and a full OS. Cost: boot time (seconds), power, MBs of RAM, non-hard-real-time behaviour. Hybrid designs use an RTOS or bare-metal core for control and Linux for everything else ([[q0836]]).

## A decision walk-through

Product: battery-powered gas sensor, Cortex-M0+, 16 KB RAM. Measures every 10 s, averages, transmits over LoRa once an hour, one button.
- Concurrency: low; the activities are sequential and infrequent.
- Deadlines: none hard (a 100 ms jitter is fine).
- Power: sleep current dominates; tickless needed anyway.
- Decision: bare-metal with an event loop and a state machine. An RTOS would add nothing.

Product: industrial gateway, Cortex-M7, 512 KB RAM. Runs 1 kHz fieldbus control, TLS to cloud, USB config, file logging, web UI.
- Four+ concurrent activities with a 1 ms hard deadline and 100+ ms blocking operations.
- Decision: RTOS (priorities for the control loop, thread-based network/USB/file stacks). Utilisation check: control 0.3 ms per 1 ms = 0.30, fieldbus 1 ms per 5 = 0.20, others in lower-priority tasks with slack: well within the budget.

::: applications
- **Connected consumer devices** (smart speakers, thermostats): RTOS or Linux for UI, networking and audio in parallel.
- **Industrial controllers and PLC-like devices**: RTOS tasks with deadlines for I/O scan and fieldbus.
- **Automotive ECUs**: OSEK/AUTOSAR-style OSes with fixed-priority scheduling and timing analysis.
- **Drones and robots**: RTOS or Linux plus real-time cores for flight/motor loops.
- **Medical devices**: certified RTOS for isolated, analysable tasks.
- **Bare-metal counterexamples**: simple remote controls, LED drivers, battery-powered sensor nodes, bootloaders.
:::

::: assumptions
- "OS" here mostly means an **RTOS** for microcontrollers; the Linux-vs-RTOS decision is mentioned separately.
- The **RMS bound** assumes independent periodic tasks, deadline equal to period, fixed priorities and negligible overhead; real systems with shared resources need blocking terms.
- Overhead numbers (tick cost, stack size, flash) are **typical for small Cortex-M** and vary with RTOS and configuration.
- The best structure is also a **team and lifecycle** question: an RTOS can reduce risk for a large codebase even when a super-loop could technically work.
- Hardware offload (DMA, timers, peripheral event systems) can remove the need for concurrency in software.
:::

::: followups
### Can you do multitasking without an OS?
Yes, in limited forms: interrupts give concurrency of event handling; a cooperative scheduler or protothreads/async state machines switch at defined points; a timer-driven "task table" runs small tasks to completion at fixed rates. These work well when every task is short, but one long task blocks the rest, which is exactly what a preemptive RTOS prevents.

### What's the downside of adding an RTOS?
RAM (a stack per task plus kernel), flash, tick overhead (a percent or two of CPU, more if the tick is fast), and new bug classes: priority inversion, deadlock, races on shared data, stack overflow of individual tasks, and harder debugging with non-deterministic interleavings. Behaviour becomes a function of timing, which makes some bugs rare and hard to reproduce.

### Your 1 ms control loop jitters by 200 µs in a bare-metal design. How do you fix it without an RTOS?
Move the control loop into a timer interrupt with the highest priority so no main-loop code can delay it, keep the ISR short and bounded, push slow work to the main loop, use DMA for transfers, and make sure other ISRs and critical sections are shorter than the jitter budget. Measure with a GPIO toggle on a scope. This is often better than an RTOS for a single hard loop.

### Do three tasks of (1 ms/5 ms), (2 ms/10 ms) and (4 ms/20 ms) fit under rate-monotonic scheduling?
$U = 0.2 + 0.2 + 0.2 = 0.60 \le 0.780$ for $n=3$, so yes, guaranteed. Remaining 40% can absorb tick overhead and an extra low-priority task.

### Harder: utilisation is 0.82 for 3 tasks, above the 0.78 bound. Is the system necessarily unschedulable?
No. The bound is sufficient, not necessary. Run exact response-time analysis: for each task compute $R_i = C_i + \sum_{j<i}\lceil R_i/T_j\rceil C_j$ iteratively and check $R_i \le D_i$. If the periods are harmonic (each a multiple of the previous), RMS can reach 100% utilisation. If the exact test fails, options are a faster clock, trimming execution time, offloading to DMA/hardware, or adjusting periods/priorities.
:::
