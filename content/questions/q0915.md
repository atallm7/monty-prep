::: testing
Whether you know RISC-V as an **open instruction set architecture** and can say what that does and does not mean. The interviewer wants to hear:

1. It is an ISA (a specification), not a chip, a company or a core.
2. It is RISC in style: simple fixed-format instructions, load/store memory access, 32 general registers.
3. It is modular: a small mandatory base plus optional standard extensions.
4. It is open and royalty-free to implement, maintained by RISC-V International, and that is why people care.

Bonus points for a concrete encoding example and an honest take on what "open" does not give you (verified cores, software ecosystem, free silicon).
:::

::: why
RISC-V is the first ISA with serious momentum that anyone can implement without a license fee. That matters to startups building accelerators with a small control core, universities teaching architecture, and companies that want to avoid dependence on a single vendor. In an interview for a hardware role, it is the most likely "modern ISA" to come up, and it is a good way to show you can reason about instruction formats, extensions and the ISA/microarchitecture boundary ([[q0914]]).
:::

::: concepts
- **ISA**: the hardware/software contract. See [[q0913]].
- **RISC philosophy**: a small set of simple instructions, uniform encoding, load/store architecture. See [[q0917]].
- **Base ISA plus extensions**: RV32I/RV64I are the integer bases; M, A, F, D, C, V and others are optional add-ons.
- **Register file**: 32 integer registers, with x0 hardwired to zero.
- **Open standard**: the specification is freely available and no license is needed to build a compliant implementation.
- **Privilege modes**: machine, supervisor and user modes support everything from microcontrollers to Linux-class systems.
:::

::: answer
"RISC-V is an open instruction set architecture. It started at UC Berkeley around 2010 as a clean-sheet RISC design for research and teaching, and it's now maintained by RISC-V International. Being open means anyone can read the spec and build a processor that implements it without paying a license fee, which is the big difference from x86 or Arm.

Technically it's a classic load/store RISC: fixed 32-bit instructions in a few simple formats, 32 integer registers with x0 tied to zero, and arithmetic only on registers. What I like is that it's modular. There's a tiny base integer ISA, like RV32I or RV64I, and then optional standard extensions: M for multiply and divide, A for atomics, F and D for floating point, C for 16-bit compressed instructions, V for vectors. So a small microcontroller can implement just RV32IMC while a server core implements RV64GC plus vectors.

One thing I'd stress: RISC-V is the specification, not a chip. Companies and universities build their own cores, open or proprietary, and the quality, performance and tool support vary a lot. The ISA being open doesn't make the silicon free."
:::

::: technical
**Origins and governance.** Developed starting 2010 at UC Berkeley (Asanović, Patterson and collaborators) as the fifth Berkeley RISC design, hence "V". Maintained by RISC-V International, a non-profit based in Switzerland, which ratifies the specifications through technical groups. The spec is published under open licenses; implementing it needs no fee. The *RISC-V* trademark and compliance rules still apply.

**Base ISAs.** RV32I (32-bit integers, 32 registers), RV64I, RV128I (defined, rarely used) and RV32E (16 registers for the smallest embedded cores). The base has about 40 instructions.

**Standard extensions (selection).**

| Ext. | Adds |
|---|---|
| M | integer multiply/divide |
| A | atomic memory operations (LR/SC, AMOs) |
| F, D | single and double-precision floating point |
| C | 16-bit compressed encodings, improving code density |
| V | scalable vector processing |
| Zicsr, Zifencei | CSR access and instruction-fetch fence |

"G" is shorthand for IMAFD plus Zicsr and Zifencei, the general-purpose profile for application cores. Profiles such as RVA are being defined to reduce fragmentation.

**Encoding.** All base instructions are 32 bits with six formats (R, I, S, B, U, J). The opcode, rd, rs1 and rs2 fields sit in fixed positions, which simplifies decode. Example: `add x3, x1, x2` is R-type with funct7 = 0000000, rs2 = 2, rs1 = 1, funct3 = 000, rd = 3, opcode = 0110011, giving `0x002081B3`. Immediates in the other formats are scattered so that the sign bit is always instruction bit 31, helping sign-extension hardware.

**Design choices.** No condition-code flags (compare and branch in one instruction); no branch delay slot; x0 gives a free zero and discard register; precise exceptions and a defined weak memory model (RVWMO). Privilege levels: M (machine), S (supervisor), U (user), with the virtual-memory modes Sv32/Sv39/Sv48.

**What it is not.** It is not a microarchitecture ([[q0916]]), not a specific core, and not a guarantee of an ecosystem. Custom extensions are allowed in reserved opcode space, which is both a strength (accelerators) and a fragmentation risk.
:::

::: short
"RISC-V is an open, royalty-free instruction set architecture, started at Berkeley and now run by RISC-V International. It's a clean load/store RISC with fixed 32-bit instructions and 32 registers, built modularly: a small base like RV32I plus optional extensions such as M, F, C and V. It's only the spec, not a chip, so anyone can build their own core."
:::

::: long
"RISC-V is an open instruction set architecture. It came out of UC Berkeley around 2010, where the goal was a clean, modern RISC for research and teaching, and now it's governed by a non-profit called RISC-V International. The key point is that the specification is free to use. Anyone can design a processor that implements it without a license, which is very different from x86, where you'd need Intel's or AMD's permission, or Arm, where you pay license and royalty fees.

Architecturally it's a textbook load/store RISC. Instructions are 32 bits with a handful of regular formats, so decode is simple. There are 32 integer registers, with x0 always reading zero. Memory is touched only by loads and stores. Branches compare registers directly, so there are no condition flags to track.

The thing that makes it interesting is modularity. The base integer ISA is tiny, about forty instructions. Then you add standard extensions as needed: M for multiply and divide, A for atomics, F and D for floating point, C for compressed 16-bit instructions that improve code density, and V for vectors. A small IoT controller might be RV32IMC. A Linux-capable application core would be RV64GC with vectors. There's also reserved opcode space for custom instructions, which is great for accelerators, though it can fragment software.

I'd also be clear about what RISC-V isn't. It's not a chip. It only says what a processor must do, not how. Cores like Rocket and BOOM from Berkeley, and many commercial cores, are separate microarchitectures. And open ISA doesn't mean free silicon or a mature software stack, so the real cost moves to implementation, verification and tooling."
:::

::: terms
- **RV32I / RV64I**: the 32-bit and 64-bit base integer instruction sets.
- **Extension**: an optional standard addition, such as M, A, F, D, C, V.
- **x0**: register hardwired to zero; writes are discarded.
- **Compressed (C)**: 16-bit encodings of common instructions for smaller code.
- **CSR**: control and status register, accessed via Zicsr instructions.
- **Privilege mode**: machine, supervisor or user; controls access to hardware resources.
- **RVWMO**: RISC-V weak memory ordering model.
- **Custom extension**: vendor-defined instructions in space reserved for that.
- **RISC-V International**: the non-profit that maintains the specification.
:::

::: exceptional
**An average answer** says "an open-source instruction set" and mentions that it is RISC.

**An exceptional answer**:
- Corrects "open source" to **open standard**: the spec is free, a given core may or may not be open.
- Names the base ISAs and the main extensions, and explains how combinations (RV32IMC vs RV64GC) map to products.
- Gives one encoding example, such as `add x3,x1,x2` into `0x002081B3`, showing fixed field positions.
- Explains design simplifications (x0, no flags, regular formats) and why they help hardware.
- Is honest about the costs: fragmentation from custom extensions, ecosystem maturity, and that verification effort is still yours.
:::

::: mistakes
- **"RISC-V is a processor."** It is a specification. Many different processors implement it.
- **"RISC-V is free, so the chip is free."** The ISA license is free. Design, verification, IP blocks, tools and fabrication still cost money.
- **"RISC-V stands for RISC five-letter something."** The V is the Roman numeral five: the fifth Berkeley RISC generation.
- **Confusing open ISA with open-source core.** Several cores are open source, but many commercial ones are proprietary.
- **Assuming all RISC-V chips run the same binaries.** Only if they implement the same extensions and profile. RV32IMC code will not necessarily run on a core without C or M.
- **Thinking "RISC" means fewer instructions only.** It is also uniform encoding and load/store access, which simplify pipelining.
:::

::: deep
## Why a new ISA at all?

Most ISAs in use today grew over decades. x86 started with the 8086 in 1978 and has kept backward compatibility through every extension. Arm is cleaner but proprietary: you license it from Arm Ltd, pay an upfront fee, and typically pay royalties per chip. In 2010 the Berkeley group wanted an ISA for teaching and research that was free of legal restrictions, small enough to understand, and realistic enough for real silicon. The result was RISC-V, and its principle is to put the *stable* things in a small base and push everything else into extensions.

## Anatomy of a RISC-V instruction

Every base instruction is 32 bits and the register fields are in the same place every time. A decoder can read rs1 and rs2 and start the register file lookup before it even knows the instruction type.

A few more encodings, all computed from the field layouts:

| Instruction | Format | Hex |
|---|---|---|
| `add x3, x1, x2` | R | `0x002081B3` |
| `addi x1, x0, 5` | I | `0x00500093` |
| `lw x5, 8(x2)` | I | `0x00812283` |
| `sw x5, 12(x2)` | S | `0x00512623` |
| `beq x1, x2, +8` | B | `0x00208463` |

Notice `addi x1, x0, 5` uses x0 as a free zero: it is the way to load a small constant. A `mv` is `addi rd, rs, 0`, and `nop` is `addi x0, x0, 0`. No special opcodes are needed.

## Worked example: the scattered branch immediate

Branch offsets are the odd-looking part of the encoding, and working one through shows the design thinking. A B-type instruction has a 13-bit signed offset in units of bytes, but bit 0 is always zero because instructions are at least 2-byte aligned, so only bits 12:1 are stored. For `beq x1, x2, +8`:

1. Offset $8 = 0\text{b}0\,0000\,0000\,1000$, so imm[12] = 0, imm[11] = 0, imm[10:5] = 000000, imm[4:1] = 0100.
2. Place them: inst[31] = imm[12], inst[30:25] = imm[10:5], inst[11:8] = imm[4:1], inst[7] = imm[11].
3. Fill the rest: rs2 = 2 in 24:20, rs1 = 1 in 19:15, funct3 = 000, opcode = 1100011.
4. Only inst[11:8] is non-zero among the immediate bits, so the word is $2\cdot2^{20} + 1\cdot2^{15} + 4\cdot 2^{8} + \text{0x63} = \text{0x00208463}$.

Why scatter the bits? RISC-V keeps the sign bit of every immediate in inst[31], so sign-extension hardware starts from one fixed wire regardless of format. It also reuses the same bit positions across formats where it can: S-type stores keep rs1, rs2 and funct3 where R-type has them, splitting only the low immediate into the rd field's slot (inst[11:7]). The cost is a few muxes in the immediate generator, which is cheap compared with the decode simplicity it buys.

The reach is a design trade-off too. A 13-bit signed byte offset gives $\pm 4$ KiB for conditional branches ($-4096$ to $+4094$). JAL has a 21-bit offset, so $\pm 1$ MiB. Anything farther needs `auipc` plus `jalr`, which gives a $\pm 2$ GiB reach in two instructions.

Loading a 32-bit constant shows another subtlety. `lui` supplies the upper 20 bits and `addi` adds a *sign-extended* 12-bit value. For `0x12345FFF` the low 12 bits `0xFFF` sign-extend to $-1$, so `lui` must load `0x12346` (not `0x12345`) and `addi` subtracts 1: $0x12346000 - 1 = 0x12345FFF$. Assemblers handle this with the `%hi`/`%lo` relocations, and forgetting the rounding is a classic bug when writing assembly by hand.

## Why the fixed formats pay off in hardware

Compare decoding with x86, where instructions are 1 to 15 bytes long. A decoder cannot know where the second instruction starts until it has at least partly decoded the first, so wide x86 front ends use predecode bits and length-finding stages. In RISC-V (without C) the next instruction is always at PC+4, so a 4-wide decoder just slices a 16-byte fetch block into four words. With the C extension, instructions are 2 or 4 bytes, and the low two bits of each halfword (`11` means 32-bit) tell you the length, which is a much simpler problem than x86 length decoding. This is a microarchitectural benefit that comes from an ISA choice, a neat example of the split in [[q0914]].

## Modularity and naming

The ISA string tells you what a core supports. `rv32imc` means 32-bit base, multiply/divide, compressed. `rv64gc` is the standard application-processor set. A **profile** (like RVA for application processors) fixes a bundle of extensions so that software vendors can target a single name rather than a combinatorial explosion.

Code density is a good illustration of why the C extension exists. Without it, every instruction is 4 bytes. With C, the most frequent instructions (register moves, small adds, stack loads and stores) get 2-byte forms, and typical programs shrink by roughly 25 to 30 percent. The exact figure depends on code and compiler.

> [!UNCERTAIN]
> The 25 to 30 percent code-size reduction is a commonly cited ballpark for compressed instructions on typical compiled code; actual savings vary with compiler, workload and ISA subset.

## What openness actually changes

1. **Cost structure.** No upfront license or per-chip royalty to the ISA owner. You still pay for design, verification, EDA tools, physical IP and masks.
2. **Customization.** You can add instructions in reserved opcode space, say a custom multiply-accumulate for a DSP workload, and modify the core. With Arm or x86 this is generally not permitted (Arm has recently allowed limited custom instruction options on some cores).
3. **Longevity and sovereignty.** An ISA that no single company can withdraw is attractive to governments and long-lifecycle products.
4. **Teaching and research.** The full spec is short (the base unprivileged volume is a few hundred pages including extensions), and open cores allow students to read real RTL.

The costs are equally real: software ecosystem maturity (compilers, OS ports, debuggers) lags x86 and Arm in some areas, extension fragmentation can break binary portability, and verifying a custom core against the architecture is substantial work. Compliance test suites and formal ISA models (such as the Sail model) help.

## Real hardware context

Typical uses today: tiny RV32 cores as management and control processors inside bigger SoCs (disk controllers, GPU front-ends, accelerators), microcontrollers, and an increasing number of Linux-capable boards. A small RV32IMC core can fit in a few tens of thousands of gates (on the order of 10k to 50k NAND2-equivalents depending on options), which is why it is often used as a hidden "control plane" CPU. High-performance out-of-order RISC-V cores exist, but compared with the incumbents the ecosystem is younger.

> [!INTERVIEW]
> If you are asked "is RISC-V better than Arm?", don't pick a team. Say the ISAs are technically similar in style, and the differences are mainly licensing and ecosystem. Core quality (microarchitecture) matters far more to performance than the ISA label.
:::

::: applications
- **Embedded controllers inside SoCs**: small RV32 cores manage power, boot or I/O so a vendor avoids per-chip royalty for a minor core.
- **Microcontrollers**: many MCU families now use RISC-V cores in the RV32IMC class for low-cost IoT parts.
- **Accelerators with custom instructions**: add a domain-specific instruction (for example for cryptography or ML) in the custom opcode space.
- **Education and research**: open cores like Rocket and BOOM, and teaching cores in courses, let students modify real RTL.
- **Linux-class boards and servers**: application cores with RV64GC and virtual memory, plus vector extension for compute.
:::

::: assumptions
- "Open" means the ISA specification is open and royalty-free. Individual cores may be open source, proprietary or somewhere between.
- Descriptions of extensions are as of the ratified specifications; names and profiles continue to evolve, so check the current RISC-V International documents for the exact list.
- Gate-count figures for small cores depend on the options chosen (multiplier, CSR set, debug) and the synthesis flow, so they are order-of-magnitude.
- If asked "RISC-V vs MIPS", note that the ISAs are architecturally similar in spirit, but classic MIPS has features RISC-V deliberately avoids (branch delay slots, HI/LO multiply registers) and RISC-V is actively governed as an open standard today.
:::

::: followups
### Is RISC-V open source?
The ISA specification is an open standard that anyone can implement without a fee. "Open source" applies to implementations: some cores (Rocket, BOOM, many small ones) are open-source RTL under permissive licenses, but a company can implement RISC-V in a fully proprietary core.

### Why does RISC-V have no condition flags?
Compare-and-branch is a single instruction, so there is no global flag register to rename or serialize. This removes a dependency that complicates out-of-order cores. The cost is that some multi-word arithmetic (add with carry) needs a few extra instructions to compute carries.

### What does RV32IMC mean?
32-bit base integer ISA, the M extension (integer multiply and divide), and C (16-bit compressed instructions). Typical of low-cost microcontrollers. It has no hardware floating point (no F/D) and no atomics unless A is added.

### Two vendors both claim RISC-V cores, but software built for one crashes on the other. Why?
They probably implement different extension sets or custom instructions. If the binary was compiled for rv64gcv and the other core lacks V, illegal-instruction faults result. Profiles and an ISA string check at build or boot time prevent this. Also check the privilege spec version and non-standard CSRs.

### How would you decide between RISC-V and Arm for a new product?
Compare cores available at your performance level, tool and OS support, license cost over volume (royalties matter at high volume), need for custom instructions, supply-chain risk and in-house expertise. Often the available IP and software ecosystem, not the ISA itself, decides.
:::
