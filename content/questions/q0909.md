::: testing
Whether you understand pipelining as an **organizing idea**, not just "the five-stage thing". A strong answer:

1. States the core trick: split the work into stages separated by registers so different instructions occupy different stages at the same time.
2. Separates **throughput** (instructions per second goes up) from **latency** (time for one instruction does not improve, and gets slightly worse).
3. Ties the benefit to the clock period: the clock only has to cover the slowest stage plus register overhead.
4. Admits the cost: registers, hazards, stage imbalance, and a speedup that falls short of the stage count.
5. Shows that pipelining is not CPU-specific. The same idea shows up in multipliers, ADCs and network switches.
:::

::: why
Pipelining is the single most important idea in processor performance. Almost every modern core, from a three-stage Cortex-M to a 20+ stage out-of-order desktop core, is pipelined, and so are floating-point units, GPUs, DSP datapaths and even pipelined ADCs. Interviewers use this question to see whether you can reason about throughput versus latency, and whether you can connect an architecture concept back to hardware: registers, critical path and clock frequency. It is also the gateway to hazards, forwarding and branch prediction ([[q0910]]), and to how a CPU gets faster without a faster transistor ([[q0908]]).
:::

::: concepts
- **Critical path and clock period**: the clock must be slower than the longest register-to-register combinational delay plus clock-to-Q and setup time. See [[q0906]].
- **Pipeline registers**: flip-flop banks between stages that hold each instruction's intermediate state for one cycle.
- **Throughput vs latency**: throughput is completed instructions per second; latency is how long one instruction takes from start to finish. Pipelining improves the first, not the second.
- **Fetch/execute breakdown**: an instruction naturally splits into fetch, decode, execute, memory and writeback steps. See [[q0905]].
- **Hazards**: structural, data and control dependences that stop the next instruction from proceeding on schedule.
- **Iron law of performance**: time = instructions x CPI x clock period. Pipelining shrinks the clock period while trying to keep CPI near 1.
:::

::: answer
"Pipelining is overlapping the execution of several instructions by splitting the datapath into stages and putting registers between the stages. The classic analogy is a laundry line: while the first load is in the dryer, the second is already in the washer. Each load still takes the same total time, but a finished load comes out every time the slowest machine finishes, instead of every time the whole job finishes.

In a CPU, I'd cut the instruction path into fetch, decode, execute, memory and writeback. Without pipelining, the clock period has to cover the entire path, so say 900 picoseconds. With five stages, each is a fifth of the work, so the clock only needs to cover the slowest stage plus the register overhead, about 270 picoseconds in my example. Once the pipeline is full, one instruction completes every cycle.

What I'd stress is that latency doesn't improve. One instruction actually takes slightly longer, five cycles of 270 instead of one of 900. What improves is throughput. And it's never a perfect five times, because the stages aren't balanced, the registers add overhead, and hazards force stalls when one instruction depends on another or a branch changes the fetch address. That's why you see forwarding paths and branch predictors in every real pipelined design."
:::

::: technical
**Definition.** A $k$-stage pipeline splits a combinational datapath of total delay $t_{comb}$ into $k$ stages with delays $t_1\dots t_k$, separated by registers with overhead $t_{reg}=t_{clk\to Q}+t_{su}$ (plus skew/jitter margin). The clock period must satisfy

$$T_{pipe}\ \ge\ \max_i(t_i)+t_{reg}$$

versus $T_{unpipe}\ge t_{comb}+t_{reg}$ for the unpipelined design.

**Timing.** The first instruction takes $kT_{pipe}$ to finish (latency). After that one instruction completes per cycle. For $N$ instructions:

$$t_{total}=(k+N-1)\,T_{pipe},\qquad \text{Speedup}=\frac{N\,T_{unpipe}}{(k+N-1)\,T_{pipe}}$$

For $N\to\infty$ the speedup approaches $T_{unpipe}/T_{pipe}$, which is at most $k$ and equals $k$ only if the stages are perfectly balanced and register overhead is zero.

**Throughput vs latency.** Throughput rises from $1/T_{unpipe}$ to $1/T_{pipe}$. Latency per instruction becomes $kT_{pipe}\ge T_{unpipe}$, so it gets worse.

**Realistic CPI.** Hazards add stall cycles: $\text{CPI}=1+\text{stalls per instruction}$. Using the iron law, performance = $1/(\text{IC}\cdot\text{CPI}\cdot T)$. Deepening the pipeline lowers $T$ but raises stalls per mispredicted branch or load-use dependency, so there is an optimum depth that depends on workload and power budget.

**Hazards.** Structural (two instructions need the same hardware, fixed by duplicating it, e.g. split instruction/data caches), data (RAW dependence, fixed by forwarding or stalling), control (branches, fixed by prediction or flushing).

**Cost.** Extra registers (area, clock load and power, since the clock toggles every flop each cycle), forwarding muxes, hazard-detection logic and more complex exception handling, because several instructions are in flight when a trap occurs.
:::

::: short
"Pipelining splits an instruction's work into stages separated by registers so several instructions are in flight at once, each in a different stage. The clock only has to cover the slowest stage instead of the whole path, so you get a much higher clock and, once full, roughly one instruction per cycle. Latency for a single instruction doesn't improve, it gets slightly worse, so it's a throughput win. The speedup is less than the number of stages because of register overhead, unbalanced stages and hazards like data dependencies and branches."
:::

::: long
"Pipelining is the assembly-line idea applied to instruction execution. Instead of doing fetch, decode, execute, memory access and writeback for one instruction before starting the next, I put a register between each step so that while instruction one is in execute, instruction two is in decode and instruction three is being fetched.

The reason it helps is the clock. The clock period has to be longer than the longest register-to-register path. If the whole instruction path is 900 picoseconds, the clock can't go faster than about 1.1 gigahertz. Cut it into five stages with the slowest at 250 picoseconds, add 20 for register overhead, and the clock period is 270, around 3.7 gigahertz. Once the pipeline is full, one instruction finishes every cycle, so throughput goes up by roughly 3.3 times in this example rather than a full five, because the stages aren't equal and the registers cost time.

The important subtlety is that latency doesn't improve. A single instruction now takes five cycles of 270 picoseconds, 1,350, which is worse than 900. Pipelining is purely a throughput trick.

The cost is hazards. If an instruction needs a result that the previous one hasn't produced yet, I either forward the value from a later stage back into the ALU, or I stall. A load followed by a dependent instruction still costs a bubble. Branches are worse, because I've already fetched the next instructions before I know which way the branch goes, so I need branch prediction and a flush on a miss.

That also limits how deep you go. More stages means a faster clock but bigger penalties and more power from all the extra flops, so real designs balance it."
:::

::: terms
- **Pipeline stage**: one slice of the datapath between two register banks. Each stage does its work in one clock cycle.
- **Pipeline register**: flip-flops between stages holding the in-flight instruction's data and control bits.
- **Throughput**: completed instructions (or results) per unit time.
- **Latency**: time for one instruction to go from start to finish.
- **Pipeline depth**: the number of stages. Deeper means higher clock but larger hazard penalties.
- **Fill / drain**: the cycles at start and end when not all stages are busy.
- **Hazard**: a dependence that prevents the next instruction from executing in its scheduled cycle (structural, data, control).
- **Bubble / stall**: a cycle where a stage does no useful work because of a hazard.
- **Forwarding (bypassing)**: routing a result directly from a later stage back to an earlier one so the consumer need not wait for writeback.
- **CPI**: cycles per instruction; ideal pipelined value is 1.
:::

::: exceptional
**An average answer** says "it lets you run several instructions at once" and names five stages.

**An exceptional answer**:
- Uses the **clock period** argument: $T\ge\max t_i+t_{reg}$, and shows numbers (e.g. 900 ps becomes 270 ps).
- Separates **throughput from latency** without being asked, and notes latency gets worse.
- Gives the speedup formula $\frac{N\,T_u}{(k+N-1)T_p}$ and explains why it is below $k$: imbalance, register overhead, fill time, hazards.
- Names the three hazard types with one fix each, and notes the load-use bubble survives forwarding.
- Explains why deeper is not always better (branch penalty, power) and that the idea is general: multipliers, FPUs, pipelined ADCs, network switches.
:::

::: mistakes
- **"Pipelining makes each instruction faster."** Each instruction takes the same or slightly longer. Total throughput is what improves.
- **"A 5-stage pipeline is 5x faster."** That's the upper bound only for balanced stages, no register overhead, infinite instruction stream and no hazards. The example here gets about 3.3x.
- **Confusing pipelining with parallelism across cores or ILP width.** Pipelining overlaps *different stages of different instructions*; superscalar issue and multicore duplicate whole units. See [[q0907]].
- **Thinking forwarding removes every stall.** A load followed by an instruction using the loaded value still needs a one-cycle bubble in the classic 5-stage design.
- **Forgetting register overhead.** Clock-to-Q plus setup adds to every stage, so splitting a stage in half does not halve the period.
- **Ignoring power.** More pipeline registers means more clock load and switching, which is why very deep pipelines were abandoned in some designs.
:::

::: deep
## Start from the clock

Every synchronous digital circuit has a hard rule. Launching flop $\rightarrow$ combinational logic $\rightarrow$ capturing flop must complete in one clock period:

$$T\ \ge\ t_{clk\to Q}+t_{logic,max}+t_{su}+t_{skew}$$

An early, naive CPU puts the entire instruction (fetch, decode, register read, ALU, data memory, register write) between one pair of flops. That path is long, so $T$ is long.

Now insert extra register banks inside the path. Each new bank adds $t_{clk\to Q}+t_{su}$ overhead, but each segment between banks is shorter. If the segments are equal, $T$ drops toward $t_{logic}/k$. And because there are now $k$ segments, there can be $k$ different instructions in flight, one per segment.

> [!TIP]
> Pipelining does not reduce the *amount* of work per instruction. It reduces the work *per clock cycle*, and lets more instructions overlap. That's the same trade as the laundry line.

## A worked example with numbers

Take the five stages with delays IF 200 ps, ID 150 ps, EX 200 ps, MEM 250 ps, WB 100 ps, and 20 ps of register overhead.

- Unpipelined: all stages in series, $T=200+150+200+250+100=900$ ps, throughput $1/900\text{ ps}=1.11$ GHz-instructions (one instruction per 900 ps).
- Pipelined: $T=\max(200,150,200,250,100)+20=270$ ps, so the clock is 3.70 GHz and throughput is one instruction per 270 ps.
- Pipelined latency: $5\times270=1350$ ps, which is **50% worse** than 900 ps.

For $N$ instructions the speedup is $\frac{900N}{270(N+4)}$:

| $N$ | Cycles pipelined ($N+4$) | Speedup over unpipelined |
|---|---|---|
| 1 | 5 | 0.67x (slower!) |
| 5 | 9 | 1.85x |
| 100 | 104 | 3.21x |
| 1000 | 1004 | 3.32x |
| huge | | 3.33x = 900/270 |

The limit is $900/270=3.33$, not 5, because the MEM stage (250 ps) is longer than the average stage (180 ps) and registers add 20 ps. Balance is as important as depth.

## The cost side

**Registers and clocking.** Four pipeline registers hold the instruction word, operands, ALU result and memory data, plus control bits. The clock network drives every one of those flops every cycle, which is a growing share of dynamic power $P\approx \alpha CV^2f$ as depth rises.

**Hazards.** The three families:

| Type | Example | Typical fix |
|---|---|---|
| Structural | one memory port used by IF and MEM at once | split I-cache/D-cache, extra ports |
| Data (RAW) | `add x1,..` then `sub ..,x1` | forwarding; stall for load-use |
| Control | branch outcome unknown for 2+ cycles | prediction, flush, delay slots (older ISAs) |

Branch hazards are the big one. If 20% of instructions are branches and 5% of those are mispredicted with a 15-cycle penalty (a deep pipeline), CPI becomes $1+0.2\times0.05\times15=1.15$, a 15% loss. See [[q0910]].

**Exceptions.** With several instructions in flight, an exception in the MEM stage must squash younger instructions but let older ones complete, giving *precise exceptions*. Pipelines need to track program order carefully.

## How deep should it go?

Extra stages raise $f$ but also raise CPI loss and power. The Pentium 4 era pushed to 20+ stages (and later 30+) for high clock rates and ran into power and misprediction-penalty limits, after which mainstream designs settled in the roughly 10 to 20 stage range with wide out-of-order execution. A microcontroller like an ARM Cortex-M0 uses three stages, because its goal is low area and power at modest frequencies, not peak performance.

> [!UNCERTAIN]
> Exact stage counts for commercial cores are vendor-specific and change by generation. Treat "10 to 20 stages" as a typical range for high-performance cores, not a rule.

## Pipelining outside the CPU

The same idea shows up whenever a long combinational computation must be sustained at high rate:

- **Pipelined multipliers and floating-point units**: a 4 to 5 cycle latency FPU can still accept one new operation each cycle.
- **Pipelined ADCs**: each stage resolves a few bits and passes the residue on.
- **GPUs and graphics pipelines**: vertex, raster and fragment stages work on different primitives simultaneously.
- **Network switches and DMA engines**: stages for parse, lookup, queue and transmit.

In every case: higher throughput, same or worse latency, extra registers.
:::

::: applications
- **Every mainstream CPU core**: Arm Cortex-M (3 stages in M0, 2 in M0+), Cortex-A and x86 cores (many more stages, out-of-order), RISC-V teaching cores (the classic 5-stage).
- **Floating-point units and multipliers**: multi-cycle latency but one result per cycle throughput.
- **Pipelined ADCs**: high-speed converters (tens to hundreds of MS/s) trade several cycles of latency for throughput.
- **GPU shader and rasterization pipelines**: massive throughput from keeping all stages busy.
- **Network and DSP datapaths**: FIR filters and FFTs use pipeline registers to hit the target clock in FPGA/ASIC.
:::

::: assumptions
- The example assumes the textbook five stages with one instruction issued per cycle, **in-order** and **single-issue**. Superscalar and out-of-order cores add width on top.
- Stage delays are illustrative; real values depend on technology, circuit style and cache design.
- Register overhead is treated as a fixed 20 ps. In practice clock skew, jitter and **time borrowing** (latches) change the picture.
- Hazards are ignored in the ideal speedup formula. Realistic CPI is above 1.
- The answer changes if the interviewer means **software pipelining/loop pipelining** (HLS, VLIW compilers), where the same overlap idea is applied to loop iterations, or **instruction-level parallelism** in general.
:::

::: followups
### Why doesn't the clock period shrink exactly by a factor of five?
Because $T=\max t_i+t_{reg}$. The slowest stage sets the clock, and stages aren't equal (MEM at 250 ps vs 180 ps average in the example), and every stage pays clock-to-Q plus setup. With 900 ps total and five stages you'd hope for 180 ps, but get 270 ps, so the speedup is 3.33, not 5.

### Does pipelining reduce the latency of one instruction?
No, it increases it slightly: 5 cycles x 270 ps = 1350 ps versus 900 ps. What improves is throughput, one instruction per 270 ps instead of per 900 ps. This matters for latency-critical tasks: if one instruction chain is strictly dependent, the pipeline doesn't help it much.

### How do you handle a data hazard where an instruction needs the previous instruction's result?
Forward the result from the EX/MEM or MEM/WB register through a mux into the ALU input, so it doesn't wait for writeback. Hazard-detection compares source and destination register numbers across stages. The exception is load-use: the data is only available after MEM, so one bubble remains. The compiler can schedule an independent instruction in the gap.

### What happens to the pipeline when a branch is taken?
The instructions fetched after the branch (wrong path) must be flushed and fetch restarts at the target. The penalty equals the number of stages before the branch resolves, 2 cycles in the classic 5-stage design, 15+ in deep cores. That's why predictors exist ([[q0910]]).

### You have a fixed 900 ps datapath. When would adding a sixth stage hurt?
If the new register overhead (say 20 ps) is a large part of the stage, or if the slowest stage cannot be split (a cache access that must complete in one cycle). Then the clock barely improves while branch penalty and flop power both rise. If the bottleneck is MEM at 250 ps, splitting EX or IF does nothing.

### Is a pipelined ADC faster or lower latency than a SAR ADC?
Faster in throughput (new samples every clock), but with higher latency of several cycles. SAR converters have no pipeline latency in the same sense but need many internal cycles per sample. That's the same throughput-versus-latency trade as in CPUs.
:::

"What is pipelining?" in a computer-architecture list means **instruction pipelining**, as in the five-stage example. Q906 ([[q0906]]) asks about the specific five-stage design and Q908 ([[q0908]]) asks about throughput techniques in general, of which pipelining is one.
