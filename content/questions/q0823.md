::: basics
### In plain words
A microcontroller keeps its bits in a few kinds of memory, all on the same chip. Flash holds the program and keeps its contents when power is off. SRAM holds variables and is fast, but forgets everything at power-off. Registers are tiny storage spots for the CPU's current work and for controlling the chip's peripherals (built-in hardware blocks such as timers and pin controls). All of them share one numbered map of addresses.

### Picture it
Think of a workshop. The filing cabinet is flash: the plans stay there even when you go home. The workbench is SRAM: you spread out what you are working on, but it is swept clean when you leave. What you are holding in your hands is the CPU's registers. The switches on the machines are the peripheral registers. Every spot in the shop has an address, like a labeled shelf.

### Words you need
- **Flash**: memory that holds the program and keeps its data without power.
- **SRAM**: fast, writable working memory that loses its contents at power-off.
- **Non-volatile** ([[q0826]]): keeps its contents when power is removed. Volatile memory does not.
- **Register** ([[q0829]]): a small storage location, either inside the CPU or controlling a peripheral.
- **Address**: the number that labels one location in memory.

### The simplest example
A small part might have 64 KB of flash and 20 KB of SRAM. In your C program, `int count = 5;` is a variable. It lives in SRAM while the program runs, so it can change. The starting value 5 is stored in flash. At startup, the chip copies it into SRAM. After a power cycle, SRAM holds random junk, and the startup copies 5 in again. A `const` table that never changes can stay in flash.

That is the whole idea. The rest of this page follows a C program into memory, shows a memory budget, and covers real hardware behavior such as flash wear.
:::

::: testing
Whether you have a **mental map of where bits physically live** in a microcontroller, not just "it has memory". The interviewer wants to hear the split between program memory (flash), working memory (SRAM), non-volatile data memory (EEPROM or emulated EEPROM) and the registers, and how a C variable ends up in each. They are also checking that you know it is all one **address space**: the CPU reads flash, RAM and peripheral registers using the same load and store instructions, just at different addresses. Bonus points for naming `.text`, `.data`, `.bss`, stack and heap.
:::

::: why
Every embedded bug eventually becomes a memory bug: a stack that grew into the heap, a constant that was copied into scarce RAM, a calibration table lost at power-off, a peripheral register that was written at the wrong address. When you pick a microcontroller you choose it by its flash and RAM sizes, and when you write firmware you decide, often silently, which memory each byte lands in. This question is also the gateway to the rest of the Data Storage section ([[q0824]] to [[q0830]]), so interviewers use it to see whether your foundation is solid before going deeper.
:::

::: concepts
- **Von Neumann vs Harvard**: one address space for code and data, or separate buses for instruction and data fetches. Most MCUs are Harvard-like internally but present a unified memory map. See [[q0783]] for how the pins and peripherals hang off the same bus.
- **Volatile vs non-volatile memory**: SRAM forgets when power drops; flash and EEPROM do not ([[q0826]]).
- **Memory-mapped I/O**: peripheral registers occupy addresses, so a store to the right address toggles a pin ([[q0829]]).
- **Address space**: $n$ address bits select $2^n$ byte locations; 16 bits gives 64 KiB.
- **Linker sections**: `.text`, `.rodata`, `.data`, `.bss`, stack, heap decide where each C object lives.
- **Memory hierarchy**: registers, then SRAM, then flash, with very different speed, size and cost per bit.
:::

::: answer
"A microcontroller has a few different kinds of memory on the same chip, and they're all mapped into one address space so the CPU reaches them with ordinary loads and stores.

Program code and constants live in flash, which is non-volatile, so the firmware survives power-off. Working data, meaning variables, the stack and the heap, lives in SRAM, which is fast and writable but loses everything when power goes away. Then there are the registers. The CPU's own core registers hold the values it is operating on right now, and the peripheral registers, like a GPIO output register or a timer compare value, are mapped at fixed addresses, so writing to that address actually changes hardware.

When I compile C, the linker sorts things out: code and `const` data go to flash, initialised globals get stored in flash and copied into RAM by the startup code, uninitialised globals are zeroed in RAM, and local variables go on the stack. If I need data to survive power cycles, like calibration values or a serial number, I put it in EEPROM or a flash page that I write deliberately.

A typical small part might have 64 KB of flash and 20 KB of SRAM, so I always keep an eye on how much RAM the stack and heap take."
:::

::: technical
**Physical memories on a typical MCU.**
- **Flash** (program memory): floating-gate or charge-trap cells, non-volatile, read at CPU speed through a prefetch buffer, but erased in whole sectors (commonly 1-4 KB pages, vendor dependent) and rewritten only about $10^4$ to $10^5$ times. Holds code, `const` tables and the initial values of globals.
- **SRAM**: six-transistor cells (two cross-coupled inverters plus two access transistors), volatile, single-cycle access, unlimited endurance. Holds the stack, heap, `.data` and `.bss`.
- **EEPROM / data flash** (some parts): byte-erasable non-volatile storage for settings ([[q0828]]).
- **Registers**: flip-flops in the core (R0-R15 on an ARM Cortex-M) and in peripherals ([[q0829]]).

**One address space.** On a 32-bit Cortex-M, the architecture fixes coarse regions: code at `0x0000_0000`, SRAM at `0x2000_0000`, peripherals at `0x4000_0000`, system control at `0xE000_0000`. A vendor places flash (for example at `0x0800_0000` on many STM32 parts, aliased to 0 at boot) and its peripherals inside those regions. An $n$-bit address selects $2^n$ bytes, so a 64 KiB flash needs 16 address bits internally.

**Where C objects land.**

| C construct | Section | Memory |
|---|---|---|
| functions, `const` arrays | `.text`, `.rodata` | flash |
| `int x = 5;` (global) | `.data` | flash image, copied to RAM at startup |
| `int y;` (global) | `.bss` | RAM, zeroed at startup |
| local variables, return addresses | stack | RAM, grows down |
| `malloc` | heap | RAM, grows up |

**Startup.** On reset the core loads the stack pointer from the first word of the vector table and the program counter from the second, then `Reset_Handler` copies `.data` from flash to RAM, zeroes `.bss` and calls `main` ([[q0838]]).

**Rule of thumb for budgeting.** RAM left over = total SRAM - `.data` - `.bss` - worst-case stack - heap. If that is negative or close to zero, you have a bug waiting to happen.
:::

::: short
"A microcontroller keeps program code and constants in non-volatile flash, working variables and the stack in fast volatile SRAM, and uses registers both inside the CPU and as memory-mapped peripheral controls. They all share one address space, so the CPU uses ordinary loads and stores for everything. The linker decides placement: code in flash, initialised globals copied from flash to RAM at startup, locals on the stack. Anything that must survive power-off goes to EEPROM or deliberately written flash."
:::

::: long
"I think of an MCU's memory as three layers that all sit in one address map.

First, flash. It's non-volatile, so it holds the firmware and any constant tables. It's slow to write and has to be erased a page at a time, and it only tolerates something like ten thousand to a hundred thousand erase cycles, so I treat it as mostly read-only at run time.

Second, SRAM. It's built from six-transistor cells, it's fast and has no wear limit, but it's volatile. That's where variables, the stack and the heap live. On a small part it's tiny, maybe 4 to 64 KB, so it's the resource I budget most carefully.

Third, registers. The CPU has a small set of core registers that hold operands, and each peripheral exposes control and status registers at fixed addresses. Because it's memory-mapped, writing to a GPIO output register is just a store instruction, and reading a status register is just a load.

When I build a C program, the linker places code and const data in flash. Initialised globals are stored in flash and copied into RAM by the startup code before main runs. Uninitialised globals are zeroed. Local variables go on the stack, and malloc uses the heap.

For anything that has to survive a power cycle, such as calibration, a serial number or user settings, I use EEPROM if the part has it, or I reserve a flash page and write it carefully with wear levelling and a checksum. And I always check the map file to see how close I am to running out of RAM, because stack overflow into the heap is a classic silent failure."
:::

::: terms
- **Flash**: non-volatile, block-erasable memory used for program code and constants.
- **SRAM**: static RAM; volatile, fast, built from six-transistor cells that need no refresh.
- **EEPROM**: electrically erasable PROM; non-volatile and byte-erasable ([[q0828]]).
- **Memory-mapped I/O**: peripheral registers placed in the same address space as memory.
- **Linker script**: file that tells the linker where flash and RAM are and which sections go where.
- **`.data` / `.bss`**: initialised and zero-initialised global variable sections.
- **Stack / heap**: RAM regions for call frames and dynamic allocation, growing toward each other.
- **Vector table**: array of addresses at the start of flash: initial stack pointer, then reset and interrupt handlers.
:::

::: exceptional
**An average answer** says "flash for the program, RAM for variables, EEPROM for saved data" and stops.

**An exceptional answer**:
- Explains the *physical reason* for each split: flash is dense and non-volatile but slow and wear-limited to write; SRAM is fast and unlimited but volatile and costs about six transistors per bit.
- Describes the unified address map and memory-mapped peripherals, so registers are not a separate concept.
- Traces a real C variable through `.data`, `.bss`, the stack and the heap, and mentions the startup copy from flash to RAM.
- Gives a number, for example "64 KB flash, 20 KB SRAM, so 16 address bits for the flash".
- Volunteers a failure mode: stack/heap collision, `const` tables accidentally placed in RAM, or flash wear from logging into one page.
:::

::: mistakes
- **"Variables are stored in flash."** Only their *initial values* are. Variables live in RAM while the program runs, and writing flash needs a special erase/program sequence.
- **Treating flash like RAM** and updating a counter in the same flash location every second. A 100k-cycle part dies in about a day. Use wear levelling or FRAM ([[q0825]]).
- **Forgetting that RAM is volatile**, so a "saved" setting vanishes at reset. Persisting data is a deliberate act.
- **Treating registers as only the CPU's registers.** Peripheral registers are memory-mapped and are the way firmware talks to hardware ([[q0829]]).
- **Forgetting `volatile`** on a pointer to a hardware register, so the compiler caches the value or deletes the "redundant" access.
- **Not budgeting stack.** The stack is invisible in the map file's static totals, but it eats RAM at run time.
:::

::: deep
## The three kinds of storage and why they differ

A bit is stored by some physical state that persists. Microcontrollers use three different mechanisms, and the differences explain every other fact on this page.

**SRAM: a bistable circuit.** A 6T cell is two cross-coupled inverters that reinforce each other, forming a latch with two stable states. Two access NMOS transistors connect the latch to the bitlines. Reading or writing takes one clock cycle, nothing wears out, and no refresh is needed (unlike DRAM, which stores charge on a capacitor that leaks away). The price is area: six transistors per bit, and the latch only holds its state while the supply is on. Remove power for a few milliseconds and the contents are random.

**Flash: charge trapped on a floating gate.** A flash cell is a MOSFET with an extra electrically isolated gate (or a charge-trapping layer) between the control gate and the channel. Forcing electrons onto it, by hot-carrier injection or Fowler-Nordheim tunnelling, raises the transistor's threshold voltage $V_t$. Reading applies a reference gate voltage and senses whether the cell conducts. Because the gate is surrounded by oxide, the charge stays for years with no power. The catch is that tunnelling through the oxide damages it a little each time, so cells survive only a limited number of program/erase cycles, and erasing is done on large blocks to keep the cell small. The mechanism is the same family as EEPROM ([[q0826]], [[q0828]]).

**Registers: flip-flops.** Core registers and peripheral registers are built from flip-flops or latches, the same bistable idea as SRAM but wired directly into logic. A GPIO output register's flip-flop output literally drives the pin buffer; that is why a store to it changes the pin.

## One address space

The CPU does not know which kind of memory it is talking to. It puts an address on its bus, and decode logic routes the access.

## Following a C program into memory

```c
const uint16_t sine_lut[4] = {0, 707, 1000, 707};  // .rodata -> flash
uint32_t counter = 5;                              // .data   -> flash image + RAM copy
uint32_t samples[100];                             // .bss    -> RAM, zeroed
void f(void) { int tmp = counter * 2; }            // tmp     -> register or stack
```

Count the RAM cost: `counter` is 4 bytes, `samples` is $100 \times 4 = 400$ bytes, `sine_lut` costs 8 bytes of flash and 0 bytes of RAM (because it is `const`). Forgetting `const` on a big lookup table copies it into RAM, which on a 20 KB part is a real loss. The flash image also contains the 4 bytes of initial `counter`, which the startup code copies, one reason a map file's flash total is slightly larger than `.text` plus `.rodata`.

## A worked memory budget

Take a part with 64 KiB flash and 20 KiB SRAM.
- Flash address bits: $\log_2 65536 = 16$.
- Firmware: 38 KiB code, 6 KiB constant tables, 0.5 KiB `.data` init image: 44.5 KiB used, 19.5 KiB free (30%).
- RAM: `.data` 0.5 KiB + `.bss` 7 KiB = 7.5 KiB static. Reserve a 2 KiB main stack and 1 KiB for interrupt nesting, leaving 9.5 KiB for heap or growth.

The danger is the *dynamic* part: stack depth depends on call depth and on how big your local arrays are. A single `char buf[1024]` local in a function called from an ISR can overflow a 1 KiB stack silently, because most small cores have no memory protection to catch it.

## Real hardware behaviour worth knowing

- **Flash read speed.** Flash is slower than the core clock above a few tens of MHz, so parts insert **wait states** (for example, 2 wait states at 72 MHz) and use a prefetch buffer or small cache to hide them. Moving a hot loop to RAM can make it faster, or slower on parts where RAM is on a congested bus.
- **Write granularity.** SRAM writes one byte at a time. Flash can only change a bit from 1 to 0 by programming; going back to 1 requires erasing the whole sector. EEPROM erases per byte or small page.
- **Reset behaviour.** After a normal reset SRAM often keeps its old contents, but you cannot rely on it. After power loss it is random. Some parts have a battery-backed backup domain for an RTC and a few registers ([[q0825]]).
- **Bus matrix.** On bigger parts the CPU, DMA and peripherals reach flash and several RAM blocks through a bus matrix, so putting DMA buffers and CPU stack in different RAM banks avoids stalls.

::: applications
- **Sensor node firmware**: code in 256 KB flash, ring buffer of ADC samples in SRAM, calibration coefficients in the last flash page or EEPROM.
- **Motor controller**: PWM compare and period registers (peripheral registers) updated every control cycle, the control state in SRAM, gain tables in flash.
- **Bootloader**: lives in a protected flash region, copies new firmware received over UART/USB into the application region.
- **Data logger**: SRAM buffers samples, then flushes blocks to external flash or an SD card ([[q0824]]).
- **Wearable**: backup-domain SRAM kept alive by a coin cell to hold the RTC time through main power loss.
- **Automotive ECU**: flash plus a separate data-flash or emulated EEPROM region for trip counters and fault codes ([[q0825]]).
:::

::: assumptions
This answer assumes a **typical 32-bit flash microcontroller** with on-chip flash and SRAM (ARM Cortex-M class). It changes for other families.

- **8-bit Harvard parts (AVR, PIC)** have separate program and data address spaces, so a `const` table in flash needs special access macros (such as `PROGMEM` on AVR).
- **Mask-ROM parts** store code in ROM instead of flash ([[q0827]]).
- **Parts with external memory** (QSPI flash, PSRAM, SDRAM) add more regions to the map ([[q0824]]).
- **Parts with a cache or MMU** (application processors running Linux) hide physical memory behind virtual addresses.
- Sizes and endurance numbers here are typical, not guaranteed; always check the datasheet.
:::

::: followups
### Where is a local variable stored versus a global?
A local variable lives on the stack in RAM (or just in a core register if the compiler can keep it there), and disappears when the function returns. A global lives at a fixed RAM address for the program's whole life: in `.data` if it has a non-zero initialiser, in `.bss` if not. A `static` local behaves like a global that is only visible inside the function.

### Why is `.data` stored in flash and also in RAM?
The initial value must survive power-off, so it is stored in flash. The variable must also be writable at run time, so it needs a RAM home. The startup code copies the flash image to RAM before `main`. That is why initialised globals cost both flash and RAM, while `const` data costs only flash.

### How would you find out how much RAM and flash your firmware uses?
Run the toolchain's size tool (for example `arm-none-eabi-size`), which prints `text`, `data` and `bss`. Flash used is roughly `text + data`; RAM used statically is `data + bss`. Then read the linker map for the largest symbols. Stack use is not in those totals, so measure it by filling the stack with a pattern at boot and checking the high-water mark.

### Why is writing to flash so much harder than writing to RAM?
Flash programming moves charge through oxide with high voltages generated by an on-chip charge pump, which takes microseconds to milliseconds. You cannot flip 0 back to 1 without erasing a whole sector (say 2 KB), and the CPU often cannot fetch code from that same flash bank during the operation. So firmware unlocks the flash controller, erases, programs and verifies, typically from RAM or a different bank.

### Harder: your device works for weeks and then resets randomly. How might memory be involved?
Suspects: stack overflow into the heap or `.bss` (corrupting variables), heap fragmentation until `malloc` fails, a flash page worn out by frequent logging, or brown-outs corrupting a flash write in progress. I would add stack canaries or a high-water mark, check the map file, log reset cause (watchdog, brown-out, hard fault) and look at how often flash is written.
:::
