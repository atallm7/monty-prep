::: basics
### In plain words
The program counter mostly counts up. After each instruction it advances by that instruction's size, which is 4 bytes for a 32-bit instruction. Sometimes it jumps instead: a loop sends it backward, a function call sends it to the function, a return sends it back, and an interrupt sends it to a handler. Plotted over time, it looks like a staircase with occasional jumps.

### Picture it
Imagine walking down a street of numbered houses, visiting every fourth address in order. Now and then a note on a door says "go to house 64, then come back here". Or it says "go back to house 4 until the counter hits zero". Loops make you revisit the same few houses many times.

### Words you need
- **Sequential flow**: the PC moving to the next instruction in address order.
- **Taken / not-taken branch**: a branch is taken when its condition is true and the PC jumps. When not taken, the PC just goes on to the next instruction.
- **Return address**: the spot a call saves so the PC can come back after the function.
- **Interrupt handler**: the routine the PC jumps to when an outside event needs attention ([[q0911]]).

### The simplest example
Use the page's small program, with addresses in plain numbers. The PC goes 0, 4, 8. At 8 a call jumps to 64, saving return address 12. It runs 64, then 68, where a return sends the PC back to 12. At 12 a loop branch is taken and the PC jumps back to 4. The page's program repeats that cycle three times in total. The final time the branch is not taken, so the PC moves on to 16.

That is the whole idea: the PC steps by 4 and is occasionally overwritten. The rest of this page shows the full trace, how interrupts save and restore the PC, and how a pipeline that fetches ahead can fetch the wrong instructions after a jump.
:::

::: testing
Whether you can describe **control flow as a trace of PC values** and name every mechanism that makes the PC deviate from "+4 each step". The interviewer wants a narrative, ideally with a tiny example: straight-line code steps by the instruction size; loops make the PC jump backward and revisit the same addresses; calls jump to a function and return; interrupts insert a detour and come back. Strong answers also mention the pipelined reality (the fetch PC runs ahead speculatively and is redirected on mispredictions) and how you would observe it (debugger, trace).
:::

::: why
Seeing a program as a path through address space is the key to debugging, profiling, and understanding performance. A sampled PC histogram tells you where time goes. A PC stuck at one address means a hang or a deliberate idle loop. An embedded engineer reading a trace or a crash dump must know why the PC has a certain value: was it a branch, a call, an interrupt, a fault? It also explains why branches are expensive in pipelines: each non-sequential change of the PC has to be anticipated by the front end or paid for in lost cycles ([[q0910]]).
:::

::: concepts
- **PC register and next-PC mux**: where the value comes from each cycle. See [[q0903]].
- **Sequential execution**: PC advances by instruction size.
- **Branches and loops**: conditional PC-relative redirection.
- **Calls and returns**: save and restore a return address.
- **Interrupts and exceptions**: asynchronous redirection to a handler. See [[q0911]].
- **Pipelining and speculation**: the fetch PC runs ahead of the committed PC. See [[q0906]], [[q0910]].
:::

::: answer
"The program counter mostly just counts up. After each instruction it goes up by the instruction size, so by 4 on a 32-bit RISC machine. That's sequential flow. It changes pattern when something redirects it. A taken branch or jump loads a new address, usually the current PC plus an offset, so a loop makes the PC go back to the top over and over. A function call loads the address of the function and saves the return address, and the return instruction puts it back, so the PC goes to the function and then resumes after the call. An interrupt or exception forces the PC to a handler address from a vector table, saving the old PC, and then a return-from-interrupt resumes where it left off. And at reset it starts from the reset vector.

If you plot the PC against time, you'd see a staircase going up in steps of four, with occasional jumps: backward for loops, to a function and back for calls. In a pipelined CPU there's an extra wrinkle: the fetch unit keeps incrementing or following predictions ahead of the instructions actually executing, and if a branch was mispredicted the PC is redirected and the wrongly fetched instructions are flushed."
:::

::: technical
**Sequential:** $PC_{n+1}=PC_n+L$ with $L$ = instruction length (4 for fixed 32-bit; 2 or 4 with RISC-V compressed; variable on x86).

**Branch:** $PC_{n+1}=\begin{cases}PC_n+\text{offset}&\text{taken}\\PC_n+L&\text{not taken}\end{cases}$. Loops are backward branches (negative offset).

**Call/return:** `jal ra, f` sets $ra\leftarrow PC+4$, $PC\leftarrow f$; `ret` sets $PC\leftarrow ra$. Non-leaf functions spill $ra$ to the stack.

**Interrupt/exception:** hardware saves $PC$ (stack on Arm Cortex-M; `mepc` on RISC-V), sets $PC\leftarrow$ handler from the vector table, and `reti`/`mret`/exception return restores it. Asynchronous: the interrupted instruction boundary is arbitrary ([[q0911]]).

**Reset:** $PC\leftarrow$ reset vector.

**Pipeline:** The fetch PC advances every cycle, so the PC of the instruction in the execute stage lags the fetch PC by the pipeline depth (2 to 3 instructions in a 5-stage design). A taken branch resolved in EX redirects fetch and flushes the younger instructions, costing the branch penalty (2 cycles in the classic 5-stage design when resolved in EX). With branch fraction $b$, misprediction rate $m$ and penalty $P$ cycles, $\text{CPI}=1+b\,m\,P$; e.g. $b=0.2$, $m=0.1$, $P=15$ gives $1.3$ ([[q0910]]).

**Observation:** debugger halt-and-read, sampling profiler, trace (Arm ETM/ITM, RISC-V trace) or logic analyzer on the instruction address bus.
:::

::: short
"The PC normally steps forward by the instruction size, so by 4 for 32-bit instructions. A taken branch or jump loads a new address, so loops jump backward and repeat; a call loads the function's address and saves the return address, and the return restores it; an interrupt saves the PC and loads a handler address, then returns; and reset loads the reset vector. Plotted over time it's a staircase with occasional jumps. In a pipeline the fetch PC runs ahead speculatively and is redirected on mispredictions."
:::

::: long
"Think of the PC as tracing a path through the program's address space.

Most of the time it moves forward in regular steps. After each instruction the PC increases by the instruction length, so by 4 on a typical 32-bit RISC core. That's straight-line code.

Branches change that. A conditional branch has a target, generally the PC plus a signed offset. If the condition is true, the PC jumps there, and if not, it just continues. A loop is a backward branch at the bottom that sends the PC back to the top until the condition fails, so in a trace you see the same range of addresses repeating.

Function calls make a jump to the function's start address and save the return address in a link register or on the stack. When the function finishes, a return loads that saved address back into the PC, so execution resumes right after the call. A program with a loop that calls a function shows a pattern of going to the function's address and back each iteration.

Then there are interrupts and exceptions, which are asynchronous. The hardware saves the PC of the interrupted instruction, switches to a privileged mode, and loads the PC from a vector table with the handler's address. The handler runs, and a return-from-interrupt restores the saved PC, so the main program continues as if nothing happened. Reset is the same idea, forcing the PC to the reset vector.

In a real pipelined CPU there's another layer. The fetch stage keeps running ahead, either just incrementing or following a branch predictor, so the PC being fetched is several instructions ahead of the one finishing. If a branch was predicted wrongly, the right target is loaded into the PC and the instructions fetched down the wrong path are flushed. So the committed PC trace is exactly what the programmer expects, but the fetch PC trace includes speculative detours."
:::

::: terms
- **Sequential flow**: execution in address order, PC advanced by the instruction size.
- **Taken / not-taken branch**: whether the condition redirects the PC.
- **Control-flow instruction**: branch, jump, call or return; any instruction that can set the PC.
- **Return address**: PC value saved by a call (or interrupt) for later resumption.
- **Vector table**: table of handler addresses indexed by exception number.
- **Speculative fetch**: fetching along a predicted path before the branch resolves.
- **Pipeline flush**: discarding wrong-path instructions after a redirect.
- **PC trace**: recorded sequence of PC values, used for profiling and debugging.
:::

::: exceptional
**An average answer** says "it increments, except on branches and jumps".

**An exceptional answer**:
- Lists all mechanisms (sequential, branch, loop, call/return, interrupt/exception, reset) and what state each saves.
- Walks a concrete mini program and gives the actual PC trace.
- Distinguishes the fetch (speculative) PC from the committed PC and states the cost of redirection with a formula.
- Notes asynchronous interrupt behavior and precise exceptions.
- Mentions how engineers observe it: debugger, PC sampling, trace.
- Can say what a stuck or wild PC implies.
:::

::: mistakes
- **"It just increments by 1."** It advances by the instruction length in bytes (4 for fixed 32-bit instructions).
- **Forgetting that a not-taken branch also goes to PC+4.** The PC only jumps if the condition holds.
- **Saying interrupts "pause" the PC.** The PC is overwritten with the handler address and the old value is saved elsewhere (stack, link or CSR).
- **Mixing the fetch PC and the retired PC.** In an out-of-order or deeply pipelined CPU they differ by dozens of instructions.
- **Assuming a return goes to a fixed place.** It loads whatever was saved, so a corrupted saved address redirects the PC anywhere.
- **Ignoring that loops reuse the same PC values**, which is why instruction caches and branch predictors work so well.
:::

::: deep
## A tiny program and its PC trace

Take this RISC-V-style program (addresses in hex, 4 bytes per instruction):

| Address | Instruction | Meaning |
|---|---|---|
| 0x00 | `addi x1, x0, 3` | counter = 3 |
| 0x04 | `loop: addi x1, x1, -1` | counter-- |
| 0x08 | `jal ra, func` | call function at 0x40 |
| 0x0C | `bne x1, x0, loop` | if counter != 0 go to 0x04 |
| 0x10 | `end:` | |
| 0x40 | `func: add x5, x5, x6` | do some work |
| 0x44 | `ret` | return: PC = ra (0x0C) |

Executing it, the PC takes these values (I generated the trace in code): 0x00, 0x04, 0x08, 0x40, 0x44, 0x0C, 0x04, 0x08, 0x40, 0x44, 0x0C, 0x04, 0x08, 0x40, 0x44, 0x0C, 0x10. That is 17 instruction executions: 1 setup, then 3 loop iterations of 5 instructions each, then the final fall-through at 0x10.

Figure: The PC against instruction count. The staircase of +4 steps is sequential code; the spikes to 64 are calls to the function; the drops back from 12 to 4 are the loop's backward branch. Notice the repeating pattern: the same five PC values per iteration, which is why caches and branch predictors do so well on loops.

How each transition arises:

- 0x00 → 0x04, 0x04 → 0x08, 0x40 → 0x44: sequential, +4.
- 0x08 → 0x40: `jal` loads the target and saves $ra=0x0C$.
- 0x44 → 0x0C: `ret` loads $PC\leftarrow ra$.
- 0x0C → 0x04: `bne` taken (counter 2, then 1, is not zero): PC + offset where offset $=-8$.
- 0x0C → 0x10: `bne` not taken (counter is 0): falls through, +4.

## Interrupts: a detour in the middle

An interrupt can arrive between any two instructions. Suppose, in the loop above, it arrives while the PC is at 0x08. The hardware (1) finishes or squashes in-flight instructions so that the state is *precise* (everything before the interrupted instruction is complete, nothing after has changed state), (2) saves the PC (0x08 or the next address, depending on the architecture) to the stack or a CSR, (3) changes mode and loads the PC from the vector table. The PC trace then shows a jump into the handler range, a run of handler instructions, and a return to exactly where the main flow resumes:

The PC value saved depends on the architecture: precise interrupts must make it appear that the interrupt occurred exactly between two instructions. Exceptions caused by an instruction (a page fault on a load) save the PC of the *faulting* instruction so it can be re-executed after the handler fixes the cause; interrupts save the PC of the *next* instruction to run. See [[q0911]].

## The pipeline view

In a 5-stage pipeline ([[q0906]]) the front end fetches an instruction every cycle. By the time the branch at 0x0C reaches the execute stage, fetch has already requested the next two or three addresses. If the branch is taken and fetch assumed fall-through, the instructions at 0x10 and 0x14 are wrong-path and must be flushed; the PC is reloaded with 0x04.

Using the CPI formula: with branch frequency $b=0.2$, mispredict rate $m=0.1$ and a 15-cycle redirect penalty (typical of deeper, high-frequency pipelines), $\text{CPI}=1+0.2\times0.1\times15=1.3$. If a simple predictor mispredicted half the time, $\text{CPI}=1+0.2\times0.5\times15=2.5$. Accuracy of PC prediction directly determines throughput.

Modern front ends run ahead of execution by many instructions using a branch target buffer and a return address stack: a small hardware stack that predicts `ret` targets by remembering recent call return addresses. Without it, `ret` would be unpredictable at fetch time because its target is in a register.

## Exceptions, traps, and system calls

Besides asynchronous interrupts there are synchronous exceptions (illegal instruction, page fault, divide by zero on some ISAs, misaligned access) and deliberate traps (`ecall`, `svc`, `int 0x80`) used for system calls. All of them redirect the PC through a vector table and save the return PC. System calls return to the instruction *after* the trap; faults often return to the faulting instruction itself.

## What a wild PC looks like

Debugging clues from the PC value:
- **At the reset vector and never advancing**: clock/flash not working, or core held in reset.
- **In an idle loop (`wfi` or `b .`)**: system waiting for an interrupt that never arrives (check interrupt enable, pending bits, or a missed wake-up).
- **In a `HardFault` handler**: look at the stacked PC to find the faulting instruction, and fault status registers for the reason.
- **At an odd or nonsensical address, or in the data/stack region**: corrupted return address (stack overflow, buffer overflow), a bad function pointer, or a jump table entry that was never initialized.
- **Looping on the same few addresses unexpectedly**: a polling loop on a flag that is never set (a hardware bit not updating, or a compiler optimized away a non-volatile variable).

> If given a small assembly program and asked "what values does the PC take?", write the addresses in a column, mark branches and call targets, and then trace executions one at a time, writing the PC after each step. Say out loud whether each step is sequential, taken, or a return.

::: applications
- **Sampling profilers**: periodically reading the PC builds a histogram of where time goes.
- **Post-mortem crash analysis**: the stacked PC at a fault points to the offending instruction.
- **Hardware trace**: ETM-style units record PC discontinuities (branches) for replaying execution.
- **Instruction cache and branch predictor design**: loops cause repeated PC patterns that these exploit.
- **Real-time interrupt latency measurement**: the time between the IRQ edge and the first handler PC.
:::

::: assumptions
- **Fixed 4-byte instructions** for the worked trace; variable-length ISAs change the increments but not the logic.
- **Precise interrupts**: the saved PC corresponds to an instruction boundary. Imprecise exceptions exist on some deeply pipelined designs but are rare in modern CPUs.
- **Simplified single-thread view.** Multithreaded or multicore chips have one PC per hardware thread.
- **The penalty numbers (2 cycles for a 5-stage pipeline, 15 for deep pipelines) are typical**, not universal.
- **The timing diagram is idealized**: interrupt entry takes several cycles in real hardware.
:::

::: followups
### What is the PC at the start of an interrupt handler, and what happens to the old value?
It is the handler address from the vector table. The old PC (return address) is saved: pushed on the stack by hardware on Arm Cortex-M, stored in `mepc` on RISC-V, or kept in a banked link register on classic Arm. A return-from-interrupt instruction restores it.

### Why do loops make code run faster on real CPUs?
The PC revisits the same range of addresses, so instruction caches hit almost always and branch predictors learn the backward-branch pattern: a loop of 10 iterations is taken 9 times and not taken once, so a 2-bit predictor mispredicts roughly once per loop exit. Locality is what caches and predictors exploit.

### How does a processor know where to return after a function call?
The call instruction stores PC+4 in a link register or pushes it on the stack. The return loads it into the PC. Modern CPUs also keep a return-address stack in the front end to predict return targets at fetch time before the register is read.

### Your embedded device hangs. The debugger shows the PC at the same address every time you halt it. What are the possible causes?
Either a deliberate wait (`wfi`, a polling loop on a flag that never changes, a spinlock) or a fault trap (`b .` in a default handler). Check what the instruction at that address is, what it's waiting for, and whether the hardware condition (a peripheral status bit, interrupt, clock) is happening. A watchdog would normally reset it if enabled.

### How does the PC behave on a mispredicted branch in a deep pipeline?
Fetch continued along the predicted path; when the branch resolves, the correct target is written to the fetch PC, younger instructions are flushed, and fetch restarts. With a 15-cycle penalty and 1 in 50 instructions mispredicting, CPI rises by $15/50=0.3$.
:::
