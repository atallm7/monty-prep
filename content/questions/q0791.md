::: testing
Whether you know that **timing accuracy is set by the oscillator, not by the counter**. A strong candidate talks about clock sources (internal RC, crystal, TCXO, external reference), errors in ppm and what they mean per day, the right timer configuration to avoid cumulative error (no re-loading the timer inside an ISR), unsigned-subtraction timestamps that survive wrap-around, and low-power timekeeping with a 32.768 kHz crystal. The hidden skills are unit fluency (ppm to seconds per day) and recognising the two classes of error: *frequency* error of the clock and *software* error from latency and drift.
:::

::: why
Anything that talks on a bus (UART baud rate, USB, CAN), keeps a schedule, logs timestamps or measures a physical quantity from time depends on an oscillator. A UART with a 3% clock error fails; a data logger that drifts 15 minutes a day is useless; a motor controller that jitters its loop period gets noisy. Knowing how to pick and verify the clock, and how to write timekeeping code that does not accumulate error, is a basic firmware competence that interviewers probe with "how would you keep time for a month?" ([[q0792]], [[q0793]]).
:::

::: concepts
- **Hardware timer**: a counter clocked by the oscillator; the count is exact but the time scale is only as accurate as the clock ([[q0789]]).
- **Oscillator accuracy (ppm)**: parts per million error. 20 ppm is 1.73 s per day.
- **Crystal versus RC oscillator**: a crystal is typically 10-50 ppm; an on-chip RC can be 1-5%, and varies with temperature and supply.
- **Drift versus jitter**: drift is a steady frequency error that accumulates; jitter is random cycle-to-cycle variation that does not accumulate.
- **Wrap-around-safe arithmetic**: unsigned subtraction of timestamps gives the right elapsed time even when the counter overflows.
- **Interrupt latency**: delay from the event to the ISR running; accumulates if you restart timing in software ([[q0796]]).
:::

::: answer
"Accurate timekeeping really comes down to two things: a good clock and not introducing error in software.

For the clock, the internal RC oscillator on most MCUs is only accurate to a percent or a few percent and moves with temperature and voltage. A 1% error is about 14 minutes a day, which is fine for blinking an LED but bad for a UART or a clock. So for anything that matters I'd use a crystal. A typical 20 ppm crystal is about 1.7 seconds a day. For a real-time clock I'd use a 32.768 kHz watch crystal into the RTC, because it divides by 2 to the 15th to give exactly one second and it runs in the lowest power mode. If I need better than that, a temperature-compensated oscillator, or I'd periodically sync against GPS or a network time source.

For the software, I let the hardware timer free-run and count in hardware. I use its update interrupt for a millisecond tick but I don't stop and restart the timer in the ISR, because latency would accumulate as drift. I also store timestamps as unsigned integers and compare with subtraction, so a wrap-around, like a 32-bit millisecond counter every 49.7 days, doesn't break anything."
:::

::: technical
**Error budget.** Elapsed-time error is $\Delta t = t\cdot\varepsilon$ with fractional frequency error $\varepsilon$ (ppm $\times10^{-6}$). Per day (86,400 s): 1 ppm is 0.0864 s; 20 ppm is 1.73 s; 50 ppm is 4.32 s; 100 ppm is 8.64 s; 1% is 864 s = 14.4 min.

**Clock sources, typical (vendor- and part-dependent):**
- Internal RC (factory trimmed): about 1-2% over temperature, worse untrimmed; changes with VDD and temperature.
- Crystal (HC-49, 3.2x2.5 mm SMD): initial tolerance and temperature stability typically within 10-50 ppm plus load-capacitance pulling and aging of a few ppm per year.
- 32.768 kHz tuning-fork crystal: roughly 20 ppm at 25 C, with a parabolic temperature dependence (worse at temperature extremes). Used for RTCs.
- TCXO: about 0.5-2.5 ppm; OCXO: much better, at the cost of power. GPS-disciplined sources: long-term accuracy set by the reference.

**Counter configuration without drift.** Use auto-reload so the hardware wraps exactly every $(PSC+1)(ARR+1)$ ticks. Do not do "stop timer, load, restart" in the ISR; the dead time of each ISR adds to the period. Use compare mode with $CCR_{next}=CCR_{old}+\text{interval}$ for several periodic events from a free-running counter.

**Rounding.** If $f_{clk}/f_{target}$ is not an integer, the quantised period has a fixed error, e.g. 16 MHz to 3 kHz gives 5333.33 ticks: use 5333 for 0.006% error; for better, alternate 5333 and 5334 (fractional accumulation, like a software DDS) to reach exact average frequency.

**Timestamping.** Keep a monotonic counter `uint32_t ms`. Elapsed: `ms - start` evaluated in `uint32_t`. This is correct as long as the interval is less than the wrap period $2^{32}$ ms $=49.7$ days. Never compare absolute times with `<`.

**Calibration.** Measure a known reference (GPS PPS, mains frequency, or a precision source) with input capture, compute $\varepsilon$, and apply a correction in the RTC calibration register or the software divider. On a crystal with a known temperature curve, add a temperature sensor and compensate (this is how a software TCXO works).
:::

::: short
"The counter is exact; the clock isn't. So I pick the clock for the accuracy I need: the internal RC is about 1% (14 minutes a day), a crystal is around 20 ppm (1.7 seconds a day), and a 32 kHz watch crystal into the RTC gives low-power timekeeping. In software I let the timer free-run, use auto-reload so no error accumulates, and use unsigned subtraction for elapsed times so counter wrap doesn't matter. For better than crystal accuracy, add a TCXO or calibrate against a reference like GPS."
:::

::: long
"There are two sources of timing error: the clock itself, and what the software does with it. I'll take them in that order.

The counter is exact digital logic, so the accuracy comes from the oscillator. The internal RC oscillator on most microcontrollers is good to a percent or so and wanders with temperature and supply. At 1% that is about 14 minutes a day, fine for blinking an LED, not fine for a UART at high baud rates or a clock. A crystal is dramatically better: typically somewhere around 10 to 50 ppm, and 20 ppm works out to 1.7 seconds per day. For a calendar clock I'd use a 32.768 kHz watch crystal with the RTC. It divides down by 2 to the 15th to give exactly one second, and it runs on microamps in sleep. If I need sub-ppm, a TCXO is the next step, or I periodically correct against GPS or network time. Also remember that crystals drift with temperature and age, and the load capacitors affect the frequency.

On the software side, the biggest mistake is making the period depend on code execution. I let the timer free-run with auto-reload, so the hardware generates the exact period, and the ISR just updates a counter. If I need to generate several intervals from one counter, I schedule the next compare as the old compare plus the interval, never as the current count plus the interval, so interrupt latency doesn't accumulate.

For timestamps I use an unsigned 32-bit millisecond counter and compute elapsed as now minus start. That works across the wrap, which happens every 49.7 days for milliseconds.

And if the target frequency doesn't divide evenly into the clock, I'd compute the residual error and, if needed, alternate between two reload values so the average is exact."
:::

::: terms
- **ppm (parts per million)**: fractional frequency error times $10^6$. 1 ppm is about 0.0864 s per day.
- **Drift**: accumulating time error from a constant frequency offset.
- **Jitter**: short-term random variation in edge timing; does not accumulate.
- **Crystal / TCXO / OCXO**: a quartz resonator; temperature-compensated; oven-controlled oscillator, in rising order of accuracy and cost.
- **RTC**: real-time clock, usually fed from a 32.768 kHz crystal in a low-power domain.
- **Free-running counter**: a timer that never stops or reloads, so timestamps are continuous.
- **Aging / pulling**: slow crystal frequency change over time; the shift caused by load capacitance.
- **Monotonic clock**: a counter that only goes forward, unaffected by time-zone or set-time changes.
:::

::: exceptional
An average answer says "use a crystal and a timer." An exceptional answer:

- Converts accuracy to **ppm and seconds per day** on the spot (20 ppm is 1.7 s, 1% is 14 minutes).
- Separates **drift from jitter** and points out that interrupt latency adds jitter but not drift *if* the timer free-runs.
- Describes the **free-running counter and compare-plus-interval** pattern, and unsigned wrap-safe subtraction.
- Knows the **32.768 kHz** convention (2^15) and its temperature dependence, and mentions calibration or compensation.
- States the ceiling honestly: an MCU alone can't beat its reference; for absolute time you need GPS, NTP or a calibrated TCXO.
:::

::: mistakes
- **Trusting the internal RC for absolute time or baud rates.** Its error of 1-5% breaks UART at high rates and drifts clocks by minutes per day.
- **Restarting the timer in the ISR.** Each restart loses the latency of the ISR, so the period is longer than intended and the error accumulates.
- **Comparing absolute times with `<` or `>`.** After wrap-around `now < deadline` is wrong. Use `(int32_t)(now - deadline) >= 0` or unsigned subtraction against a duration.
- **Ignoring rounding error in the reload value.** 16 MHz / 3 kHz is not an integer; the quantisation error is deterministic and can be removed by alternating reload values.
- **Forgetting temperature and supply.** A 32 kHz crystal can be tens of ppm off at the temperature extremes; RC oscillators can move a percent.
:::

::: deep
## Where the error actually comes from

Break the time you read into three layers:

1. **Clock frequency error**: the oscillator's actual frequency differs from nominal by $\varepsilon$. Everything derived from it is off by the same fraction.
2. **Quantisation**: the timer divides the clock by an integer, so a target period is rounded to a whole number of ticks.
3. **Software**: interrupt latency and the way you restart timing.

The first is a property of hardware, the second is deterministic arithmetic, and the third is entirely under your control.

## Layer 1: the oscillator

An oscillator's frequency error has several components, all expressed in ppm:

| Source | Typical magnitude | Behaviour |
|---|---|---|
| Initial tolerance | 10-50 ppm (crystal), 1-2% (trimmed RC) | Fixed per part |
| Temperature | A few ppm to 50+ ppm over temperature (crystal); about 1% (RC) | Changes with environment; tuning-fork crystals are parabolic |
| Aging | A few ppm in the first year, less after | Slow |
| Load capacitance | Detuning from stray capacitance, tens of ppm if wrong | Fixed by layout and component choice |
| Supply voltage | Small for crystal, noticeable for RC | Depends on design |

> [!UNCERTAIN]
> The ppm figures are typical ranges; the exact numbers depend on the part and grade (check the crystal or oscillator datasheet) and on the MCU's trim specification for the internal oscillator.

For a one-month data logger that must stay within 1 minute, you need $60/(30\cdot86400)=23$ ppm, so a 20 ppm crystal barely passes and a typical RTC crystal at temperature extremes may not. A TCXO or a periodic resync gives margin.

## Layer 2: quantisation of the period

With $f_{clk}=16$ MHz and a target of 3 kHz, the ideal divider is $5333.33$. Using 5333 gives $f=3000.19$ Hz, error $+0.006\%$ (62 ppm), which is larger than the crystal error you worked to get. A fix is a fractional accumulator: add 1 to the reload on every third period so the average divider is 5333.33. The same idea (a software or hardware **fractional divider**) is how baud-rate generators achieve small error on awkward crystals. See [[q0775]] for the UART version of the same problem.

## Layer 3: don't make the software add error

Two ways to produce a 1 ms interrupt:

**Bad:** in the ISR do `TIMER = 0; start();` (restart timer). The ISR runs some microseconds after the compare match; during those microseconds the counter either kept running (and you threw away the count) or was stopped. Every period is longer by the latency. Over a day at 5 µs of latency per millisecond, the clock loses $0.5\%$, 7 minutes.

**Good:** use auto-reload or, with a free-running counter, `CCR += 1000;` in the ISR. The next match time is relative to the *previous scheduled* time, not to when the ISR happened to run, so latency affects only *when* the code runs (jitter), never the average period.

## Timestamps and wrap-around

A free-running 32-bit millisecond counter wraps after $2^{32}$ ms = 49.7 days. If code stores a start time and later checks `now - start >= timeout` using `uint32_t`, the subtraction is done modulo $2^{32}$ and is right across the wrap as long as the true elapsed time is less than the wrap period. Checking `now >= start + timeout` fails when `start + timeout` overflows. The same applies to a 16-bit hardware counter: capture subtraction in 16-bit unsigned arithmetic returns the correct small difference even if CNT wrapped between captures.

```c
uint32_t start = millis();
/* ... */
if ((uint32_t)(millis() - start) >= 5000) { /* 5 s elapsed, wrap-safe */ }
```

## Low-power timekeeping

An RTC clocked by a 32.768 kHz crystal ($2^{15}$ Hz) counts exact seconds through a 15-bit divider and typically draws on the order of a microamp or less (device dependent). The main MCU can sleep and be woken by the RTC alarm. To correct the crystal error, most RTCs have a calibration register that adds or removes pulses periodically; with a known $\varepsilon$ of 20 ppm you remove about one pulse in 50,000 (for a 32,768 Hz clock that is about 0.65 pulses per second). A temperature sensor and a lookup table lets software compensate for the parabolic temperature curve, improving a typical tuning-fork crystal from tens of ppm over temperature to a few ppm.

## Worked example: logging for a month

Requirement: timestamp samples to within ±30 s over 30 days. That is $30/2{,}592{,}000=11.6$ ppm. A plain 20 ppm crystal at room temperature fails; options: a TCXO RTC (about 2 ppm), temperature compensation of a 32 kHz crystal using the MCU's temperature sensor, or a daily resync from a phone, network or GPS. I would choose the TCXO or a resync depending on cost and connectivity, and say why.

## Measuring your own clock

To check a clock against a reference, connect a known frequency (say 1 PPS from GPS) to an input-capture pin and count how many ticks of your timer fit between pulses. If you count 16,000,320 ticks of a nominal 16 MHz timer in one second, the clock is fast by 20 ppm. This is how factory calibration and field calibration are done.
:::

::: applications
- **UART/USB/CAN clocking**: a few percent of baud error is tolerable for UART; USB full-speed needs about 0.25% so a crystal or trimmed oscillator is mandatory.
- **Data loggers and smart meters** using a 32.768 kHz RTC crystal plus calibration.
- **Wearables and IoT nodes** that sleep most of the time and wake from the RTC.
- **Control loops** (motor, power converter) that require a fixed sample period with low jitter.
- **GPS-disciplined timing** in telecom and test equipment.
- **Real-time stamping of events** in an RTOS using a monotonic tick.
:::

::: assumptions
- Numbers assume typical crystal and RC specs; real parts vary, so check the datasheet for tolerance, temperature stability and aging.
- Assumes a single clock domain. If the timer clock comes from a PLL, add its jitter and lock behaviour; the PLL multiplies reference error proportionally in ppm (no worse in ppm) but adds jitter.
- "Accurately" can mean *absolute* accuracy (match wall-clock time) or *relative* accuracy (constant period). Constant period needs a stable oscillator; absolute needs calibration or an external reference.
- If the question means "high-resolution timestamps" rather than long-term accuracy, the answer shifts to timer resolution, input capture and cycle counters (such as the Cortex-M DWT cycle counter where present).
:::

::: followups
### How accurate is a typical crystal and what does that mean per day?
Typically somewhere in the tens of ppm. 20 ppm times 86,400 s is 1.73 s per day; 50 ppm is 4.3 s. Temperature and aging add a few more, and wrong load capacitors can pull the frequency by tens of ppm, so layout and capacitor choice matter as well as the part.

### Why use 32.768 kHz instead of any other crystal frequency for the RTC?
$32{,}768=2^{15}$, so a 15-stage binary divider produces exactly 1 Hz with no arithmetic. The tuning-fork crystal is small, cheap, low drive-level and works at very low power, which suits always-on timekeeping.

### My `millis()` based timeout broke after about seven weeks. Why?
A 32-bit millisecond counter wraps after 49.7 days. If the timeout used `now >= start + timeout` or compared absolute stamps, the wrap breaks it. Compute elapsed as `now - start` in unsigned arithmetic, which is correct across the wrap.

### How would you get better than crystal accuracy with no GPS?
Compensate in software: measure temperature, apply the crystal's known temperature curve to adjust the RTC calibration register or divider, and periodically calibrate against a reference at the factory. That can bring a 32 kHz crystal to a few ppm over temperature. A TCXO does it in analog hardware.

### What if the timer clock comes from a PLL? Does that change accuracy?
The PLL output frequency error equals the reference error in ppm, so accuracy is unchanged, but the PLL adds jitter (cycle-to-cycle variation). For timekeeping that is irrelevant as jitter averages out, but for measuring very short intervals or generating clean high-speed signals it can matter ([[q0775]] shows the analogous UART baud case).
:::
