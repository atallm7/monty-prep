::: basics
### In plain words
Specifying an MCU means turning what your product must do into numbers, and then choosing the smallest chip that meets them with room to spare. Start from the requirements, not a datasheet. Work out how much processing, memory, input/output and battery life you need. Then check candidate chips against those totals. Too small a chip hits a wall late in the project. Too big a chip wastes cost and power.

### Picture it
Picture choosing a moving truck. You first measure what you must move: the volume of boxes, the heaviest item, and how far you are going. Then you add some extra room, because you will always find more stuff. A truck that is too small means a second trip halfway through. A truck that is far too big costs more to rent and burns more fuel.

### Words you need
- **Cycle budget**: how many clock ticks the processor has for each pass of its main task.
- **Headroom**: spare capacity left over for new features and surprises.
- **Peripheral**: a built-in hardware block such as a timer, converter or serial port ([[q0733]]).
- **Pin multiplexing**: one physical pin can serve several functions, but only one at a time.
- **Sleep current**: the tiny current the chip draws while idle, which drives battery life.
- **Errata**: the maker's list of known bugs in the chip.

### The simplest example
A motor control loop runs 20,000 times per second on a 72 MHz chip. The cycle budget is $72{,}000{,}000/20{,}000=3{,}600$ ticks per pass. If the algorithm needs 1,800 ticks, it uses half, which leaves good headroom. For memory, 64 KB of firmware plus a 16 KB starter program (bootloader) needs a second copy of the firmware for safe field updates. That is $2\times64+16=144$ KB, so you pick the next size up, 256 KB. That is the whole idea. The rest of this page covers the full checklist, pin checks, power math and prototyping.
:::

::: testing
Whether you can turn **system requirements into a part selection** with numbers, not recite a spec list. The interviewer is looking for:

1. A structured set of criteria: CPU performance, memory, peripherals, I/O count, power, voltage/temperature, package, ecosystem, cost and availability.
2. The method: derive the numbers (CPU cycles per loop, flash/RAM, ADC rate and resolution, pins) from the requirements, then add headroom.
3. Practical judgement: the datasheet traps (errata, pin-mux conflicts, peripheral count vs usable pins) and supply-chain risk.
:::

::: why
Choosing an MCU is a design decision you live with for the whole product. Too small and you hit a wall near the end of the project (out of flash, no spare timer, a pin conflict); too big and you waste cost and power. Interviewers ask to see whether you can reason from the requirements instead of defaulting to "the one I know". The skill transfers to any component selection.
:::

::: concepts
- **Requirements first**: what the system must sense, compute, drive, communicate, and under what constraints. See [[q0728]].
- **CPU and memory sizing**: cycles per task, flash and RAM budgets, headroom.
- **Peripheral matching**: timers, ADC, comms, DMA, special blocks (CAN, USB, crypto).
- **Power**: active µA/MHz, sleep currents, wake time, supply range.
- **Ecosystem**: toolchain, debugger, HAL, community, RTOS support.
- **Supply and lifecycle**: availability, pin-compatible upgrades, longevity.
:::

::: answer
"I start from the system requirements, not the datasheet. What does it have to sense, drive and talk to, how fast, on what power, in what environment, and at what cost? Then I translate that into numbers.

CPU: I take the fastest loop and count cycles. For a 20 kHz motor-control loop on a 72 MHz core I have 3,600 cycles per iteration, and I'd want the algorithm under about half of that for headroom. Does it need a floating-point unit or DSP instructions?

Memory: estimate flash for code plus bootloader and any update image, and RAM for buffers and stacks, then add 30 to 50 percent margin.

Peripherals: count what I need and check the pins can actually be routed: timers with the right outputs, ADC channels and sample rate, UART, SPI, I2C, CAN or USB, DMA channels. A feature on the datasheet isn't usable if it's muxed onto a pin I've used.

Power: the supply range, active current per MHz, and sleep current for a battery product, plus wake-up time and what stays alive in sleep.

Then the practical ones: operating temperature range and qualification, package and pin count, debug support, toolchain and library support, errata, cost at volume, and availability, ideally with a pin-compatible family so I can scale flash up or down without a respin. And I'd keep the choice flexible by designing in a family, not a single part."
:::

::: technical
**Spec checklist and what to look for**

| Category | Spec | What to check |
|---|---|---|
| CPU | Core, clock, DMIPS/CoreMark, FPU/DSP, cycles per task | Loop budget = $f_{clk}/f_{loop}$, target ≤ 50% utilization |
| Memory | Flash, SRAM, EEPROM, external memory interface | Code + bootloader + OTA image; RAM for buffers/stack; margin 30–50% |
| Flash timing | Wait states vs clock | Effective performance at the planned clock |
| Peripherals | Timers (advanced, complementary PWM with dead time), ADC (bits, MS/s, channels, sync), DAC, comparators, UART/SPI/I2C/CAN/USB count | Count and also the *usable* ones after pin muxing |
| DMA / interrupts | Channels, priority levels | Streams that need DMA; interrupt latency |
| I/O | Pin count, 5 V tolerant pins, drive current, ESD | Total GPIO needed + debug + spare |
| Power | Supply range, µA/MHz, stop/standby/shutdown current, wake time | Battery life budget; brown-out |
| Clocking | Internal oscillator accuracy, crystal support, PLL, RTC | UART/USB/radio need crystal accuracy |
| Environment | Temp range (−40 to 85/105/125 °C), AEC-Q100 | Product class |
| Package | QFN/LQFP/BGA, pitch, size | Assembly capability, board layers |
| Security / safety | Secure boot, crypto, readout protection, ECC, lockstep | Regulatory and product needs |
| Ecosystem | Vendor HAL, IDE, debugger, RTOS support, examples | Team familiarity, time to market |
| Supply | Lead time, second source, longevity program, price at volume | Production risk |
| Quality | Errata sheet | Known bugs in the peripherals you plan to use |

**Worked example: three-phase BLDC motor controller (field-oriented control).**

Requirements: 24 V, up to 20 A phase current, 20 kHz PWM and current loop, Hall sensors, CAN interface, debug UART, field firmware updates, −40 to 105 °C.

1. **CPU budget.** Loop rate 20 kHz → at 72 MHz: $72\times10^6/20\times10^3=3{,}600$ cycles per iteration. FOC (Clarke, Park, two PI controllers, inverse Park, space-vector modulation) plausibly takes about 700 to 2,000 cycles depending on FPU and fixed vs floating point (an estimate; profile it). Keep to ≤ 50%, i.e. ≤ 1,800 cycles. If the estimate is above that, choose a faster core or one with an FPU (for example 168 MHz gives 8,400 cycles).
2. **ADC.** Sample 3 phase currents + DC bus voltage + temperature = 5 channels per 50 µs period. At 1 µs per conversion that's 5 µs, 10% of the period. Prefer an ADC that can trigger from the PWM timer and sample the phase currents simultaneously or nearly so. Resolution: ±20 A through a 5 mΩ shunt is ±100 mV; a current-sense amplifier with gain 20 gives ±2 V about a 1.65 V midpoint. A 12-bit ADC on 3.3 V has 0.806 mV/LSB, which is $0.806\text{ mV}/20/5\text{ mΩ}=8.1$ mA per LSB, adequate for 20 A full scale.
3. **Timer.** Needs an advanced-control timer with three complementary PWM pairs, programmable dead time, a break input for fault shutdown, and the ability to trigger the ADC.
4. **Memory.** Firmware estimate 64 KB + bootloader 16 KB; dual-bank firmware update needs two copies: $2\times64+16=144$ KB → choose 256 KB flash. RAM: stacks, FOC state, CAN buffers, 16 KB estimated → choose 32 KB.
5. **Pins.** 6 PWM, 5 ADC, 3 Hall inputs, 2 CAN, 2 UART, 2 SWD, reset, boot, 2 LEDs, enable, spare ≈ 28 → a 48-pin package gives some headroom after pin-mux conflicts.
6. **Power and environment.** 3.3 V supply from a buck, active current not critical; −40 to 105 °C grade minimum.

**Power-spec example: sleep vs active.** Part A: active 10 mA for 1 ms per task (10 µC), sleep 1 µA. Part B: active 3 mA for 2 ms (6 µC), sleep 15 µA. Average current $I(T)=I_{sleep}+Q/T$. They are equal when $1\ \mu\text{A}+10\ \mu\text{C}/T=15\ \mu\text{A}+6\ \mu\text{C}/T$ → $T=4\ \mu\text{C}/14\ \mu\text{A}=0.29$ s. For tasks more often than every 0.29 s, B wins; rarer, A wins.

> [!UNCERTAIN]
> Cycle counts for FOC and similar algorithms depend heavily on the implementation, compiler and core. Treat them as estimates and benchmark your own code on an evaluation board before committing.
:::

::: short
"I derive the spec from the requirements. CPU: cycles per loop, such as 3,600 cycles per 20 kHz iteration at 72 MHz, with at most about half used. Memory: flash for code, bootloader and update image, RAM for buffers, plus 30–50% margin. Peripherals: enough timers, ADC channels and rate, buses and DMA, checked against pin muxing. Power: supply range, µA/MHz and sleep current. Then temperature grade, package, ecosystem, errata, cost and availability, ideally within a pin-compatible family."
:::

::: long
"I never start with a part. I start with what the system has to do, in numbers.

First the processing. I find the tightest real-time task and compute its cycle budget. For example a motor-control loop at 20 kHz on a 72 MHz core gives 3,600 cycles per iteration. I estimate the algorithm, say 1,000 to 2,000 cycles for field-oriented control, and I want to land at half the budget or less so there's room for communication and future features. That tells me whether I need an FPU, DSP instructions or a faster clock.

Second, memory. Flash for firmware plus bootloader, and if I need over-the-air or field updates, space for a second image: with 64 KB of firmware, 16 KB bootloader and dual banks I get about 144 KB, so I'd choose 256 KB. RAM for stacks, buffers and any RTOS, with a 30 to 50 percent margin.

Third, the peripherals, and this is where designs get hurt. I count what I need: timers with complementary PWM and dead time, ADC channels and the sample rate, so five channels in a 50 microsecond window, UARTs, SPI, I2C, CAN, USB, DMA channels. Then I check the pin mux to make sure the pins I need can all be reached at once, and that peripherals don't conflict.

Fourth, power: supply range, active current per MHz, sleep currents and wake-up time. For a battery product I model average current from the duty cycle, because the part with the lowest sleep current isn't always best if it works hard when awake.

Then the practical filter: temperature grade or automotive qualification, package I can route and assemble, the toolchain and debug support the team knows, the errata for the blocks I rely on, price at volume and lead time. I'd pick within a family that has pin-compatible parts with more and less flash so that I can resize late in the project, and I'd prototype on an evaluation board to measure real cycle counts and current before locking the design."
:::

::: terms
- **DMIPS / CoreMark**: CPU benchmark scores, per MHz and total.
- **Headroom**: unused margin in CPU, memory and pins for growth.
- **Errata**: manufacturer's list of silicon bugs and workarounds.
- **Pin mux**: assignment of internal peripherals to physical pins, with conflicts.
- **Advanced-control timer**: timer with complementary outputs, dead-time insertion and break input for power conversion.
- **Dual-bank flash**: two flash regions so one can be updated while the other runs.
- **AEC-Q100**: automotive IC qualification standard.
- **Longevity program**: vendor commitment to supply a part for years.
:::

::: exceptional
**An average answer** lists "speed, memory, peripherals, price".

**An exceptional answer**:
- Starts from requirements and converts them into numbers: cycles per loop, flash/RAM budgets with margin, ADC rate and resolution, pin count.
- Shows a worked example (e.g. FOC motor controller: 3,600 cycles per loop at 72 MHz, ADC LSB of 8 mA, 256 KB flash).
- Warns about pin-mux conflicts, errata, and usable vs listed peripherals.
- Treats power as duty-cycle math, not a single number.
- Includes ecosystem, supply chain and family scalability, and prototypes on an eval board to measure real numbers.
- Is honest that the cycle counts are estimates until profiled.
:::

::: mistakes
- **Choosing by clock speed or by the part you already know.** Requirements decide, not habit.
- **No headroom.** Designing at 95% of flash or CPU means the next feature breaks the product.
- **Counting peripherals, not usable pins.** A datasheet may list 6 UARTs but only 3 can coexist on your package after muxing.
- **Ignoring sleep current in battery designs**, or comparing µA/MHz without considering how long the part is awake.
- **Skipping errata and supply checks.** A peripheral you depend on may have a silicon bug, and a 52-week lead time kills the schedule.
- **Overspeccing.** A bigger MCU costs more and may draw more power; headroom has a price.
- **Forgetting the crystal and clock accuracy** needed for UART, USB, CAN and radio.
:::

::: deep
## The method: requirements to numbers

A useful way to spec any component is to move through four steps: (1) list the requirements with numbers, (2) compute the resource each demands, (3) add margin, (4) filter candidates against the totals, then break ties with ecosystem and supply.

### CPU: cycles, not megahertz

CPU capability is about *cycles available per unit of work*:
$$\text{cycles per iteration}=\frac{f_{clk}}{f_{loop}}$$
For a 72 MHz CPU, a 20 kHz loop gives 3,600 cycles; a 1 kHz loop gives 72,000; a 100 kHz loop gives only 720. The algorithm cost depends on the core: an M0+ with no hardware divide and no FPU can spend hundreds of cycles on one floating-point multiply emulated in software, whereas an M4F does it in a few cycles. So the spec isn't "72 MHz" but "enough cycles with the FPU and DSP instructions the algorithm uses".

Memory wait states matter too: at higher clocks flash needs extra cycles per access, and a prefetch buffer or cache hides some of it. A "168 MHz" device may deliver the full rate only from cache or with zero-wait RAM. The honest approach is to benchmark the actual code, not rely on the headline number.

### Memory: add the invisible parts

Flash holds the application, the bootloader, calibration data, and for safe updates a second image or at least staging space. RAM holds globals, the heap (if any), each task's stack under an RTOS, DMA buffers, and communication buffers such as USB or Ethernet packets. A good rule is to plan for 50% usage at the first release. Linker map files tell you the real sizes after the first build.

### Peripherals: count, then check pins

Write the peripheral list from the system block diagram: for the BLDC controller, one advanced timer (6 outputs), 5 simultaneous ADC channels, 1 CAN, 1 UART, 3 timer inputs for Hall sensors (or a timer's hall-sensor interface), SWD. Then open the datasheet's pin table and alternate-function table and *assign each signal to a pin*. This is the step most often skipped. Conflicts show up here: the timer channel you need may share a pin with the CAN transceiver, or the ADC channels you need may be on a different ADC from the trigger.

### Power, supply and environment

Power numbers on the first page of a datasheet are best-case: typical at 25 °C, one peripheral, a given clock. Check the conditions. Sleep-mode currents can differ by 10× depending on which modes keep RAM, the RTC, or the oscillator running, and on temperature (leakage doubles roughly every 10 °C or so; use the datasheet's high-temperature figures). Also check the supply range (1.8 V to 3.6 V parts work directly from a battery), the brown-out thresholds, and the I/O voltage tolerances.

### Ecosystem and lifecycle

A technically perfect MCU with a poor toolchain can cost months. Look at: debugger support and price, vendor code generators and HALs, RTOS ports, example code and community answers, and the quality of the reference manual. Then lifecycle: is the part in the vendor's longevity programme? Is there a pin-compatible upgrade path (more flash, faster speed grade), and a second source or equivalent? In the last few years part shortages made availability a first-class requirement.

### Errata

Always read the errata sheet. A peripheral bug (an ADC that misses a trigger when DMA is active, an I2C controller that locks up on clock stretching, a timer that glitches on update) can cost weeks if discovered late. A short check of errata for the blocks you rely on is cheap.

## Putting it together: the spec sheet for one product

| Requirement | Derived spec | Candidate check |
|---|---|---|
| 20 kHz FOC loop | ≥ 3,600 cycles, FPU preferred; target ≤ 1,800 used | 72 MHz M4F: pass |
| 5 ADC channels in 50 µs | ≥ 12-bit, ≥ 0.5 MS/s total, timer-triggered | pass |
| 3-phase PWM | Advanced timer, 3 complementary pairs, dead time, break | pass |
| OTA update | Dual-bank or 2× firmware size flash | 256 KB: pass |
| CAN + UART + SWD | 1 CAN, 1 UART, SWD | pass |
| −40 to 105 °C | Industrial grade | pass |
| 28 signals | 48-pin package, check mux | pass after assignment |
| Cost | Under target at volume | check distributor pricing |
| Availability | Lead time below plan; second family option | check |

Finally, order an evaluation board and run the actual control loop with a cycle counter and a current meter. The datasheet tells you what the part might do; the board tells you what it does.
:::

::: applications
- **Motor control**: advanced timers, fast simultaneous ADCs, FPU or DSP instructions (STM32G4/F3-class, TI C2000-class).
- **Battery-powered IoT**: very low sleep current, fast wake, integrated radio, small package.
- **Automotive**: AEC-Q100 grade, CAN/LIN, lockstep or ECC for safety, long-term supply.
- **Audio and DSP**: I2S, FPU, SRAM bandwidth, DMA.
- **USB and display products**: USB device/host, LCD or SPI display interfaces, enough RAM for frame buffers.
- **Industrial sensors**: 4–20 mA/analog front end, 12–16 bit ADC, extended temperature, robust ESD.
:::

::: assumptions
- **Cortex-M-class MCU** assumed; the method is the same for other architectures.
- **Numbers** (cycles, flash sizes, cost) are for the example application, not general rules.
- **Headroom** targets (50% CPU, 30–50% memory) are rules of thumb that depend on project risk and future plans.
- **Datasheet "typical" values** are not guaranteed; use min/max tables for design limits.
- **The answer changes** for safety-critical or high-volume cost-driven designs, where formal selection criteria and second sourcing dominate.
:::

::: followups
### How do you estimate how much flash and RAM you need before writing the code?
Use prior projects, library sizes (RTOS, USB stack, filesystem, BLE stack, each from a few KB to hundreds of KB) and a rough line-count estimate, then add margin; prototype the biggest stacks first to measure real sizes with the linker map. For RAM, add stacks for every task or interrupt level and buffers, and use a stack-usage tool or watermark test later.

### Why does the number of ADC channels on the datasheet not equal what you can use?
Channels share pins with other functions, some channels share one ADC converter (sampled sequentially), and some pins are reserved by the package or board. Also simultaneous sampling needs multiple ADCs. So you assign signals to pins and check which ADC each lands on.

### How would you compare two MCUs for a battery product?
Build a current model with the real duty cycle: sleep current (with the needed wake sources active), wake-up time and current, active current at the clock needed to finish the task, and radio or sensor power. Then compute average current and battery life. Verify with a measurement on an eval board with a current profiler, since datasheet typical figures are optimistic.

### What's an advanced-control timer and why would you care?
A timer designed for power conversion: complementary outputs with programmable dead time (so high-side and low-side switches never overlap), a break input that shuts outputs off in hardware on a fault, and trigger outputs to start ADC conversions at precise points in the PWM period. It's essential for motor drives, inverters and converters.

### Scenario: halfway through development you run out of flash. What do you do?
Check the map file for the biggest consumers (printf or float libraries, graphics assets, debug code), compile with size optimization and link-time optimization, remove unused libraries, compress or move assets to external flash. If still short, move to the next flash size in the same family; this is why choosing a pin-compatible family at the start matters.

### What do you check in the errata?
Whether any listed bug affects the peripherals and modes you plan to use, whether a workaround exists and what it costs in CPU or pins, and which silicon revision you will receive in production. A workaround that costs a spare pin or a timer is only usable if you've reserved one.
:::
