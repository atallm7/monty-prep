::: testing
Whether you can map interrupts to **real jobs and judge when they are the right tool**. Naming "button, UART, timer" is the floor. A strong answer groups applications (communication, timing, sensing, power, safety), says what the ISR does in each, gives rough rates and CPU load, and also names where interrupts are the wrong answer (very high event rates, hard determinism) and what replaces them (DMA, timer hardware).
:::

::: why
Firmware architecture is largely a decision about which events get interrupts, at what priority, with what ISR contents. Getting it right gives a responsive, low-power product; getting it wrong gives dropped bytes, jitter and un-debuggable races. Interviewers like this question because a candidate with real projects answers with specifics (what was the ISR, how fast, what priority).
:::

::: concepts
- **Event-driven design**: firmware reacts to events instead of looping; see [[q0795]].
- **Producer/consumer**: ISR produces data into a buffer, main code consumes it ([[q0802]]).
- **Sleep and wake-up**: interrupts bring the MCU out of low-power modes.
- **Priority assignment**: more time-critical sources get higher priority ([[q0803]]).
- **Event rate and CPU load**: load $=r\cdot t_{ISR}$; high rates need DMA or hardware ([[q0800]]).
- **Hardware shortcuts**: timers and DMA can replace interrupts for high-rate events ([[q0794]]).
:::

::: answer
"Interrupts are how an MCU deals with the outside world without wasting time. I'd group the applications.

Communication: a UART, SPI or I2C peripheral interrupts when a byte arrives or the transmit buffer empties, and the ISR moves the byte into a ring buffer so nothing is lost while main code is busy. At 115,200 baud a byte comes every 87 microseconds, so that's cheap.

Timing: a timer interrupt gives a periodic tick for the scheduler, a control loop, or sampling an ADC at a fixed rate.

Inputs: a pin-change interrupt for a button or a sensor's data-ready line, and it can wake the processor from deep sleep, which is how battery products last years.

Real-time control: an ADC end-of-conversion interrupt running a motor current loop at 20 kHz, or an encoder index pulse.

Safety and fault: overcurrent comparator, brown-out detect, or a watchdog early warning triggering a controlled shutdown.

The caveat is rate. A 400 kHz encoder, or a fast SPI stream, would eat the CPU if every event were an interrupt, so for those I use a hardware timer in encoder mode or DMA, and keep interrupts for the block-level events."
:::

::: technical
**Communication.** UART RX: ISR reads the data register (clearing RXNE) and writes to a lock-free single-producer/single-consumer ring buffer. At 115,200 baud (10 bits/byte) the period is 86.8 µs; with a 2 µs ISR the load is 2.3%. TX: "transmit empty" interrupt feeds the next byte, then disables itself when the buffer is empty. Also I2C/SPI slave events, CAN receive, USB endpoints. For continuous high-rate streams use DMA with half-/full-transfer interrupts (a 1 MB/s SPI stream would be 1 million interrupts per second without it).

**Timing.** Periodic tick (1 kHz): load $=t_{ISR}\cdot f$. Control loop at fixed rate, ADC trigger. Software timers ([[q0793]]).

**Inputs/wake-up.** GPIO edge on a button or sensor INT/DRDY line; an RTC alarm; a UART start-bit wake. Wake-up current: the MCU may sleep at around microamps and be active only for the ISR and following work.

**Control.** ADC end-of-conversion or timer update ISR runs the current loop; for a 20 kHz loop the ISR period is 50 µs, so if the control computation takes 15 µs the CPU load is 30% and the interrupt must have the highest priority.

**Safety.** Overcurrent comparator (use a hardware break path with an ISR for logging), brown-out reset/warning, clock-failure NMI, watchdog early-wake interrupt, thermal alarm from a temperature sensor's ALERT pin.

**RTOS support.** SysTick for the tick, PendSV for context switch, and "give from ISR" APIs to wake tasks (e.g. a semaphore signalled from the ISR).

**When not to use interrupts.** If $r\cdot(t_{ISR}+t_{entry+exit})$ approaches a large fraction of the CPU, switch to DMA, a hardware timer (encoder mode, input capture), or polled burst processing. Entry+exit alone is about 0.33 µs on a 72 MHz Cortex-M ([[q0797]]).
:::

::: short
"Interrupts handle communication (UART/SPI/I2C bytes into ring buffers), timing (periodic ticks and fixed-rate control or ADC sampling), inputs (button or sensor data-ready pins, and waking from sleep), and faults (overcurrent, brown-out, watchdog warnings). They keep the CPU free or asleep until something happens. The limit is event rate: very fast streams or encoders go to DMA or timer hardware, and interrupts are used for block-level events."
:::

::: long
"I'd split the applications by what kind of event is coming in.

Communication is the classic one. A UART interrupts when a byte arrives. The ISR grabs it, drops it into a ring buffer and returns, and the main loop parses the data later. At 115,200 baud that's one interrupt every 87 microseconds, and a couple-microsecond ISR is about 2% of the CPU. Transmit works the other way: a 'transmit empty' interrupt feeds the next byte and turns itself off when the buffer is empty.

Timing is next. A periodic timer interrupt, often 1 kHz, is the heartbeat for the scheduler, debouncing and timeouts. A faster one, say 20 kHz, can run a motor current loop, and the timer can trigger the ADC so the sample time is exact.

Third, discrete inputs and wake-up. A pin-change interrupt on a button, a sensor's data-ready line, or a wake-up from an RTC alarm lets the chip sleep at microamps and wake only when there's work. That's the basis of battery-powered design.

Fourth, safety. An overcurrent comparator, a brown-out detect, a thermal alert or a watchdog early-warning interrupt can start a controlled shutdown and log the cause. For the fastest protection I'd wire the comparator straight into the PWM break input and use the interrupt just for reporting.

I'd also mention RTOS use: the tick and context switch are interrupt driven, and ISRs wake tasks by posting to a queue or semaphore.

The thing to be careful about is rate. Each interrupt has overhead of a few hundred nanoseconds for entry and exit, so a 400 kHz encoder or a megabyte per second of SPI data would swamp the CPU. For those I use timer encoder mode or DMA, and take interrupts per block, not per event."
:::

::: terms
- **Ring buffer (circular FIFO)**: a fixed-size queue where ISR writes and main code reads without locks.
- **Producer/consumer**: ISR produces, main consumes.
- **Data-ready (DRDY) line**: sensor output pin that signals a new sample.
- **Wake-up source**: an event allowed to bring the MCU out of sleep.
- **Brown-out detect**: monitors supply and signals/reset when it drops below a threshold.
- **Half/full transfer interrupt**: DMA notifications at the middle and end of a buffer.
- **Deferred processing**: ISR sets a flag, main (or an RTOS task) does the real work.
- **Break input**: hardware shutdown path for PWM outputs.
:::

::: exceptional
An average answer lists "button, timer, UART". An exceptional answer:

- Organises by **category** (communication, timing, inputs/wake, control, safety, RTOS).
- Describes **what the ISR does** in each (ring buffer, flag, trigger), not just that one exists.
- Gives **rates and load numbers** (87 µs per byte, 2.3% load, 20 kHz loop at 30%).
- Mentions **wake from sleep** and power numbers.
- Knows the **limits**: use DMA or timer hardware when rates are high, and a hardware break path for the fastest safety actions.
- Mentions **priorities** (control loop above comms).
:::

::: mistakes
- **Interrupt per sample for high-rate data.** At 1 MS/s that is 1 million ISR entries per second. Use DMA ([[q0800]]).
- **Doing the parsing or `printf` in the UART ISR.** The ISR should only move bytes ([[q0802]]).
- **Polling a button in a tight loop in a battery product.** It prevents sleep. Use a pin-change wake-up.
- **Giving a communications ISR higher priority than the control loop**, so a burst of bytes jitters the loop.
- **Relying on an ISR alone for a nanosecond-scale safety action.** Use hardware for the trip and software for the report.
:::

## Four architectures for the same event

Take a UART receiving 115,200 baud data (11.52 kB/s):

| Method | Interrupts/s | CPU load (2 µs ISR) | Notes |
|---|---|---|---|
| Polling in main | none | up to 100% | can lose bytes if main is busy |
| Interrupt per byte | 11,520 | about 2.3% (+0.4% entry/exit) | simplest, standard |
| FIFO with threshold (e.g. 8 bytes) | 1,440 | lower | needs idle-line timeout for short messages |
| DMA to buffer + idle-line interrupt | few per frame | near 0% | best for streaming |

The progression is: **move work from the CPU into hardware as the rate rises**.

## Application 1: communication with a ring buffer

```c
#define N 64
volatile uint8_t buf[N]; volatile uint8_t head, tail;   // head written by ISR, tail by main

void USART1_IRQHandler(void) {            // ISR: producer
    if (USART1->SR & USART_SR_RXNE) {
        uint8_t b = USART1->DR;           // reading DR clears RXNE
        uint8_t next = (head + 1) & (N-1);
        if (next != tail) { buf[head] = b; head = next; }   // drop on overflow
    }
}
int uart_getc(void) {                     // main: consumer
    if (tail == head) return -1;
    uint8_t b = buf[tail]; tail = (tail + 1) & (N-1);
    return b;
}
```
Single producer, single consumer, each index written by exactly one side: no lock needed. The buffer must be large enough for the longest burst while main is busy: if main can stall for 5 ms, at 11.5 kB/s you need at least $5\text{ ms}\times11.52\text{ kB/s}=58$ bytes, so 64 is marginal and 128 is safer.

## Application 2: wake from sleep

A sensor node wakes once a minute, takes a reading and transmits for 20 ms:
- Sleep current 2 µA; active 10 mA for 20 ms every 60 s.
- Average $=2\ \mu A+10\ mA\cdot(0.02/60)=2\ \mu A+3.3\ \mu A=5.3\ \mu A$.

On a 220 mAh coin cell that is about $220\text{ mAh}/5.3\ \mu A\approx41{,}500$ h, or 4.7 years (ignoring self-discharge and derating). With a polling loop at 10 mA continuous it lasts 22 hours. Interrupt-driven wake-up is the difference. (Values illustrative.)

## Application 3: fixed-rate control loop

A motor current loop at 20 kHz: the ISR (triggered by the timer-synchronised ADC) reads the current, runs a PI controller and writes the PWM compare registers. Constraints: the ISR must finish within $50\ \mu s$ minus other interrupt time; its jitter must be small relative to the PWM period; and it should have the highest priority below hard faults. At 15 µs execution the load is 30%, leaving 70% for everything else, including entry/exit overhead.

## Application 4: safety and fault handling

Layered protection is the norm:
1. Hardware comparator trips the PWM break input within a clock or two (ns-scale).
2. A fault interrupt then records the cause, the stacked state or ADC values, sets a latch and reports.
3. The watchdog (a separate timer) catches software that never runs the above.
4. Brown-out detect warns of supply droop so non-volatile data can be saved before reset.

## Application 5: RTOS integration

The RTOS tick (SysTick) and context switch (PendSV) are interrupts; peripheral ISRs call "FromISR" functions to hand data to tasks: the ISR posts an item to a queue, the RTOS makes the waiting task ready and, if it has higher priority, switches on ISR exit. This is the deferred-processing pattern ([[q0802]]) formalised.

## Choosing priorities

A usable heuristic: **faster deadline, higher priority**, then **lower rate gets lower priority**. Typical order: hardware faults, control loop timer/ADC, high-speed communications (USB, SPI), low-speed communications (UART), tick, user inputs. See [[q0803]] for what preemption implies.

## Worked example: will the budget hold with three sources at once?

Load numbers for one interrupt in isolation are the easy part. The real question is whether all the sources together fit and whether the slowest-deadline one still gets served. Take a Cortex-M at 72 MHz with an entry-plus-exit cost of 0.33 µs and three sources:

| Source | Rate | ISR body | Cost per event | Load |
|---|---|---|---|---|
| Motor current loop | 20 kHz | 10 µs | 10.33 µs | 20.7% |
| UART RX at 115,200 baud | 11.52 kHz | 2 µs | 2.33 µs | 2.7% |
| 1 kHz tick | 1 kHz | 5 µs | 5.33 µs | 0.5% |

Total interrupt load is $0.2066+0.0268+0.0053=0.239$, so about 24%, comfortably under the 30-50% guideline. Utilization is only half the story, though. Latency is the other half. Deadline-monotonic order would put the UART (86.8 µs deadline, below) above the tick (1 ms), but check the pessimistic assignment first: control loop highest, tick in the middle, UART lowest. A UART byte can arrive just as the control ISR starts, and then the tick fires too. The UART ISR waits for $10.33+5.33=15.7\ \mu s$ of higher-priority work, then runs its own 2.33 µs, so the worst-case response is about 18 µs (iterating the standard response-time recurrence $R = C + \lceil R/T_{ctl}\rceil C_{ctl} + \lceil R/T_{tick}\rceil C_{tick}$ converges to 17.99 µs). Without a hardware FIFO, the receive data register must be read before the next byte's stop bit completes, which is one byte time, 86.8 µs. The margin is $86.8-18=68.8\ \mu s$, so even the pessimistic order works, and the deadline-monotonic order (UART above tick) only improves it to $2.33+10.33=12.7$ µs. Swap the priorities, so that a 40 µs USB handler outranks the control loop, and the control loop's start slips by up to 40 µs against a 50 µs period. That is jitter large enough to wreck a current loop, which is why priority follows deadline, not importance to the user.

## Where the simple model breaks on real hardware

- **Flash wait states.** The 0.33 µs entry-plus-exit cost (roughly 12 cycles in, about 10-12 out on a Cortex-M3/M4) assumes zero-wait-state memory. Running from flash at 72 MHz needs wait states, and the first fetch after a vector lookup may miss the prefetch buffer. Expect the first ISR execution after a long sleep or cache flush to run slower than the steady state. Measure the worst case, not the average.
- **Tail-chaining and late arrival.** Cortex-M3/M4 cores skip the full pop/push when one ISR finishes and a pending one is waiting (tail-chaining, about 6 cycles instead of roughly 22 for a full exit plus re-entry at zero wait states), and a higher-priority interrupt arriving during stacking steals the entry. Both reduce cost on average but make timing vary by a few cycles; budget with the unfavorable case.
- **Sleep wake-up latency.** From deep sleep the clock tree, PLL and regulator may need microseconds to milliseconds to settle before the first ISR instruction runs. This does not show up in the active-mode numbers above. The 41,500-hour battery estimate also ignores this wake-up energy, which can matter at one-per-second rates.
- **Shared bus contention.** A DMA transfer running in the background can delay the CPU's register accesses, so the ISR body is longer than in a quiet test.
- **Level versus edge sources.** A bouncing mechanical button on an edge interrupt can generate dozens of interrupts in a millisecond. Debounce by disabling the pin interrupt in the ISR and re-enabling from a timer tick, rather than filtering in the ISR.

> [!UNCERTAIN]
> Entry/exit cycle counts, wake-up times from each sleep mode and flash wait-state counts depend on the specific core, clock and vendor. Read the reference manual's electrical section for your part; the figures here are typical Cortex-M3/M4 values for illustration.

## How to verify it on the bench

1. **Toggle a GPIO** at the first and last lines of each ISR and capture both on a logic analyzer or scope. The pulse width is the true ISR duration including bus effects, and the repetition rate is the true event rate. Four channels (one per source) show overlap directly.
2. **Measure latency**, not just duration: put the external stimulus (for example a signal edge on the pin) on one scope channel and the ISR's GPIO pulse on another. The delay between them is hardware latency plus any blocking. Trigger on the ISR pulse with infinite persistence and look at the worst case over minutes of random traffic.
3. **Stress the combination**: run the UART at full back-to-back rate while the control loop is active, then inject a burst on every other source. Check for overrun flags (the UART's ORE bit) and for missed control-loop deadlines (a counter that increments when the timer update flag is already set at ISR entry).
4. **Measure sleep current** with a source-measure unit or a shunt and the scope in averaging mode, with the wake-up pulses visible, to confirm the 5.3 µA average in the example. A 2 µA sleep current that measures 40 µA usually means a floating GPIO or an enabled peripheral clock.

A convincing interview answer ends there: "I'd put a GPIO on every ISR and look at it on the analyzer." It shows that the load numbers are a model and you know how to check the model against silicon.

::: applications
- **Serial consoles and protocol stacks** (UART/CAN/USB) with ring buffers.
- **Battery-powered sensors** waking from RTC or pin interrupts.
- **BLDC/servo motor control loops** at 10-40 kHz.
- **Audio and data acquisition** with DMA and half-transfer interrupts.
- **Industrial safety shutdown** from overcurrent and over-temperature alarms.
- **RTOS-based products** where ISRs signal tasks.

::: assumptions
- Load figures use 0.33 µs entry/exit (Cortex-M3/M4 at 72 MHz) and example ISR bodies; they scale with clock and core.
- The coin-cell life estimate ignores self-discharge, regulator quiescent current, peak-current derating and temperature; real life is shorter.
- Ring-buffer code assumes single-byte indices on a core where byte access is atomic (true on Cortex-M, AVR) and a single producer and consumer.
- Answers change with the target. A PC-style OS uses interrupts through drivers; here the focus is bare-metal and RTOS firmware.

::: followups
### Why use a ring buffer between the ISR and main code?
It decouples timing: the ISR must run quickly when the byte arrives, while the main code consumes at its own pace. With one writer (ISR) and one reader (main) each updating its own index, no lock is needed. Size it for the longest time main may stall times the data rate, plus margin.

### How would you receive a 1 MB/s SPI stream?
Not with per-byte interrupts (1 million per second at about 0.8 µs minimum each, near 100% CPU with any ISR body). Use SPI with DMA into a double buffer, and interrupt at half- and full-transfer (with a 1 KB buffer split into 512-byte halves that is one interrupt per 512 bytes, about 2,000 per second). Process one half while DMA fills the other.

### What priority would you give a UART ISR relative to a motor control loop?
Lower. The control loop has a hard periodic deadline and jitter directly affects performance; the UART has a hardware FIFO or a buffer and tolerates tens to hundreds of microseconds of delay if the buffer is sized. The UART should not be starved forever, so keep control ISR short.

### How do interrupts help power consumption quantitatively?
They let the CPU sleep. If the active current is 10 mA and sleep is 2 µA, spending 0.03% of time awake gives an average of about 5 µA. A polling design that keeps the CPU running is 10 mA: three orders of magnitude difference.

### What if the sensor's data-ready line is level-triggered and stays low until you read the data?
Then use a level interrupt (or edge falling) and read the data in the ISR or from the main context before the line releases. If the ISR defers the read to main, mask that interrupt in the ISR so it doesn't re-fire immediately, and unmask after the read ([[q0799]]).
:::
