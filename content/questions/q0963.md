::: basics
### In plain words
You are handed a short assembly program (a processor's instructions written as text, see [[q0962]]) and asked three things. What does it do? How long will it take? How many times does a certain subroutine run? The method is to find the loops and calls first, then count the instructions that actually execute, then convert to time. The interviewer watches your process as much as the final number.

### Picture it
Think of timing laps around a track. Each lap has the same fixed set of steps, plus a warm-up before the first lap and a cool-down after the last. Total steps equal warm-up plus laps times steps per lap plus cool-down. Multiply the steps by the time per step to get the total time. If a lap includes a detour, the detour's steps count every single lap, not just once.

### Words you need
- **Trip count**: how many times a loop body runs.
- **Executed instruction count**: instructions that actually run, counting repeats and those inside subroutines.
- **CPI**: the average clock ticks per instruction. It is 1 in the simplest model and higher when the processor must pause (stall).
- **Taken branch**: a branch (a jump that depends on a test) that does jump. It costs extra ticks on a pipelined core, one that overlaps several instructions.
- **Subroutine call**: a jump to another block of code that returns afterward.

### The simplest example
A program sums the squares of 1 to $n$ by calling a `square` subroutine in a loop. Setup takes 3 instructions. Each loop pass runs 7, including the 2 inside `square`. One final jump runs once. The total is $3+7n+1=7n+4$, so for $n=5$ it is 39. Check $n=1$ by hand and you get 11. The subroutine runs once per pass, so 5 times. At CPI 1 and 100 MHz, 39 instructions take $39\times10$ ns = 390 ns. The result is $1+4+9+16+25=55$. That is the whole idea. The rest of this page adds pipeline stalls, nested loops, and conditional calls.
:::

::: testing
Whether you can **read unfamiliar code methodically** and turn it into numbers. This is a three-part question, and each part tests a different habit:

1. *What is it doing?* Can you identify inputs, outputs, loops and calls, and summarize the program in one sentence?
2. *How long will it take?* Can you count instructions (setup + iterations times body + exit), then convert with cycles per instruction and clock frequency, and say what you are assuming?
3. *How many times does the subroutine run?* Can you multiply trip counts correctly for nested loops and conditional calls?

Interviewers are watching your process (stay calm, trace a couple of iterations, state assumptions) at least as much as the final number.
:::

::: why
Reading code you didn't write, and estimating its cost, is daily work: reviewing firmware, debugging a missed deadline, sizing a delay loop, or checking how many times an interrupt handler fires. In architecture roles it links directly to CPU performance ([[q0918]]): run time equals instruction count times cycles per instruction divided by clock frequency. The question uses a short assembly program because it forces you to count *machine-level* work, not just C lines, and exposes whether you know what branch and call overhead do to timing.
:::

::: concepts
- **Instruction counting**: total executed instructions = setup + (iterations x instructions per iteration) + cleanup. See [[q0962]].
- **CPU time equation**: $T = \dfrac{N_{inst}\times CPI}{f_{clk}}$. See [[q0918]].
- **Control flow**: branches, loops, calls and returns; a taken branch changes the program counter.
- **Calling convention**: argument in `a0`, return in `a0`, return address in `ra`, so you can see what a subroutine receives and returns.
- **Pipeline effects**: taken branches and load-use hazards add stall cycles in a simple pipeline. See [[q0909]].
- **Loop trip counts**: nested loops multiply, conditional calls need a count of how often the condition holds.
:::

::: answer
"I'd work through it in three passes. First, what is it doing: I skim for labels and branches to find the loops, note which registers are inputs and which hold the result, and trace the first two iterations with real values. Then I say it out loud in one sentence, like 'this sums the squares of 1 to n by calling a square subroutine on each i'.

Second, how long. I count instructions: setup, then iterations times the loop body, including the instructions inside any subroutine it calls, plus the exit. Then time is instruction count times cycles per instruction divided by the clock. If I'm told it's a simple one-cycle-per-instruction core I use CPI equals 1; for a pipelined core I'd add stall cycles for taken branches and load-use hazards, and I'd say that assumption.

Third, how many times the subroutine runs: that's the number of times the call instruction executes, so the loop trip count if the call is in a simple loop, the product of the trip counts if it's inside nested loops, and the number of times the condition is true if the call is conditional.

For a loop of n iterations with seven instructions in the body, I'd write the total as seven n plus the setup and exit, check it against n equals one by hand, and then plug in the real n."
:::

::: technical
**Worked program.** Sum of squares of 1..n through a subroutine (RISC-V RV32I). n = 5.

```
main:   li   s0, 0          # sum = 0
        li   s1, 1          # i = 1
        li   s2, 5          # n = 5
loop:   mv   a0, s1         # argument a0 = i
        jal  ra, square     # call square(i)
        add  s0, s0, a0     # sum += result
        addi s1, s1, 1      # i++
        ble  s1, s2, loop   # repeat while i <= n
        j    done           # skip over the function
square: mul  a0, a0, a0     # a0 = a0 * a0
        ret                 # return to caller
done:
```

**1. What it does.** For $i=1\ldots n$ it calls `square(i)` and accumulates the results: $s_0 = \sum_{i=1}^{n} i^2$. For $n=5$: $1+4+9+16+25 = 55$.

**2. Instruction count.** Setup 3 (`li` x3). Per iteration: `mv`, `jal`, `mul`, `ret`, `add`, `addi`, `ble` = 7 executed instructions (including the two inside `square`). After the loop falls through, `j done` executes once.

$$N = 3 + 7n + 1 = 7n + 4 \;\Rightarrow\; N(5) = 39$$

**3. Cycles (simple 5-stage pipeline, predict-not-taken, branches resolved in EX).** Using $\text{cycles} = N + 4 + 2\,(\text{taken branches} + \text{jumps}) + \text{load-use stalls}$: the taken branches are $n-1 = 4$ (the final `ble` falls through), the jumps are `jal` ($n$), `ret` ($n$) and `j done` (1), so $2n+1 = 11$. No loads, so no load-use stalls.

$$\text{cycles} = 39 + 4 + 2(4+11) = 73,\qquad CPI = 73/39 \approx 1.87$$

At $f_{clk} = 100$ MHz: $73\times10$ ns $= 730$ ns.

**4. Subroutine executions.** `jal ra, square` executes once per iteration: **5 times** (equivalently the `mul` executes 5 times).

> [!UNCERTAIN]
> The cycle count depends on the pipeline model. The formula above (2-cycle penalty for each taken branch or jump, 1 for a load-use stall, 4 cycles to fill) is a textbook-style model of a classic 5-stage in-order core. A real core with branch prediction, a different pipeline depth or single-cycle execution will give a different CPI. State the model you assume.
:::

::: short
"I'd do three passes. First read it: find the loops and calls, identify inputs and outputs, trace two iterations, and summarize it in a sentence. Second, count instructions: setup plus iterations times loop-body instructions plus exit, remembering to include instructions inside called subroutines, then time equals instructions times CPI over clock frequency, stating my pipeline assumption. Third, the subroutine count is how many times the call instruction executes: the trip count for a simple loop, the product for nested loops, or the number of times a condition holds."
:::

::: long
"I'd handle this in three passes, and I'd narrate as I go.

Pass one, what is it doing. I scan for labels and backward branches, which tell me where the loops are, and for call instructions. Then I figure out which registers are inputs, which are loop counters and which hold the result. I trace the first two iterations with actual numbers, and then summarize in one sentence. For example: 'it computes the sum of squares of one to n, by calling a square subroutine for each i, and leaves the result in s0.'

Pass two, how long. I count executed instructions, not lines. Setup instructions run once. The loop body runs once per iteration, and if it calls a subroutine, the subroutine's instructions count every time. So if the body is six instructions plus the call, the return and the two inside the function, that's seven per iteration, giving seven n plus the setup and exit. I check it for n equals one by hand. Then time equals instruction count times CPI divided by clock frequency. If the interviewer says assume one cycle per instruction, CPI is one. Otherwise I'd mention that on a pipelined core each taken branch or jump costs a couple of stall cycles and a load followed by a dependent instruction costs one, so CPI is above one, and I'd state the assumption rather than hide it.

Pass three, how many times does the subroutine run. It's however many times the call instruction executes. In a single loop, that's the iteration count. In nested loops, multiply the trip counts: a call inside an inner loop of M inside an outer loop of N runs N times M. If the call is guarded by a condition, I count how often the condition is true, for example only odd i means about half.

Finally, I sanity-check: does the result make sense for a small n I can do by hand, and does the time sound plausible, for example microseconds rather than seconds?"
:::

::: terms
- **Trip count**: the number of times a loop body executes.
- **Executed instruction count**: the number of instructions that actually run, which includes repeated loop bodies and called subroutines.
- **CPI (cycles per instruction)**: average clock cycles each instruction takes; 1 for an ideal pipeline, higher with stalls.
- **CPU time equation**: $T = N\cdot CPI / f$.
- **Taken branch**: a branch whose condition is true so the PC jumps to the target; costs fetch-redirect cycles in a pipeline.
- **Link register (`ra`)**: holds the return address after a call (`jal ra, ...`); `ret` jumps back through it.
- **Subroutine / function call**: transfer to another code block with a return; each call executes the callee's body again.
- **Load-use hazard**: an instruction needing a register that the immediately preceding load has not yet produced; costs a stall cycle.
- **Hot loop**: the loop that accounts for most executed instructions and therefore run time.
:::

::: exceptional
**An average answer** reads the code line by line and gives an approximate time.

**An exceptional answer**:
- Starts with structure (loops, calls) and states the program's purpose in one sentence before counting.
- Writes the count as a formula (for example $7n + 4$), checks it with $n=1$, and counts instructions inside the subroutine for every call.
- Converts to time with $N\times CPI/f$ and names the assumed CPI or pipeline model, noting taken-branch and load-use penalties.
- Gets the call count right for nested and conditional calls, and distinguishes "times the call line executes" from "times the loop runs".
- Sanity-checks the result (small-n hand trace, plausibility) and mentions how they would confirm it, such as a simulator or cycle counter.
:::

::: mistakes
- **Counting lines instead of executed instructions.** A line inside a loop executes many times; instructions inside a called subroutine count on each call.
- **Forgetting the call and return instructions** (`jal` and `ret`) themselves, which are executed once per call.
- **Off-by-one on loop bounds.** `ble s1, s2, loop` repeats while $i \le n$, giving $n$ iterations starting from 1, and the branch is taken $n-1$ times. `blt` with a start at 0 gives the same $n$ but a different value of the final counter.
- **Adding nested trip counts instead of multiplying them.** Inner body runs $N\times M$ times, not $N+M$.
- **Assuming CPI = 1 without saying so** (or ignoring it entirely).
- **Forgetting that the subroutine count is independent of its length.** A subroutine with 50 instructions executed 5 times is 250 instructions, but it is still 5 *executions*.
:::

::: deep
## Pass 1: understand the program

Don't start at line 1 and translate each instruction. Look for **structure** first:

- **Labels that are the targets of backward branches** are loops. In the program above, `loop:` is targeted by `ble` at the bottom.
- **`jal ra, label`** is a call; `ret` is the matching return. Control leaves the main flow and comes back.
- **`j done`** after the loop exists only to skip over the function body that follows in memory. That is common layout when functions sit in the same file.

Then identify **roles**: `s0`, `s1`, `s2` (callee-saved) hold sum, i and n across the call; `a0` carries the argument in and the result out. Now trace two iterations:

| step | i (s1) | a0 on entry | a0 after `mul` | sum (s0) |
|---|---|---|---|---|
| iter 1 | 1 | 1 | 1 | 1 |
| iter 2 | 2 | 2 | 4 | 5 |
| iter 3 | 3 | 3 | 9 | 14 |

The partial sums 1, 5, 14, 30, 55 match $\sum i^2 = \frac{n(n+1)(2n+1)}{6}$, which for $n=5$ is $\frac{5\cdot6\cdot11}{6}=55$, and for $n=100$ is $338{,}350$ (a good check on larger inputs).

## Pass 2: count instructions and time

Break the program into parts that run a known number of times:

| Part | Instructions | Runs | Total |
|---|---|---|---|
| Setup (`li` x3) | 3 | 1 | 3 |
| Loop body incl. `square` (`mv, jal, mul, ret, add, addi, ble`) | 7 | $n$ | $7n$ |
| `j done` | 1 | 1 | 1 |
| **Total** | | | $7n+4$ |

Check $n=1$ by hand: `li`, `li`, `li`, `mv`, `jal`, `mul`, `ret`, `add`, `addi`, `ble` (not taken), `j` = 11 instructions, and $7+4 = 11$. ✓.

Now time. With an **ideal single-issue core, CPI = 1**, $n=100$ gives 704 instructions; at 100 MHz that is $704\times10\text{ ns} = 7.04\ \mu\text{s}$.

For a **classic 5-stage pipeline** the textbook adjustments are: 4 extra cycles to fill the pipeline, 2 stall cycles for every taken branch or jump (predict-not-taken, resolved in EX), and 1 for each load-use pair. Here the taken events are $(n-1)$ branches plus $(2n+1)$ jumps ($n$ calls, $n$ returns and the final `j done`):

$$\text{cycles} = (7n+4) + 4 + 2\big[(n-1) + (2n+1)\big] = 13n + 8$$

At $n=100$: $13\times100+8 = 1{,}308$ cycles, which is 13.08 µs at 100 MHz, nearly twice the ideal figure. The call/return overhead dominates because `square` is only two instructions long. This is exactly why compilers inline tiny functions.

> [!TIP]
> Say the model out loud: "Assuming CPI of 1 it's N instructions over the clock frequency; on a pipelined core I'd add a couple of cycles per taken branch, so closer to 1.5 to 2 for this call-heavy loop." The interviewer wants to hear that CPI is an assumption.

## Pass 3: how many times does the subroutine run?

It is the number of times the *call instruction* executes. Three common structures:

**Simple loop.** Call inside a loop of $n$ iterations: $n$ calls. Above: 5.

**Nested loops.** A call inside the inner loop of an $N\times M$ nest runs $N\times M$ times. The nested-loop program below counts body executions: with $N=5$ and $M=3$ the inner body runs 15 times. Its instruction count is $4 + N(1 + 3M + 2) = 4 + 5\times12 = 64$ for the setup, outer-loop overhead and inner bodies.

**Conditional call.** If the call sits behind a test such as `andi t4, s1, 1 ; beq t4, zero, skip`, it executes only for odd $i$. For $n=7$ the calls happen at $i=1,3,5,7$: 4 calls. The sum becomes $1+9+25+49 = 84$. Instruction count: setup 3, loop overhead 4 per iteration ($\text{andi}, \text{beq}, \text{addi}, \text{ble}$) $= 28$, each of 4 calls adds 5 ($\text{mv}, \text{jal}, \text{mul}, \text{ret}, \text{add}$) $= 20$, plus the final `j` $= 1$: $3 + 28 + 20 + 1 = 52$ instructions.

## A second timing example: delay loops

A classic firmware idiom is a software delay:

```
        li   t0, 1000000
dly:    addi t0, t0, -1
        bne  t0, zero, dly
```
Executed instructions: $2 + 2\times10^6 = 2{,}000{,}002$ (a constant this large does not fit the 12-bit immediate, so `li` expands to `lui` + `addi`). At 1 cycle per instruction and 100 MHz that is 20 ms. With the 5-stage model's 2-cycle taken-branch penalty the loop costs about $4$ cycles per iteration, so roughly 40 ms. The point: a delay loop's duration depends on the clock, the compiler and the pipeline, which is why real firmware uses a hardware timer.

## Real hardware caveats

- **Branch prediction** removes most of the taken-branch penalty in loops, so measured CPI is closer to 1 than the simple model suggests ([[q0910]]).
- **Caches and memory latency** make loads and stores cost more than one cycle when they miss; small loops run from cache so they hide this.
- **Multi-issue cores** can complete more than one instruction per cycle, giving CPI below 1.
- **The only real measurement** is a cycle counter or a simulator; hand counts are for estimation and for checking the simulator.

> [!INTERVIEW]
> If the program isn't in an ISA you know, say so, and ask for an instruction reference. Then use the same method: structure first (loops and calls), roles of registers, trace one iteration, count. The method transfers across ISAs.
:::

::: applications
- **Estimating interrupt handler cost**: count instructions in the ISR and divide by clock to see if it meets a deadline ([[q0801]]).
- **Sizing software delays and polling loops** on a microcontroller.
- **Code review of firmware**: spotting loops or calls that execute far more often than intended.
- **Profiling for architecture work**: instruction counts per function, CPI and call counts are the raw inputs to CPU performance analysis.
- **Simulator validation**: hand estimates for small kernels sanity-check a cycle-accurate model.
- **Optimization decisions**: finding that a tiny subroutine is called a million times and is worth inlining.
:::

::: assumptions
- **ISA and pipeline model.** The program is RV32I-style and the cycle numbers follow the textbook 5-stage model (4 fill cycles, 2 per taken branch or jump, 1 per load-use). A different core changes the cycle count but not the instruction count.
- **Instruction count is exact; cycles are model-dependent.** The $7n+4$ count holds for any implementation of this program; CPI depends on the hardware.
- **Pseudo-instructions expand** to real ones: `li` becomes `addi`, `mv` becomes `addi rd, rs, 0`, `ble a,b` becomes `bge b,a`. Each still counts as one instruction here, but `li` with a large constant may be two (`lui` + `addi`).
- **No cache misses or memory-mapped I/O delays**; all instructions are fetched in one cycle.
- **The program halts** at `done`. If the interviewer's program has data-dependent loops, you need the data to give a number, or a bound.

If the interviewer's program is different, the same method applies: the formula changes, the three passes don't.
:::

::: followups
### What changes if the loop body also loads from memory?
Loads add instructions (one `lw` per element) and may add a load-use stall if the next instruction uses the loaded register immediately: one extra cycle per pair on a 5-stage pipeline, unless forwarding or reordering hides it. Cache misses add many more cycles per miss, so time depends on the data access pattern as well as instruction count.

### The subroutine is inside a doubly nested loop with N = 8 outer and M = 4 inner. How many calls?
$8\times4 = 32$ calls. Multiply nested trip counts. If the subroutine has 6 instructions plus call and return overhead, add $32\times(6+2)$ instructions on top of the loop overhead.

### How would you estimate run time if you don't know the CPI?
Bound it. The best case is CPI of 1 (ideal pipeline), and the pessimistic case adds penalties for taken branches, loads and calls (CPI around 1.5 to 2 for call-heavy code on a simple pipelined core). Give a range, then say you would measure with a cycle counter or simulator to pin it down.

### What would the timing look like with a perfect branch predictor?
Taken-branch and jump penalties disappear (calls and returns are predictable too, using a return-address stack), so cycles approach $N+4$, i.e. $7n+8$, with CPI near 1. For $n=100$ that is 708 cycles instead of 1,308, 7.1 µs at 100 MHz.

### The program runs correctly but takes twice as long as your estimate. What do you check?
First that your instruction count includes everything executed (callees, loop overhead). Then clock frequency and any wait states on flash or memory (a microcontroller running from flash may insert wait states at high clock speeds). Then branch or load penalties and cache behavior, and whether interrupts or an RTOS tick preempt the loop. A cycle counter (or `perf` on a larger system) tells you which.

### How would you cut the cost of this program's loop?
Inline `square` (saves `mv`, `jal` and `ret`, leaving `mul`, `add`, `addi`, `ble`: 4 instructions per iteration instead of 7), or use the closed form $n(n+1)(2n+1)/6$ and skip the loop entirely. Inlining brings the loop from about $13n$ cycles to about $6n$, because only the loop branch remains taken: $4n + 2(n-1)$.
:::
